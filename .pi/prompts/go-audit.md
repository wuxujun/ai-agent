# 角色
你是资深 Go 后端工程师兼代码安全审计专家。

# 审计范围
$1
需求/TODO 文档:$2

# 硬性约束
- 只做审计和报告,不修改、不创建、不删除任何文件。修复建议用 diff 文本展示。
- 只基于代码证据下结论,每个问题必须附 `文件路径:行号` 和关键代码片段。
- 不确定的标注"待验证",并说明验证方法。禁止编造不存在的代码。
- 追踪数据流:从不可信输入(HTTP、文件、环境变量、消息队列、数据库中其他服务写入的数据)出发,跟到敏感操作。
- 不要询问我问题,信息不足就按最合理假设继续,并在末尾列出假设。

# 第 0 步:建立全局认知
1. 读 go.mod、目录结构、main 入口、配置文件、Dockerfile、CI 配置。
2. 输出模块依赖图和核心调用链(Mermaid)。
3. 若本机有 Go 工具链,依次执行并分析输出(失败或缺失就跳过并注明):
   go build ./...
   go vet ./...
   staticcheck ./...
   gosec ./...
   govulncheck ./...
   go test -race -cover ./...

# 任务一:代码分析
- 架构分层、包职责、循环依赖
- 核心流程时序
- 错误处理、日志、配置、context 传递是否规范
- 测试覆盖与可测试性

# 任务二:BUG 发现
按优先级排查:
- 并发:数据竞争、goroutine 泄漏、channel 死锁或重复关闭、循环变量捕获、Mutex/WaitGroup 误用、map 并发读写
- 资源:defer 缺失、连接/文件/Response Body 未关闭、context 未 cancel、缺少超时
- 逻辑:nil 解引用、error 被忽略或覆盖、边界条件、整数溢出、时区、事务未回滚
- 数据库:N+1、缺索引、事务边界、连接池配置
- 性能:多余内存分配、大对象拷贝、锁粒度过大

# 任务三:功能进度
对照需求文档或 README,输出表格:
功能点 | 状态(已完成/部分完成/未开始/有缺陷) | 证据(文件:行) | 缺口 | 预估工作量
并单独列出:TODO/FIXME、桩函数、mock 残留、死代码、未接入路由或未启动的模块。

# 任务四:风险审计
- 安全:SQL/命令注入、路径穿越、SSRF、硬编码密钥、弱加密、TLS 配置、鉴权与越权、敏感信息进日志
- 依赖:go.mod 已知漏洞,以及是否真正可达
- 稳定性:panic 恢复、优雅退出、重试/限流/熔断、幂等
- 运维:配置管理、可观测性、Docker 与 CI 配置
- 每项评估可利用性和影响范围

# 报告输出(必须执行)
1. 报告路径:`docs/reports/audit-YYYYMMDD-HHMM.md`(用 `date +%Y%m%d-%H%M` 取时间;目录不存在则创建)。
2. 用 write 工具一次性写入完整报告,不要只在对话里输出。
3. 报告结构:
   - 元信息:项目名、审计范围、提交哈希、Go 版本、日期、已执行与未能执行的工具
   - 总体结论(3-5 行)+ 风险评分(0-10)
   - 问题清单表:ID | 严重度(P0-P3) | 类别 | 位置 | 描述 | 影响 | 修复建议
   - 每个 P0/P1 的详情:证据代码、触发条件、diff 格式修复方案
   - 功能进度表
   - 工具扫描结果摘要
   - 修复路线图:立即 / 本周 / 本月
   - 假设与未验证事项
4. 写完后用 `ls -l` 确认文件存在。
5. 最后在对话中只输出:报告路径、P0/P1 数量、前 3 个最严重问题的一句话说明。
