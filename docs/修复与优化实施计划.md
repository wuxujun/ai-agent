- **验证状态**：串行全量测试、相关竞态测试、`go vet ./...` 和 Windows server 交叉编译均通过。
- **问题根因**：`internal/tools/apply_patch.go` 仅对目标文件以 `O_NOFOLLOW` 方式打开；祖先目录在“校验成功”到“打开文件”之间被并发替换为软链接时，仍可能越界写入工作区外文件；Windows 下 `O_NOFOLLOW` 为 0。
- **涉及文件**：
  - 修改：`internal/tools/apply_patch.go`
  - 新增测试：`internal/tools/apply_patch_security_test.go`
- **详细设计**：

### 任务 1.2：并发信号量取消容量泄漏与权威限流重构

- **状态**：代码修复已完成。`resizableSemaphore` 使用 waiter 状态机和内部权威 `limit`；API 手动 reload、SIGHUP 和配置文件监听 reload 成功后都会同步调整限流。
- **验证状态**：取消不泄漏、缩容上限与自动重载有效/拒绝配置测试通过；串行全量测试及相关竞态测试通过。
- **问题根因**：`resizableSemaphore` 在 `wakeWaiters` 唤醒等待者并递增 `s.current` 后，若客户端取消与通道可读产生竞争，取消分支无法在队列中定位该 waiter，导致 `current` 计数器永远无法减回；且 `Acquire/Release` 独立传 limit 导致配置缩容时唤醒超限。
- **涉及文件**：
  - 修改：`internal/api/handler.go`
  - 新增测试：`internal/api/semaphore_test.go`
- **详细设计**：
  1. **引入 Waiter 显式状态机**：
     ```go
     type waiterState int
     const (
         waiterStatePending waiterState = iota
         waiterStateGranted
         waiterStateCancelled
     )

     type semWaiter struct {
         ch    chan struct{}
         state waiterState
     }

     type resizableSemaphore struct {
         mu      sync.Mutex
         limit   int
         current int
         waiters []*semWaiter
     }
     ```
  2. **重构 `Acquire`、`Release` 与 `Resize`**：
     - `func (s *resizableSemaphore) Acquire(ctx context.Context) bool`：不再接收外部 limit。
       ```go
       s.mu.Lock()
       if s.current < s.limit {
           s.current++
           s.mu.Unlock()
           return true
       }
       w := &semWaiter{ch: make(chan struct{}), state: waiterStatePending}
       s.waiters = append(s.waiters, w)
       s.mu.Unlock()

       select {
       case <-w.ch:
           return true
       case <-ctx.Done():
           s.mu.Lock()
           defer s.mu.Unlock()
           if w.state == waiterStateGranted {
               // 竞争中已被唤醒并授予容量，取消时必须补偿归还容量
               s.current--
               s.wakeWaitersLocked()
           } else {
               w.state = waiterStateCancelled
               // 从 waiters 切片中移出
               s.removeWaiterLocked(w)
           }
           return false
       }
       ```
     - `func (s *resizableSemaphore) Release()`：
       ```go
       s.mu.Lock()
       defer s.mu.Unlock()
       s.current--
       s.wakeWaitersLocked()
       ```
     - `func (s *resizableSemaphore) Resize(newLimit int)`：
       ```go
       s.mu.Lock()
       defer s.mu.Unlock()
       if newLimit <= 0 { newLimit = 10 }
       s.limit = newLimit
       s.wakeWaitersLocked()
       ```
  3. **调用点改造**：
     - `h.taskSem.Resize(newLimit)` 注册到配置热重载监听回调中；
     - `runTaskStep` 与 `runAll` 直接调用 `h.taskSem.Acquire(ctx)` 与 `defer h.taskSem.Release()`，消除入参漂移。
- **回归验证用例**：
  - 构造确定性取消竞争测试：同时启动 100 个并发 goroutine 尝试 Acquire，并在 1ms 后全部取消 Context，等待全部退出后断言 `s.current == 0`，多次 `-count=50 -race` 保证零泄漏。
  - 构造缩容测试：先占满 10 个并发槽，将 limit 动态 Resize 到 3，释放全部槽位后再次并发请求，断言任何时刻活跃数不超过 3。

### 任务 1.3：结构化终止原因与消除 Shutdown 文本启发式

- **状态**：代码修复已完成。SQLite、PostgreSQL、Redis 和内存存储均可原子转换状态及终止类型；停机回滚持久化 `shutdown_rollback`，恢复运行清除旧类型，超时与客户端取消分别归类。旧数据仅在 `TerminationKind` 为空时使用兼容判断。
- **验证状态**：短业务失败、长取消信息、存储往返、超时归类及审批恢复测试通过；串行全量测试及相关竞态测试通过。PostgreSQL/Redis 的外部集成测试仍依赖对应服务。
- **问题根因**：`SetTaskFailed` 抹除 `ErrorCode` 并拼接字符串，导致 API Shutdown 回滚与启动扫描使用 `len(task.FinalAnswer) > 20` 猜测失败性质，易误恢复真实业务失败或遗漏取消任务。
- **涉及文件**：
  - 修改：`internal/types/task.go`
  - 修改：`internal/orchestrator/state.go`
  - 修改：`internal/api/handler.go`
  - 修改：`cmd/server/build.go`
  - 修改：`internal/store/sqlite.go`、`internal/store/postgres.go`、`internal/store/redis.go`、`internal/store/memory.go`
  - 新增测试：`internal/orchestrator/state_contract_test.go`
  - 修改测试：`internal/api/graceful_shutdown_test.go`
- **详细设计**：
  1. **定义结构化终止类型与原因**：
     在 `internal/types/task.go` 中增加：
     ```go
     type TerminationKind string

     const (
         TerminationNone             TerminationKind = ""
         TerminationBusinessFailed   TerminationKind = "business_failed"
         TerminationShutdownRollback TerminationKind = "shutdown_rollback"
         TerminationClientCancelled  TerminationKind = "client_cancelled"
         TerminationTimeout          TerminationKind = "timeout"
         TerminationLeaseLost        TerminationKind = "lease_lost"
     )
     ```
     在 `Task` 结构体中持久化 `TerminationKind` 字段。
  2. **重构 `SetTaskFailed` 与状态流转**：
     ```go
     func SetTaskFailedWithKind(task *types.Task, code, reason string, kind TerminationKind) error {
         if err := TransitionTask(task, types.StatusFailed); err != nil {
             return err
         }
         task.FinalAnswer = "Failed: " + reason
         task.ErrorCode = code
         task.ErrorMessage = reason
         task.TerminationKind = kind
         return nil
     }
     ```
  3. **废除 `len(FinalAnswer) > 20` 启发式**：
     修改 `internal/api/handler.go` 中的 `rollbackRunningTaskOnShutdown`：
     ```go
     // 仅对运行中或因服务停机被取消的任务执行恢复，明确的业务失败严禁复活
     if task.Status == types.StatusFailed && task.TerminationKind != types.TerminationShutdownRollback && task.TerminationKind != types.TerminationClientCancelled {
         return
     }
     ```
- **回归验证用例**：
  - 短文本业务失败（如 `"Failed: 404"` 长度 < 20）：断言 Shutdown 不会将其错误恢复为 `paused`；
  - 长文本取消信息（如包含长调用栈的取消信息 长度 > 100）：断言 Shutdown 依然可以精准识别并将其标记为可恢复。

### 任务 2.2：MultiAgent DAG 批处理并发有界控制

- **状态**：已实现（2026-09-30）。共享只读批次执行器使用至多 5 个 worker 消费步骤索引，避免为每个排队步骤创建 goroutine；结果依旧按输入顺序合并。取消后未执行步骤记录取消失败，不再调用下游，保留原批次预算和 Trace 计数语义。
- **验证**：20 步批次验证峰值并发不超过 5、结果顺序与预算不变、取消后排队步骤不调用下游且 worker 全部退出。

- **问题根因**：`partitionBatch` 连续只读步骤通过 `go func` 同时启动，无并发槽位约束，极端场景下瞬间并发打满下游 LLM 速率限制。
- **涉及文件**：
  - 修改：`internal/multiagent/coordinator.go`
  - 新增测试：`internal/multiagent/coordinator_concurrency_test.go`
- **详细设计**：
  1. **固定数量 Worker**：单批次 `maxBatchConcurrency = 5`，通过无缓冲索引队列派发任务，worker 执行前检查 `ctx.Err()`；批次结束后统一等待 worker 退出。
  2. **结果顺序保持**：原有按照切片索引回填结果机制保持不变，不破坏审计 Trace 顺序。
- **回归验证用例**：

### 任务 2.3：启动暂停任务扫描生命周期优雅停机纳管

- **状态**：已实现（2026-09-30）。启动扫描返回支持 `Stop/Wait` 的 runner，通过 `builtApp` 交给 `runApp`；正常信号退出及监听失败均在 HTTP 停止后取消并等待扫描，之后才进入 Store 关闭。扫描保留 30 秒超时并检查恢复循环取消状态。
- **验证**：阻塞 Store 夹具分别模拟 SIGTERM 与监听失败，确认取消传播、扫描尚未退出时停机流程继续等待，以及 Store 关闭前扫描已退出；Stop/Wait 可重复调用。SIGHUP 仍只触发配置重载，不作为停机信号。

- **问题根因**：`startPausedTaskScan` 在后台启动后未返回可等待通道，极早停机时与底层 Store 的 `Close()` 存在并发关闭竞态。
- **涉及文件**：
  - 修改：`cmd/server/build.go`
  - 修改：`cmd/server/main.go`
  - 修改：`cmd/server/runtime.go`、`cmd/server/build_test.go`
  - 新增测试：`cmd/server/paused_scan_test.go`
- **详细设计**：
  1. **抽象可停止后台 Runner**：
     ```go
     type BackgroundRunner interface {
         Stop()
         Wait()
     }
     ```
  2. 将 `startPausedTaskScan` 重构为返回 `BackgroundRunner`，内部持有 `context.CancelFunc` 与 `sync.WaitGroup`。
  3. `cmd/server/main.go` 在接收到停机信号时：
     - 先停止 HTTP 监听（拒绝新请求）；
     - 调用 `pausedTaskRunner.Stop()` 并等待其 `Wait()` 完成；
     - 最后关闭 Store、Redis 等持久化连接，避免在查询过程中发生 `sql: database is closed`。
- **回归验证用例**：
  - 编写极早停机单元测试：服务启动后立即触发 SIGTERM（SIGHUP 仅重载），断言进程干净退出，无并发 panic 或未捕获错误。
