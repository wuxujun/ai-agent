**建议优先处理的具体问题**

1. **P1：Harness 配置恢复和超时处理。**
   `run` 会直接写服务的 `teams.yaml`；恢复失败只打印错误，不改变退出码。重载使用没有显式超时的 `http.DefaultClient`，可能导致流程或恢复阶段长时间阻塞。建议增加原子写入、并发修改检测、请求超时，并让恢复失败返回非零状态。依据：[run.go](../cmd/harness-refine/run.go)。

2. **P1：自优化结果缺少明确的发布门槛。**
   多个候选各自胜出后会合并，合并组合没有独立联合评测；指定 lesson 目录即可记录，线上开启灰度后会读取最新未撤回记录。如果评测与线上使用同一目录，未经联合验证的结果可能被选用。建议引入“候选→已验证→已发布→已撤回”状态，发布前验证合并结果及延迟、费用回归。依据：[compose.go](../cmd/harness-refine/compose.go)、[refine.go](../internal/orchestrator/refine.go)。**当前默认关闭，风险发生在启用后。**

3. **P1：Release 与质量检查缺少工作流内的绑定。**
   发布只依赖 `build-release`，没有在工作流内要求同一提交的测试、安全扫描和浏览器检查通过。建议绑定同一 SHA 的验证结果，再生成正式 Release，并附校验和及构建来源。依据：[release.yml](../.github/workflows/release.yml)。本次没有核查远端仓库保护规则。

4. **P2：后台 assessment 缺少统一资源管理。**
   每个符合条件的任务直接启动 goroutine，并使用 `context.Background()`；这一层没有有界队列、并发配额或停机等待。LLM editor 的费用上限也在调用完成后检查，不能阻止该次费用发生。建议增加后台 worker、生命周期取消、并发限制及调用前预算预留。依据：[refine.go](../internal/orchestrator/refine.go)、[llm_editor.go](../internal/refine/llm_editor.go)。

5. **P2：Trace 增量保存仍有线性开销。**
   SQL 重复写入已经优化，但每次检查点仍复制完整 Trace，并比较整个历史前缀；长任务累计处理量仍可能趋近 O(N²)。应复用现有 1k/10k Trace benchmark，测量分配、保存耗时和混合读写 P95，再决定是否引入不可变分段或显式追加协议。依据：[task_progress.go](../internal/store/task_progress.go)。

6. **P2：Lesson 查询与运行产物管理。**
   `List(team, 1)` 仍扫描、读取全部 lesson 后排序，且忽略 context；文件增长会影响任务启动。建议按团队索引并缓存，同时把默认运行产物放进已忽略的 `data/`。当前 `var/improvement`、`runs/` 没有 Git 忽略规则。依据：[store.go](../internal/improvement/store.go)。

## 后续 P2：后台 assessment 资源与停机管理

本批继续处理 P2 中的后台任务生命周期，未修改默认启用状态、运行配置或模型预算策略。

- 每个 Engine 延迟启动 2 个 worker，最多排队 16 项；入队采用非阻塞发送，队列满或停止后跳过并记录安全日志。
- 单项从入队起共享 30 秒 context 期限，过期排队项不调用 proposal。运行中的任务收到停机取消；panic 被隔离，仅记录类型，worker 继续处理后续任务。

- lesson 的 List 在入口及逐项迭代间检查 context，assessment 在技能摘要读取后、proposal 前后复查取消。

2/16/30 秒为固定内部默认值，本批没有新增热重载配置。取消是协作式的，不能强杀忽略 context 的回调或中断所有文件 I/O；等待超时只报告退出未完成。嵌入式 Engine 调用者须自行 Stop 后 Wait，具体步骤见 [Harness 指南](harness.md)。调用前费用预留/硬预算、Trace 增长治理和 lesson 索引缓存仍未在本批实现。

## 后续 P2：Trace 检查点分配优化

本批优化默认 SQL run-all 的检查点捕获及比较，不更改数据库 schema、事务、维护版本或租约检查。

- 历史快照使用每块 256 行的不可变分块。`AdvanceTaskProgress` 仅在同一 SQL Store、同一任务、相邻已保存版本且历史前缀严格相等时复用完整历史块；只复制块索引、最后一个未满块和新增 Trace 的嵌套数据。
- 旧检查点保持不变，允许并发读取或从同一父检查点生成不同分支，不会共享可写的尾块或 task 的可变 evidence/timing 指针。
- 逐字段比较保留原 `reflect.DeepEqual` 的表示语义，包括 nil/空 Evidence、nil/空 Lines、DurationMS、time.Time 单调信息及结构相等的不同 Location；时间表示不同时保留反射比较兜底。字段覆盖回归在 StepTrace/Evidence schema 增加字段时会失败，要求同步审核比较和克隆。
- 历史修改、重排、截断及 owner/task/version 不匹配继续完整捕获/保存；Memory、自定义 Store 及 owned/恢复专用 SQLite 保留既有路径。首次完整保存前不建立检查点，避免丢失传入的未落盘 Trace。

**性能仍不是 O(1)**：每轮仍执行 O(N) 的严格历史比较，完整 task.Trace 也继续驻留内存，累计最坏复杂度仍可能为 O(N²)。本批降低常数、分配和重复嵌套克隆；没有引入盲目信任调用方的 append 标记或用 hash 碰撞风险替代严格比较。后续若要消除历史扫描，需要独立的不可变追加协议及并发/恢复契约。

## 后续 P2：Lesson 团队索引与缓存

本批为 List/ListPublished 增加进程内轻量索引，避免每次选择团队的最新 lesson 都读取、反序列化并排序整个目录。

- 按规范化真实根目录共享索引，支持短生命周期 Store handle、不同 handle 和符号链接别名；LRU 最多保留 32 个根目录，单根目录元数据仍为 O(N)。索引仅保存 ID、团队、观察时间及发布候选集合，不缓存 lesson 正文或授权决定。
- Record（含同 ID 重录）、Validate、Publish、Retract 成功写入状态后，原子更新非秘密的 0644 `.lesson-index-generation`。读者核对随机变更代号、根/状态目录身份和修改时间，冷重建前后复查；变动持续发生时最多重试三次，随后报错并让线上回落基线。
- 托管写入完成后的新查询能检测变更，即使目录 mtime 被合并或恢复。缓存最长 5 秒重建一次，补充检测绕过托管操作、原地修改且保留目录 mtime 的非选中元数据。没有标记的旧只读目录仍可读取。
- 每个选中结果都现场读取并核验内容摘要、发布绑定和撤回标记；因此索引即使陈旧，也不能直接授权已撤回或被篡改的结果。返回值是新反序列化的正文，调用方修改不会污染缓存。已经持有的 overlay 仍遵循既有在途执行边界，不被撤回操作追溯中断。
- 普通候选列表不新增对发布目录可读性的依赖；发布目录损坏时仍可列候选供排查，ListPublished 保持拒绝。修复目录后重建可恢复查询。

- 新增 `.gitignore` 的 `/var/improvement/` 和 `/runs/`，并用 `git check-ignore` 验证；没有移动、删除文件或更改运行配置。详细使用边界同步到 [Harness 指南](harness.md)。
