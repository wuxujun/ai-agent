## 4. 详细发现

### B01 — 恢复执行忽略审批人修改的参数

**位置：** `internal/orchestrator/engine.go:1082–1083`、`:1150–1162`、`:1293–1318`；入口包括 `cmd/server/build.go:164` 和 `internal/api/handler.go:1526`。

在线审批流程会把非 nil 的 `ApprovalResult.Parameters` 替换到动作中。持久化时也加密保存了这个结果，但 `RecoverApprovedApproval` 只解密 `ActionPayload`，没有解析 `ResolutionPayload` 中的最终参数，就消费审批并调用 Executor。

**验证：** 原动作参数为 `original.txt/original`，审批人改为 `approved.txt/approved`。通过真实 `PersistApprovalResolution` 保存后恢复，假执行器收到的仍是原参数。验证没有创建这些目标文件或执行高风险工具。

**影响：** 同一审批在线处理与重启恢复的行为不一致。审批人纠正的路径、命令或其他参数可能失效。现有审批租约和 approved→consumed CAS 能限制重复消费，但不能保证执行内容符合批准结果。

**建议：** 在消费前解密、验证批准结果，统一在线与恢复路径的最终动作构造逻辑；非 nil 参数按现有语义整体替换，不擅自合并。损坏或不一致的审批结果应停止执行。

**验收：** 覆盖修改参数、保持原参数、空 map、损坏结果、重复恢复；断言执行器实际收到的参数以及审批状态。

### B02 — 任务创建判重不是原子操作

**位置：** `internal/api/handler.go:489–500`、`:545`；`internal/store/sqlite.go:518–539`。

自定义 ID 的创建流程先调用 `ExistsTask`，再调用通用 `SaveFullTask`。SQLite 的保存使用 `ON CONFLICT(id) DO UPDATE`，并允许更新 `tenant_id`、workspace、goal 等字段。

**触发交错：** 请求 A、B 使用尚不存在的同一 ID，均在对方写入前完成存在性检查；A 保存成功后，B 的保存变成更新。两个创建流程都没有数据库级“仅插入”语义。

**影响：** 同租户并发创建可覆盖任务内容；多租户共享存储且使用相同自定义 ID 时，可改变任务归属。普通已有 ID 的顺序请求会被 409 拦截，此发现限定于并发窗口，不是任意已有任务均可直接覆盖。未进行双请求 HTTP 动态复现。

**建议：** 增加独立 `CreateTask` 存储操作，数据库唯一约束冲突返回明确的已存在错误并映射为 409；更新接口不应承担创建判重职责。租户归属字段宜在更新时保持不可变。

**验收：** 用同步屏障让两个请求同时通过创建前检查；对各 Store 验证恰好一个创建成功，另一个 409，既有任务及租户归属不变。跨实例时不能只依赖进程内 mutex。

### B03 — SSE Publish 与 Unsubscribe 存在 send/close 竞争

**位置：** `internal/api/sse.go:85–94`、`:104–123`；生产发布回调见 `cmd/server/build.go` 的 `wireEngineEvents`。

`Publish` 在锁内复制订阅 channel 后释放锁，再逐个发送。`Unsubscribe` 可以在释放锁后移除并关闭同一个 channel。后续发送会触发 `send on closed channel`；`select` 的 `default` 不能避免向关闭 channel 发送时的 panic。

**影响：** SSE 断开或处理终态时即可与正常事件发布形成交错。发布可能运行在后台任务 goroutine，HTTP recovery 无法保护其他 goroutine；未恢复的 panic 可终止进程。

**已有保护与缺口：** 订阅表有 mutex、发送非阻塞，但这两者没有覆盖“取得 channel 到实际发送”的生命周期。本次现有竞态测试通过，未专门构造该交错的动态复现。

**建议：** 将非阻塞发送与关闭纳入同一生命周期同步机制，例如在同一锁保护范围内完成发送；或改成显式关闭状态的订阅对象。不要仅在发送处吞掉 panic。

**验收：** 并发 Publish、Subscribe、Unsubscribe，覆盖活跃输出与终态断开；验证无 panic、无 race、无重复关闭、无永久阻塞。

### B04 — 审批暂停时间超过租约，另一实例可重新接管

**位置：** `internal/api/handler.go:930`、`:950`、`:974–978`；`internal/orchestrator/engine.go:1467`；`internal/store/sqlite.go:1212–1223`。

run-all 用可暂停超时管理执行预算，进入审批时暂停计时；任务租约却只在启动时按 `timeout + 30s` 获取一次。运行路径中没有发现续租调用，且状态转换允许从 `running`、`awaiting_approval` 启动。

当前主配置的执行预算为 600 秒，审批 TTL 为 86400 秒（`config.yaml:158`、`:171`）。等待超过 630 秒后，原执行上下文仍可能存活，另一实例却可取得已过期租约。

**验证：** 以 MemoryStore 和 20/30/60 毫秒的缩时边界验证：暂停后的执行上下文未过期，另一 owner 已能获得同一任务租约。此用例证明组件时间模型不一致，未运行完整双实例 HTTP 场景。

**影响：** 可能产生重复规划、工具调用、费用和状态覆盖。`activeTasks` 只能保护当前进程；单个审批记录的消费 CAS 不能覆盖两个任务执行流程。

**建议：** 活跃执行与审批等待期间持续续租；续租失败时取消旧执行。对关键状态写入引入 owner/fencing 校验，防止旧 owner 在失租后继续写入。

**验收：** 两个 Handler 共享同一外部 Store，长审批等待期间第二实例不能启动；模拟续租失败，验证旧执行停止，合法接管不会重复执行动作。

### B05 — trace 序号重复造成 SQL 持久化丢失

**位置：** `internal/executor/executor.go:52`；`internal/orchestrator/engine.go:182`；`internal/answerpipeline/pipeline_v2.go:144`、`:264`、`:278`、`:368`；`internal/store/sqlite.go:220`、`:583–607`；PostgreSQL 同类逻辑见 `internal/store/postgres.go:560–588`。

工具 trace 从 `StepCount + 1` 编号，引用校验等附加 trace 却直接使用已有 `StepCount`。SQL 以 `(task_id, step)` 唯一识别 trace，并跳过已保存序号，或用忽略冲突的插入方式处理，因此会静默丢弃重复编号的不同事件。

**验证：** 已保存 `Step=1/read_file` 后调用真实 `verifyCitations`，内存新增 `Step=1/citation_verify`，其用量为 6 token。再次保存、读取临时 SQLite，仅剩 `read_file`。

**影响：** trace 中的校验结果与用量丢失，影响任务报告、基于 trace 的用量聚合、恢复输入和追溯。`AnswerAudit` JSON 独立持久化，不应将此问题表述为所有审计数据均丢失。

**建议：** 将执行步预算与事件序号分离，统一分配持久化 trace ID/序号。修复时不要简单为每个审计阶段增加执行步数，以免改变 `MaxSteps` 语义。冲突应可观测，不能静默忽略不同事件。

**验收：** 针对 legacy、AnswerPipeline V2、多 agent 和审批恢复做 SQL 往返测试；验证不同事件不会覆盖或丢失，trace 用量与序列稳定。

### B06 — Redis 状态转换漏维护租户状态索引

**位置：** `internal/store/redis.go:946–950`；查询索引选择见 `:348–349`，分页见 `:360`，状态过滤见 `:398–399`；调用入口 `internal/api/handler.go:1558–1563`。

`TryTransitionTaskStatus` 的 Lua 修改任务 JSON 和全局状态索引，却未修改 `tasks:tenant_status:<tenant>:<status>`。非管理员的租户＋状态列表依赖后者。

**触发链：** 保存 created 任务→CAS 为 running→租户查询 running，任务仍不在新索引；旧 created 索引保留残项。列表先分页再过滤真实状态，会产生空页或遗漏。后续保存只按 JSON 中的旧状态清理索引，不能保证移除更早遗留的 created 成员。

**影响：** Redis 后端租户视角的任务列表错误。这是索引一致性问题，未据此认定为跨租户信息泄漏。本次未连接真实 Redis。

**建议：** 同一 Lua 中维护全局与租户索引；对存量索引提供可验证的重建或修复流程。

**验收：** Redis 集成测试覆盖 CAS 前后按 tenant＋status 查询、分页、再次完整保存，以及多个租户的互不影响。

### B07 — HTTP 入站连接与请求体缺少完整限制

**位置：** `cmd/server/build.go:59`；`internal/api/handler.go` 中的 JSON binding 路径；`internal/api/session.go` 等输入入口。

生产 `http.Server` 只设置 Addr 和 Handler，没有配置 `ReadHeaderTimeout`、`ReadTimeout`、`IdleTimeout`。API 未发现 `http.MaxBytesReader` 或等效统一请求体字节限制。处理器内部的业务超时不能保护尚未完成请求头读取的连接，也不能代替 JSON 解码前的体积限制。

**影响与前提：** 能直连监听地址的客户端可用慢请求占用连接；有权限进入 JSON handler 的客户端可提交大请求体消耗内存。当前默认监听 `127.0.0.1:8088`，限制了直接远程暴露；反向代理若已设置限制，也会降低风险。未进行资源耗尽或慢连接实验。

**建议：** 设置请求头超时和空闲连接超时；按 API 类型限制请求体并返回 413；对需要长连接的 SSE 单独设计写入/空闲策略，避免统一短 `WriteTimeout` 破坏正常流式输出。明确部署代理与应用各自承担的限制。

**验收：** 小体积请求成功，超限请求确定返回 413；不完整请求头在期限内关闭；正常长时间 SSE 仍工作。

### B08 — 输出上限在缓冲之后才生效

**位置：** LLM：`internal/llm/transport.go:216–229`；进程：`internal/tools/runner.go:35–40`；截断点：`internal/tools/execute.go:53–56`。

流式 LLM 将每个 chunk 写入 `strings.Builder` 并调用 `onChunk`，到整个流结束才检查 4 MiB。Scanner 的上限只约束单行，不约束累计内容。命令执行器用两个无上限 `bytes.Buffer` 收集 stdout/stderr，`execute_code` 的 4000 字节截断发生在 `cmd.Run` 之后；失败路径还可能保留完整输出。

**验证：** 内存 HTTP transport 返回 6 个各 1 MiB 的普通文本 chunk。函数最终报告超限，但回调已经收到 **6,291,456 字节**，超过 **4,194,304 字节**上限。没有调用真实 LLM。命令缓冲问题为静态确认，未运行高输出压力进程。

**影响：** 声明的输出长度限制不能约束处理期间内存；流式内容还会在拒绝前向下游传播。时间限制能约束持续时间，不能保证该时间内的内存消耗。命令路径中的高风险审批仍有效，但审批不提供内存配额；其他读取工具也复用了同一 runner。

**建议：** 在每次追加和回调前检查累计字节；超限及时关闭响应。为 stdout/stderr 使用有界 writer，定义保留头部/尾部和截断标识，并确保超限后的进程/管道可以正确结束。

**验收：** 限制以内、跨界 chunk、stderr 超量、失败退出和取消均覆盖；断言分发和保留字节数，不只断言最终返回的字符串长度。

### B09 — SSE 终态缓存的 TTL 只限制回放，不限制内存

**位置：** `internal/api/sse.go:73–79`、`:104–110`、`:126–138`。

每个终态事件都会写入 `sticky`。过期判断只在再次订阅同一个 task ID 时发生；`Forget/ForgetAll` 依赖任务删除。没有全局过期清理或容量限制，因此“5 分钟 TTL”并不意味着条目会在 5 分钟后释放。

**验证：** 用虚拟时钟发布 old 任务的终态，时间推进到两倍 TTL，再发布 new 任务；old 仍保留在 map 中。

**影响：** 长期运行且保留任务数据时，缓存条目数随不同已完成任务累计增长，而不是随最近 5 分钟吞吐量变化。条目还可能引用答案或事件内容；本次未测量生产堆占用。

**建议：** 添加有界过期队列、定期清理或容量受限缓存；避免每次发布都做大 map 全扫描。缓存丢弃后继续利用现有 Store 查询兜底。

**验收：** 虚拟时钟下，即使不再访问旧 task ID，也会清理过期条目；持续发布不同 ID 时容量有界，终态回放仍正确。

### B10 — 部分重启必需配置没有被热更新拒绝

**位置：** `internal/config/config.go:923–946`、`:964–975`、`:1164–1168`；Wiki 装配：`cmd/server/wiki_builder.go:234–257`；Store/HTTP 装配：`cmd/server/build.go:39`、`:59`。

`validateRestartRequiredReload` 目前仅拒绝 Brain 配置和 Brain 项目 allowlist 的变化。Wiki/MCP 的配置注释明确要求重启，但一般 reload 仍可安装这些新值。Wiki client、工具注册、数据库连接和 HTTP listener 等则在启动时绑定，未在此路径重建。

**验证：** 函数级用例将 Wiki Directory 从 old-wiki 改为 new-wiki，restart guard 返回 nil。结合 reload 安装快照与启动装配路径，确认配置快照和运行依赖可能不一致；未启动服务执行完整热更新演示。

**影响：** reload 看似成功，新配置可被部分动态消费者读到，实际 Wiki 仍读取旧目录，或 MCP 工具仍沿用旧会话。运维难以判断变更是否生效。不能据此断言每一个 Wiki 字段都会导致安全绕过。

**验收：** 重启必需字段变化返回明确错误且旧 revision/快照保持不变；支持热更新的字段仍成功；覆盖文件 watcher、SIGHUP 和 HTTP 三个入口。

### B11 — Embedding 错误将上游正文带入日志路径

**位置：** `internal/memory/embed.go:205–208`、`:274–277`、`:122`；`internal/logger/logger.go:169–198`。

OpenAI/Ollama embedding 遇到错误状态时全量读取响应，并拼接到 error。`GetEmbedding` 的回退日志直接记录此 error。日志脱敏主要按字段名处理，名为 `error` 的字符串不会自动移除其中的上游正文。

**验证：** 假 transport 返回 503 和合成标记 `UPSTREAM_PRIVATE_MARKER`，错误字符串完整包含该标记。到日志的传播由调用链确认；没有使用真实秘密。

**影响：** 若代理或提供方在错误正文中回显请求内容、凭据或内部细节，将进入应用日志。该路径也缺少错误正文的字节上限。是否泄漏真实信息取决于上游返回内容，不代表已经发生真实密钥泄漏。

**建议：** 复用结构化、受限且不包含原始正文的 HTTP 状态错误；日志只记录 provider、状态码、可安全公开的错误类型及关联 ID。不要依赖统一字符串替换覆盖任意格式的秘密。

**验收：** 成功和失败响应均有字节限制；合成敏感内容不能出现在错误、应用日志或任务报告中；保留可用于诊断的状态信息。

### B13 — 自定义 Gin recovery 仍有原始请求转储路径

**位置：** `internal/api/middleware.go:130–139`；当前依赖 `github.com/gin-gonic/gin@v1.12.0/recovery.go` 的 `CustomRecovery`、`CustomRecoveryWithWriter`、`secureRequestDump`。

项目调用 `gin.CustomRecovery` 并在回调中生成安全的结构化响应，但 Gin 仍保留默认 `DefaultErrorWriter` 日志。当前依赖在 broken-pipe 类 panic 分支中转储请求，即使是 release 模式；转储只遮盖 Authorization，未遮盖 X-API-Key、Cookie 或 URL 查询参数。debug 模式的普通 panic 也进入转储路径。

**验证：** 使用 `gin.ReleaseMode` 和内存 recorder，路由仅抛出包装了 `syscall.EPIPE` 的合成错误；捕获到 `DefaultErrorWriter` 中包含合成 X-API-Key。未建立真实连接，也未使用真实凭据。

**影响边界：** 默认 release 模式的普通 panic 不一定转储请求；本项限定于依赖中的相应分支。原始输出绕过项目 `logger.Component` 的脱敏，和项目“recovery 不输出请求头”注释不符。

**建议：** 显式关闭 Gin 内建原始错误转储，或提供经过核查的 writer/recovery 实现；保留安全的异常类型、关联 ID、必要堆栈与正确响应状态。处理断开连接时，不应为了写响应再次触发错误。

**验收：** release/debug、普通 panic、EPIPE、ECONNRESET 均用合成秘密验证；检查 stderr 和结构化日志两条出口，不能只检查 HTTP 响应。

## 5. 待验证风险：SQL 只读边界

**位置：** `internal/tools/sql_query.go:18–19`、`:55`、`:77`、`:150`、`:239–245`。

`sql_query` 被标记为低风险，并宣称只读 AST 检查。实际实现是手写 tokenizer 和关键词检查，数据库却用普通读写方式打开，没有在 SQLite 连接层强制只读。tokenizer 对反斜杠及引号的处理也需要与 SQLite 方言逐项对照验证。

## 6. 优化建议

### O01 — 在 CI 增加依赖漏洞可达性扫描

当前 `.github/workflows/ci.yml` 已包含格式检查、vet、单元测试、竞态、Compose 验证、gitleaks 和外部存储集成；未见 govulncheck 步骤。本机也未发现可直接执行的 govulncheck，因此本报告没有第三方依赖 CVE 扫描结论。

建议固定扫描工具版本，运行 `govulncheck ./...` 并留存 Go 工具链版本、扫描时间和结果；区分依赖存在受影响版本与实际调用到受影响符号。该工具利用调用关系判断已知漏洞是否影响项目，方法说明见 [Go 官方漏洞管理文档](https://go.dev/doc/security/vuln/)。不要根据依赖版本号或本次测试通过，宣称依赖无漏洞。

### O02 — 把跨层不变量补成契约测试

本次缺陷集中在单层测试之外：审批保存到恢复执行、执行暂停到分布式租约、内存 trace 到 SQL、状态 CAS 到列表索引、配置快照到长期依赖。

建议优先补这些跨层契约，再扩展测试数量。为不同 Store 复用创建判重、租约、trace 往返和租户状态查询测试；时间与并发用虚拟时钟和屏障控制。将审计用例转成正式回归测试时，应在修复前失败、修复后通过，而不是保留针对错误行为的断言。

### O03 — 统一输入输出与缓存预算

目前限制分散在工具观察值、HTTP 读取、LLM 单行 Scanner 和候选缓存等层。建议为“接收字节、解码对象、累计缓冲、下游分发、最终保留”分别定义预算，并记录截断/拒绝指标。

验收以有界内存、有限结果和取消及时性为核心；针对低容量环境做有限基准测试，记录峰值分配、延迟与缓存大小，再确定默认值。报告未测量生产吞吐，不提供无依据的性能提升百分比。

### O04 — 围绕职责逐步拆分大型模块

`internal/config/config.go` 约 2071 行、`internal/api/handler.go` 约 1872 行、`internal/orchestrator/engine.go` 约 1740 行、`internal/store/sqlite.go` 约 1236 行。文件大本身不是 Bug，但生命周期、授权、持久化与恢复逻辑交织，增加保持跨路径一致性的成本。

建议在修复相关问题时逐步抽取最终批准动作构造、执行 owner/租约管理、trace 追加和任务创建存储操作；保留现有接口测试。优先用小范围修改统一语义，避免为拆文件做大规模机械重构。

## 7. 已核查的保护与避免误报的说明

- API 路由使用 AuthMiddleware；按任务访问使用租户检查，管理性操作有 AdminMiddleware。B02 不代表所有租户检查缺失。
- 审批已有加密、版本 CAS、消费状态和租约。B01 是最终参数没有应用，B04 是任务租约生命周期缺口，不能概括为“审批完全无保护”。
- 文件工具已有 workspace 路径策略，网络工具已有相关 URL/私网策略。未依据单个调用点就将项目整体判定为路径穿越或 SSRF。
- 非流式 LLM HTTP 响应已有有限读取；B08 指向流式累计缓冲与命令输出路径。
- 配置 reload 已有校验后安装快照和 Brain 重启拒绝逻辑；B10 是其他启动绑定字段覆盖不全。
- SSE 有非阻塞发送、终态缓存和 Store 轮询兜底；这些设计解决慢消费者/漏事件问题，但不能解决 channel 关闭竞争或缓存清理。
- Brain 的 struct 解码和后续业务验证限制了 B12 的实际影响，未认定为已成功污染知识库。
