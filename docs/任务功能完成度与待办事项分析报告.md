## 一、任务功能“能否完成”总体判定

### 核心结论
**研发主干完成度高，Unix 内部开发与单机测试环境具备交付条件；但当前【暂不能宣称生产环境全平台完成】。**

- **可交付状态（Unix / 本地开发 / 测试环境）**：
  - 多编排引擎（Eino / Legacy / Step / ADK / Multi-Agent）、统一工具注册表、审批流与持久化骨架运行稳健；
  - 核心执行与安全漏洞（B01–B13、SQL 只读加固、外部 RAG 流量预算限制 O03 第一批）均已完成修复与契约化验证；
  - 只读 Wiki 检索（本地 BM25 + GSE 分词）、Brain Eval P0 评测与 Brain Read-Only MVP P1 均已高质量闭环；
  - 自动化回归套件（48 个测试包）及核心并发 race 测试全部通过。

- **不能宣称全平台生产闭环的原因**：
  1. **发布硬阻塞 (P0)**：Windows 目标交叉编译失败（Brain 撤回逻辑直接调用 Unix syscall），发布矩阵无法全线通过；
  2. **核心安全与并发缺陷 (P1)**：`apply_patch` 祖先目录存在 TOCTOU 越界写漏洞；API 并发信号量存在取消时容量泄漏及热重载并发唤醒超限问题；
  3. **任务终止恢复启发式 (P1/P2)**：Shutdown 回滚和启动恢复依赖 `len(FinalAnswer) > 20` 等脆弱的文本推断，根因是 `SetTaskFailed` 抹除了结构化 `ErrorCode`；
  4. **Wiki 检索质量门禁 (P1)**：真实中文 Wiki 评测中无答案误召回率（No-answer FP）高达 40%，且 CLI 默认阈值掩盖了此门禁；
  5. **生产级高可用与容灾缺失**：尚未完成生产环境双实例 PostgreSQL/Redis 共享运行、systemd 服务平滑升级及故障演练。

### 2. 深入模块走查发现的代码缺陷与设计弱点

#### 模块 A：编排与执行 (`internal/orchestrator` & `internal/multiagent`)
1. **DAG 批量并行执行缺乏并发上限控制（并发扇出无界）**
   - **代码位置**：`internal/multiagent/coordinator.go:1560-1575` (`partitionBatch`)
   - **机理分析**：在 `partitionBatch` 中，连续的只读步骤只要满足 `budgetLeft` 和 `stepsLeft`，就会被全部打入一个批次；随后的执行循环直接为该 batch 中所有 step 调用 `go func(...)` 并发执行。如果步骤达数十步，将无上限并发启动 goroutine，导致瞬间并发峰值击穿外部 LLM 速率限制或本地文件句柄。
   - **优化建议**：引入固定 worker 池或使用有界信号量（如 `max_parallel_steps = 5`）限制并发扇出。

2. **`SetTaskFailed` 抹除结构化错误码（状态机脆弱性的根源）**
   - **代码位置**：`internal/orchestrator/state.go:85-94`
   - **机理分析**：`SetTaskFailed(task, reason)` 发生时，将 `task.FinalAnswer` 硬编码赋值为 `"Failed: " + reason`，同时将 `task.ErrorCode` 和 `task.ErrorMessage` 强制清空置为 `""`。相反，`SetTaskCanceled` 则设置了 `ErrorCode`。这种不一致直接迫使下游（如 `handler.go` 的 Shutdown 回滚）只能通过检查 `len(task.FinalAnswer) > 20` 这种极其脆弱的字符串长度来猜测任务究竟是业务失败还是主动取消。
   - **优化建议**：统一保留结构化错误码，在 `Task` 结构体新增强类型 `TerminationKind`（`TerminatedBusinessFailed`、`TerminatedShutdown`、`TerminatedClientCanceled`、`TerminatedTimeout` 等），禁止用人类可读字符串做状态机分支判断。

3. **`engine.RunAll` 存储持久化失败未做状态回滚与通知**
   - **代码位置**：`internal/orchestrator/engine.go:1678-1685`
   - **机理分析**：每步执行完毕后调用 `e.Store.SaveFullTask(ctx, task)`，若存储层出错直接 `return err`，但此时内存中的 task 状态已发生变更，未对内存对象进行回滚，也未向 `StepCallback` 发送失败事件，可能导致长轮询/SSE 客户端永久挂起。

#### 模块 B：API 接入与并发控制 (`internal/api`)
1. **`resizableSemaphore` 等待者取消导致并发槽永久泄漏**
   - **代码位置**：`internal/api/handler.go:1903-1956`
   - **机理分析**：`wakeWaiters` 唤醒排队 waiter 时，首先将其移出 `waiters` 切片并执行 `s.current++`，然后关闭通道 `close(ch)`。如果客户端恰好取消请求（`ctx.Done()` 与 `<-ch` 同时满足），Go 的 `select` 随机命中取消分支；由于该 waiter 已经被移出切片，取消逻辑未能找到它，未扣减已分配的 `s.current`。频繁发生后，`current` 将虚高并最终达到 limit，导致系统误认为并发已满而拒绝所有后续请求（503 假死）。
   - **优化建议**：给 waiter 增加 `state` 字段（`pending`/`granted`/`cancelled`），在同一把互斥锁内完成状态流转，命中取消且发现状态为 `granted` 时强制执行 `s.current--` 补偿。

2. **限流配置热重载后仍以旧 Limit 唤醒**
   - **代码位置**：`internal/api/handler.go:1913-1946`
   - **机理分析**：`runTaskStep` 和 `runAll` 进入时从 `config.Get()` 捕获当时的 limit 并分别传入 `Acquire(ctx, limit)` 和 `Release(limit)`。如果系统发生热重载将 limit 调小（例如从 20 调至 5），旧任务退出调用 `Release(20)` 时，`wakeWaiters(limit)` 仍按照旧限额 20 唤醒排队的任务，导致实际并发严重超标。
   - **优化建议**：将权威 limit 维护在 `resizableSemaphore` 结构体内部，对外暴露线程安全的 `Resize(newLimit int)` 方法，`Acquire` 和 `Release` 不再接收外部 limit 参数。

3. **异步排队任务过早置为 `running` 状态**
   - **代码位置**：`internal/api/handler.go:1060-1120` (`runAll`)
   - **机理分析**：在启动后台 goroutine 前，handler 就调用 `TryTransitionTaskStatus` 将数据库状态改为 `StatusRunning` 并获取租约。然而在 goroutine 内部，任务还必须通过 `h.taskSem.Acquire(bgCtx, limit)` 竞争并发槽。若槽位紧张，任务可能在信号量中排队数分钟，但在数据库和外部 API 看来却已经处于 `running` 状态并消耗租约，造成外部观测与实际执行严重脱节。
   - **优化建议**：引入 `StatusQueued`（排队中）状态，或者在成功获得 `taskSem` 信号量后再做数据库向 `StatusRunning` 的 CAS 转换。

#### 模块 C：持久化与存储层 (`internal/store`)
1. **`PostgresStore` 严重缺失连接池参数设置**
   - **代码位置**：`internal/store/postgres.go:60-75` (`NewPostgresStore`)
   - **机理分析**：`SQLiteStore` 严格配置了 `db.SetMaxOpenConns(1)`、`db.SetMaxIdleConns(1)` 和 `PRAGMA`，但 `PostgresStore` 在 `sql.Open("postgres", dsn)` 后未对 `db` 设置任何连接池参数。Go 默认的 `MaxOpenConns` 为 0（无限制），在高并发压力下，可能会在短时间内向 PostgreSQL 发起海量连接，迅速耗尽数据库端连接配额（`FATAL: sorry, too many clients already`），导致整个服务雪崩。
   - **优化建议**：在配置中增加连接池参数（如 `max_open_conns: 50`, `max_idle_conns: 10`, `conn_max_lifetime: 5m`），并在 `NewPostgresStore` 初始化时显式应用。

2. **Wiki 候选缓存缺少总内存字节上限（O03 残余）**
   - **代码位置**：`internal/tools/wiki.go:190-250` (`wikiCache`)
   - **机理分析**：虽然通过 `maxTasks`（默认 1024）和 TTL 控制了任务条目数量，但并未限制单个任务内部的 `candidates` 字典大小和文档摘要/正文字节数。若外部恶意构造或大模型触发大量包含巨额文档的检索，缓存堆内存占用将线性失控。
   - **优化建议**：增加全局估算字节大小计数器，超过软上限（如 64 MiB）时触发基于 LRU 的强制驱逐。

#### 模块 D：工具与沙箱安全 (`internal/tools` & `internal/policy`)
1. **`apply_patch` 祖先目录 TOCTOU 路径越界 (P1)**
   - **代码位置**：`internal/tools/apply_patch.go:156-201`
   - **机理分析**：`applySearchReplaceBlocks` 先调用 `policy.ValidateReadPath` 检查路径有效性，再使用 `os.OpenFile(filePath, os.O_RDONLY|policy.O_NOFOLLOW, 0)` 打开文件。虽然 `O_NOFOLLOW` 能阻止最后一级文件名是软链接，但如果攻击者在工作区并发将某个父级目录（例如 `workspace/sub/`）替换为指向系统根目录的符号链接，中间路径解析仍然会跨越工作区。而在 Windows 平台，`policy/nofollow_windows.go` 直接将 `O_NOFOLLOW` 定义为 0，完全失去了对符号链接和重解析点（reparse point）的保护。
   - **优化建议**：Linux 平台使用 `openat2`（指定 `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`）；Windows 平台使用具备安全属性的原生文件句柄打开策略，禁止跟随重解析点。

2. **`config.Get()` 指针逃逸风险**
   - **代码位置**：`internal/config/config.go:789-795`
   - **机理分析**：`config.Get()` 直接返回全局结构体指针 `*Config`。尽管配置更新是原子替换指针，但由于返回的是结构体原指针，若系统内任何组件在读取配置后意外对指针内的 slice（如 `Tools.Allowlist`）或 map（如 `API.Tenants`）做写操作，将直接破坏全局运行配置且不受锁保护。
   - **优化建议**：调用点遵守只读约定，或对内部 slice/map 提供深拷贝/接口封装隔离。

#### 模块 E：检索质量算法 (`internal/wiki/directory_bm25.go`)
1. **BM25 检索缺少绝对置信度下限过滤（No-Answer FP 40% 的根因）**
   - **代码位置**：`internal/wiki/directory_bm25.go:280-325`
   - **机理分析**：在过滤合格候选集时，代码仅检查 `detail.matchCount >= minimumMatches`；对于分词后命中少量常见字（或单字）的场景，即使文档与查询语义毫不相关，也会被判定为合格（`qualified`），进而计算 BM25 分数并推入 Top-K 堆中返回给调用方。这就导致在“明确没有对应答案”的查询场景下，系统依然强行返回弱匹配页面。
   - **优化建议**：引入最低绝对分数下限（`min_score_threshold`）或相对阈值，过滤掉无显著信息增益的噪音召回页面。

## 四、待完成事项与缺陷修复清单（按优先级）

### 🔴 P0 级：发布硬阻塞

#### 1. Windows 平台交叉编译失败
- **代码位置**：`internal/brain/retraction.go:162`
- **问题根因**：Brain 撤回账本读取实现直接引用了 `golang.org/x/sys/unix` 包中的 Unix 特有系统调用（`unix.Openat`、`unix.Stat_t`、`unix.Fstat`），导致 `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./cmd/server` 编译失败。
- **影响**：发布脚本 `build.sh` 和 GitHub Actions `release.yml` 的 Windows 发布矩阵全部断裂，无法产出合法 Windows 二进制包。
- **修复方案**：
  1. 将文件底层安全访问抽象为平台接口（如 `retraction_unix.go` 与 `retraction_windows.go`）；
  2. Windows 下使用防重解析点（reparse-point-safe）的 Windows 句柄访问策略；
  3. 若暂时不支持 Windows 运行环境，则必须从发布矩阵与发布文档中暂时移除该目标，保证发布流水线绿灯。

### 🟠 P1 级：安全、并发与核心状态缺陷

#### 2. `apply_patch` 祖先目录 TOCTOU 安全越界
- **代码位置**：`internal/tools/apply_patch.go:156-201`
- **影响**：在存在并发写权限的工作区场景下，攻击者可通过替换父级目录，将补丁写入工作区边界之外。
- **修复方案**：
  - Linux/Unix 采用基于安全工作区目录文件描述符的 `openat2`（配 `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`）或受控 `openat` 逐层解析；
  - 增加针对“祖先目录在打开瞬间被替换为软链接”的确定性回归测试。

#### 3. 并发信号量等待者取消引发配额永久泄漏
- **代码位置**：`internal/api/handler.go:1903-1956` (`resizableSemaphore`)
- **影响**：在高并发交错取消场景下，`current` 会不断虚高递增，最终导致并发槽被假占满，正常请求被无故排队或拒绝（503）。
- **修复方案**：引入明确的 waiter 状态机（`pending` / `granted` / `cancelled`），在统一互斥锁保护下处理，当已授予许可但触发取消时必须执行补偿释放。

#### 4. 限流配置热重载后仍以旧 Limit 唤醒等待者
- **代码位置**：`internal/api/handler.go:1913-1946`
- **影响**：配置缩容后实际并发度不能立即稳定服从新配置。
- **修复方案**：将权威 `limit` 维护在信号量内部，提供原子的 `Resize(newLimit)` 接口；`Acquire` 和 `Release` 不再接收外部传入的 limit 参数。

#### 5. Shutdown 回滚与启动恢复依赖字符串长度启发式
- **代码位置**：`internal/api/handler.go:367-374`、`internal/orchestrator/state.go:85-94`
- **影响**：短业务失败可能被误恢复为 `paused`，而带有详细取消原因的任务又可能被遗漏无法恢复。
- **修复方案**：在 Task 表与内存模型中持久化结构化的终止原因（如 `termination_kind`、`error_code`），重构 `SetTaskFailed` 废除基于人类可读文本长度或关键词子串的猜测逻辑。

#### 6. Wiki 真实检索存在 40% 的无答案误召回
- **代码位置**：`internal/wiki/directory_bm25.go:280-325`
- **影响**：无答案测试用例误召回率高达 40%，且 CLI 默认阈值设为 1.0 导致门禁被静默放行。
- **修复方案**：收紧评测 CLI 默认门禁阈值为 0 或经评估的极低值；引入绝对置信度下限过滤，把真实 Wiki 测试集做成工程内确定性夹具。
