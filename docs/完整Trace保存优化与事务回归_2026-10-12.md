## 实现与行为

[saveTraceSnapshotSQL](../internal/store/trace_sql.go) 原来对每条 Trace 调用 `tx.ExecContext(ctx, query, args...)`，重复准备同一复杂 UPSERT。现在每次非空快照在当前事务调用一次 `tx.PrepareContext`，逐行使用该语句执行，并在函数返回时关闭。不缓存到其他连接/事务，不取消调用方的 Begin/Commit/Rollback；空快照删除原有行后直接返回，避免无用的准备。

预编译作用域与关闭方式依据 [Go 官方说明](https://go.dev/doc/database/prepared-statements)。本仓 SQLite 驱动 modernc.org/sqlite v1.50.1 对单条 prepared statement 缓存底层 SQLite handle；本机结果表明解析/准备开销是此前热点。SQLite 和 PostgreSQL 共用该函数；PostgreSQL 驱动行为及线上时延仍需专用实例验收，不能把 SQLite 收益推广到其他后端。

逐行参数绑定、PostgreSQL 文本清洗、逻辑 Step 与物理 sequence、unchanged-row 判断和 recorded_at 的 SQL 保持原样。仍逐条比较完整快照，并在同一事务中删除尾部/无效位置；不是只追加尾部。重排和内容更新保留同一物理位置的首次 recorded_at，截断删除尾部，空快照清空该任务 Trace。任务元数据与 Trace 更新依然由原 SaveFullTask 事务提交。

## 本机复测

Apple M4 Max、darwin/arm64、Go 1.26.8、GOMAXPROCS=16；串行操作，Trace 每条约 1 KiB observation 和 evidence，20 次/场景、两轮。初始化、建库和填充不计入测量。前后用同一固定长度、未改 Trace 的完整保存夹具；这测量重复快照 UPSERT 成本，不等同于持续增长/并发压测。

下表平均取两轮算术平均，P95 为两轮范围。

| SQLite 完整快照长度 | 优化前平均 | 优化后平均 | P95：前 → 后 |
|---|---:|---:|---|
| 100 条 | 3.026 ms | 0.494 ms | 3.195–3.200 ms → 0.537–0.550 ms |
| 1000 条 | 29.342 ms | 3.281 ms | 29.768–30.250 ms → 3.533–3.695 ms |
| 10000 条 | 301.981 ms | 37.209 ms | 304.432–306.173 ms → 38.675–38.694 ms |

万条场景平均约 **8.1 倍加速**。每次分配约 13.68 MB → 13.44 MB，分配量并未同比大幅降低；JSON 编码、参数构造和逐行执行仍存在，复杂度仍随 Trace 长度增长。

补充优化后“每次实际修改最后一条 observation”的夹具：1000 条平均 3.385 ms，10000 条平均 37.314 ms，万条 P95 38.018–38.204 ms。该场景包括构造新 observation，只有优化后数据，不能另算前后加速。它也不覆盖全量每行改写、尾部增长、重排压测或网络型 SQL 后端。

P95 仅 20 个样本/轮，作为本机诊断，不是生产 SLO、统计显著性或最大安全并发数；GC、缓存和后台负载影响结果。工作区有此前未提交改动，前后其他运行时代码一致，不代表一个已发布提交。

## 事务与兼容回归

[新增回归](../internal/store/trace_write_test.go) 使用真实 SQLite 和触发器注入第二条 Trace 的写入失败：第一条已经更新、尾部已经删除、任务元数据已经 UPSERT 时，整个 SaveFullTask 仍须回滚。读取完整 Task 和带 recorded_at 的 Trace 页都与失败前一致。独立 ReplaceTraces 的相同故障也回滚；失败后另一个事务仍能正常保存，验证语句资源释放。

另一用例验证不变快照、同 Step 多条事件、重排、截断及清空：Trace 内容、物理顺序和首次 recorded_at 按原契约保持。既有 timing-only 更新、legacy execution_step 转换、租约门禁、轻量快照/usage 一致性、SSE 断线恢复和独立 SQL 连接并发回归继续通过。

## 后续容量边界

这一批减少重复准备成本，没有实现增量 Trace 协议、批量绑定或后台归档。完整保存仍为 O(N)，SQL 网络往返和大字段编码在目标环境可能成为主要成本；不能在缺少完整替换/截断一致性契约时只保存最后一条。

下一步建立单机并发读写压力基线，观察排队、长快照与 SSE 数值聚合的争用，并据目标工作负载制定 Task/Trace 保留、归档、备份及磁盘预算。任何清理流程应先提供可审核的候选/归档方案，不能自动删除真实记录或批量文件。F05 在线身份待输入，HA/DAG 延后安排保持不变。
