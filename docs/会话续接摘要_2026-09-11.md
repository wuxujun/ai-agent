## 已完成

### B01–B04：高优先级执行、审批和并发问题

- B01：审批恢复前解密并验证最终批准结果。批准结果中的非 nil 参数整体替换动作参数，空 map 也会持久化；缺失、损坏、拒绝或无效结果不会消费审批或执行任务。
- B02：Memory、SQLite、PostgreSQL、Redis 增加原子 `CreateTask` 能力。API 删除先查后写的竞态，重复自定义 ID 返回 409；不支持 `TaskCreationStore` 的自定义 Store 返回 501。
- B03：SSE `Publish` 与 `Unsubscribe` 在同一生命周期锁内完成，避免向已关闭 channel 发送；保留慢订阅者的非阻塞行为。
- B04：`run-all` 和 HTTP/启动扫描审批恢复统一使用可续租执行租约。续租失败、租约丢失或独立截止计时器到期会取消执行，并阻止旧 owner 写入任务或状态；保存和状态转换带 owner/期限校验。获取租约后重新读取任务，流式断连和关闭回滚也不会覆盖新 owner 的结果。

### B05–B13：记录、Redis、边界和配置问题

- B05：SQL trace 按完整 trace 快照的数组位置保存，新增可空 `execution_step` 保留公开的逻辑 `Step`，相同逻辑步数的多个审计事件不再互相覆盖或丢失。
- B06：Redis 状态 CAS 在同一 Lua 脚本中维护全局和租户状态索引；引入 v4 索引命名空间、带 owner 的迁移锁、分批扫描和从当前任务 JSON 修复索引。
- B07：请求体在 handler 执行前限制为 10 MiB，覆盖已知长度和 chunked 请求；HTTP server 加入 10 秒请求头、30 秒请求读取、60 秒空闲连接超时，未设置 SSE 写超时。
- B08：LLM 流式输出累计内容在缓冲和 callback 前限制为 4 MiB；命令 stdout/stderr 各保留最多 1 MiB，超出部分继续排空并在返回文本中标记截断。
- B09：SSE 终态缓存使用单个 TTL 计时器主动清理，最多 1024 条，每条文本最多 64 KiB；含审批或超大事件依赖实时事件和 Store 回读。
- B10：热重载拒绝启动绑定配置变化并保留原快照和 revision；空 MCP 列表的 nil/empty 表示等价。查询上限、Wiki space、缓存和熔断参数等动态设置仍可热更新。
- B11：OpenAI/Ollama embedding 错误响应只读取有限字节并返回状态错误，不把上游正文带入错误；成功响应限制为 4 MiB，解析错误不返回原始正文。
- B12：严格 JSON schema 正确处理 `additionalProperties`：false 拒绝未知字段，true 或省略允许，schema 对象会验证额外字段值。
- B13：自定义 recovery 只记录 panic 类型、路径、请求/trace ID 和栈，不格式化 panic 值，也不输出原始请求头或请求体；已写响应和 EPIPE/ECONNRESET 路径有专门处理。

## 未完成和验证边界

1. 实际 PostgreSQL/pgvector 实例尚未连接验证；外部 PostgreSQL 合约已加入 CI 的测试选择范围，但当前工作区没有远端 CI 结果。
2. SQL 只读边界风险仍未完成动态证明：`sql_query` 的 tokenizer、SQLite 只读连接和方言边界需要专项验证，因此不能声称该风险已修复。
3. 没有进行生产环境双实例故障演练，也没有验证 Linux/systemd 部署行为；当前双 Handler 测试是进程内组件验证。
4. B04 失租后的取消依赖下游工具遵守 context；已经开始的外部副作用无法撤回。
5. B05 的 `traces.execution_step` 是可空新增列。升级时应备份数据库、停止旧版本写入，避免新旧二进制混写；旧版本回滚可能误解新 trace 序号，修复前已丢失的 trace 无法自动恢复。完整快照比较的长 trace 性能尚未专项基准测试。
6. Redis v4 索引首次使用时会惰性迁移；旧索引保留且程序不会批量删除。所有写入实例应先统一升级，旧版本状态 CAS 不会维护 v4 索引；大量存量数据的首次迁移延迟尚未专项压测。
7. 尚未运行 `govulncheck`、生产性能基准或真实服务端到端测试。
8. O01–O04 工程优化建议尚未实施：依赖漏洞可达性扫描、更多跨层契约测试、统一输入输出/缓存预算、按职责拆分大型模块。
