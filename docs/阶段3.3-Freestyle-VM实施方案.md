## 1. 环境拓扑与验收边界

| 角色 | 示例私网地址 | 职责 |
|---|---|---|
| node-a | 10.77.33.11 | Agent A，systemd 管理 |
| node-b | 10.77.33.12 | Agent B，使用与 A 相同发布物 |
| storage | 10.77.33.20 | 专用 PostgreSQL、Redis、NFSv4 |
| control | 10.77.33.30 | Prometheus、离线模型夹具、契约/负载/门禁工具 |

默认四台 `freestyle/ubuntu`，每台 4 vCPU / 8 GiB / 32 GB；仅免费策略也允许选择 `ubuntu-sm`，拒绝超过 Free 单机限制的 `ubuntu-lg`。先核对账号总配额、剩余使用额度和预计运行时间。至少安排基础 HA 负载一小时，以及 20%、50%、100% 各档独立观察窗口，另留出准备、恢复和复核时间；实际耗时可能超过四小时。

### 预算限制（2026-10-09 补充）

本次仅使用 Free，付费预算为 US$0。默认四台共分配 16 vCPU 和 32 GiB 内存，运行 1 小时消耗 16 vCPU·小时，完整 6 小时最多 96 vCPU·小时及 192 GiB·小时内存。官方 Free 月度额度为 CPU 200 vCPU·小时、内存 400 GiB·小时、存储 60000 GiB·小时和流量 50 GB；这些总额不能当作账号剩余额度。空闲时间也按分配资源计量。暂停停止计算消耗，保留的四台磁盘仍占存储额度，初始合计 128 GiB。[官方额度说明](https://www.freestyle.sh/docs/vms/pricing-and-limits)。

用户已确定“仅免费”：`spendingPolicy.mode=free-only`、`maxPaidSpendUsd=0`，不升级套餐或进入付费超额。Free 套餐没有付费超额，耗尽计算额度会暂停 VM；Hobby/Pro 允许付费超额，即使仍有免费额度或赠送信用也不作为本次允许的账号。已核对的公开文档及 SDK 未提供可据此宣称美元总账单硬上限的配置；本轮依靠实际 Free 套餐的无付费超额机制，不能用本地费用估算替代账号核验。

创建器现要求 `runtimeBudget.maxRunSeconds` 与 `runtimeBudget.maxRunTotalSeconds` 都为正整数，单次上限不得大于累计上限。仅免费方案初始将两个值均设为 21600，即每台单次及整个生命周期累计最多 6 小时；未配置上限的输入仍可离线规划，但创建资源前会被拒绝。四台默认规格完整使用此窗口最多消耗 96 vCPU·小时、192 GiB·小时内存；须核对实际剩余额度，另留存储保留及下载流量的额度。创建后必须核对服务端返回的两个有效上限，丢失或放宽时立即停止后续创建并保留资源检查点。

预算保护为 2026-10-09 新增的操作工具修改，不能直接使用原 `9aeb24b` 的无限运行创建器。最新工具位置、测试结果与完整 `.env` 清单见[预算核对记录](../records/ha-freestyle-budget-env-2026-10-09.md)；应用发布包仍可保持已核验的干净 `9aeb24b` 身份。

用户选择与最新操作资产以[仅免费策略记录](../records/ha-freestyle-free-only-2026-10-09.md)为准；预算金额为 0，凭据及只读认证已完成，套餐依据用户明确确认。200 是月度 vCPU·小时总额，四台默认规格分配 16 vCPU，即空闲也按分配时长计量；完整 6 小时最多 96 vCPU·小时，不把总额记为剩余额度。

累计上限由平台控制，到期暂停，重启不会重置；本批脚本不会自动提高上限。该机制限制计算运行时间，不能限制持续存储、流量、套餐费或账号其他操作的费用。套餐未知、付费或已知额度不足时拒绝创建。用户明确确认 Free 且剩余额度未知时，可按平台无付费超额的硬额度执行，记录 `quotaSufficient=null`、`quotaPolicy=stop-on-platform-limit`，不得声称额度足够。运行期间保持 Free，额度耗尽就停止续跑，不以升级绕过。不要用自动删除 TTL 充当预算限制，以免丢失证据。额度或运行上限中断的负载窗口必须如实记为未完成。

创建器额外要求 `--account-review` 私密 JSON，绑定本次 API key 的 SHA256。`freestyle-dashboard` 来源要求账号引用、30 分钟内的实际 Free/剩余额度复核；模板所有结论均为 null。也接受明确的 `user-confirmation` 来源，限 24 小时内续接，记录凭据引用而不虚构账号 ID；额度未知时必须明确采用平台硬额度停止策略，并检查请求的累计 CPU 时间不超过确认的月度总额。缺失、付费、已知不足、过期或密钥不匹配时，在创建前停止。两种来源都是事实记录，不是自动账单 API 响应；API key 认证本身不能证明套餐。实际 API key 和原始证据保留在私密目录。

A/B 使用相同 `ha_cluster`、`ha_role=agent` 标签，并配置 `placement.antiAffinity`，`topology=node`。当前官方 OpenAPI 与 SDK 0.2.16 将其定义为不同宿主机的硬性约束；服务端无法满足时应停止，不允许去掉约束重试。脚本还检查返回的 placement。此约束不证明跨可用区或跨地域容灾。

Storage 是隔离测试依赖，不提供 PostgreSQL、Redis、NFS 自身的冗余。Control 独立于故障节点，避免停止 A/B 时同时失去压测和监控。NFS 功能、权限、跨节点即时读写及重启后的挂载必须实测；如果目标镜像不支持 NFSv4，应停止部署，改用经验证的共享存储方案。

## 2. 网络与凭据

VPC 创建时不添加全网互通规则。脚本只开放下列实例间 TCP 路径：

| 来源 | 目标 | 端口 |
|---|---|---|
| A/B/Control | Storage | 15432 PostgreSQL、16379 Redis、2049 NFSv4 |
| Control | A/B | 8088 API/授权 JSON 指标，9464 OTLP collector 的 Prometheus 指标 |
| A/B | Control | 18080 离线模型夹具 |

每台 VM 另外允许出站 TCP 80/443、TCP/UDP 53，用于系统包、容器镜像及依赖下载。不创建公网入口、TLS 域名、WireGuard 隧道或通配私网规则。API 绑定 `0.0.0.0:8088`，同时兼容现有部署脚本的 loopback 健康检查；入站可达性由 Freestyle 防火墙限制。若账号原有规则、域名或隧道扩大了访问范围，须在环境核验中处理，不能仅凭本脚本的规则推断隔离成立。

`FREESTYLE_API_KEY` 仅保留在操作端环境中，不进入 VM。`render.py` 在仓库外生成随机且不同的管理员 key、测试租户 key、PostgreSQL/Redis 密码、stub token，以及共享的 32 字节审批加密密钥。生成目录为 0700，文件为 0600。真实环境也可使用秘密管理提供相同 JSON 字段。

Agent 环境文件由 root 持有，权限 0600。应用需要读取的测试配置与 Team 文件为 root:ai-agent、0640。Prometheus/Redis 的容器挂载文件在 root 专用的 0700 父目录内，文件授予容器读取权限。不要输出 `docker compose config` 的明文结果；仅使用 `config --quiet`。

生成配置使用独立 `ha_test` 非管理员租户，只允许 `software` 测试 Team。管理员 key 仅供授权 JSON 指标检查，负载使用租户 key。Prometheus 通过私网 9464 采集本机 OTLP collector 的 `/metrics`，不直接采集返回 JSON 的 `/api/metrics`，不转发管理员 key 到 collector。默认 Team 的工具白名单只有 `read_file`；审批演练需要另外准备经过评审的有限副作用夹具和 Team，不能直接把普通软件开发 Team 放开后运行。

## 3. 脚本清单

脚本位于 [deploy/ha/freestyle](../deploy/ha/freestyle/)。新增环境脚本不进入现有应用发布包，按独立操作工具分发，并记录其提交或文件摘要。

| 文件 | 行为 |
|---|---|
| `topology.example.json` | 四角色、私网地址、镜像、仅免费及初始 6 小时上限，无凭据 |
| `account-review.template.json` | Free 套餐及剩余额度复核模板，所有结论待核验 |
| `provision.mjs` | 默认打印本地规划；`--apply` 才创建 VPC、VM、规则，并逐步保存资源 ID |
| `render.py` | 在仓库外生成随机秘密和四角色私密配置，拒绝覆盖已有输出 |
| `bootstrap.sh` | 默认打印计划；在 fresh Linux VM 上准备存储、NFS、身份及服务配置 |
| `prepare-nfs.sh` / `verify-listener.py` | 选择内核 NFS 或 Ganesha，验证仅私网监听，识别 IPv4 映射地址 |
| `prepare-telemetry.sh` | A/B 本机固定版本 OTLP collector，4318 仅 loopback、9464 仅节点私网；配置先校验 |
| `workspace-probe.py` | 以固定 ai-agent UID 写入/校验共享哨兵，保留文件 |
| `deploy-agent.sh` | 检查初始 0%、共享挂载及测试配置，再复用 `deploy-node.sh` |
| `run-control.sh` / `control-worker.sh` | 使用 systemd 后台运行七项契约、smoke、soak 或只读门禁 |
| `observe-load.mjs` | 操作端观察已有 smoke/soak，私密导出后暂停四台专用 VM；不创建或恢复资源 |
| `verify-contracts.py` | 必须七项顶层契约通过，拒绝缺失、失败或任意跳过的子用例 |
| `offline_stub.py` | 有 token、大小限制的 OpenAI Chat/embedding 夹具，只支持固定只读 Team |
| `fault-node.sh` | 在 A/B 执行显式停服、主进程 SIGKILL 或启动，记录命令与任务信息 |
| `acceptance.template.json` | 全部待验收的证据模板，不预填成功 |

创建资源、安装服务、部署、负载和故障入口默认只展示计划。`render.py` 是本地文件生成器，`workspace-probe.py` 的 write 会明确写一个新哨兵。脚本不提供删除资源、删除数据、批量清理、接管同名 VM 或自动升灰度功能。失败时保留部分资源和记录；先核对最后一个 state 文件再决定恢复方式，不重复创建同名环境。

## 4. 操作端准备

先核对当前 HEAD 和工作区。已有文档及记录的未提交改动应保留。当前已验证及目标部署的应用包对应 `9aeb24b`；如果部署另一提交，先从该提交的干净检出重新回归、构建和校验。即使 HEAD 不变，临时发布包也必须重新校验存在性和 SHA256。

在仓库根目录执行本地规划，无需凭据或安装 SDK：

```bash
node deploy/ha/freestyle/provision.mjs \
  --config deploy/ha/freestyle/topology.example.json
```

为每次环境选择唯一 prefix 和不与现有网络冲突的私网段。执行前，安装目录内 `package.json` 固定的 `freestyle@0.2.16`：

```bash
cd deploy/ha/freestyle
npm install --ignore-scripts
npm ls freestyle
```

保存产生的 lockfile、SDK/Node 版本与脚本摘要作为操作工具身份。`--apply` 要求脚本旁的 SDK 版本精确匹配 0.2.16。Freestyle CLI 可使用该目录的 `node_modules/.bin/freestyle`，避免另装不同版本的全局 CLI。以下命令中的 `freestyle` 均指该已固定版本。

通过秘密管理向操作端注入 `FREESTYLE_API_KEY`。创建资源命令示例（这一步会创建资源并消耗账号额度）：

```bash
node provision.mjs --config topology.example.json \
  --account-review /private/tmp/ai-agent-ha-free-account-review-001.json \
  --output /private/tmp/ai-agent-ha-freestyle-resources-001 --apply
```

输出目录必须不存在。`plan.json` 是规划，递增的 `state-NNN.json` 是成功操作后的资源检查点。检查最后一份记录、四台 VM 的实际地址/资源/镜像、A/B placement、有效运行策略，以及账号全部适用的防火墙规则。部分错误只显示脱敏摘要，详细原因应在平台后台核对，禁止把上游原始响应贴入仓库。

创建时关闭 idle 与 TTL，单次及累计运行时限必须按选定预算填写为有限正值，不使用 ephemeral VM。平台可能限制停止后的保留时间；记录实际 `autoDeleteSeconds`，并保证证据已经导出。创建后应定期检查账号额度，避免免费配额耗尽导致窗口中断。

项目根目录 `.env`、`deploy/litellm/.env` 和 `deploy/opentelemetry/.env` 是不同用途的实际配置文件。Freestyle CLI 只自动读取当前目录的 `.env`；自定义 `provision.mjs` 只读取进程环境，不自动遍历或合并这些文件。操作端按明确路径仅提取 `FREESTYLE_API_KEY` 注入，建议秘密文件权限 0600，禁止把该密钥分发给 guest 或混入模型/监控配置。模板 `.env.example` 不作为凭据来源。

生成本地秘密及 guest 资产：

```bash
python3 render.py secrets --output /private/tmp/ai-agent-ha-secrets-001.json
python3 render.py assets --config topology.example.json \
  --secrets /private/tmp/ai-agent-ha-secrets-001.json \
  --output /private/tmp/ai-agent-ha-assets-001
```

保持秘密文件私有，不将其加入 Git，不打印内容。生成配置是隔离环境专用配置：关闭 Wiki/Brain、Langfuse 和答案质量流水线，固定离线模型与价格，并保持 0%。它覆盖的是运行时测试场景；不证明生产模型、Wiki/Brain 或质量流水线已经验收。若这些能力属于本次验收范围，应另建一致的配置版本和语料，再补测对应链路。

## 5. 上传并准备四角色

先用各 VM 的 `uname -m` 确认架构，三台需运行发布二进制的 VM（A、B、Control）必须选择匹配的发布包。为简化同包验证，优先使用相同架构。

使用 `freestyle vm scp` 上传**脚本目录本身，不包含 node_modules 或秘密文件**到每台 VM 的 `/root/ha-kit`。可以先将本目录中的脚本、JSON 示例和模板复制到仓库外的新 staging 目录；整个操作包另存 SHA256。将各角色资产分别上传到对应节点的 `/root/ha-assets`，不要把 Storage/Control 凭据整包交给 A/B。CLI 的 scp 以 root 写文件；目标目录应预先不存在，避免出现多套嵌套目录。

下例使用示例 prefix；实际以最新 state 文件内的 VM ID 为准，可用固定版本 CLI 的 `vm fs mkdir` 创建父目录：

```bash
freestyle vm scp /private/tmp/ai-agent-ha-assets-001/storage \
  ai-agent-ha-20261008-storage:/root/ha-assets
freestyle vm exec ai-agent-ha-20261008-storage --linux-user root -- \
  bash /root/ha-kit/bootstrap.sh --role storage --assets /root/ha-assets
```

先检查无 `--apply` 的计划，再在对应 VM 内执行带 `--apply` 的命令。顺序为 **Storage → Control → A → B**。不复用已有业务 VM。bootstrap 遇到已有状态会停止，不覆盖半完成环境；检查 `/etc/ai-agent-ha/status`，只有 `bootstrap-complete-not-accepted` 才进入后续步骤。

`apt-get` 或镜像下载可能超过 Freestyle exec 的五分钟上限。应使用 `freestyle vm ssh <vm>` 的持久 PTY 执行 bootstrap，或在 guest 中用 systemd 启动准备过程并轮询状态。不要将一次 exec 超时误判为服务安装一定失败；先检查 guest 内进程和标记。

Storage 使用仓库已有 PostgreSQL/Redis 固定镜像版本，`max_connections=150`，Redis 开启密码及 AOF。`prepare-nfs.sh` 在内核支持 `nfsd` 时准备 `/etc/exports.d` 并使用内核服务端，否则安装 Ubuntu 官方 NFS-Ganesha/VFS 包。Ganesha 仅绑定 Storage 私网、只提供 NFSv4/TCP，默认拒绝客户端，仅允许 A/B/Control，保留 root_squash；服务启动不替代实际跨节点权限与重挂载验收。三台客户端挂载均位于 `/opt/ai-agent/workspace`，使用固定 UID/GID 21088。Agent 的 systemd drop-in 依赖挂载成功后启动。

完成后双向验证共享哨兵。先在 A 以 `ai-agent` 用户执行：

```bash
python3 /opt/ai-agent-ha/bin/workspace-probe.py --mode write --id a-to-b-001
```

在 B 以相同用户执行 read，并把 A 输出的 SHA256 作为 `--sha256`；再反方向执行一次。CLI 可通过 `--linux-user ai-agent` 运行。重启挂载/节点后重复读取并核验路径与 UID，记录结果。哨兵保留，不提供批量删除命令。

## 6. 存储契约、同包部署与 smoke

将校验通过的同架构发布包复制到 A、B、Control 的 `/srv/ha-bundle`，该目录不能包含秘密，且 ai-agent 用户必须可遍历并读取，二进制必须可执行。复制后在每台执行 `sha256sum --check SHA256SUMS`；保存实际 Server 摘要、提交、架构和 `git_dirty=false`。

将同提交的**干净 Git 检出**复制到 Control 的 `/srv/ha-source`，使 ai-agent 用户拥有并可读取它。为 Control 单独安装官方、经过校验的 Linux 原生 Go 1.26.8 到 `/usr/local/go`；当前 `go.mod` 要求 1.26.8，不能照旧项目简介使用 1.25。bootstrap 已准备 race 所需的 C 编译环境，但不会自动下载或替换 Go 工具链。

在 Control 启动七项存储契约：

```bash
bash /root/ha-kit/run-control.sh --mode contracts --bundle /srv/ha-bundle \
  --source /srv/ha-source --run contracts-001 --apply
```

该脚本核对干净源码提交与发布清单一致，使用专用 PostgreSQL 和 Redis DB 15。检查后台单元退出码，以及 `/var/lib/ai-agent-ha/results/contracts-001/contracts-summary.json`：必须 `passed=true`、七项全齐、无失败/跳过。仍应复核连接上限与真实 110 连接持有证据；150 不自动涵盖新增其他客户端。

随后在 A、B **依次**部署：

```bash
bash /root/ha-kit/deploy-agent.sh --bundle /srv/ha-bundle --apply
```

脚本复用已有干净发布部署器，保持原发布文件和校验清单。测试配置放在 `/etc/ai-agent/ha-config.json`，通过环境文件选择；测试 Team 放在 `/opt/ai-agent-ha/runtime/teams.yaml`，通过 systemd `BindReadOnlyPaths` 映射到服务内部的 `/opt/ai-agent/teams.yaml`。WorkingDirectory 保持 `/opt/ai-agent`，确保租户 workspace 位于应用根目录内，不放宽现有路径策略；日志使用已允许写入的 `/opt/ai-agent/logs`。报告须分别记录应用包身份和环境配置身份，不能把测试 override 说成发布包内原配置。

最小配置保留空的 `llm.api_key` 字段，使 Viper 解码时识别环境中的 `AI_AGENT_LLM_API_KEY`；实际 stub token 只来自 root 所有、0600 的环境文件。不要移除 stub 认证来绕过密钥映射问题。通过 `bash -s` 的 stdin 执行操作脚本时，Docker Compose 临时容器必须使用 `-T` 并重定向 `</dev/null`，避免容器消耗后续脚本输入；始终复核最终标记和服务状态。

检查 systemd、`/ping`、`/ready`，以及 Prometheus targets 中 A/B 均 `up=1`、无认证或采集错误。Prometheus HTTP 仅在 Control loopback:9090 可达，离线 stub 监听 Control 私网 18080，拒绝未知 schema 和非固定只读工具。

再从 Control 执行 smoke：

```bash
bash /root/ha-kit/run-control.sh --mode smoke --bundle /srv/ha-bundle --run smoke-001 --apply
```

轮询 `systemctl show ai-agent-ha-smoke-001 -p ActiveState -p Result -p ExecMainStatus`，读取新 run 目录中的 `status.json` 与 `load/report.json`。后台启动成功不等于负载成功；必须检查最终退出码。现有 smoke 包装器要求任务全部通过且两个端点均有样本；底层短时 HOLD 不算完成一小时验收。

## 7. 一小时连续负载与独立故障验收

```bash
bash /root/ha-kit/run-control.sh --mode soak --bundle /srv/ha-bundle --run soak-zero-001 --apply
```

负载由独立 systemd 单元持续运行，操作端断开不会终止进程。检查窗口至少 60 分钟、无任务数上限提前停止、两节点分布、错误率/P95、runtime Trace、数据库连接峰值和逐任务结果。`status.json` 记录开始/结束及命令退出码；中断或超时不能当作成功。运行时缺少选择 Trace 时仍记为 unknown，不推断成 Legacy。

通用 `observe-load.mjs` 目前只通过离线回归。**本轮发现瞬时暂停响应与后续运行状态不一致；再次使用 `--apply` 前，须补充停止 Control Prometheus/stub 和暂停后延时资源清单核对。** 本轮已通过私有纠正脚本停止采集后重新暂停，并三次确认稳定 paused；原因尚未独立复现。该脚本当前的行为说明及规划入口如下，先不加 `--apply` 核对计划。仅使用现有创建 state 中的四台 ID；应用时检查每台 slug、标签、单次与累计有效上限。它每 45 秒观察一次，最多 90 分钟；三次连续读取错误或本地检查点写入失败会停止观察，仍尝试导出及暂停已核对的四台。导出原始结果到仓库外的新私密目录，随后停止 A/B 服务并按 A、B、Control、Storage 顺序暂停，逐台确认平台 `state=paused`。该脚本只覆盖负载与暂停，不自动运行门禁、注入故障、提高预算或宣称完整 HA 通过。

```bash
node deploy/ha/freestyle/observe-load.mjs \
  --state /private/tmp/ai-agent-ha-run/resources/state-019.json --run soak-zero-001
# 明确注入 FREESTYLE_API_KEY 后，使用一个不存在的仓库外输出目录执行：
node deploy/ha/freestyle/observe-load.mjs \
  --state /private/tmp/ai-agent-ha-run/resources/state-019.json --run soak-zero-001 \
  --output /private/tmp/ai-agent-ha-observation-001 --apply
```

负载、导出或任意暂停未通过时返回 2，保留检查点供续接；平台累计上限始终是最后保护。操作端进程被终止后不能继续观察，应检查原负载及 VM 状态，不能据此宣称已经暂停。本轮实际运行使用先前生成的私有监视器，额外保存只读门禁和 Prometheus 查询；新通用脚本未用于本轮云端执行。`soak-001` 已由用户主动停止，64/64 条任务通过但运行仅约 31 分 40 秒，不能计为完整窗口；最终停止过程及暂停异常纠正见[实施记录](../records/ha-freestyle-start-2026-10-09.md)。

默认离线夹具只覆盖固定 README 的 planner/writer/embedding 传输和执行流程。它不产生审批、Replan、长任务副作用，也不评价真实模型能力。独立验收必须另备可控延迟、审批及副作用观测夹具，限定到专用目录/计数器，保存夹具与 Team/配置版本，并在 A/B 同步验证；本方案不自动放宽白名单。

下一版的计数服务、固定 probe、审批 API 和故障断言见[独立 HA 夹具设计](阶段3.3-Freestyle-独立HA夹具设计.md)，当前未部署；尤其要区分至多一次消费与实际动作是否发生。

按以下清单逐项实施并填写模板：

| 场景 | 必须保存的断言 |
|---|---|
| A 创建，B 批准/拒绝 | 两条路径均执行；并发同一决定只有一次 CAS 接受；工具最多执行一次 |
| 跨节点取消 | 接纳响应之后仍核对最终任务状态；旧执行器实际停止 |
| 失租/续约失败 | 对指定测试任务/实例注入；旧 owner 停止且不能覆盖新 owner 结果 |
| SIGTERM | 任务 paused/恢复行为、退出耗时、重新启动后的状态 |
| SIGKILL/重启 | 租约到期、显式恢复、审批恢复、重复副作用计数 |
| 实时 SSE | 故障发生前已连接的流、故障中的事件、跨节点重连和持久化终态比较 |

`fault-node.sh` 仅支持对标记为 A/B 的本机 `ai-agent.service` 操作。示例：

```bash
bash /root/ha-kit/fault-node.sh --action term --task-id ha-fixture-task-001 \
  --output /root/fault-term-001.json --apply
bash /root/ha-kit/fault-node.sh --action start --task-id ha-fixture-task-001 \
  --output /root/fault-start-001.json --apply
```

`term` 通过 systemctl stop 发送服务单元配置的 SIGTERM，保持停止直到显式 start。`kill` 使用主进程 SIGKILL，原服务的 Restart=on-failure 仍会生效；记录新 PID、恢复时间与任务结果。脚本的命令结束时间不是恢复完成时间，输出始终 `recovery_verified=false`，需独立核验。

失租注入、数据库/Redis 中断必须按本次环境负责人确定的范围实施。本批脚本不提供直接改租约表、整机强制断电或全网断连命令。若采用 guest 防火墙隔离某实例的续约流量，要预设自动恢复，保留 Control 与平台管理通道，并核验既有连接确实中断。Freestyle pause 保存内存，不代替 SIGKILL 或冷启动验收。

## 8. 灰度推进与回退

完成基础 HA 和上述独立断言后，才进入 20%。由操作员在 A/B 的环境文件中统一修改 `AI_AGENT_MULTIAGENT_DAG_CANARY_PERCENT`，始终保留 `AI_AGENT_MULTIAGENT_RUNTIME=legacy`；逐台重启并验证 readiness，不能同时停止两台。实际环境值要与文档和模板一致。

每次重启后重新积累完整窗口；默认门禁包装器使用一小时。先运行无人工复核标志的 gate，保存 HOLD 原因：

```bash
bash /root/ha-kit/run-control.sh --mode gate --bundle /srv/ha-bundle --run gate-20-initial --apply
```

人工审查审批/Replan Trace、故障证据和监控覆盖后，使用新 run ID 再运行：

```bash
bash /root/ha-kit/run-control.sh --mode gate --bundle /srv/ha-bundle \
  --run gate-20-reviewed --manual-review-passed --apply
```

只有报告 `decision=PROMOTE`、最终退出码 0 且对应故障检查通过，才能按同样方式进入 50%、100%。默认门禁要求至少 20 个成功 DAG 样本和 20 个 Legacy 调用；0% 不适合比较，20% 的一小时默认负载也可能样本不足，应延长/增加受控测试样本，不调低门槛凑通过。默认只读 stub 不提供审批/Replan 复核证据，不能单凭它晋级。

50% 完整窗口必须保存进入 100% 的 DAG/Legacy 对照晋级证据。100% 稳态按绝对 SLO 和已保存证据复核，不能伪造新的 Legacy 对照。回退将两节点百分比恢复到 0，依次重启并检查 readiness；已创建任务保持持久化 runtime，不强改。脚本不会自动设置人工通过、修改百分比或移除 Legacy。

## 9. 证据归档与完成判据

复制 `acceptance.template.json` 到仓库外，为每次实测填写；所有 pending/null 均表示未通过。至少归档：

- 云资源 ID、A/B placement、实际 IP/架构/镜像/配额与有效生命周期。
- 发布提交及包摘要、操作工具版本、脱敏配置版本、共享 workspace 双向及重挂载检查。
- 七项契约完整执行与容量摘要，smoke、至少一小时 soak 的 JSONL/JSON。
- Prometheus 指标覆盖、各档 DAG/Legacy 样本、错误率/P95、连接数峰值。
- 每次故障的任务 ID、注入/恢复时间、审批 CAS、旧 owner 写入、重复副作用与实时 SSE 断言。
- 20%/50% 晋级报告、100% 稳态检查、回退验证及人工复核人/时间。

后台单元的原始日志和 `contracts.jsonl` 可能包含测试错误细节，保留在私有目录，脱敏审查后再提交摘要。不要整包归档 `/etc/ai-agent*`、assets、秘密文件、原始任务回答或环境变量。

`ha-soak`、本批脚本和模板初始值均不宣称完整 HA 验收。只有全部场景实测并完成复核，才更新阶段 3.3 为完成。结束时先导出证据，再按角色停止服务/暂停 VM；这属于运维操作，须确认本轮任务已结束。本批不执行或提供批量删除。
