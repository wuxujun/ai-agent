## 读取与一致性

新增可选 `store.TaskStreamSnapshotStore` 接口，返回 ID、status、step_count、updated_at、final_answer、error_code/error_message、Trace 数量及累计 token usage。它不返回 Trace/evidence/observation/memory/audit 明细。累计值来自物理持久化 Trace，不根据逻辑 StepCount 推算；重复 Step、截断和替换均按当前 Trace 重新统计。

- Memory：持有同一读锁，复制状态字段并遍历 Trace 的数值字段，无完整 Task/Trace 深复制。写入仍使用原有锁；读取仍是 O(Trace count)，本次没有引入可漂移的独立缓存。
- SQLite/PostgreSQL：一条参数化 SELECT 将任务行与该任务 Trace 的 COUNT/SUM 聚合关联，不先读 metadata 再执行第二次查询。这样状态与统计来自同一 SQL 语句观察，避免跨查询拼接两个保存版本。没有新增索引、列或 SQL 迁移；数据库仍需扫描该任务的数值列，尚非 O(1) 汇总。
- Redis：现有原子保存脚本写入的 `task:metadata:v1:<id>` 增加 `stream_stats`（version=1、trace_count、token_usage），与该次 Task/Trace 快照同时保存。状态迁移脚本保留此嵌套字段并更新同一 metadata 状态，不增加新的 key。旧 Task reader 忽略新 JSON 字段；删除仍按现有 metadata key 生命周期清理。

Redis 旧 metadata 缺少汇总/存在不支持的版本，或 metadata 尚不存在时，回退到一次完整 Task JSON 读取，以该次读取重新计算全部字段。不会将先读到的 metadata 状态与后读的 Trace 拼接。未重新保存的历史任务可能继续走重读取；新版本保存或原有读模型修复生成新版 metadata 后才能使用轻量路径。混合旧写入实例也可能重新生成无汇总的 metadata；升级所有写入实例后再评估收益。本次没有扫描并改写真实历史任务。

自定义 Store 未实现该可选接口时，SSE 继续以单次 GetTask 完整快照兼容；实现接口但读取失败时不回退绕过错误，仍按 SSE 故障策略处理。API 还核对返回快照 ID，不能发送另一个任务的投影。数据库隔离语义依据 [SQLite 官方说明](https://www.sqlite.org/isolation.html) 和 [PostgreSQL statement snapshot 说明](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)；PostgreSQL 实例本次未在线验收，不能将文档依据等同于实测。

## 测量结果

沿用前一批夹具：Apple M4 Max、darwin/arm64、Go 1.26.8、GOMAXPROCS=16；串行读取，100 次/场景、两轮，初始化排除。每条 Trace 约 1 KiB 独立 observation 和一个 evidence；万条夹具 JSON 约 12.26 MB。full 与 stream_snapshot 在同一次基准中比较，响应序列化、HTTP 网络和生产并发不包含在测量内。

| 万条 Trace 场景 | 完整读取 | 轻量读取 |
|---|---:|---:|
| Memory 平均耗时（两轮） | 0.378 ms | 30.3 μs |
| Memory 每次分配 | 约 2.49 MB | 0 B / 0 allocs |
| SQLite 平均耗时（两轮） | 19.70 ms | 3.98 ms |
| SQLite P95（两轮范围） | 20.21–20.27 ms | 4.05–4.17 ms |
| SQLite 每次分配 | 约 38.33 MB | 1,920 B / 50 allocs |

B/op 是分配量，不是峰值 RSS；亚微秒及 P95 数据受采样/GC/缓存影响。SQLite 的数值扫描仍随 Trace 长度增长，宽行存储布局也影响读取成本。Redis 网络会读取现有 metadata JSON，较大 audit/答案等字段仍可能增加传输与 JSON 扫描；轻量路径没有承诺所有任务固定字节开销。Memory 返回不可变字符串字段不复制字符串内容，最终答案的 SSE JSON 序列化仍有其原始成本。

原始 [基准输出](benchmarks/task-stream-snapshot-2026-10-12/read.log) 和 [机器可读结果/环境/源码哈希](benchmarks/task-stream-snapshot-2026-10-12/results.json) 已保留。基准入口为 [task_capacity_benchmark_test.go](../internal/store/task_capacity_benchmark_test.go)。采样工作区包含此前未提交改动，不代表一个发布提交的性能。

## 回归与验收

Memory/SQLite 契约测试覆盖空 Trace、追加、同 Step 多事件、重排、截断、清空、状态迁移、partial 答案/错误、取消和删除；SQLite 独立 ReplaceTraces 路径也与 GetTask 的完整快照对比。双 SQLite 连接及 Memory 的并发保存/读取，逐次验证 status、Trace 数量和 usage 必须属于同一保存版本。

API 回归验证实现可选接口时禁止调用 GetTask、正确映射终态/Trace 数量/usage，且接口错误不回退；既有强制断线、双处理器共用 SQLite、丢终态、Store 短暂失败、旧缓存、初次订阅竞争窗口和授权回归继续通过。自定义测试适配器未实现新接口时继续验证原兼容路径。

真实 Redis 7.2.6 验收在本机新启动的专用实例完成：TCP port=0，仅私有 Unix socket，禁用 RDB/AOF。覆盖完整契约、状态迁移保留汇总、旧 metadata 回退，以及现代 metadata 在完整 Task JSON 被夹具故意置为不可解析时仍正确读取汇总。使用唯一夹具 ID，完成后恢复/删除自己的记录并停止专用进程；没有操作已有服务或批量清理。

PostgreSQL 保留显式启用的独立契约入口；没有提供专用 DSN，本次在线状态为 **NOT_RUN**。Memory/SQLite 和 Redis 成功不能代替 PostgreSQL、真实 HA 或目标环境并发验收。
