## 建议优先修复

### O01 / P1：搜索错误包含上游响应原文

- 位置：`internal/tools/web_search.go:140–159`，`internal/tools/middleware.go:67–73`，`internal/logger/logger.go:169–188`。
- 非成功 HTTP 响应最多读取 4096 字节后直接拼入 error；Firecrawl 的 error 字段也直接返回。工具重试会以 `error` 属性记录该错误，而 logger 的属性脱敏并不清洗 `error` 的内容。
- 因此，上游若在错误中回显认证信息、请求文本或内部诊断内容，这些内容会进入应用日志。执行器还会将工具错误放入 Trace 的 Error/Observation；OTel 也记录错误。这里确认的是传播路径，不声称真实上游已经返回过秘密。
- 建议：在工具边界构造安全错误，只携带 provider、HTTP status、安全错误码和可公开的关联标识；不把原始上游 body 当错误信息。不要只依赖事后正则脱敏。
- 验收：模拟 401/429/500 和 HTTP 200 的业务 error，注入唯一敏感哨兵，确认工具错误、重试日志、Trace 和遥测均不包含哨兵。

### O02 / P1：通用错误中间件直接公开内部错误

- 位置：`internal/api/middleware.go:46–59`。
- 任意 handler 调用 `c.Error(err)` 后，客户端收到 `err.Error()` 原文；该错误也原样进入应用日志。数据库驱动、文件操作及远程客户端的内部错误可能携带路径、查询上下文或连接信息。
- 建议：对外固定安全消息和稳定错误码，附已有 request ID；日志使用受控错误字段。对已开始写入的响应检查 `Writer.Written()`，避免再次写 JSON。
- 验收：注入包含内部路径和敏感哨兵的 Store 错误，HTTP 响应不暴露原文；已经写出的响应不追加第二段 JSON。保留内部定位能力且不记录秘密。

### O03 / P1：SEARCH/REPLACE 补丁执行忽略取消

- 位置：`internal/tools/apply_patch.go:75–84,157–193`。
- SEARCH/REPLACE 分支调用的 helper 没有 context 参数。工具中间件虽然创建 timeout context，但它同步等待底层 Execute 返回，不能强行中断此分支。执行中发生超时或取消后，仍可能继续遍历替换并提交文件写入。
- Unified Diff 已有部分 context 检查，两个补丁格式的取消行为不一致。
- 建议：传入 context，在读取、每个替换块和提交前检查取消；明确最后一次检查与原子提交之间的不可中断边界。
- 验收：在处理中途取消和 deadline 到期时拒绝提交、保留原文件；正常补丁行为及路径限制不变。

### O04 / P1：补丁输入文件和替换结果无容量上限

- 位置：`internal/tools/apply_patch.go:174–193,196–216`，`internal/tools/apply_patch_unified.go:34–48`。
- 共享读取 helper 对普通文件使用无界 `io.ReadAll`。随后又转换字符串、遍历替换或拆分行，文件内容会产生多份内存分配。HTTP 请求的 10 MiB 限制不能限制已有工作区文件大小。
- 建议：设置目标文件、patch、块数和最终输出上限；打开后核对实际文件属性，使用 `limit+1` 有界读取，不能仅检查路径的初始 Stat 大小；替换期间预检输出增长。
- 验收：边界大小、超过限制一个字节、读取中增长以及多块输出膨胀均有明确拒绝行为；失败不改变源文件。

## 接口一致性与观测

### O05 / P2：创建会话把所有持久化失败都报告为冲突

- 位置：`internal/api/session.go:59–61`。
- 数据库关闭、磁盘写入失败、连接故障或 context 超时，同样返回 409 `session already exists`，客户端不能正确决定重试，监控也难以识别服务故障。
- 建议：Store 层统一重复记录的 sentinel error，仅明确冲突映射 409；其他故障进入安全的服务错误处理。同步接口示例与契约。
- 验收：四种 Store 的重复 ID 保持 409，fake Store 的非冲突失败返回合适的服务错误且不泄露原文。

### O06 / P2：会话分页元数据与实际执行值不同

- 位置：`internal/api/session.go:88–105`；如 `internal/store/sqlite.go:901–917`。
- handler 返回未经归一化的 `filter.Limit`，Store 则默认 50、最大 500。不传 limit 时响应报告 0，传 1000 时报告 1000，实际最多读取 500。非法值还会被静默忽略。
- 建议：handler 统一验证和归一化分页参数，返回实际执行值；评估兼容性后明确非法参数的 400 行为。Store 仍保留防御性上限。
- 验收：默认、边界、超限、非数字和负值的请求/响应一致，Console 分页不回归。

### O07 / P2：访问日志的客户端 IP 缺少可信代理配置

- 位置：`cmd/server/build.go:41–50`，`internal/api/middleware.go:101`。
- router 创建后没有调用 `SetTrustedProxies`，访问日志直接使用 `ClientIP()`。Gin 默认信任全部代理，直连客户端提供的转发头可能影响记录的 client_ip。
- 建议：本地直连默认禁用代理信任；部署在反向代理后时显式配置代理地址/CIDR，并验证转发头链。当前只用于日志，不将它描述成已存在的认证绕过。
- 验收：直连伪造 X-Forwarded-For 无效，可信代理转发有效，非可信来源无法覆盖审计来源。

## 性能与维护优化

### O08 / P2：长 Trace 保存仍重复扫描完整历史

- 位置：`internal/orchestrator/engine_lifecycle.go:512–519`，`internal/store/trace_sql.go:54–76`，`internal/store/sqlite.go:45–47`。
- 每轮 run-all 调用 SaveFullTask，SQL 对所有已有 Trace 逐条编码并执行 upsert。已复用事务内预编译语句且未变化行不更新，但每次保存仍为 O(N)；Trace 持续线性增长时，累计处理量可能达到 O(N²)。SQLite 单连接还让这段写事务与读取竞争。
- 建议先建立当前基线，再设计带预期版本的增量 append；保留历史重排、截断和替换的完整快照路径。不要简单取消租约、事务或盲目增大 SQLite 连接数。
- 验收：比较 1k/10k Trace 的新增单步保存耗时、分配量和混合读写 P95；回归 recorded_at、顺序、截断、回滚、租约 fencing 和并发快照一致性。
