# 2026-07-20 变更记录

## 一、Multi-Agent 双工作流支持

### 1. 背景

原有 Multi-Agent 模式只支持以下三角色流水线：

```text
Planner -> Researcher -> Writer
```

本次在保留原工作流的同时，新增带计划评审和结果验证的四角色流水线：

```text
Planner -> Critic -> Executor -> Verifier
```

两种工作流同时存在，通过 `teams.yaml` 或环境变量切换；未配置工作流时继续使用原三角色模式，保持向后兼容。

### 2. 工作流配置

`internal/multiagent/teams.go` 新增工作流类型：

- `planner_researcher_writer`：原三角色研究与写作工作流。
- `planner_critic_executor_verifier`：新增四角色评审与执行工作流。

每个团队通过 `workflow` 选择拓扑：

```yaml
active_team: "software_reviewed"

teams:
  software:
    workflow: "planner_researcher_writer"

  software_reviewed:
    workflow: "planner_critic_executor_verifier"
```

同时支持环境变量覆盖：

```bash
AI_AGENT_MULTIAGENT_TEAM=software_reviewed
AI_AGENT_MULTIAGENT_WORKFLOW=planner_critic_executor_verifier
```

`AI_AGENT_MULTIAGENT_WORKFLOW` 也接受 `review`、`reviewed` 和 `execution` 别名。未知或空值回退到原三角色工作流。

### 3. 角色配置与 Trace

`TeamConfig` 在原有 `planner`、`researcher`、`writer` 之外新增：

- `critic`
- `executor`
- `verifier`

`types.AgentRole` 同步新增 `critic`、`executor`、`verifier`，四角色工作流产生的 Trace 会明确标注：

```text
planner -> critic -> executor -> verifier
```

原三角色工作流仍记录：

```text
planner -> researcher -> writer
```

### 4. Critic 执行语义

- 四角色工作流中的 Critic 是必经阶段，不受可选计划评审开关影响。
- Critic 复用 `internal/plancritic` 的结构化评审协议，检查完整性、顺序、依赖、可行性、效率和安全风险。
- Critic 首次拒绝计划时，Coordinator 会把评审结果写入 Trace，并要求 Planner 根据评审意见重新规划。
- 修订计划必须再次通过 Critic；第二次仍被拒绝时任务失败，不执行工具。
- 原三角色工作流继续保留已有的按场景、复杂度和风险触发的可选 Plan Critic 行为。

### 5. Executor 执行语义

- `ExecutorAgent` 与原 `ResearcherAgent` 共享底层工具执行实现。
- 保留 workspace 边界校验、工具注册表、风险等级、人工审批、并行只读批次、Token/工具/步数预算和取消传播。
- 四角色工作流的工具执行 Trace 标记为 `executor`，原工作流仍标记为 `researcher`。
- 失败后的协作式 Replan 在四角色工作流中也必须再次通过 Critic。

### 6. Verifier 执行语义

- 四角色工作流不经过 Writer，Verifier 根据 Executor 收集的证据生成最终答案并校验支持度。
- Final Verifier 分成两个独立 LLM 调用：第一个只生成候选答案，第二个只根据证据审查候选答案，避免单次调用自生成、自验证。
- Verifier 结构化输出包含：
  - `final_answer`
  - `evidence_summary`
  - `draft_confidence`
  - `supported`
  - `issues`
- 问题类型限定为 `unsupported_claim`、`evidence_gap`、`contradiction`。
- `supported=false` 时强制将草稿置信度降为 `low`，并把结构化问题写入 Trace Evidence。
- JIT 检索模式下如果事实性答案没有成功检索证据，继续使用保守拒答策略。

### 7. 主要文件

- `internal/multiagent/coordinator.go`：双工作流选择、强制 Critic、Executor 调度和最终 Verifier 阶段。
- `internal/multiagent/critic_agent.go`：团队配置感知的 Critic Agent。
- `internal/multiagent/researcher_agent.go`：新增 ExecutorAgent，共享受策略保护的工具执行实现。
- `internal/multiagent/verifier_agent.go`：新增最终验证输出与 `Finalize` 能力。
- `internal/multiagent/teams.go`：工作流和四角色团队配置。
- `internal/multiagent/types.go`、`internal/types/task.go`：新增角色常量和说明。
- `teams.yaml`：三角色和四角色团队示例。

## 二、teams.yaml Prompt 支持 Langfuse

### 1. 背景

项目已有 `internal/promptmanager`，支持从 Langfuse 获取 Prompt、缓存和本地 fallback，但原先 `teams.yaml` 一旦配置非空 `system_prompt`，Agent 会直接使用内联内容并绕过 Langfuse。

本次为每个 LLM 角色增加显式 Langfuse Prompt 引用，并统一 Prompt 解析逻辑。

### 2. 新增配置字段

`AgentConfig` 新增：

- `prompt_name`：推荐字段，指定 Langfuse Prompt 名称。
- `langfuse_prompt`：兼容别名；两者同时配置时优先使用 `prompt_name`。
- `draft_prompt_name`：四角色 Verifier 的候选答案生成 Prompt；`prompt_name` 用于独立支持度审查。
- `draft_system_prompt`：候选答案生成 Prompt 的本地 fallback。

配置示例：

```yaml
teams:
  software_reviewed:
    workflow: "planner_critic_executor_verifier"
    planner:
      name: "Software Execution Planner"
      prompt_name: "teams/software-reviewed/planner"
      system_prompt: |
        Local planner fallback prompt.
    critic:
      name: "Software Plan Critic"
      prompt_name: "teams/software-reviewed/critic"
    executor:
      name: "Software Tool Executor"
    verifier:
      name: "Software Result Verifier"
      draft_prompt_name: "teams/software-reviewed/verifier-draft"
      prompt_name: "teams/software-reviewed/verifier-check"
```

Executor 是纯工具角色，不调用 LLM，因此不需要 Prompt 配置。

### 3. Prompt 解析优先级

当角色配置 `prompt_name` 或 `langfuse_prompt` 时：

1. 通过 PromptManager 从 Langfuse 获取指定名称的 `production` 标签 Prompt。
2. Langfuse 未启用、凭证缺失、请求失败或内容无效时，回退到该角色的 `system_prompt`。
3. 未配置 `system_prompt` 时，回退到代码内置默认 Prompt。

当角色未配置 Langfuse Prompt 名称时：

1. 非空 `system_prompt` 保持原行为，直接作为团队 Prompt。
2. 未配置 `system_prompt` 时，继续通过原默认 Prompt 名称访问 PromptManager，并以代码默认 Prompt 兜底。

现有 PromptManager 缓存策略保持不变：成功结果缓存 10 分钟，失败 fallback 短缓存 1 分钟，避免持续请求 Langfuse。

### 4. 已接入角色

- Planner
- Replanner
- Critic
- Writer
- Answer Verifier
- 四角色工作流的 Final Verifier

Replanner 在团队 Planner Prompt 基础上追加失败诊断和禁止重复失败步骤的约束，保持原重规划协议。

### 5. Langfuse 环境配置

继续复用已有配置，无新增密钥字段：

```bash
LANGFUSE_ENABLED=true
LANGFUSE_PUBLIC_KEY=...
LANGFUSE_SECRET_KEY=...
LANGFUSE_BASE_URL=https://cloud.langfuse.com
```

## 三、兼容性与安全性

- 未配置 `workflow` 时默认使用 `planner_researcher_writer`。
- 原有 `system_prompt`、Provider、Model 和 `llm_scene` 配置继续有效。
- Langfuse 不可用不会阻断任务，始终使用内联或代码默认 Prompt 回退。
- Prompt 获取继续使用现有超时、缓存和凭证隔离逻辑。
- Executor 继续经过 workspace 校验、工具风险判断和高风险审批，不因工作流切换绕过策略层。
- Critic 不能降低或绕过确定性策略和审批控制。

## 五、P0 正确性优化

### 1. Critic 反馈进入 Replanner

原实现把 Critic 的详细问题与修改建议存入 Trace Evidence，但 Replanner Prompt 只包含 Trace Observation 摘要，导致 Planner 看不到具体拒绝原因。

优化后，Replanner 上下文会附带 Critic Evidence 中的问题等级、描述和 `Recommendation`。内容限制为最多 10 条 Evidence、每条最多 4 行、每行最多 1000 个字符，避免反馈放大 Prompt。

### 2. 工具步数与角色阶段分离

`Task.StepCount` 继续作为全局 Trace 序号，记录 Planner、Critic、Executor/Researcher、Writer/Verifier 等全部阶段；`MaxSteps` 改为只限制实际工具执行。

工具步数从持久化 Trace 中按 `researcher` 或 `executor` 角色统计，因此任务恢复后仍能维持同一限制，无需新增存储字段或迁移。Planner、Critic、Replanner 和 Verifier 的调用不再挤占工具执行配额。

### 3. Partial 状态语义

以下情况不再错误标记为 `completed`：

- `MaxSteps`、工具预算或 Token 预算耗尽，仍有计划步骤未执行。
- 工具步骤失败且没有被成功 Replan 修复。
- 最终答案被独立 Verifier 判定为不受证据充分支持。

这些任务标记为 `partial`，并在 `Task.Unresolved` 中记录 `max_tool_steps_reached`、`tool_budget_exhausted`、`token_budget_exhausted`、`execution_step_failed` 或 `final_answer_not_fully_supported` 等机器可读原因。计划、Critic 或 Verifier 调用本身发生错误时仍标记为 `failed`。

### 4. 回归测试

- 验证两个 Executor 步骤在 `MaxSteps=2` 时均可执行，即使全局 Trace 序号已经超过 2。
- 验证执行计划被步数限制截断时状态为 `partial`。
- 验证 Final Verifier 返回 `supported=false` 时状态为 `partial`。
- 验证 Replanner Prompt 包含 Critic 的具体问题与修改建议。
- 验证候选答案生成与支持度审查是两次独立 LLM 调用，并正确合并 Token 用量。

## 六、P1 自适应工作流路由

### 1. 目标

在保留两个固定工作流的基础上新增 `adaptive` 模式，根据任务复杂度和执行风险自动选择：

- 低风险、低复杂度任务：`planner_researcher_writer`。
- 高风险或高复杂度任务：`planner_critic_executor_verifier`。

路由复用 Orchestrator 已有的 IntentRouter Trace 和 Planner 已生成的计划，不增加额外 LLM 调用。

### 2. 配置

```yaml
teams:
  software:
    workflow: "adaptive"
    routing:
      reviewed_intents: ["coding", "automation"]
      reviewed_complexities: ["high"]
      reviewed_min_plan_steps: 4
      allow_research_high_risk_tools: false
```

也可使用 `AI_AGENT_MULTIAGENT_WORKFLOW=adaptive` 或别名 `auto` 覆盖当前团队的固定工作流。原 `planner_researcher_writer` 和 `planner_critic_executor_verifier` 配置行为不变。

### 3. 决策顺序

1. 计划包含注册表中 `RiskLevelHigh` 工具时，默认选择四角色工作流。
2. IntentRouter 的复杂度命中 `reviewed_complexities` 时选择四角色工作流；未配置时默认匹配 `high`。
3. Intent 命中 `reviewed_intents` 时选择四角色工作流。
4. 计划步骤数达到 `reviewed_min_plan_steps` 时选择四角色工作流。
5. 其余任务选择三角色工作流。

`allow_research_high_risk_tools=true` 可以关闭第一条自动升级规则，但工具自身的确定性审批和策略护栏仍然有效。

### 4. 审计与恢复

自适应决策写入 `multiagent_workflow_route` Trace，包含 configured workflow、effective workflow 和 reason，并同步写入 OpenTelemetry Span 属性。任务恢复时默认复用已持久化的路由决策；如果新计划风险升高，则只允许从 Research 单向升级到 Reviewed。

新增测试覆盖固定模式兼容、高风险工具、高复杂度、Intent、计划步数阈值、低风险三角色路径、四角色路径和持久化决策复用。

## 七、P0 安全闭环补强

### 1. 高风险审批 Fail-Closed

Coordinator 执行注册表中 `RiskLevelHigh` 工具时，如果没有注入 `SuspendForApproval`，不再继续调用工具。系统会写入 `approval/handler_unavailable` Trace Evidence，保留工具预算，并返回错误将任务标记为 `failed`。

标准 Server 入口仍使用已有审批总线；本项主要防止测试入口、替代二进制或自定义依赖注入遗漏审批器后形成静默绕过。

### 2. Adaptive Replan 单向升级

自适应工作流不再只检查初始计划。以下位置产生新计划后都会重新评估风险：

- 工具执行失败后的纠错 Replan。
- 草稿低置信度触发的 Adaptive Depth Replan。
- 暂停任务恢复后重新生成的初始计划。

如果原工作流为 `planner_researcher_writer`，而新计划命中高风险、复杂度、Intent 或计划长度规则，则单向升级为 `planner_critic_executor_verifier`，重新经过 Critic，并由 Executor 和 Final Verifier 接管后续阶段。运行中不会从 Reviewed 降级回 Research。

每次升级追加新的 `multiagent_workflow_route` Trace，恢复时以最新决策为准。

### 3. 审批拒绝 Trace 与工具计数

Coordinator 在调用审批器前通过 Context 传递实际执行角色。Reviewed 工作流的拒绝记录现在标记为 `executor`，Research 工作流仍标记为 `researcher`。

审批拒绝和审批器缺失都属于 Gate 结果，不属于实际工具执行，因此不计入 `MaxSteps` 工具步数，也不扣减 `ToolBudget`。拒绝 Trace 的 `Step` 同步使用当前全局 Trace 序号，消除原先的序号跳跃。

验证命令：

```bash
GOCACHE=/private/tmp/ai-agent-go-cache go test ./...
GOCACHE=/private/tmp/ai-agent-go-cache go test -race ./internal/multiagent/... ./internal/orchestrator/...
```

验证结果：全部通过，无 race 报告，`git diff --check` 通过。

## 八、P1 生产可控性优化

### 1. Team 配置快照

Coordinator 在每次执行链路开始时只读取一次 `teams.yaml`，生成包含 Active Team、TeamConfig 和 SHA-256 摘要的 Context 快照。Planner、Replanner、Critic、Researcher、Executor、Writer、Verifier 后续统一从该快照读取 Prompt、Provider、Model、Scene 和策略配置，避免热更新期间同一执行链路混用新旧配置。

Planner Trace 的 `team_config` Evidence 记录团队名与配置摘要，OpenTelemetry Span 同步记录 `multiagent.team` 和 `multiagent.team_config_digest`，便于审计。新任务或暂停后重新启动的执行链路仍会读取最新配置；已持久化的 Adaptive 工作流路由继续按原有规则复用或单向升级。

### 2. Adaptive 预算感知

`routing` 新增两个可选门槛：

```yaml
routing:
  reviewed_min_remaining_llm_calls: 3
  reviewed_min_remaining_tokens: 0
```

复杂度、Intent 或计划长度命中 Reviewed 时，如果任务启用了对应预算且剩余预算低于门槛，则回落到 Research，并记录 `budget_fallback:llm_calls:<原路由原因>` 或 `budget_fallback:tokens:<原路由原因>`。未配置门槛、任务未启用对应预算、以及两个固定工作流的行为保持不变。

高风险工具优先级高于预算回落：计划包含高风险工具时仍强制进入 Reviewed，不能通过预算配置绕过 Critic、审批或策略护栏。

### 3. Critic 收敛策略

Reviewed Team 支持配置 Critic 驳回后的最大 Replan 次数：

```yaml
critic_policy:
  max_replans: 2
```

未配置时保持原行为，最多 Replan 1 次；显式设为 0 时首次拒绝即失败；为限制失控开销，运行时上限为 5。每轮使用规范化计划指纹检测重复，Replanner 返回已审核过的相同计划时立即终止，不再重复调用 Critic。

### 4. Verifier 模型隔离

Verifier 的候选答案生成与独立支持度审查除了使用不同 Prompt，现在也可使用不同的模型配置：

```yaml
verifier:
  draft_prompt_name: "teams/software-reviewed/verifier-draft"
  draft_provider: "openai-responses"
  draft_model: "gpt-5-mini"
  draft_llm_scene: "multiagent_writer"
  prompt_name: "teams/software-reviewed/verifier-check"
  llm_scene: "answer_verifier"
```

Draft 未单独配置 Provider 或 Model 时兼容回退到 Verifier 对应字段；未配置 `draft_llm_scene` 时默认使用 `multiagent_writer`。Verify 继续使用 Verifier 的 `provider`、`model`、`llm_scene`，默认场景为 `answer_verifier`。

新增回归测试覆盖配置快照稳定性与审计摘要、LLM Call/Token 预算回落、高风险预算豁免、Critic 多轮收敛与重复计划终止、Draft/Verify 独立 Scene，以及新增 YAML 字段解析。

## 九、P2 Verifier 检查点与恢复

### 1. Draft 检查点

标准 `VerifierAgent` 新增独立 `Draft` 阶段，并实现 `CheckpointFinalVerifier`。Coordinator 在 Draft 成功后、Verify 开始前追加 `verify_draft` Trace，检查点包含：

- 候选答案、证据摘要和草稿置信度。
- Draft Token 使用量。
- 本轮 Verify 使用的执行证据。
- 工具执行是否完整及未完成原因。

候选答案同步写入 `Task.FinalAnswer`。Server 启动时把现有 Store 的 `SaveFullTask` 注入 Coordinator，因此标准运行路径会在 Verify 前立即原子持久化 Task 与检查点，不需要新增数据库字段或迁移。

已有只实现 `FinalVerifier.Finalize` 的自定义实现继续走原子调用兼容路径；只有实现 `CheckpointFinalVerifier` 的实现启用阶段检查点。

### 2. Verify 失败语义

Draft 成功但 Verify 调用失败时：

- 保留候选答案和完整检查点。
- Task 标记为 `partial`，而不是 `failed`。
- `Task.Unresolved` 记录 `final_verification_retry_required`。
- Verify 错误和本次 Token 使用量写入 Trace。

Draft 生成失败、检查点持久化失败或缺少可恢复的 Verifier 实现仍标记为 `failed`，避免把不可恢复故障伪装成部分成功。

### 3. 精确恢复

带有效 `verify_draft` 检查点的 Multi-Agent `partial` Task 是终态规则的唯一窄范围例外。再次调用：

```http
POST /api/tasks/{task_id}/run-all
```

系统会从检查点直接调用 Verify，不重复 Planner、Critic、Executor 或 Draft。Verify 成功后清除 `final_verification_retry_required`；证据充分且原执行完整时转为 `completed`，否则保持 `partial` 并记录原执行原因或 `final_answer_not_fully_supported`。

单次 `run-all` 最多执行一次恢复 Verify；如果服务仍不可用，任务继续保持可恢复的 `partial`，不会在同一请求内循环重试。其他 `partial`、`completed` 和 `failed` Task 仍维持原有终态行为。

### 4. 回归覆盖

- 验证 Draft 后立即调用持久化回调。
- 验证首次 Verify 失败保留候选答案和检查点。
- 验证恢复只增加 Verify 调用，Planner、Critic、Executor、Draft 均不重复。
- 验证 Engine `RunAll` 可以进入带检查点的终态 Task。
- 验证恢复再次失败时单次请求只调用一次 Verify。
- 验证 HTTP `run-all` 接受可恢复的 `partial` 并持久化最终状态。

## 十、P2 跨恢复 Team 配置锁定

### 1. 配置策略

`teams.yaml` 新增顶层恢复策略：

```yaml
active_team: "software"
resume_config_policy: "require_match"
```

支持两个值：

- `require_match`：恢复时 Team 名称或配置摘要不一致则阻止继续。
- `use_latest`：明确接受当前配置，记录迁移后继续执行。

也可使用 `AI_AGENT_MULTIAGENT_RESUME_CONFIG_POLICY` 临时覆盖；支持 `strict/locked` 和 `latest` 别名。未配置时为兼容旧部署默认 `use_latest`，非法非空值按 `require_match` 处理，避免配置拼写错误意外放宽约束。仓库示例配置显式使用 `require_match`。

### 2. 漂移检测

Planner Trace 已记录 Active Team 和 TeamConfig SHA-256 摘要。任务重新进入 Coordinator 时，在任何 Planner、Critic、Executor、Draft 或 Verify 调用之前，将最近一次持久化摘要与当前快照比较。

摘要覆盖工作流、路由、Critic 策略以及所有角色的 Prompt 引用、内联 Prompt、Provider、Model 和 Scene；同时单独比较 Active Team。任务记录只保存团队名与摘要，不保存完整 System Prompt，也不新增数据库字段。

### 3. 严格阻塞与显式迁移

`require_match` 检测到漂移时：

- 追加 `multiagent_team_config_change` Trace，记录旧/新团队、摘要和策略。
- Task 标记为 `partial`，`Unresolved` 增加 `team_config_changed`。
- 当前 `run-all` 结束，不调用 LLM 或工具，也不会在同一请求内循环。

需要使用新配置继续时，运维显式设置：

```bash
AI_AGENT_MULTIAGENT_RESUME_CONFIG_POLICY=use_latest
```

再次调用 `POST /api/tasks/{task_id}/run-all`。系统追加带新 `team_config` Evidence 的迁移 Trace，清除 `team_config_changed`，并把新摘要作为后续恢复基线。

Verifier Draft 检查点恢复同样执行该检查，因此 Draft 使用旧配置而 Verify 使用新配置的情况不会静默发生。

### 4. 回归覆盖

- 相同 Team 与摘要恢复时不新增 Trace。
- `require_match` 检测漂移并形成可恢复的阻塞状态。
- `use_latest` 记录迁移、更新摘要基线并清除阻塞原因。
- 环境变量可以显式覆盖恢复策略。
- Engine 只为 Verifier 检查点或 Team 配置阻塞开放 Multi-Agent 终态恢复例外。

## 十二、P2 Critic Prompt 校准与离线评测

### 1. 固定评测集

新增 `evals/plan_critic.yaml`，使用带版本号的严格 YAML Schema 保存 Critic 基准案例。首批 11 个案例覆盖：

- 正常代码检索、Web 调研、检查后修改、检查后运行测试。
- 未注册 Tool、非法 Tool 参数、缺失依赖、前向依赖。
- 修改前未取证、依赖变更前未取证等高风险漏检场景。
- 重复只读步骤只产生中等级效率建议但仍批准，作为误拒边界案例。

每个案例声明期望批准结果、风险级别和可选 Issue Category。数据集加载使用 `KnownFields`，未知字段、重复名称、非法 Category、非法风险级别、空计划和越界阈值均直接失败，避免配置拼写错误静默污染基准结果。

### 2. 可复用评测核心

新增 `internal/criticeval`，统一计算：

- Accuracy。
- False Rejection Rate。
- False Acceptance Rate。
- High Risk Miss Rate。
- Issue Category Match Rate。
- Error Rate、Token 和耗时。

阈值随数据集版本管理。任一阈值不满足时 CLI 返回退出码 1；参数、数据集或输出错误返回 2；全部通过返回 0，适合直接作为 CI Gate。

规则基线只处理客观可判定问题：Tool 是否注册、参数能否通过 Tool Validator、依赖是否存在且顺序正确、高影响变更前是否取证。它不会调用 LLM，也不会执行计划中的 Tool。低/中等级效率建议不会触发拒绝。

### 3. CLI 与 Langfuse Prompt 链路

默认离线运行：

```bash
go run ./cmd/critic-eval
go run ./cmd/critic-eval -format json
```

显式在线运行：

```bash
go run ./cmd/critic-eval \
  -mode online \
  -allow-live \
  -team software_reviewed \
  -timeout 30s \
  -max-total-tokens 20000
```

在线模式使用 `multiagent.CriticAgent`，因此与生产路径一致：读取指定或当前 Active Team 的 Critic Provider、Model、Scene 和 Prompt 配置；配置了 `prompt_name` 或 `langfuse_prompt` 时通过 Prompt Manager 获取 Langfuse production Prompt，获取失败时回落到 `system_prompt` 或默认 Prompt。在线模式必须提供 `-allow-live`，避免测试或本地误操作产生真实调用和费用；不存在的 Team 会直接失败，不会静默使用空配置。

支持 `-max-cases` 做快速抽样，支持 `-max-total-tokens` 在已完成案例达到预算后停止下一案例。JSON 输出为逐案例 JSONL 加最终 Summary，可供 CI、报表或后续 Langfuse Dataset 同步程序消费。

### 4. 默认 Prompt 拒绝边界

默认 Critic Prompt 明确约束：

- 只有不可执行、必需依赖缺失、高影响动作在必要取证前执行或实质安全风险才使用 high severity。
- 只有可选改进或 low/medium Issue 的可执行计划必须批准。
- 不得仅因存在更优方案、高风险 Tool 需要正常审批或确定性 Policy 会再次校验而拒绝。

Team 内联 Prompt 或 Langfuse Prompt 仍可覆盖默认 Prompt；固定评测集用于验证覆盖后的 Prompt 是否保持同一批准边界。

### 5. 验证结果

离线基准结果：11/11 决策正确，Accuracy 和 Category Match Rate 均为 1.0，误拒率、误放率、高风险漏检率和错误率均为 0。

新增测试覆盖严格数据集解析、规则边界、中等级建议仍批准、Tool Middleware 解包后的参数校验、超时、各类失败率与阈值计算、在线显式授权保护、JSON 输出和默认 Prompt 校准约束。在线评测依赖实际 LLM/Langfuse 凭据，不纳入默认测试套件。

## 十三、P2 Langfuse Prompt 版本选择与 A/B Gate

### 1. Team Prompt Selector

所有 Team 角色的 `AgentConfig` 新增：

```yaml
prompt_name: "teams/software-reviewed/critic"
prompt_label: "production"
# prompt_version: 12
```

`prompt_label` 与正整数 `prompt_version` 互斥；两者均未设置时继续使用 `production` Label，兼容已有配置。Verifier Draft 使用独立的 `draft_prompt_label` 和 `draft_prompt_version`，不会与最终 Verify Prompt 的 Selector 混用。

Selector 接入所有实际调用 LLM Prompt 的角色：Planner/Replanner、Critic、Writer、Verifier，以及 Verifier Draft。Executor 与 Researcher 是 Tool 执行角色，不发起角色 Prompt LLM 调用。Team 配置摘要自动包含新增字段，因此恢复中的任务切换 Prompt Label 或 Version 会被既有 `resume_config_policy` 漂移检测捕获。

### 2. Prompt Manager

`PromptManager.GetWithSelector` 支持按 Label 或 Version 调用 Langfuse Public API：

- Label 请求使用 `?label=<label>`。
- Version 请求使用 `?version=<positive integer>`。
- Prompt Name 继续作为单一 URL Path Segment 转义。
- 缓存键包含 Host、Public Key、Prompt Name 和 Selector，不同 Label/Version 不会共享内容。
- 非法组合在普通运行中记录错误并使用本地 fallback，保持生产可用性。

新增 `GetStrict` 用于评测和发布 Gate。严格模式在 Langfuse 未启用、凭据缺失、请求失败或返回内容非法时直接失败，不接受普通模式写入的 fallback 缓存，避免 Baseline 与 Candidate 实际测试了同一份本地 Prompt。

### 3. Critic A/B 评测

比较当前 Team 配置与 Candidate Label：

```bash
go run ./cmd/critic-eval \
  -mode online \
  -allow-live \
  -team software_reviewed \
  -candidate-label latest
```

比较两个固定 Version：

```bash
go run ./cmd/critic-eval \
  -mode online \
  -allow-live \
  -team software_reviewed \
  -baseline-version 11 \
  -candidate-version 12 \
  -format json
```

也可使用 `-baseline-label` 覆盖 Team 配置的 Baseline。A/B 模式对同一批案例顺序执行两次，分别输出 Case、Summary、Token 和耗时，并计算 Candidate 相对 Baseline 的 Accuracy、Category Match、误拒、误放、高风险漏检、错误率、Token 与耗时变化。

`-max-cases` 可用于对称抽样。A/B 模式禁止使用 `-max-total-tokens`，因为两个变体可能在不同案例达到 Token 上限，产生不可比较的样本；单变体在线评测仍支持该限制。

### 4. 发布判定

Candidate 同时满足以下条件才返回退出码 0：

- Candidate 通过数据集定义的全部质量阈值。
- Baseline 决策正确的案例，Candidate 没有变为错误或调用失败。
- Baseline 已命中期望 Issue Category 的案例，Candidate 没有丢失该 Category。

Baseline 错误而 Candidate 正确会记录为 Improvement；反向变化记录为 Regression。Regression 按案例输出，平均指标提升不能抵消单个已知安全或正确性退化。比较失败返回 1，Selector、Team、数据集或输出错误返回 2。

### 5. 回归覆盖

新增测试覆盖 production 默认值、Label/Version URL、互斥和负 Version 校验、Selector 缓存隔离、fallback 缓存不能进入严格评测、Team 与 Draft Selector YAML 解析、Critic Context 覆盖、Langfuse 禁用时严格失败、逐案例 Regression/Improvement、Candidate Threshold Gate、案例对齐校验以及 JSON A/B 输出。

## 十四、P2 Prompt 解析元数据与可追溯性

### 1. ResolvedPrompt

Prompt Manager 新增结构化解析结果：

```go
type ResolvedPrompt struct {
    Name     string
    Version  int
    Labels   []string
    Selector Selector
    Source   string
    Content  string
}
```

`Get` 和 `GetWithSelector` 继续只返回字符串，调用方无需迁移；`Resolve`、`ResolveStrict` 用于需要审计元数据的路径。`Content` 明确标记为不参与 JSON 序列化，防止评测结果或调试输出意外泄漏完整 System Prompt。

缓存现在保存完整解析元数据，并在读出时复制 Labels，避免调用方修改共享缓存。普通 fallback 缓存的 `Source` 为 `fallback`，远端成功内容为 `langfuse`。

### 2. 严格解析约束

严格模式除原有的启用状态、凭据、Selector 和远端错误检查外，新增：

- 响应必须包含正整数 Version。
- 响应 Prompt Name 必须与请求一致；响应未提供 Name 时使用已验证的请求 Name。
- Version 缺失的旧远端缓存不会被严格模式接受。
- fallback 内容即使缓存未过期，也不会被作为远端 Prompt 返回。

这保证 A/B 输出中的 `resolved_version` 是 Langfuse 实际返回并经过校验的版本，而不是根据请求 Label 推测。

### 3. OpenTelemetry Span 事件

每次 Prompt 解析在当前 Span 写入以下事件之一：

- `agent.prompt.resolved`
- `agent.prompt.resolve_failed`

事件属性包括 `agent.prompt.name`、`agent.prompt.selector`、`agent.prompt.source`、`agent.prompt.outcome`、`agent.prompt.version` 和可选 `agent.prompt.labels`。Prompt Content、fallback 正文、凭据和 Task 输入均不写入 Span。

Outcome 区分远端获取、缓存命中、严格缓存命中、配置未启用、非法 Selector、远端失败、Version 缺失和 Name 不匹配，便于区分“业务使用 fallback”与“真实使用指定 Langfuse Version”。

### 4. A/B 实际版本输出

Critic A/B 在任何 LLM 调用前严格预解析 Baseline 与 Candidate Prompt。任一 Prompt 无法解析时直接返回退出码 2，不产生 Critic LLM Token 费用。

文本输出增加：

```text
VARIANT baseline selector=configured:label:production prompt=teams/software-reviewed/critic resolved_version=11 labels=production
VARIANT candidate selector=label:latest prompt=teams/software-reviewed/critic resolved_version=12 labels=latest
```

JSON Comparison 使用结构化 `baseline` 和 `candidate` 字段，分别保存请求 Selector、Prompt Name、实际 Version 和响应 Labels；逐案例结果仍不包含 Prompt Content。

### 5. 当前边界

本阶段完成请求级可追溯和评测审计，但尚未把 Label 首次解析出的 Version 持久化到 Task。长时间暂停后恢复的任务仍可能在同一 Label 已移动时解析到新 Version。下一阶段应在任务首次使用时记录角色到 Version 的绑定，并让恢复策略决定严格复用或显式迁移。

新增测试覆盖远端 Version/Labels 缓存、严格 Version 校验、fallback 元数据、Prompt Content JSON 脱敏、Span 属性脱敏和实际 Version、内联 Prompt A/B 拒绝，以及 JSON Comparison 的版本元数据。

## 十五、P2 Task 级 Prompt Version 固定

### 1. Version Pin Registry

新增并发安全的 `promptmanager.VersionPinRegistry`。Pin 仅包含：

- Prompt Name。
- Langfuse 实际返回的正整数 Version。
- 首次请求的 Label 或 Version Selector。
- 有界 Labels 元数据。

Registry 通过 Context 注入，不使用进程全局 Task 状态。相同 Name/Version 重复 Pin 是幂等操作；同一 Prompt Name 出现不同 Version 时立即报错。Labels 在读写时复制，避免共享切片被调用方修改。

### 2. 首次解析与后续固定

带 Task Registry 的 Prompt 解析遵循：

1. 尚无 Pin 时，按 Team 配置的 Label/Version 使用原有解析和 fallback 语义。
2. 远端成功且响应包含有效 Name/Version 后，创建 Version Pin。
3. 同一 Task 后续调用把 Label 请求改写为 `version=<pinned version>`。
4. 固定 Version 使用严格解析；远端不可用、Version 缺失、Version 不匹配或 Name 不匹配时返回阶段错误，不使用本地 fallback。

首次远端解析失败时可以继续使用原有 fallback，但不会建立虚假 Pin。只有实际成功解析的 Langfuse Prompt 才会固定。

### 3. Task Trace 持久化

Coordinator 为每个实际解析成功的 Prompt 追加一次：

```text
action: multiagent_prompt_version
query: <prompt_name>
evidence.path: prompt_version
evidence.lines:
  - version:<actual_version>
  - selector:<original_selector>
  - team_digest:<team_config_digest>
```

Observation 使用版本化 JSON Schema，保存 Team Digest 和 `VersionPin`，不保存 Prompt Content、凭据或用户输入。绑定 Trace 会随现有 Task Store 一起持久化，不需要数据库迁移。

Prompt Binding 是协调器内部审计记录，不会进入 Replanner 的 Execution History，避免 Langfuse Labels 或内部元数据污染规划 Prompt。

### 4. Team 配置迁移语义

Version Pin 按 TeamConfig Digest 分组：

- `require_match` 且 Digest 不变：恢复时加载原 Pin，Label 即使已经移动也继续使用原 Version。
- `require_match` 且 Digest 改变：沿用既有配置漂移阻塞。
- `use_latest` 显式迁移：新 Digest 不加载旧 Pin，新配置首次解析后建立新的 Version Pin。

因此修改 Prompt Name、Label、固定 Version、模型或其他 Team 配置后，不会错误复用旧配置下的 Pin。

### 5. 角色与恢复覆盖

可失败的固定版本解析已接入 Planner、Replanner、Critic、Writer、Verifier Draft 和 Verifier。可选 Critic/Verifier 获取失败时不会运行另一份 fallback Prompt；必需阶段按既有错误语义失败或保留可恢复检查点。

Verifier Draft 的 Pin 在 Draft 检查点之前写入 Trace，因此检查点持久化会原子包含 Draft Prompt Version。Verify 恢复时加载已有 Pin，并对尚未使用的 Verify Prompt 建立独立 Pin。

### 6. 回归验证

新增测试覆盖：

- Registry 并发 Pin 只触发一次持久化回调。
- 同名不同 Version 冲突。
- 首次 Label 解析后续改为 Version 请求。
- 固定 Version 不可用或返回错误 Version 时拒绝 fallback。
- Binding Trace 按 Team Digest 隔离且不进入 Replanner Prompt。
- 两次 Coordinator 运行模拟服务重启：Label 从 v7 移到 v8 后，恢复任务仍请求 `version=7`，且不重复写 Binding Trace。
