# Brain Agentic Memory 对当前项目的适用性分析

日期：2026-08-27  
参考文章：https://www.perplexity.ai/hub/blog/brain-agentic-memory-as-a-knowledge-wiki

## 一、结论

Perplexity Brain 的设计对当前项目有明显参考价值，建议增加 Brain 能力，但不应把它实现为与 `eino`、`step`、`multiagent` 并列的新 Orchestrator 模式。

Brain 更适合作为所有执行模式共享的长期上下文基础设施：在现有 Task、Session、Trace、Memory、Wiki 和 JIT Context 之上，增加跨会话知识整理、可追溯引用、按需探索和后台增量维护能力。

当前项目已经具备约一半以上的基础组件，主要缺口不是向量检索，而是以下三条连接：

1. 将 Task、Trace 和 Memory 组织为可引用的原始证据层。
2. 将现有 Wiki 作为跨会话知识综合层，而不是独立的只读知识源。
3. 增加带 staging、验证、审批和审计的后台增量编译闭环。

推荐推进顺序：

```text
P0 跨会话 Brain Eval
→ P1 只读 Brain + 手工编译
→ P2 Dream Proposal Worker
→ P3 受控自动发布与持续优化
```

## 二、文章核心设计

Brain 不是单纯的向量数据库，而是构建在原始记忆和证据之上的结构化知识 Wiki。

### 2.1 分层记忆

```text
memory/
├── knowledge/   # 综合后的知识 Wiki
├── notes/       # 按主题整理的事实片段
└── sessions/    # 会话索引、摘要和原始记录
```

简单事实可以从 Notes 获取；需要跨会话、跨时间或跨项目综合的问题，则通过 Knowledge 层回答。

### 2.2 两类关系

- `[[wikilink]]` 表示上下文边，用于连接项目、人员、组织和概念。
- `[cite:N]` 表示证据边，用于把知识主张回溯到会话、文件或 Connector 来源。

两类关系分别回答“还需要了解什么”和“为什么相信这个结论”。

### 2.3 渐进式上下文加载

Agent 初始只获得 Brain 的紧凑索引，然后按需搜索页面、跟随 Wiki 链接、检查引用或下钻到原始会话。较大的记忆语料通过 Memory Agent 搜索，并将相关文件按需物化到本地工作集，避免把全部历史塞入 Prompt。

### 2.4 Dream 后台整理

Dream Agent 在后台增量处理新会话：

1. 确定权限范围、规则、删除记录和停止条件。
2. 总结新增或发生变化的会话。
3. 将重要事实挂到正确的实体或主题。
4. 新建、更新或保持知识页面不变。
5. 先写入 staging tree。
6. 执行格式校验和语义一致性校验。
7. 受控同步正式 Wiki，并保留版本历史。

### 2.5 评测结论

文章报告 Brain 对跨会话偏好、时间推理和历史活动细节问题有明显收益，同时降低 Token、成本和延迟。但这些是 Perplexity 的内部结果，不能直接推断当前项目也会获得相同比例的提升。

文章同时表明，Brain 对单会话事实提取的收益有限。其主要价值来自跨会话综合、知识关联和证据回溯，因此本项目应先建立匹配这些场景的评测集。

## 三、当前项目已有基础

| Brain 所需能力 | 当前情况 |
|---|---|
| Durable Memory | 已支持 SQLite、Postgres、Redis 和 Memory 后端 |
| Session/Task 历史 | Session、Task 和 Trace 已持久化 |
| Memory 摘要 | 完成任务可生成 KeyFindings 和 Embedding |
| 按需历史检索 | 已有 `memory_search → memory_get` |
| Wiki 检索 | 已有 `wiki_search → wiki_fetch` |
| Wiki 图遍历 | 已有 `wiki_graph` 和有限深度扩展 |
| 引用完整性 | 已检查回答引用是否来自实际 Fetch 的 Wiki 页面 |
| Wiki 评测 | 已覆盖 Recall、NDCG、MRR、Graph Recall 和引用覆盖 |
| JIT Context | 已按需检索并限制候选数、全文数和上下文字节 |
| Wiki 写入预览 | 已有 dry-run proposal 和冲突 Hash 检查 |

这些能力说明 Brain 不需要从零建设。现有 Memory 可以作为原始 Evidence/Notes 层，Wiki 可以作为 Knowledge 层，JIT Context 可以继续承担前台按需探索。

## 四、主要差距

### 4.1 Memory 仍是扁平任务记录

当前一条 Memory 主要包含 Goal、FinalAnswer、KeyFindings、Timestamp 和 Embedding，缺少：

- 实体和主题归属；
- Claim 级引用；
- 信息有效期；
- Confidence；
- `supersedes` 或冲突关系；
- 来源可信度和更新时间。

因此它适合召回历史任务，不适合直接充当持续维护的知识图谱。

### 4.2 Memory 与 Wiki 尚未形成编译链路

当前 Wiki 主要是外部或本地只读知识源，Memory 来自任务完成后的异步索引，两套系统尚未形成：

```text
Task / Trace / Memory
        ↓
Knowledge Compiler
        ↓
Brain Wiki
```

### 4.3 缺少通用后台 Consolidation Worker

当前后台任务主要服务于任务执行、审批和维护，没有专门负责跨会话知识整理的 Dream Worker。

### 4.4 正式 Wiki Apply 链路尚未实现

现有 Wiki Write Proposal 只负责验证和 Diff 预览，正式 Apply 被刻意留空。Brain 自动维护需要补充审批、幂等、Compare-And-Swap、发布审计和回滚机制。

### 4.5 Session Scope 阻碍跨会话记忆

任务带有 Session ID 时，当前 Memory 查询通常被限制在该 Session。这对会话隔离有利，但无法满足 Brain 的跨 Session 偏好、项目决策和长期知识召回。

Brain 需要独立的长期作用域：

```text
tenant
└── workspace/project
    └── brain space
        ├── sessions
        ├── notes
        └── knowledge
```

Session ID 应继续作为来源和会话内快速召回条件，但不应成为长期知识的最高边界。

## 五、推荐的 Brain 定位

不建议增加：

```yaml
orchestrator:
  mode: brain
```

建议增加正交的上下文能力，例如：

```yaml
brain:
  enabled: false
  foreground_mode: jit
  scope: project
  compact_index_max_bytes: 4000
  compiler:
    enabled: false
    apply_mode: proposal
```

这样可以形成：

```text
eino + brain
step + brain
multiagent + brain
```

Brain 前台能力可优先复用现有 `wiki_search`、`wiki_fetch` 和 `wiki_graph`，将 Brain 表示为一种受管 Wiki Space，避免重复注册一套同类工具。

## 六、分阶段实施建议

### P0：建立跨会话 Eval

覆盖以下场景：

- 用户偏好跨 Session 召回；
- 项目决策、负责人和状态变化；
- 新事实替代旧事实；
- 多个会话共同支持一个结论；
- 相似实体不得串线；
- 删除或撤回的事实不得重新出现；
- Brain 开关前后的准确率、召回率、新鲜度、Token、成本和延迟对照。

### P1：只读 Brain MVP

```text
Completed Tasks + Traces + Memories
              ↓
        Brain Compiler
              ↓
           staging/
              ↓
格式、引用、租户和冲突校验
              ↓
         人工审阅发布
```

前台提供紧凑 Brain Index，并通过现有 Wiki 工具按需探索。第一阶段只生成 Proposal，不允许 LLM 直接修改正式知识。

### P2：Dream Proposal Worker

- 只处理新增或变化的 Session；
- 增量生成页面和链接；
- 执行 deterministic lint；
- 检查 Claim-to-Evidence 覆盖；
- 检查冲突、过期和 Tenant Space；
- 使用 Hash Compare-And-Swap；
- 通过审批或明确策略后发布；
- 保留生命周期审计和版本记录。

### P3：受控自动化

在 Eval 证明收益后再考虑：

- 定时后台运行；
- Connector 新鲜度验证；
- 自动识别被替代事实；
- 热门工作集物化；
- 低风险更新自动发布；
- 基于 Eval 的检索和 Prompt 优化。

## 七、主要风险与约束

- **记忆污染**：错误回答可能被总结并在后续任务中持续强化。
- **持久化 Prompt Injection**：外部内容中的恶意指令可能进入长期知识。
- **陈旧事实**：必须支持时间、来源和替代关系。
- **隐私与删除**：删除 Session 后，其派生 Memory、Notes、Wiki 页面和缓存必须可追踪清理。
- **跨租户泄漏**：Brain Space 必须继续遵守 Tenant 到 Wiki Space 的隔离。
- **后台成本**：Dream 必须受到批次、Token、时间和并发预算约束。
- **自主写入**：必须使用 staging、验证、幂等键、冲突检测和审计，不能直接覆盖正式 Wiki。

## 八、最终建议

Brain 方向适合当前项目，并且比继续单独增强向量召回更有长期价值。但第一阶段不应追求全自动“自我学习”，而应先验证跨会话知识综合是否真正改善准确率、新鲜度、召回和成本。

最合理的目标架构是：

```text
Task / Session / Trace
        ↓
原始证据与历史 Memory
        ↓
后台知识整理（Dream / Compiler）
        ↓
可追溯 Brain Wiki
        ↓
前台 Agent 按需探索
```

Brain 应当成为所有 Agent 执行模式共享的长期上下文层，而不是新的独立执行模式。
