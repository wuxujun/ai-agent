# LLM Wiki 接入可行性分析

日期：2026-08-13

## 结论

当前项目可以接入 LLM Wiki，并且已经具备约 60%～70% 的基础设施。

如果目标只是查询 Wiki，可以基于现有 MCP/RAG 能力进行较小改造；如果目标是完整的 LLM Wiki，包括持续整理、写回、引用、知识图谱和多租户隔离，则建议增加专用 Wiki Adapter，不能只修改一项 MCP 配置就视为完成。

本次分析以 `geronimo-iia/llm-wiki` 为主要参考。该项目是 Git-backed Markdown Wiki，通过 MCP 提供 `wiki_search`、`wiki_content_read/write`、`wiki_ingest`、`wiki_graph` 等工具：

- 项目：https://github.com/geronimo-iia/llm-wiki
- 搜索协议：https://raw.githubusercontent.com/geronimo-iia/llm-wiki/main/docs/specifications/tools/search.md

## 当前项目已有能力

- 外部 RAG 已支持 REST、MCP Streamable HTTP，入口为 `internal/memory/rag_search.go`。
- 已有标准 MCP 初始化、工具发现、调用及会话管理，位于 `internal/mcpclient/client.go`。
- MCP 工具能动态注册到统一 Registry，位于 `internal/tools/mcp.go`。
- 已实现 JIT 两阶段检索：

  ```text
  rag_search → 候选列表 → rag_fetch → 正文证据
  ```

- Planner 已要求事实回答必须由检索证据支持。
- 已具备长期记忆、pgvector/ParadeDB、本地 Embedding、冲突检测、引用审计、多租户和审批机制。
- Skill 系统可承载 `wiki-research`、`wiki-ingest`、`wiki-crystallize` 等工作流。

因此，无需重写编排器，也不需要为此引入 LangChain 或 LlamaIndex。

## 接入方式比较

| 方式 | 可行性 | 适用场景 | 评价 |
|---|---:|---|---|
| 通用 MCP 直接接入 | 高 | 快速验证 Wiki 工具 | 最快，但风险和引用能力不足 |
| 将 Wiki 接成现有 `rag_search` | 中 | 只读问答 | 需要适配请求和响应结构 |
| 专用 Wiki Adapter | 高 | 生产环境、可引用问答 | 推荐方案 |
| 完整 DKR 写回闭环 | 中高 | 自动沉淀长期知识 | 需要审批、冲突和幂等设计 |

## 当前不兼容或不完整之处

### 1. 专用 RAG 请求参数不兼容

当前 RAG MCP 调用固定发送：

```json
{
  "query": "...",
  "top_k": 5,
  "min_score": 0,
  "rewrite": false,
  "include_sources": true,
  "include_chunks": true
}
```

LLM Wiki 的 `wiki_search` 主要接受 `query`、类型过滤、`top_k`、Wiki 空间和输出格式。严格校验时，当前发送的额外字段可能被拒绝。

### 2. Wiki 搜索结果无法完整映射

LLM Wiki 返回的核心字段类似：

```json
{
  "slug": "concepts/mixture-of-experts",
  "uri": "wiki://research/concepts/mixture-of-experts",
  "title": "Mixture of Experts",
  "score": 0.94,
  "confidence": 0.9,
  "excerpt": "...",
  "summary": "..."
}
```

当前 `parseSliceToMemories` 不识别 `slug`、`uri`、`excerpt`、`summary`、`score` 和 `confidence`，会丢失正文摘要和来源定位。

同时，现有 `types.Memory` 主要面向任务记忆，不足以表达 Wiki URI、页面状态、置信度、版本或 Git commit。

### 3. 没有真正读取 Wiki 页面

LLM Wiki 的合理只读流程是：

```text
wiki_search
    ↓ 返回 slug / wiki:// URI
wiki_content_read
    ↓ 返回完整页面与可选 backlinks
Agent 基于页面回答
```

当前 `rag_fetch` 只读取本地候选缓存中的 `KeyFindings` 和 `FinalAnswer`，不会再次调用 `wiki_content_read`。当搜索摘要过短时，Agent 无法获得页面正文。

### 4. 引用信息会丢失

当前外部 RAG 的来源统一为 `third_party_rag`，最终 Evidence 路径是临时候选 ID，例如：

```text
rag-a83...-1
```

理想路径应保留稳定来源：

```text
wiki://research/concepts/mixture-of-experts
```

否则会削弱现有的 Evidence Audit、可信度评分和回答引用能力。

### 5. MCP 风险等级粒度不足

当前风险等级按整个 MCP Server 配置，而不是按远程工具配置。

- 如果配置为 `low`，`wiki_content_write`、`wiki_ingest`、空间管理等写操作可能不经审批。
- 如果配置为 `high`，`wiki_search`、`wiki_content_read` 等只读操作也需要审批。

生产环境应按工具分类：

- 低风险：`wiki_search`、`wiki_content_read`、`wiki_list`、`wiki_graph`、`wiki_history`、`wiki_stats`、`wiki_lint`。
- 高风险：`wiki_content_new`、`wiki_content_write`、`wiki_content_commit`、`wiki_ingest`、Schema 修改和 Space 管理。

### 6. 多租户隔离尚未贯通 Wiki

当前 Task 和内部 Memory 有 `TenantID`，但外部 RAG 使用全局 URL 和全局凭据，查询时也没有传递 Tenant 或 Wiki Space。

生产环境至少需要以下映射：

```text
tenant_id → wiki space
tenant_id → MCP credential
tenant_id → allowed operations
```

否则多个租户可能访问同一个 Wiki。

### 7. 默认编排模式需要适配

当前默认编排模式是 `eino`。在 JIT 事实任务中，普通 Planner 会过滤工具，只保留固定的 `rag_search`、`rag_fetch` 和 Web 等工具；动态注册的 `mcp_llmwiki_wiki_search` 不一定会被展示给 Planner。

因此，仅在 `mcp.servers` 中增加 LLM Wiki 不能保证所有编排模式都会主动使用其工具。

## 推荐架构

只读查询链路：

```text
User Task
   ↓
Planner / Multi-Agent
   ↓
wiki_search（低风险）
   ↓
Wiki Adapter
   ├─ 调用 MCP wiki_search(format=json)
   ├─ 保留 slug、URI、score、confidence
   └─ 返回紧凑候选
   ↓
wiki_fetch（低风险）
   ├─ 调用 wiki_content_read(uri)
   └─ 生成带 wiki:// URI 的 Evidence
   ↓
Writer / Finalizer
   ↓
带 Wiki 页面引用的回答
```

写回链路应独立设置，并强制审批：

```text
任务完成
  → crystallize skill
  → 生成拟写入页面和 diff
  → 人工审批
  → wiki_content_write
  → wiki_ingest(dry_run)
  → wiki_ingest / commit
```

不能将当前任务成功后的 Memory 自动索引直接等同于 Wiki 写回：前者是内部任务记忆，后者是可审计的组织知识。

## 推荐实施顺序

### P0：只读 Wiki Adapter

- 新增 `internal/wiki`。
- 封装 `wiki_search` 和 `wiki_content_read`。
- 增加 `WikiDocument`，保存 URI、slug、score、confidence、status 和正文。
- 最终 `Evidence.Path` 使用 `wiki://...`。
- 配置 Tenant 到 Wiki Space 的映射。

### P1：编排和安全

- 注册稳定工具名 `wiki_search`、`wiki_fetch`，或在内部复用现有 `rag_search`、`rag_fetch`。
- 修改各编排模式的工具过滤规则。
- 支持按远程工具设置风险等级。
- 对 Wiki 正文执行 Prompt Injection 检测和内容大小限制。
- 添加 Wiki 服务 Readiness、延迟、错误率和 Circuit Breaker 指标。

### P2：知识写回

- 增加 `wiki-research`、`wiki-crystallize`、`wiki-ingest` Skill。
- 写入前生成页面 Diff。
- 强制审批、Dry Run 和 Schema Validation。
- 使用 `task_id + target_uri + content_hash` 实现幂等。
- 检测已有页面、内容冲突、过期页面和重复概念。

### P3：图谱能力

- 暴露 `wiki_graph` 和 `wiki_suggest`。
- 用于复杂研究与多跳问题。
- 第一阶段不建议将全部 Wiki MCP 工具暴露给 Planner。

## 快速 POC 配置

如果 LLM Wiki 以 HTTP MCP 方式启动，可先尝试：

```yaml
mcp:
  servers:
    - name: "llmwiki"
      url: "http://127.0.0.1:18765/mcp"
      tool_prefix: "mcp_llmwiki"
      risk_level: "high"
      timeout_seconds: 15
      max_tools: 32
      required: false
      allow_private_network: true
```

LLM Wiki 可通过类似以下命令开启 HTTP 服务：

```bash
llm-wiki serve --http :18765
```

该配置仅适合验证 MCP 协议连接和工具发现。由于当前风险等级按服务器统一设置，POC 阶段建议保持 `high`，不要为了减少搜索审批直接改成 `low`。

## 最终判断

- 只读 Wiki 问答：改造较小。
- URI 引用、正文按需读取、多租户：需要专用 Adapter。
- 自动整理并写回 Wiki：需要新增受审批保护的工作流。
- 不建议直接将全部 Wiki MCP 工具以低风险等级注册。
- 推荐优先完成 P0 只读 Adapter，再逐步增加写回和知识图谱能力。

## P0 实施结果（2026-08-15）

P0 只读 Wiki Adapter 已完成：

- 新增 `internal/wiki`，通过现有 MCP Client 连接 LLM Wiki。
- 启动时发现并校验 `wiki_search`、`wiki_content_read` 的实际 MCP Schema。
- 只发送服务 Schema 支持的参数，避免复用第三方 RAG 的固定扩展参数。
- 新增低风险工具 `wiki_search` 和 `wiki_fetch`，未开放任何写入、摄取、提交、Schema 或空间管理操作。
- 搜索结果保留 `slug`、`wiki:// URI`、`score`、`confidence`、`summary` 和 `excerpt`。
- `wiki_fetch` 按需调用 `wiki_content_read`，最终使用稳定的 `wiki://` URI 作为 `Evidence.Path`。
- 候选缓存按 `tenant_id + task_id` 隔离，并限制候选数量、读取页数和正文总字节数。
- 支持 `api.tenants.<tenant>.wiki_space`，并提供显式的 `wiki.default_space` 共享回退。
- 已接入 Eino/Legacy Planner、Multi-Agent 自动 Search→Fetch 流程和 ADK Registry 工具桥接。
- Wiki 服务为可选时，初始化失败不会阻止启动；配置 `wiki.required: true` 可切换为启动失败策略。
- Wiki 返回内容在工具描述和 Observation 中明确标记为不可信证据，供现有 Prompt Guard/Evidence Pipeline 继续处理。

### 目录型 Wiki 路径兼容修复（2026-08-15）

- 明确 `wiki://<space>/<slug>` 是稳定证据标识，不是可直接访问的网络 URL 或文件路径。
- `wiki_content_read` 的 Schema 同时提供 `slug/path` 与 `uri` 时，读取优先使用目录相对的 `slug/path`。
- 搜索结果缺少 `slug` 时，可从 `wiki://<space>/<slug>` 推导目录相对路径。
- Evidence 仍保留原始 `wiki://` URI，避免目录位置变化导致引用身份漂移。
- 已增加 `concepts/...`、`comparisons/...` 目录形态的单元测试，并将 MCP HTTP 端到端测试调整为 Path 读取。

### 本地目录 Reader（2026-08-15）

- 增加 `wiki.directory` / `AI_AGENT_WIKI_DIRECTORY`，与 `wiki.url` 互斥。
- 目录可以指向包含 `AGENTS.md`、`raw/`、`wiki/` 的 llm-wiki 根目录，也可以直接指向 `wiki/`。
- 递归只读检索 `wiki/` 下的 Markdown，支持 `comparisons/`、`concepts/`、`entities/`、`sources/` 及顶层索引文件。
- 页面读取经过真实路径与符号链接边界校验，拒绝 `../` 等目录越界；不注册任何写操作。
- 本地文件路径不进入 Evidence，引用仍统一为 `wiki://<space>/<slug>`。
- JIT Planner 的启用判断同时识别 `wiki.url` 与 `wiki.directory`，确保目录 Reader 注册后会优先选择 `wiki_search`。

示例：

```yaml
wiki:
  url: ""
  directory: "/path/to/llm-wiki"
  default_space: "local"
  required: true
```

### Wiki 专用 Multi-Agent Team（2026-08-15）

- `teams.yaml` 与 `teams_zh.yml` 新增 `wiki` team。
- Planner 通过 `tools: ["wiki_search"]` 限定动作白名单，结构化输出 Schema 仅暴露 `wiki_search`。
- Wiki team 允许单步骤搜索计划；候选正文仍由 Coordinator 自动执行内部 `wiki_fetch`，不开放给 Planner 选择。
- Writer 仅基于 Wiki Evidence 合成答案，并统一生成数字引用和文末参考资料。
- 通过 `AI_AGENT_MULTIAGENT_TEAM=wiki` 启用。
- `wiki_search.top_k` 可省略；Multi-Agent Step 未显式提供时使用 `wiki.search_top_k`，避免 Wiki-only Planner 因参数模型不含 `top_k` 而重复失败。
- Multi-Agent 核心日志统一增加 `team` 字段，覆盖外层编排、规划、重规划、检索、写作和验证阶段；Team 名称取自任务级配置快照，支持并发任务隔离。

## P1 实施结果（2026-08-16）

本地目录 Wiki 搜索完成第一阶段质量与性能增强：

- 启动时构建 Markdown 内存索引，缓存 slug、标题、标题层级、摘要和规范化正文。
- 查询时只扫描文件元数据；文件路径、大小或修改时间变化时自动重建内容索引，无需重启服务。
- 搜索评分区分标题、slug、Markdown 标题和正文，标题及 slug 命中权重更高。
- 完整短语命中额外加权，多查询词全部覆盖时增加组合分，正文重复词频设置上限以避免关键词堆积压过标题页面。
- 规范化过程基于 Unicode 字母和数字，支持中英文混合查询，例如 `PBL 历史旅行指南`。
- 缓存采用读写锁和双重检查，并发查询在索引未变化时共享缓存，重建过程保持 Race 安全。
- 摘要截断改为按 Unicode Rune 截断，避免截断中文 UTF-8 字符。

新增测试覆盖中文标题/短语排序、文件修改后自动刷新及并发搜索。

P1 第二阶段增加 Wiki 关系召回：

- 索引提取页面中的相对 Markdown 链接，并将链接目标规范化为 Wiki slug。
- 直接命中的主题页可对其一跳关联页面施加有限加权，用于补充来源、实体、概念和对比页。
- 关系加权限制为一跳并设置得分上限，关联页面不能压过直接标题命中。
- `index.md`、`_index.md` 和 `log.md` 作为导航/运行页面统一降权，避免宽泛关键词查询被目录页占据。
- 增加主题页关联导师与课程来源的回归测试。

P1 第三阶段补齐 LLM Wiki frontmatter 兼容：

- 支持从 YAML frontmatter 读取 `title`、`summary`、`tags` 和 `aliases`。
- 标题和摘要进入搜索结果，标签、别名与摘要进入独立的元数据评分字段。
- frontmatter 标题优先于 Markdown 一级标题，便于重命名页面而不改变 slug。
- 英文别名可召回中文标题页面，适配中英文混合知识库。
- frontmatter 缺失、未闭合或 YAML 格式损坏时安全回退为普通 Markdown，不阻断整个索引。

P1 第四阶段增加紧凑短语匹配：

- 查询与索引同时生成忽略空格和标点的紧凑文本，兼容 `PBL历史旅行指南`、`PBL-历史旅行指南`、`PBL：历史旅行指南` 等写法。
- 紧凑匹配权重低于标准规范化短语匹配，避免宽松匹配取代精确匹配。
- 标题、slug、frontmatter 元数据和正文的紧凑形式在建索引时预计算，查询阶段不重复进行 Unicode 规范化。

P1 第五阶段增加查询相关摘要：

- 建索引时为每页保留有界的 Markdown 文本片段及其规范化/紧凑形式。
- 搜索结果根据完整短语、紧凑短语和查询词覆盖选择最相关原文片段作为 `excerpt`。
- 正文深处命中时不再固定返回页面开头，提升候选可解释性和 Writer 选择正文的准确性。
- 每页最多缓存 256 个片段、每片段最多 500 个 Unicode 字符，限制额外内存使用。
- 仅通过页面关系进入候选且自身没有关键词命中的页面继续使用默认摘要。

P1 第六阶段加固目录读取边界：

- `DirectoryClient.Read` 只允许读取 `.md` 文件，拒绝伪造候选访问 Wiki 根目录内的 JSON、配置或其他非 Markdown 文件。
- 索引和正文读取统一使用受限流式读取，每页上限 2 MiB；在内存分配前通过 `LimitReader` 截止，不再先完整读取再截断。
- 读取目标必须是普通文件，并继续经过既有真实路径与符号链接边界校验。
- 增加非 Markdown 文件和超大 Markdown 页面拒绝测试。

P1 第七阶段增加 Wiki 后端可观测性与熔断保护：

- `wiki_search` 与 `wiki_fetch` 的实际后端调用记录调用次数、错误次数和延迟直方图，并按 `search` / `read` 操作区分。
- 增加熔断开启次数与拒绝次数指标；参数校验、租户空间缺失等本地错误不计入后端失败。
- 搜索和读取共享同一个 Wiki 后端熔断状态，连续失败达到阈值后快速失败，冷却结束后仅允许一个半开探针。
- 新增 `wiki.circuit_breaker_failure_threshold`（默认 3）和 `wiki.circuit_breaker_cooldown_seconds`（默认 30）；任一配置为 0 时禁用熔断。
- 熔断配置在每次调用时通过 `config.Get()` 读取，支持现有配置热加载语义。

P1 第八阶段将 Wiki 纳入 readiness：
