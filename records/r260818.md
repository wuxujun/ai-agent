## 二、Wiki 接入与问题修复

### 2.1 初始项目分析

项目是 Go 1.25 服务，入口为 `cmd/server/main.go`，核心代码位于 `internal/`，已有工具注册、策略、编排、多代理、存储、指标与配置热更新能力，适合通过注册只读工具和专用 Team 接入 Wiki。

Wiki 目录结构确认如下：

```text
AGENTS.md
raw/
wiki/
  comparisons/
  concepts/
  entities/
  sources/
  index.md
  log.md
```

`.env` 使用 `AI_AGENT_WIKI_DIRECTORY` 指向包含 `wiki/` 的知识库目录。服务本地端口最终使用 8088 进行真实验收。

### 2.2 `wiki://` 访问语义

发现不能通过浏览器或普通 URL 客户端直接访问 `wiki://...`，但可读取目录。这不是目录读取失败，而是 URI 语义不同：

- `wiki://local/concepts/...` 用作稳定证据引用和来源标识。
- 页面定位由 `wiki_search` 完成。
- 页面正文由 `wiki_fetch` 完成。
- API 最终回答可包含 `wiki://` 引用，但不能假设用户点击后由浏览器直接打开。

### 2.3 Wiki Space 配置问题

真实日志曾出现：

```text
tenant "6492" has no api.tenants.6492.wiki_space and wiki.default_space is empty
```

由此补齐了 Wiki Space 解析、租户配置检查与错误信息。Wiki 工具调用必须取得租户 Space 或默认 Space，不允许静默跨租户检索。

### 2.4 Wiki Team 与提示词

会话澄清运行环境为：

```text
AI_AGENT_MULTIAGENT_TEAM=software
```

而不是 `kb_qa`。随后完成：

- 同步检查 `teams.yaml` 与 `teams_zh.yml`。
- 为 `kb_qa.writer` 补充 Wiki 回答要求。
- 新增只允许 `wiki_search` 的 `wiki` Team，后续扩展为严格只读检索链。
- 修复服务重启后查询“PBL 历史旅行指南”未使用 `wiki_search` 的路由问题。
- Multi-Agent 日志增加当前 Team 名称，便于确认实际路由。

### 2.5 Wiki 回答排版

Wiki Search 返回内容本身是证据，最终中文回答的标题、列表、引用形式由 Team Writer 的 `system_prompt` 控制，主要修改位置为 `teams.yaml` 对应 Team 的 writer 配置；中文镜像同步维护在 `teams_zh.yml`。

最终 Wiki Writer 约束包括：

- 基于 Wiki 证据回答，不输出无证据扩展。
- 使用清晰 Markdown 标题与列表。
- 保留可追溯的 `wiki://` 来源。
- 不使用“根据知识库中的 Wiki 页面”等机械化开场。
- Wiki Suggest Writer 只能使用过滤后的 Suggest 证据，不能根据搜索或全文自行扩展建议。

## 五、Team 生命周期 P7

### 5.1 生命周期语义

支持：

- `active`：允许新任务和存量任务恢复。
- `draining`：拒绝新任务，但允许已锁定任务恢复。
- `retired`：拒绝新任务，并将存量恢复任务转为 partial，增加 `team_retired` 未解决原因。

进程默认与租户默认 Team 必须为 active。生命周期只控制准入与恢复，不进入执行摘要，因此 active/draining/retired 切换不产生配置摘要漂移。

### 5.2 API 与指标

- `/api/teams` 每项返回 `lifecycle`、`selectable`。
- draining/retired 新任务返回 HTTP 409。
- 未知 Team 仍返回 400，白名单越权返回 403。
- 指标区分 draining 与 retired，同时计入总拒绝和来源拒绝。
- Prometheus 对仍向 draining/retired Team 发送新任务进行告警。

### 5.3 真实故障注入

曾临时将非默认 `data` Team 切换为 draining 和 retired，分别确认：

- 列表显示不可选。
- 创建返回 409。
- 指标精确增加 1。
- 被拒绝任务未持久化，查询返回 404。
- 演练后均恢复 active/selectable=true。

当前 `teams.yaml` 与 `teams_zh.yml` 中所有 Team 均为 active。

## 六、生命周期管理 API P8

### 6.1 管理接口与 CAS

`GET /api/teams` 增加 `config_revision`，基于 `teams.yaml` 原始字节摘要。

新增管理员接口：

```http
PATCH /api/teams/:name/lifecycle
```

请求包含：

```json
{
  "lifecycle": "draining",
  "expected_revision": "..."
}
```

行为：

- 非管理员：403。
- 过期 revision：409。
- 未知 Team：404。
- 默认 Team 改为非 active：422。
- no-op：200、`changed=false`，不写文件。

写入在进程内串行化，拒绝非普通文件，仅替换 lifecycle 单行，保留注释、引号、其他配置字节和文件权限；采用同目录临时文件、fsync 和 rename 原子替换。

### 6.2 在线验收

真实 active→draining→active 验收确认：

- CAS revision 正确变化和恢复。
- 恢复后 revision 精确回到演练前值，证明无关字节未改变。
- 旧 revision 返回 409。
- 默认 `wiki_suggest` 保护返回 422。
- no-op 不改变 revision。

### 6.3 指标与结构化审计

增加生命周期变更、CAS 冲突和默认 Team 保护指标及 OTel 事件；结构化日志记录操作者租户、Team、前后生命周期、前后 revision 和 changed。

## 七、生命周期持久化审计 P8/P9

### 7.1 JSONL 审计

成功与 no-op 生命周期请求追加到：

```text
data/team-lifecycle-audit.jsonl
```

可由 `AI_AGENT_TEAM_LIFECYCLE_AUDIT_FILE` 覆盖。记录包含：

- UUID
- UTC 时间
- 操作者租户
- Team
- 前后 lifecycle
- 前后 revision
- changed

目录以 0700 创建，文件以 0600 创建，每条 append 后 fsync。拒绝符号链接、目录等非普通路径。

管理员查询接口：

```http
GET /api/teams/lifecycle-audits?limit=50&offset=0
```

支持 `team` 精确过滤和 `changed=true|false`，过滤先于分页；非法 changed 返回 400。

### 7.2 跨重启验收

最初生成两条 no-op 审计：

- `5387b836-eb89-44d6-a33d-b723ae7e51f9`
- `ac0cd6b1-cc72-4187-b120-de250848f4a5`

跨重启后 UUID、顺序、内容、文件权限和分页结果均保持不变。

### 7.3 SHA-256 哈希链

新记录增加 `previous_hash` 与 `hash`。追加前验证已有受保护链，篡改后拒绝继续追加。上线前记录保持原样并计为 legacy。

```http

```

健康返回 200；非法 JSON、记录篡改或链断裂返回 409。响应提供记录数、protected/legacy 数量、文件大小和容量状态，不泄露正文。

### 7.4 容量治理

默认硬上限为 64 MiB，可由以下环境变量覆盖：

```text
AI_AGENT_TEAM_LIFECYCLE_AUDIT_MAX_BYTES
```

完整性响应增加：

- `max_bytes`
- `usage_percent`
- `capacity_status`：ok、warning、full

达到 80% 为 warning；预计追加超过上限时返回 HTTP 507，且不截断、覆盖或删除原审计。

### 7.5 显式非破坏归档

管理员归档接口：

```http
POST /api/teams/lifecycle-audits/archive
```

提交完整性响应中的 `expected_file_digest`。行为：

- 使用摘要进行 CAS。
- 当前 JSONL 原子移动到 `<audit>.archives/`。
- 创建新的 0600 当前文件。
- 创建失败时 rename 回滚。
- 归档文件名包含纳秒 UTC 时间和文件摘要。
- 拒绝符号链接归档目录。
- 不自动归档，不提供删除操作。

普通审计查询会合并当前文件与所有归档记录，按时间倒序统一过滤和分页。

真实归档演练结果：

- 原 4 条记录移动至一个 0600 归档，大小 1298 bytes。
- 新当前文件初始为 0 bytes/0600。
- 合并查询仍返回原 4 条历史。
- 新当前文件追加记录 `e1a55a3a-bc71-443a-8f3a-c9476bce9c16`。
- 新链 hash：`563d6d91b8e814d8e9bcc725b8b75ca90eb0c0407daefe10273d1a0ebd1a63cb`。
- 最终总记录 5、legacy=2、protected=3、归档 1 个/4 条、当前文件 341 bytes、整体 healthy=true。
- 上述状态跨重启保持有效。

## 十三、Wiki 功能专项分析与后续路线

### 13.1 当前能力边界

当前 Wiki 子系统定位为“租户隔离、证据可追溯、默认只读”的知识检索组件，主要分为四层：

| 层级 | 已有能力 | 当前边界 |
| --- | --- | --- |
| 数据源 | 本地目录、远程 Streamable HTTP MCP | 两种来源互斥；配置变更需要重启 |
| 检索 | `wiki_search`，标题、摘要、标签、别名、标题层级、正文分块和一跳链接加权 | 本地实现为确定性词法评分，尚无语义向量或混合检索 |
| 内容与关系 | 自动 `wiki_fetch`、`wiki_graph`、`wiki_suggest` | Graph 深度限制为 1–2；每任务 Graph/Suggest 最多调用一次 |
| 回答 | `wiki`、`wiki_graph`、`wiki_suggest` 和 `kb_qa` Writer，输出 `wiki://` 引用 | `wiki://` 仅为证据 URI，尚无 HTTP 跳转或页面查看接口 |

核心实现位置：

- `internal/wiki/client.go`：远程 MCP 适配、Schema 发现和参数映射。
- `internal/wiki/directory.go`：本地 Markdown 索引、搜索、读取、图关系和策展候选。
- `internal/wiki/graph.go`、`internal/wiki/suggest.go`：图谱和建议结果校验、归一化及数量上限。
- `internal/tools/wiki.go`：稳定工具名、租户 Space、候选缓存、读取预算及每任务调用约束。
- `internal/tools/wiki_resilience.go`：延迟、错误、熔断和 readiness 指标。
- `cmd/wiki-eval`：离线数据集评测与质量门禁。
- `teams.yaml`、`teams_zh.yml`：Wiki Team 的 Planner/Writer 行为约束。

### 13.2 已实现的安全与可靠性措施

- 本地目录既可指向包含 `AGENTS.md/raw/wiki` 的仓库根，也可直接指向 `wiki/`；初始化时统一解析真实路径。
- 目录读取仅接受 Markdown 页面，限制单页大小，并防止路径穿越和符号链接逃逸。
- 远程 MCP 启动时发现并校验必需的 `wiki_search`、`wiki_content_read`，Graph/Suggest 仅在后端确实支持时注册。
- 工具层只暴露稳定的低风险只读边界，未注册 ingest、commit、schema、space 管理或实际写入工具。
- 每次调用从当前租户解析 `wiki_space`，无租户 Space 且无默认 Space 时明确失败，避免静默跨空间访问。
- 搜索结果先生成任务级候选 ID，读取只能使用同任务搜索得到的 ID，降低任意 URI 读取风险。
- `fetch_max_items`、`fetch_max_bytes`、Graph 节点/边数量和 Suggest 数量均有边界。
- Wiki 内容被标记为不可信证据，Writer 只能依据过滤后的证据回答；`wiki_suggest` Writer 与搜索/全文证据隔离。
- Wiki 后端具有超时、共享熔断、半开探针、required/optional readiness 和 OTel/本地指标。
- `cmd/wiki-eval` 可检查召回、噪声、引用和性能门槛；关键流程已有单元、集成、HTTP 和真实 8088 验收。

### 13.3 当前不足与待优化项

#### P0：近期应优先处理

1. **消除配置与文档漂移**  
   `config.yaml` 注释仍写明 suggestion 不注册，但代码已按能力注册 `wiki_suggest`；应同步修正 `config.yaml`、中文镜像、README 和示例，确保运行行为与说明一致。还应检查 `teams.yaml` 与 `teams_zh.yml` 的 `active_team` 是否有意不同，避免将中文镜像误当作可直接替换的等价运行配置。

2. **补充可点击的 Wiki 页面访问能力**  
   当前答案中的 `wiki://` 适合机器追踪，但用户无法通过浏览器直接访问。建议增加只读解析接口，例如 `GET /api/wiki/pages/:space/*slug`，将 URI 映射为经过租户授权和路径校验的 Markdown/HTML；也可在回答中同时给出 `wiki://` 证据 URI 与受控 HTTP 链接。接口不得接受未经鉴权的任意文件路径。

3. **完善检索可解释性和零结果诊断**  
   搜索响应应可选返回命中字段、基础分、链接加权、最终排序原因及索引版本；日志和指标应区分零结果、Space 缺失、索引失败、读取失败和预算截断。这样可以直接诊断“为什么没有调用 Wiki”与“调用后为什么没找到”。

4. **强化索引刷新一致性**  
   当前本地索引按 Markdown inventory 变化刷新。后续应验证内容原地修改、原子替换、时间戳精度和大目录场景，增加内容摘要或增量索引策略，并公开索引页数、最后刷新时间、刷新耗时和刷新失败状态。

5. **扩大真实查询回归集**  
   将“PBL 历史旅行指南”等已验证问题纳入固定 Canary，覆盖中英文混合、别名、缩写、标题变体、无答案、近似重复、跨页面关系和错误 Space。质量门禁应按数据集版本记录结果，避免单一查询通过即代表整体有效。

#### P1：质量与运维优化

1. **混合检索与可插拔排序**  
   在保留确定性词法检索的基础上，可增加可选 BM25、向量召回和轻量 reranker，采用词法与语义分数融合。必须维持租户 Space 隔离、离线可测和无向量服务时的降级路径。

2. **查询改写与多查询召回**  
   对中英文名称、别名和年代等查询生成有界改写，但需限制次数、去重，并在 Trace 中保留原始查询与改写来源，避免恢复早期重复搜索和预算耗尽问题。

3. **缓存生命周期治理**  
   当前候选缓存按任务保留并在访问时清理 30 分钟前的项。可增加任务完成时主动释放、容量上限、缓存项指标和高并发压力测试，避免长时间低流量进程中旧任务缓存滞留。

4. **细化后端隔离与熔断**  
   搜索和读取目前共享熔断器。可评估按 Space、后端和操作拆分，避免某个租户或慢读取拖累全部搜索；同时增加熔断当前状态、最近失败原因和恢复时间的安全运维视图。

5. **引用与回答质量校验**  
   在 Writer 输出后增加 URI 存在性、引用覆盖率、引用与结论对应关系检查；对无证据结论执行删除或降级说明，而不是仅依赖 Prompt 约束。

6. **可观测性完善**  
   增加按 Team、operation、backend 类型和结果状态聚合的低基数指标，持续跟踪 search→fetch 转化率、零结果率、截断率、缓存命中、Graph/Suggest 使用率和 Eval 趋势。

#### P2：能力扩展

1. **Wiki 浏览与导航 API/UI**  
   提供目录、页面、反向链接和关系图的只读浏览入口，使 `wiki://` 引用可落地查看，并支持从回答跳转到原始证据。渲染 Markdown 时必须过滤危险 HTML 和外链协议。

2. **增量变更与历史能力**  
   增加只读 history/diff 接口，回答可引用页面版本或 Git commit，避免知识变化后旧回答无法复现。Evidence 建议补充内容摘要、版本和读取时间。

3. **策展工作台**  
   将 `wiki_suggest` 结果持久化为待审核队列，支持接受、拒绝、备注、去重和审计；此阶段仍不自动修改 Wiki。建议结果应绑定根页面版本，页面变化后标记为过期并重新评估。

4. **多知识库和 Space 目录**  
   在明确授权模型后支持一个租户访问多个 Space，并允许请求选择 Space。必须使用服务端白名单，不能让用户通过自由字符串绕过租户边界。

5. **异步索引与大规模 Wiki**  
   对较大目录引入后台增量索引、快照切换和有界内存查询；保留旧快照直到新快照完整可用，索引失败不得影响当前可用版本。

### 13.4 Wiki 回写的现状与恢复条件

代码中已有 `internal/wiki/writeback.go`，它只实现无副作用的写入提案预览：

- 校验 `wiki://<space>/<kind>/<slug>` 目标。
- 仅允许 comparisons、concepts、entities、sources 四类页面。
- 校验 Markdown 标题/frontmatter、内容上限和安全路径。
- 计算现有内容与新内容 SHA-256、乐观并发冲突、幂等键和有界 diff。
- 区分 create、update、noop。

该代码当前没有注册为工具或 API，也不会读取或写入文件/MCP；实际 apply、审批、持久化审计、失败补偿和回滚仍未实现。因此它只能视为未来回写流程的纯函数基础，不能表述为“已支持 Wiki 回写”。

恢复回写开发前至少需要明确：

1. 回写仅支持本地 Git Wiki、远程 MCP，还是两者都支持。
2. 谁可以发起提案、谁可以审批，是否禁止同一主体自批。
3. create/update 的版本 CAS、幂等和跨重启状态保存方式。
4. 写入后的 lint、引用检查、测试、Git commit/PR 和回滚策略。
5. 审计记录、敏感信息脱敏、失败重试和人工处置流程。
6. 是否先上线“提案与人工审核”，继续禁止自动 apply；建议采用这一阶段化方案。

### 13.5 推荐实施顺序

建议后续按以下顺序推进，且 Wiki 回写继续独立暂缓：

1. 修正文档与配置注释漂移，并确认中英文 Team 配置同步规则。
2. 增加受鉴权的只读页面解析/访问接口，解决 `wiki://` 不可直接打开的问题。
3. 增加检索解释、索引状态和零结果指标，扩充固定 Eval/Canary 数据集。
4. 优化任务缓存释放、索引刷新一致性及大目录性能。
5. 在基线指标稳定后试验混合检索与 reranker，通过离线门禁再启用。
6. 增加历史版本、策展审核队列和多 Space 能力。
7. 仅在审批、CAS、审计、回滚方案评审完成后恢复 Wiki 回写，实现顺序为 proposal → review → approved apply，默认始终禁止自动写入。

### 13.6 建议验收标准

- `wiki://` 引用均能通过受控只读接口解析，越权 Space、路径穿越和非 Markdown 请求被拒绝。
- 固定 Eval 集的召回、噪声、引用覆盖率和 P95 达到配置门槛，结果可按数据集与索引版本复现。
- 服务重启、Wiki 内容变更、远程后端超时和熔断恢复均有自动化与真实环境测试。
- Multi-Agent Trace 明确记录 Team、原始查询、Wiki 工具链、Space 和证据 URI，不记录 Wiki 正文或密钥到高基数指标。
- 无答案时明确说明证据不足，不由 Writer 使用常识补齐内部事实。
- Graph/Suggest 输出经过 URI、Space、数量和证据隔离校验，不产生任何写动作。
- 回写功能恢复前，工具注册表和 Planner Schema 中不存在任何 Wiki apply/write/ingest/commit 操作。
