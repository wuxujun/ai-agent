### 2.1 ParadeDB / PostgreSQL

- `database "ai_agent" does not exist` 通过在 ParadeDB 中创建 `ai_agent` 数据库解决。
- UTF-8 `0xc2 0x0a` 持久化错误已通过执行/证据文本 UTF-8 规整链路处理。

## 四、Adaptive、审批和 execute_code 修复

### 4.1 Adaptive 路由与审批

真实任务验证：

- 初始 Research 路由正常；
- 失败重规划引入 High Risk `execute_code` 后正确升级 Reviewed；
- 高风险动作进入 `awaiting_approval`，未绕过审批；
- durable approval 可持久化、批准、消费并恢复；
- 重复 `run-all` 会返回 already running，防重入有效。

### 4.2 execute_code argv

旧实现使用 `strings.Fields`，会把：

```text
python3 -c "import json; ..."
```

错误拆分，产生 Python `SyntaxError`。

现改为不经过 shell 的引号感知 argv 解析，支持：

- 单引号、双引号；
- 转义字符；
- 空参数；
- 未闭合引号和尾随转义校验。

真实 Canary 已确认 Python 收到完整 `-c` 程序。

### 4.3 execute_code workspace 路径

Planner 可能在 cwd 已是 `./workspace` 时生成：

```text
open('./workspace/p2-json-query-fixture.json')
```

导致重复 workspace。现已将 execute_code 相对参数中的 task workspace 前缀归一化，并同步更新审批与执行共享的 `RepairedParameters`；绝对 workspace 路径不变。

真实审批预览和执行已确认命令变为：

```text
open('p2-json-query-fixture.json')
```

### 4.4 恢复段证据继承

Multi-Agent 新执行段会从既有 Researcher/Executor 工具 Trace 重建 `StepEvidence`，避免审批或中断前已读取的证据在 Writer/Verifier 阶段丢失。

真实 Canary 中，审批前的 fixture 内容被后续 Verifier 正常使用。

## 五、审批等待与执行超时分离

旧行为：`run_all_timeout_seconds=600` 包含人工审批等待，长时间审批后恢复可能立即 `context deadline exceeded`。

修复：

- 新增可暂停 execution timeout context；
- 活跃执行时消耗预算；
- `awaiting_approval` 期间冻结剩余预算；
- 批准/拒绝后从剩余额度恢复；
- 显式 cancel、父 context 取消和 graceful shutdown 在暂停期间仍立即生效。

真实 Canary 的审批等待超过 600 秒后仍成功恢复，最终完成，证明暂停计时生效。

最终任务经历两次审批：

1. 首次 Python 脚本错误读取顶层 modes，输出 0；
2. Verifier 拒绝冲突草稿，Adaptive 重规划为 `data['project']['modes']`；
3. 第二次审批后输出 project name `ai-agent`、modes `5`；
4. 最终 completed，Verifier supported/high。
