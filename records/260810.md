## 三、PostgreSQL 与 ParadeDB 选择分析

ParadeDB 不是完全独立于 PostgreSQL 的另一种协议，而是以 PostgreSQL 为基础并提供 `pg_search` BM25 搜索能力。因此：

- 标准 PostgreSQL + pgvector 更适合当前事务、任务状态、Session、租约和向量记忆存储。
- 当需要 BM25、专有名词/错误码精确召回、全文搜索和向量混合排序时，ParadeDB 更有价值。
- 仅将 DSN 指向 ParadeDB，而不创建 BM25 索引和调用 `pg_search` SQL，不会自动获得 ParadeDB 搜索收益。
- ParadeDB Community 的 BM25 索引恢复、物理复制和 PITR 能力需要谨慎评估；生产关键搜索建议评估 Enterprise/BYOC。

## 五、ParadeDB 混合检索实现

### 5.1 配置

新增/启用：

```bash
AI_AGENT_STORE_TYPE=postgres
AI_AGENT_STORE_VECTOR_SEARCH=paradedb
AI_AGENT_STORE_PGVECTOR_DIMENSIONS=1536
```

`store.vector_search` 现在支持：

- `in_process`：读取候选后在 Go 中排序
- `pgvector`：使用 PostgreSQL/pgvector 余弦距离
- `paradedb`：融合 ParadeDB BM25 与 pgvector 排名

### 5.2 实现内容

- 显式 `paradedb` 模式下自动检查/启用 `pg_search`。
- 为 `memories` 创建 covering BM25 索引，覆盖：
  - `id`
  - `tenant_id`
  - `session_id`
  - `goal`
  - `final_answer`
  - `key_findings`
  - `timestamp`
- 使用 `goal ||| query`、`final_answer ||| query`、`key_findings ||| query` 做 BM25 候选检索。
- 使用 `paradedb.score(id)` 排序 BM25 结果。
- 分别获取 BM25 和 pgvector 候选，再使用 Reciprocal Rank Fusion（RRF）融合名次，避免直接混合不可比的 BM25 分数和余弦分数。
- 融合后继续应用已有的记忆时间衰减。
- BM25 或 pgvector 任一路径失败时使用剩余路径；全部失败时回退到原有进程内排序。
- 保留租户和 Session 过滤。

### 5.3 验证

- 在事务内验证 `pg_search 0.20.7` 的 `bm25`、`|||`、`@@@` 和 `paradedb.score` 语法后回滚探测索引。
- 新增真实 ParadeDB 混合排序集成测试。
- 测试使用三个随机 ID 的 Memory 验证“BM25 与向量均匹配”的结果排在首位。
- 修复了集成测试清理顺序，确保 Store 关闭前逐条删除测试 Memory。
- 曾遗留的三条集成测试 Memory 已按明确 ID 逐条删除，最终残留数为 0。

## 六、PostgreSQL UTF-8 错误分析与修复

### 6.1 故障

任务 `3288ca7b-933a-4e70-9909-7138e8cba04a` 执行时出现：

```text
failed to persist run-all progress
pq: invalid byte sequence for encoding "UTF8": 0xc2 0x0a (22021)
```

数据库中该任务最后状态为：

```text
status=running
step_count=0
trace rows=0
task lease rows=0
```

因此失败发生在第一条 Trace 保存前；任务没有活动租约，修复并重启后可以直接重新调用 `run-all`。

### 6.2 根因

`internal/tools/middleware.go` 原逻辑：

```go
result.Observation = result.Observation[:4000] + "\n...[truncated by middleware]"
```

该逻辑按字节切片。如果第 4000 字节是 UTF-8 多字节字符的首字节（本次为 `0xC2`），切片会丢失后续字节，然后直接追加以 `0x0A` 开头的换行，形成 PostgreSQL 拒绝的非法序列 `0xC2 0x0A`。

### 6.3 修复

源头修复：

- 工具 Observation 先通过 `strings.ToValidUTF8` 规范化。
- 超过 4000 字节时向前寻找合法 UTF-8 边界，再追加截断标记。

持久化防线：

- PostgreSQL Store 新增 `postgresText`。
- 对 Task、Trace、Memory 的直接文本列写入前统一执行 UTF-8 验证。
- 非法字节使用 Unicode replacement character `U+FFFD` 替换。
- JSON 字段继续由 `encoding/json` 负责有效 UTF-8 编码。

### 6.4 回归验证

新增测试覆盖：

- 3999 个 ASCII 字节后追加 `¢`，确保第 4000 字节恰好是 `0xC2`，验证截断结果仍为合法 UTF-8。
- 直接输入 `before\xC2\nafter`，验证工具边界和 PostgreSQL 边界均转换为 `before�\nafter`。
- 在真实 ParadeDB 中保存含非法 UTF-8 的 Task Trace，确认写入成功且读回内容正确。
- 测试任务按唯一 ID 清理，数据库残留数为 0。

## 十、P1 检索调优配置

ParadeDB 混合检索的两个关键参数已从硬编码改为可热更新配置：

- `store.paradedb_candidate_multiplier`：BM25 和 pgvector 每个分支的候选倍率，默认 `4`。
- `store.paradedb_rrf_k`：Reciprocal Rank Fusion 平滑常数，默认 `60`。
- `store.paradedb_slow_query_threshold_ms`：单个检索阶段的慢查询阈值，默认 `250ms`，`0` 表示关闭慢阶段计数。

两者设为 `0` 时使用默认值，负数会被配置校验拒绝。实际生效值写入
OpenTelemetry Query Trace；BM25、pgvector 和 RRF 融合均有独立子 Span，并记录候选上限、
实际候选数、结果数和错误，便于按召回质量和延迟进行对照调优。

`/api/metrics` 已增加检索调用、失败、降级、慢阶段、候选/结果总数、总耗时，以及
BM25、pgvector、RRF 各自的调用数。

后续又补齐了三个阶段各自的失败数、条目总数和耗时总和，可通过“总耗时 / 调用数”
直接对比平均耗时。RRF 纯计算基准已覆盖每分支 `20/100/400` 个候选和 `K=30/60/90`。
本机 100ms 基准中，20 个候选约 `6.2–6.5µs/op`，100 个约 `30.8–33.7µs/op`，400 个约
`131–135µs/op`。K 值对计算成本影响很小，候选数是主要成本因素；召回质量仍需在真实
ParadeDB 数据上评估。

服务端返回的平均毫秒与原始 Duration 纳秒值换算完全一致，零调用时安全返回 `0`。
尝试将慢查询阈值临时改为 `1ms` 后再调用 Reload API，API 返回 `no_changes: true`。
日志证实这不是环境变量覆盖：文件 watcher 已抢先将 `250 → 1` 自动应用，手动 API 执行时
配置已是最新值，因此无二次变化。恢复文件后 watcher 也已成功应用 `1 → 250`。
当前有效阈值与两份样例配置均为 `250ms`。

为解决 watcher 与手动 Reload API 存在竞态时的运维判断问题，配置模块新增了进程内
单调递增的 revision。`POST /api/config/reload` 现在返回 `config_revision`；即使本次手动调用

“重载次数”。现已改为只有配置内容实际变化时才递增；no-op Reload 保持 revision 不变。
如果未来新增配置字段但尚未补充详细 diff，API 会返回通用的脱敏变更提示，避免
实际变更被错报为 `no_changes: true`。

1. 连续两次 no-op Reload 均返回 revision `1`；
2. watcher 应用阈值 `250 → 249` 后 revision 为 `2`；
3. watcher 应用恢复 `249 → 250` 后 revision 为 `3`；
4. 两次 watcher 之后的手动 no-op Reload 均未额外增加 revision。

当前运行配置及 `config.yaml` / `config_zh.yml` 中的慢检索阈值均已恢复为 `250ms`。

## 十一、P2 结构化 JSON 查询工具

新增低风险、只读的 `json_query` 工具：

- 只能读取 Workspace 内的相对路径，复用现有路径策略并以 `O_NOFOLLOW` 打开；
- 使用 RFC 6901 JSON Pointer，支持对象键、数组下标以及 `~0` / `~1` 转义；
- 使用 `json.Number` 保留数字精度，拒绝非法转义、越界下标和多个顶层 JSON 值；
- 输入文件限制为 2 MiB，输出继续由统一工具中间件进行 UTF-8 规整和截断；
- 通过工具注册表自动进入 Planner schema，无需手工维护 action 枚举。

### 18.1 重启后验收发现并修复并行 Trace 覆盖

真实任务 `o4-parallel-live-20260810-01` 在同一 Planner 决策并行读取 `README.md` 与 `go.mod`，

分别为 1、2。

### 19. P4 持久化审批第一阶段实现

P5 当前仍为进行中，下一阶段是历史审批清理与 AES 密钥轮换。全量 `go test ./...`、
Metrics/API/Orchestrator/Store race 测试及 `git diff --check` 均通过。

### 20.1 历史审批安全清理

新增独立 `ApprovalCleanupStore`，不扩张 durable 核心契约。`approval.retention_days` 默认 30，0 禁用，
可通过 `AI_AGENT_APPROVAL_RETENTION_DAYS` 热更新。维护器启动立即清理、此后每小时执行，只删除
resolved_at 早于 cutoff 的 consumed/expired；pending、approved 以及尚待恢复消费的 rejected 明确保留。

SQLite/Postgres 使用带终态和时间条件的单条 DELETE；Memory 在锁内复核；Redis 以增量 SCAN 找到记录，
WATCH 后重新解码并复核终态/时间，再以事务同时删除正文和 task ZSET 索引，避免与并发状态更新竞争。
本地指标新增 `durable_approvals_cleaned` 和 `durable_approval_cleanup_failures`，OTel 复用低基数 cleaned/
cleanup_failure event。新增 Memory 保留矩阵、SQLite 实际删除和指标回归。
全量测试、Server/Config/Metrics/API/Orchestrator/Store race 测试及 diff 格式检查通过。

### 20.2 AES 审批密钥轮换

线上重启后确认 cleaned/cleanup_failure 指标已加载。审批密文升级为版本化信封 v2：密文头携带主密钥
SHA-256 摘要前 8 字节作为非敏感 key ID，Decrypt 据此选择密钥，正文仍由随机 nonce 的 AES-256-GCM
认证加密。既有无 key ID 的 v1 载荷会依次尝试 keyring，因此不需要数据库迁移。

`AI_AGENT_APPROVAL_ENCRYPTION_KEY` 是唯一写入主密钥；新增逗号分隔的
`AI_AGENT_APPROVAL_ENCRYPTION_PREVIOUS_KEYS` 只用于读取历史 v1/v2。任何无效历史密钥会让启动
fail-closed；日志仅输出 payload_version=2 和 previous_keys 数量，不记录密钥、key ID 或密文。
轮换测试覆盖旧 v1、旧 v2 可读，新密文只可由新主密钥读取，以及 Engine 装配后的旧 checkpoint 解密。

全量测试和 ApprovalCrypto/Server/API/Orchestrator/Store race 测试通过。P5 代码与自动测试已完成，
剩余最终门禁是配置真实新旧密钥后执行一次跨重启审批恢复验收。
