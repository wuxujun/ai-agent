## 二、当前 Wiki 支持范围

### 2.1 数据源

- 本地目录模式：`AI_AGENT_WIKI_DIRECTORY` 可指向包含 `AGENTS.md/raw/wiki` 的仓库根，也可直接指向 `wiki/`。
- 远程模式：通过 Streamable HTTP MCP 连接 LLM Wiki。
- 本地目录与远程 MCP 模式互斥。
- Wiki Runtime 配置属于重启生效项，尚不支持在不重建 Runtime 的情况下完整热切换。
- `required=true` 时初始化失败阻止启动；可选 Wiki 初始化失败不阻止主服务，但不会注册可用工具。

### 2.2 工具链

| 工具 | 状态 | 用途与限制 |
| --- | --- | --- |
| `wiki_search` | 已支持 | 搜索候选，`top_k` 上限为 10 |
| `wiki_fetch` | 已支持 | 只能读取同一任务搜索产生的候选 ID，受数量和字节预算限制 |
| `wiki_graph` | 条件支持 | 后端支持时注册，深度限制为 1–2，每任务最多一次 |
| `wiki_graph_fetch` | 条件支持 | 读取有界图邻居页面，最多 3 个 URI |
| `wiki_suggest` | 条件支持 | 后端支持时注册，每任务最多一次，只生成策展候选 |

本地目录客户端同时支持 Search、Read、Graph 和 Suggest，因此本地模式会注册上述完整只读工具链。远程模式根据 MCP 实际 Schema 发现 Graph/Suggest，不注册占位工具。

### 2.3 Multi-Agent Team

- `wiki`：固定 `wiki_search -> wiki_fetch`，用于普通 Wiki 问答。
- `wiki_graph`：受控执行搜索、全文读取、图遍历和邻居读取。
- `wiki_suggest`：受控执行搜索、全文读取和只读策展建议。
- `kb_qa` Writer 也包含 Wiki 证据与引用规则，但是否选择 Wiki 仍取决于 JIT 路由、Team allowlist 和实际注册工具。
- 当前 Wiki Team 已配置 Langfuse Prompt 名称与 `production` 标签；相关工作区修改尚未提交。

### 2.4 安全、隔离与可靠性

- 每次执行按 Tenant 解析 `api.tenants.<tenant>.wiki_space`，否则使用显式 `wiki.default_space`。
- 非默认租户缺少 Space 且无默认 Space 时明确失败，避免静默跨租户检索。
- 本地读取仅接受普通 Markdown 文件，限制单页大小，保留路径穿越与符号链接边界检查。
- Wiki 内容被视为不可信证据，继续经过 Prompt Guard、Evidence Filter 和 Writer 约束。
- 搜索候选 ID 绑定 Tenant 和 Task，不能跨任务直接用于 `wiki_fetch`。
- 搜索与读取共享超时、熔断、半开探针、readiness 和 OTel/本地指标。
- `wiki_suggest` Writer 只接收建议证据，不能根据搜索结果或全文自行扩展建议。

### 2.5 明确未支持的能力

- `wiki://` 是稳定证据 URI，不是浏览器可直接打开的 URL；当前没有受控页面解析 HTTP API。
- 没有实际 Wiki create/update/delete/ingest/commit 工具或 API。
- `internal/wiki/writeback.go` 仅实现无副作用的提案校验、hash、幂等键和 diff 预览，未接入工具注册、审批或实际写入。
- 没有页面历史、版本/commit 引用、策展审核队列和多 Space 请求选择能力。
- `config.yaml` 注释仍称 suggestion 不注册，但实现会按后端能力注册 `wiki_suggest`，存在文档漂移。

## 三、本地搜索当前实现

当前本地检索流程：

```text
Search
  -> WalkDir 枚举全部 Markdown，并生成 path + size + mtime 签名
  -> 签名变化时重建全部页面索引
  -> 规范化 query，并生成去空格 compact phrase
  -> 遍历全部页面执行 Contains/Count 评分
  -> 对直接链接页面做一次受限加权
  -> 全量排序并返回 TopK
```

索引字段包括：

- slug、标题、所有 Markdown heading。
- frontmatter 的 title、summary、tags、aliases。
- 正文规范化文本与 compact 文本。
- 最多 256 个非空行式 chunk，每个最多 500 rune，用于生成较相关的 excerpt。
- 标准 Markdown `.md` 链接，用于一跳关系召回、Graph 和 Suggest。

当前权重偏向标题和完整短语：title phrase 100、slug phrase 70、heading 40、metadata 35、body 20；term 频次按字段继续加分，正文单 term 最多计 10 次。导航页 `index`、`_index`、`log` 会降权。

## 四、本地搜索优势与瓶颈

### 4.1 已有优势

- 完全本地、确定性、无模型费用，远程依赖失败不影响目录搜索。
- 对精确标题、slug、frontmatter alias 和中英文标点/空格变化效果较好。
- 同分按 slug 排序，结果可复现。
- 内容变更能够触发刷新，并已有并发搜索回归测试。
- 搜索结果天然保留 `wiki://` URI，便于证据引用和租户隔离。
- 已有 Recall@K、First Hit、MRR、Fetch、Keyword、Citation、Graph、Suggest 和 P95 Eval 指标。

### 4.2 主要瓶颈

1. **每次搜索都扫描目录**：即使索引未变化，也要 `WalkDir` 计算签名；Wiki 扩大后文件系统开销会进入查询延迟。
2. **不是倒排索引**：查询遍历全部页面，并对多个完整字符串执行 `Contains/Count`，复杂度随页面数和总文本线性增长。
3. **中文分词不足**：连续中文通常成为一个 term；compact 只能处理空格和标点，不能稳定处理部分词、词序变化和同义表达。
4. **人工权重缺乏统计归一化**：没有 IDF 和文档长度归一化，常见词、重复 metadata 或长正文可能影响排序。
5. **链接加权可能带来噪声**：强匹配页面可提名所有直接链接页面，即使邻居本身不匹配 query。
6. **刷新粒度过粗**：任意文件变化都会重建全部索引；签名只依赖路径、大小和 mtime，缺少内容摘要与文件级增量状态。
7. **链接格式覆盖不完整**：主要识别标准 Markdown `.md` 链接，纯 `[[wikilink]]`、无扩展名链接等形式可能缺失。
8. **Eval 样本不足**：当前 `evals/wiki_retrieval.jsonl` 只有 5 条，集中在 PBL 主题，容易对现有人工权重过拟合。

## 五、推荐优化路线

### P0：质量基线与可解释性

先保持默认排序行为不变，建立可以判断优化是否真实有效的基线：

1. 将 Eval 扩充到至少 30–50 条，覆盖精确标题、部分标题、别名、中英文混合、词序变化、多正确答案、相似标题、高频通用词、导航页干扰和无答案查询。
2. 增加 Precision@K、NDCG@K、Top1/Top3 命中率、零结果率和无答案误召回率。
3. 增加冷/热查询 P50/P95、索引刷新耗时、页面数和索引内存估算。
4. 为搜索增加内部 explain 结构，报告命中字段、phrase、基础分、链接加权和索引版本；默认 API 不必暴露。
5. 增加 100、1,000、10,000 页面合成 Benchmark，固化当前算法基线。

### P1：倒排索引、BM25 与 CJK n-gram

1. 引入不可变 `directoryIndexSnapshot`，保存页面、posting、document frequency、字段长度、平均长度、版本和构建时间。
2. 英文按 Unicode 单词切分；数字保留年代、范围和常见课程编号。
3. CJK 段落生成受限二元组，必要时三元组，同时保留完整标题/alias phrase。
4. 使用字段化 BM25，建议初始权重：title 8、slug 6、aliases 5、headings 4、summary/tags 3、body 1。
5. 在 BM25 上叠加完整标题、alias 和连续 phrase 加分，继续保留确定性 slug tie-break。
6. 旧评分器保留为 feature flag/fallback，通过同一 Eval 对比后再切换默认实现。

### P1：增量不可变快照

1. 周期性扫描或显式 Refresh 替代每次查询扫描；`fsnotify` 只作为刷新提示，不能作为唯一一致性机制。
2. 保存文件级 path、size、mtime 和可选内容 hash，只重建新增或变化页面，并移除已删除页面的 posting。
3. 在锁外构建新快照，完整验证后原子替换；构建失败继续提供上一份健康快照。
4. readiness/metrics 增加索引版本、页数、最后成功时间、刷新耗时、失败数和当前是否 stale。

### P1：链接召回校准

- 先生成纯词法 TopN，再只从高置信种子扩展一跳。
- 邻居必须自身命中 query token，或属于明确的 entity/source/comparison 关系。
- 使用绝对上限控制 link boost，不让链接关系覆盖强标题匹配。
- 导航页不能作为扩展种子。
- explain 中记录 `link_boost_source`，方便定位噪声来源。

### P2：可选混合检索

BM25 基线稳定后再增加向量召回：

```text
BM25 Top50 + Vector Top50 -> Reciprocal Rank Fusion -> 可选 Reranker -> TopK
```

要求：Embedding 不可用时自动退回 BM25；向量索引绑定 Wiki snapshot/version；不同 Tenant Space 不共享候选；默认继续支持完全离线运行。LLM 查询改写和 LLM reranker 不应进入第一阶段。

## 六、建议下一步实施内容

下一阶段建议只实施“本地搜索 P0”，不要同时引入向量检索：

1. 扩充检索 Eval 数据集。
2. 增加 Precision@K、NDCG@K 和无答案误召回指标。
3. 增加当前评分器的结构化 explain。
4. 增加大目录 Benchmark 和索引刷新测试。
5. 保存当前质量与性能基线。
6. 基线稳定后单独实施 BM25/CJK n-gram，并以 feature flag 灰度。

建议初始验收门槛：

```text
Recall@5                 >= 0.90
Top1 hit rate            >= 0.75
NDCG@5                   >= 0.85
无答案误召回率            <= 0.10
wiki:// citation coverage = 1.00
错误率                    = 0
1,000 页热查询 P95        <= 100ms
10,000 页热查询 P95       <= 300ms
索引更新失败时旧快照仍可查询
```

推荐顺序：

```text
扩大 Eval -> 固化基线 -> 可解释评分 -> 倒排索引/BM25
          -> CJK n-gram -> 增量快照 -> 链接校准 -> 可选混合检索
```

## 十、P1 不可变索引快照

本地目录索引现以原子指针发布完整只读快照，快照同时包含页面、版本与 BM25 posting。`Search`、`Graph` 和 `Suggest` 直接复用同一代快照，不再逐请求复制页面或执行 `WalkDir`。新增 `wiki.local_refresh_interval_seconds`（环境变量 `AI_AGENT_WIKI_LOCAL_REFRESH_INTERVAL_SECONDS`），默认 30 秒；普通读取在间隔到期时由单个请求惰性检查，配置为 0 时仅由 `Probe` 显式检查。无需后台 goroutine，关闭流程不增加生命周期负担。

刷新先完整构建候选索引，再一次性发布。普通查询遇到重建错误时继续使用最后一份完整快照；`Probe` 会返回实际错误用于健康检查。初始化仍失败关闭，查询上下文取消也不会被旧快照掩盖。回归测试覆盖自动刷新、Probe-only、失败保留旧快照、负配置和 race 并发访问。

相同宽查询的快照化 Benchmark：

```text
页面数    Legacy       BM25
100       1.72ms       0.75ms
1,000     25.23ms      11.17ms
10,000    266.77ms     120.85ms
```

与上一批相比，10,000 页 BM25 从 323.23ms 降到 120.85ms，约降低 62.6%；分配从约 114MB/op 降到约 10MB/op。剩余成本主要来自宽查询命中大量 posting 后的候选评分、结果 map 和 excerpt 计算，而不是目录扫描。下一步应为 BM25 加入候选上界/稀有词优先与 Top-K 堆，再处理 Graph 无关节点率门禁。

## 十一、P1 BM25 Top-K 热路径

BM25 查询评分由按文档分配的 map/pointer 改为连续评分数组，仅在 explain 模式创建字段明细；slug 到文档编号的映射随不可变索引快照预构建。词项覆盖筛选后使用固定容量 Top-K 最小堆，仅为最终结果生成 `Document` 和相关 excerpt，避免宽查询先构造全部结果再全量排序。评分公式、phrase boost、链接加权上限、导航页降权及 slug 确定性 tie-break 均保持不变。

真实 30-case Eval 保持：Recall@5、NDCG@5、Top1、Top3、MRR、Fetch、Keyword、Citation 均为 1.000，无答案误召回为 0，P95 从 20ms 降至 1ms。Graph 无关节点率仍为 0.970，是当前唯一独立门禁缺口。

相同宽查询的新 Benchmark：

```text
页面数    Legacy       BM25
100       1.64ms       0.054ms
1,000     25.15ms      0.273ms
10,000    276.09ms     2.43ms
```

10,000 页 BM25 相比不可变快照首版的 120.85ms 再降低约 98%，分配降至约 1.32MB/op、52 allocs/op。当前无需引入可能改变召回的候选硬截断；下一阶段可直接校准 Graph 遍历与无关节点控制。

## 十二、P1 Graph 扩散校准

本地 `Graph` 原先按文件链接顺序执行两层 BFS，高出度的项目设计页、来源目录页会迅速触发 100 节点全局上限。现改为逐层收集候选，并按根页面标题在候选页面 title、slug、heading、metadata、body 中的相关性排序；导航页降权，同分按 slug 稳定排序。只有选中节点及其真实连接边进入结果，避免出现指向已裁剪节点的悬空边。

新增 `wiki.local_graph_max_nodes`（环境变量 `AI_AGENT_WIKI_LOCAL_GRAPH_MAX_NODES`），默认 12、允许 1–100，配置 0 使用内置默认值。真实 PBL 二跳图从 100 节点、无关率 0.970 降至 12 节点、无关率 0.727，三个期望节点全部保留，Graph recall 维持 1.000。至此当前 30-case 的搜索、无答案、引用、Graph 和 Suggestion 门禁全部通过。

## 十三、P1 默认启用 BM25

在真实 30-case 全部门禁通过后，运行时配置与 `cmd/wiki-eval` 的默认本地排序器从 `legacy` 切换为 `bm25`。`AI_AGENT_WIKI_LOCAL_SEARCH_MODE=legacy` 继续作为重启后立即回退路径；底层 `NewDirectory` 未传 option 时仍保留 Legacy 兼容行为，避免无配置的库调用方发生隐式语义变化。服务启动日志增加 `search_mode`、刷新间隔和 Graph 节点上限，便于确认实际生效配置，不记录页面内容或鉴权信息。

## 十四、P1 索引运行状态

本地目录 client 新增内容无关的状态快照：backend、搜索模式、页数、索引版本、构建时间、最近刷新尝试/成功时间、刷新耗时、连续失败数、是否正在服务旧快照、刷新间隔和 Graph 上限。状态不包含目录路径、页面标题、摘要、查询词或鉴权信息。`/ready` 的 `wiki.status` 返回该信息；远程 MCP 模式仅返回 `backend=remote`。索引重建失败时 readiness 的 Probe 仍失败，同时状态明确标记 `serving_stale_snapshot=true`，便于区分“完全不可用”和“健康检查失败但旧快照仍可查询”。

## 十五、线上验证与近似课程隔离

8088 重启后 `/ready` 返回 200，确认 `search_mode=bm25`、419 页、Graph 上限 12、刷新失败数 0 且未服务旧快照。真实 `team=wiki` 任务成功调用 `wiki_search` 与 `wiki_fetch`，前两名为目标概念页和课程来源页，并生成 `wiki://` 引用。

验证同时发现第三名通用 `sources/raw-doc-*` 页面描述另一版本的相似课程，writer 将其中 Estelle 与目标课程 Vanessa 合并。为降低此类实体串线，BM25 对“查询未精确匹配标题”的通用 raw-doc source note 使用 0.2 来源特异性倍率；标题精确匹配 raw-doc 时倍率仍为 1，保留直接查询能力。Explain 新增 `source_multiplier`。Wiki writer 规则同步要求优先精确标题页面及其明确链接来源/实体，不得合并名称相近 offering 的人物、日期、门槛或交付细节，无法消解时报告冲突。

第二次线上任务确认串线已消失：Top-5 为目标概念、课程来源、课程设计、CT/NCT 对比和 Vanessa 实体，最终答案仅报告 Vanessa。但自动 fetch 原先仍机械读取前三名，导致实体页虽在 Top-5 却未直接读取。后续选择改为保留第一名后，在有限预算内优先覆盖 sources、entities、comparisons、concepts 等不同页面类别，再按原排名补齐。单元测试已确认候选集同时含有来源页和实体页时，三个 fetch 会选取目标概念、课程来源和 Vanessa 实体，减少重复概念页占用证据预算。

第三次重启后线上任务 `wiki-bm25-live-260824-v4` 确认多样化选择已生效：自动 fetch 读取目标概念页、课程来源页和 CT/NCT 对比页，不再读取通用课程设计页。本次查询的 Top-5 未包含 Vanessa 实体页，因此有限候选集无法直接选取该页；导师姓名、学历和批改经验仍由课程来源页直接支撑。最终答案仅报告 Vanessa Ruales，正确说明 800–1,000 字产出与 6 CT + 1 NCT 结构，并引用三个已读取页面；近似 raw-doc 页虽位于第五名，未被 fetch 且未污染答案。

## 十六、P1 候选发现与全文读取预算解耦

为解决实体页偶尔排在默认 Top-5 之外、导致类别多样化无候选可选的问题，`wiki.search_top_k` 默认值由 5 调整为 8，`wiki.fetch_max_items` 继续保持 3。这使搜索阶段能看到更多轻量标题与摘要，再从中按 sources、entities、comparisons、concepts 类别选取最多三页全文；不增加 Wiki 全文读取次数、证据字节上限或 LLM 调用次数。

主配置、中文注释配置和内建默认值已同步。针对性测试、全仓 `go test ./...` 及 config/tools/multiagent/server 竞态测试均通过。该配置修改需重启服务后才会应用到线上任务。

重启后线上任务 `wiki-bm25-live-260824-v5` 完成闭环验收：`wiki_search` 返回 8 个候选，Vanessa Ruales 实体页位于第 6 名；多样化选择在三页 fetch 预算内读取目标概念页、课程来源页和 Vanessa 实体页。第 5 名的近似 raw-doc 候选没有被读取，最终答案仅引用上述三页，正确报告 800–1,000 字产出、6 CT + 1 NCT 结构及 Vanessa Ruales，未出现相似课程导师串线。
