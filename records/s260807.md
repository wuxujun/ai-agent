## 3. LiteLLM 与 Langfuse 可观测性

实现了两条 Langfuse 观测链路：

1. `ai-agent -> OpenTelemetry Collector -> Langfuse`：记录应用任务、Prompt 管理和应用 Trace。
2. `ai-agent -> LiteLLM -> langfuse_otel -> Langfuse`：记录模型请求、响应、模型、耗时和 token usage。

两条链路通过 `trace_id`、`parent_observation_id`、`task_id`、`session_id`、`tenant_id` 和 Prompt metadata 关联。

已处理的问题：

- `otel-collector` 因缺少 `LANGFUSE_OTEL_ENDPOINT` 反复重启；必须使用正确的 `.env` 显式启动：

  ```bash
  docker compose --env-file deploy/opentelemetry/.env \
    -f deploy/opentelemetry/docker-compose.yml \
    up -d --no-deps --force-recreate otel-collector
  ```

- Langfuse OTLP 401 的根因是 Basic Authorization、Public/Secret Key 或 endpoint 配置不匹配。Authorization 应由正确的 Public Key 和 Secret Key 生成，且 endpoint 应指向项目 OTLP 接口。
- 应用 Prompt fetch/create 请求增加 span，Prompt 名称、版本、来源可在 Langfuse 查询；不记录 Prompt 正文、Authorization 或 Secret Key。
- LiteLLM Generation 中保留 request/response 日志时必须结合 Langfuse 访问控制、保留期限和敏感信息脱敏。

## 4. Planner、Writer 和超时问题

- `falling back to secondary planner` 仅在主 Planner 返回错误或决策校验失败时输出，例如决策没有 Action、主模型返回 400 或响应无法解析；备用模型为 `agent-planner-legacy`。
- `agent-writer-legacy` 仅在主 Writer 失败、不可用或兼容性回退时调用，不是每次请求都会调用。
- LiteLLM 返回包含 `reasoning_content`、`usage` 和 JSON 字符串的响应时，应用需要按模型响应协议解析并校验最终 JSON；推理内容被截断或最终字段不完整会导致 synthesis failed。
- `context deadline exceeded` / `Client.Timeout exceeded while awaiting headers` 表示客户端在等待 LiteLLM/Gateway 首包时超时，应同时检查上游排队、模型耗时、Nginx/Gateway timeout 和应用 `timeout_seconds`。场景配置的超时应继承 Gateway 默认值时，需要在配置解析层统一 fallback，而不是只修改单个调用方。

## 5. API 认证、第三方验证和访问日志

- API 支持 `api_key`、JWT、introspection 和 hybrid 模式。
- `X-API-Key` 有值时只进行本地静态 API Key 验证，不调用第三方 JWT/introspection 服务。
- Bearer introspection 使用 GET 请求，Token 放在 `Authorization: Bearer <token>`，并解析返回包 `data.userid`、`data.aud`、`data.exp` 等字段；`code` 作为租户标识的方案已纳入校验设计。
- API 请求和响应不把 Authorization、X-API-Key、JWT 或请求体写入 access log；访问日志记录 method、path、status、latency、request_id、tenant、trace_id 等安全字段。
- 所有日志增加应用版本号，便于定位不同部署版本的行为差异。
- `GET /api/tasks` 支持按 Tenant、status、分页和 `session_id` 查询。

## 6. 多任务 Session 与共享 Memory

### 目标

同一 Tenant 下，一个 Session 支持创建多个任务；后续任务可以读取同一 Session 的任务结果和 Memory，其他 Tenant 或 Session 不可见。

### 数据模型

- 新增 `types.Session`：`id`、`tenant_id`、`title`、`status`、`next_sequence`、创建/更新时间。
- Session 状态支持 `active` 和 `archived`。
- `Task` 新增 `session_id`、`sequence_no`、创建/更新时间。
- `Memory` 新增 `session_id`。

### API

- `POST /api/sessions`
- `GET /api/sessions`
- `GET /api/sessions/{id}`
- `PATCH /api/sessions/{id}`
- `POST /api/sessions/{id}/archive`
- `GET /api/sessions/{id}/tasks`
- `GET /api/sessions/{id}/memories`
- 原有 `/api/tasks` 和 `/api/memories` 增加 `session_id` 查询参数。

创建任务示例：

```json
{
  "session_id": "session-id",
  "goal": "继续分析已有内容",
  "workspace": "."
}
```

### 实现范围

- 内存 Store、SQLite、PostgreSQL、Redis 均实现 SessionStore。
- 任务创建时通过 Store 原子分配 Session 序号，避免多实例并发冲突。
- SQLite/PostgreSQL 启动时幂等创建 sessions 表，并补充 tasks/memories 的 Session 字段、时间字段和索引。
- Redis 增加 Session JSON、Tenant Session 索引、Session Memory 索引和 WATCH 原子序号更新。
- Engine 在进入各执行模式前建立 Tenant/Session scope；所有 RAG 查询按同一 Session 过滤。
- 新任务开始时直接读取同 Session 最近完成任务，保证异步 Embedding 尚未完成时也能共享上下文。
- `rag.session_recent_task_limit` 默认值为 5，设置为 0 可关闭直接历史注入。
- 归档 Session 保留历史任务和 Memory，但禁止继续创建任务。
- 不带 `session_id` 的旧任务保持原有 Tenant 级 Memory 语义。

### Langfuse Session 关联

- 有 Session 的任务使用真实 `Task.SessionID` 作为 Langfuse `session.id`。
- `task_id` 继续作为 Trace metadata，`tenant_id` 作为用户和租户 metadata。
- 无 Session 的旧任务使用 `task_id` 作为兼容 fallback。
