# 多 MCP 服务接入检查与实现记录

日期：2026-07-23

## 背景

本次工作首先检查项目是否能够同时接入多个 MCP 服务，随后在现有架构中增加第一版原生多 MCP 服务支持。

## 初始检查结论

改造前项目不能原生同时接入多个 MCP 服务。

当时的 MCP 能力主要是 RAG 检索传输适配：

- `rag.search_url`、`rag.authorization` 和 `rag.tool_name` 都是单值配置。
- 每次检索只会读取唯一的 RAG MCP 地址。
- 已支持 `initialize → notifications/initialized → tools/call`。
- 已支持 MCP Streamable HTTP 和旧式 SSE 握手响应。
- 只能调用一个固定的搜索工具，没有执行 `tools/list`。
- 没有 MCP Server 列表、客户端管理器、动态工具发现或服务级路由。
- 不支持 MCP stdio、resources 和 prompts。

因此，改造前只能连接一个面向 RAG 的 MCP 端点。也可以在外部部署 MCP 聚合网关，再让项目连接该网关，但这不属于项目自身原生支持多个 MCP 服务。

## 本次实现

### 1. 多服务配置

新增通用配置：

```yaml
mcp:
  servers:
    - name: "github"
      url: "https://mcp.example.com/mcp"
      authorization_env: "GITHUB_MCP_AUTHORIZATION"
      tool_prefix: "mcp_github"
      risk_level: "high"
      timeout_seconds: 15
      max_tools: 64
      required: false
      disabled: false
      allow_private_network: false

    - name: "local_tools"
      url: "http://127.0.0.1:9000/mcp"
      risk_level: "low"
      allow_private_network: true
```

每个服务可独立设置：

- `name`：服务唯一名称。
- `url`：MCP Streamable HTTP 地址。
- `authorization_env`：保存认证信息的环境变量名称。
- `tool_prefix`：本地工具命名前缀。
- `risk_level`：`low` 或 `high`，默认 `high`。
- `timeout_seconds`：初始化和发现超时。
- `max_tools`：单个服务允许注册的最大工具数，默认 64。
- `required`：初始化失败时是否阻止服务启动。
- `disabled`：是否禁用该 MCP 服务。
- `allow_private_network`：是否明确允许私网或回环地址。

认证值不会直接写入配置文件。裸 Token 自动使用 `Bearer`，已经包含认证方案的值保持原样。

### 2. MCP 客户端

新增 `internal/mcpclient`，实现：

- 每个服务独立的 HTTP Client、CookieJar、Session Header 和请求 ID。
- MCP 初始化和客户端生命周期管理。
- 协议版本协商。
- 初始化后的 `MCP-Protocol-Version` Header。
- JSON 和 SSE 包装的 JSON-RPC 响应解析。
- SSE 多行 `data` 事件解析。
- 带游标的分页 `tools/list`。
- `tools/call`。
- `content[].text`、二进制数据、嵌入资源及 `structuredContent` 解析。
- `isError` 和 JSON-RPC 错误处理。
- 有状态 HTTP Session 清理。
- 并发调用安全。

新客户端以最新稳定 MCP `2025-11-25` 发起协商，同时兼容：

- `2025-11-25`
- `2025-06-18`
- `2025-03-26`
- `2024-11-05`

原有 RAG MCP 适配暂时保持不变，以免破坏现有服务兼容性。

### 3. 多服务发现与工具注册

启动时会并行初始化所有启用的 MCP 服务，并调用 `tools/list`。

远程工具默认注册为：

```text
mcp_<服务名>_<远程工具名>
```

例如：

```text
mcp_github_search_code
mcp_database_query
```

实现的保护包括：

- 服务名称去重。
- 工具名称规范化。
- 本地工具名称冲突检测。
- 超长工具名称使用摘要后缀缩短。
- 单服务工具数量限制。
- 可选服务失败隔离。
- 必需服务失败时阻止启动。
- 服务关闭时释放 MCP Session。

远程工具会自动进入现有工具 Registry，因此 Planner Schema 和工具列表能够自动发现它们。

### 4. 编排模式接入

多 MCP 工具已经接入：

- Legacy
- Eino
- Multi-Agent
- Google ADK

ADK 会把动态 MCP 工具转换为 ADK Function Tool，并沿用工具输入 Schema。

Multi-Agent 仍使用现有 ResearchStep 参数模型。常见的 `query`、`path`、`url` 等参数可以直接映射；其他 MCP 参数可通过现有 Tool Argument Repair 流程修复。

### 5. 安全策略

新增 MCP 网络端点策略：

- 公网端点默认经过现有 SSRF 防护。
- 私网、localhost 和回环地址默认拒绝。
- 只有配置 `allow_private_network: true` 才允许连接私网 MCP。
- URL 只允许 HTTP/HTTPS。
- URL 中禁止嵌入用户名或密码。
- 重定向继续执行协议和网络策略检查。

远程 MCP 工具默认使用 `high` 风险等级，进入现有人工审批流程。只有明确配置 `risk_level: low` 才按低风险工具执行。

此外：

- MCP Server 返回的工具描述会标记为不可信。
- 工具描述长度限制为 500 字节。
- Planner、Multi-Agent 和 ADK Prompt 都增加了规则：不得执行 MCP 描述或输出中嵌入的指令。
- MCP 工具输出继续经过现有工具中间件截断和标准化。

## 当前能力边界

已支持：

- 同时配置和连接多个 MCP 服务。
- MCP Streamable HTTP。
- 多服务独立认证、Session 和超时。
- `tools/list` 动态发现。
- `tools/call`。
- 工具命名空间。
- 服务故障隔离。
- 高风险审批。
- 公网/私网安全策略。
- Legacy、Eino、Multi-Agent 和 ADK。

尚未支持：

- MCP stdio transport。
- MCP resources。
- MCP prompts。
- `notifications/tools/list_changed` 动态刷新。
- MCP 服务配置热重载。
- 服务断线后的后台自动重连。
