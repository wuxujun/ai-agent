1. **Redis DSN 凭证和常规日志业务内容泄露项已于后续优化关闭**；

3. **Redis ApprovalBus 生命周期项已于后续优化关闭**。

综合判断：**工程成熟度中上，默认单实例运行基础可靠；主要代码级 P0/P1 已关闭，真实 PostgreSQL/Redis 多实例联调仍需在部署环境验收。**

## 3. 当前架构与主执行链

### 3.1 服务装配

`cmd/server/main.go` 集中完成：配置与日志初始化、OTel、Langfuse Prompt bootstrap、Store、Skill、MCP、LLM Runtime、Planner、Orchestrator、Multi-Agent Coordinator、审批总线、Gin API 和优雅关闭装配。

主链路可概括为：

```text
HTTP API
  -> 认证与 Tenant 解析
  -> Task/Session 持久化与租约
  -> Orchestrator 模式路由
       -> Eino / Legacy / Step / ADK / Multi-Agent
       -> Planner / Critic / Researcher|Executor / Writer|Verifier
  -> Tool Registry + Policy + High-Risk Approval
  -> Answer Pipeline
  -> Store + Metrics + OTel/Langfuse
```

### 3.2 API 与多租户边界

API 已覆盖 Task、Session、Memory、Audit、Usage、Prompt 初始化、配置热重载、SSE 和健康检查。认证支持 `api_key`、JWT/JWKS、introspection、hybrid；静态密钥使用常量时间比较，JWT 校验限制算法、issuer、audience、exp 和 RSA 密钥强度，introspection 对响应大小、超时、缓存、Tenant claim 和私网访问均设有边界。

Task 路由通过 `TaskTenantMiddleware` 做对象级租户校验；批量删除、指标、配置重载和 Prompt 初始化要求管理员权限。Session 和 Memory 查询也显式携带 Tenant scope。

### 3.3 执行、安全和并发

- 工具通过统一 Registry 注册，Planner schema 与校验由 Registry 派生；
- `write_file`、`apply_patch`、`execute_code` 等高风险工具需要人工审批；
- Multi-Agent 并行批次会把高风险工具强制移回串行审批路径；
- Workspace 路径经过真实路径、父目录、软链接和边界校验，Unix 文件打开同时使用 `O_NOFOLLOW`；
- HTTP/RAG/MCP 出站路径包含 URL、私网、重定向、超时和响应大小控制；
- 单实例通过 `activeTasks` 和可调整 semaphore 控制并发，多实例通过 Store lease 与原子状态迁移避免重复执行；
- 任务关闭时可转为 paused，并支持后续恢复；审批可通过 Redis Pub/Sub 跨实例转发。

### 3.4 数据与质量流水线

Store 支持 memory、SQLite、PostgreSQL、Redis，Session 序号采用后端原子分配。Task、Trace、Memory、租户 LLM 使用量均可持久化。SQLite/PostgreSQL 的 Trace 保存已采用“只追加新步骤、截断时局部删除”的策略，避免每步全量重写。

答案流水线支持 citation、fact freshness、numeric consistency、uncertainty、safety 等阶段，并具备独立 token reserve、阶段超时、并行执行、required stage 与 Tenant 级 enforcement。

## 4. 主要发现与风险

### P0（已优化）：Redis DSN 被完整写入日志，可能直接泄露凭证

**原问题**：ApprovalBus 曾把 Store DSN 或 `AI_AGENT_REDIS_BUS_URL` 以 `redis_url` 原值写入启动日志。常见 Redis URL 形如 `redis://user:password@host/db`，会使生产日志、日志平台和 Trace 采集侧获得密码。

**本轮处理**：`cmd/server/main.go` 现在只从解析后的 `redis.Options` 记录 `redis_address`、`redis_db` 和 `redis_tls`，不记录原始 DSN、用户名或密码；无效 URL 的解析错误也改为通用诊断，避免错误字符串回显原始 URL。`cmd/server/main_test.go` 新增带用户名和密码的 `rediss://` 回归测试，验证安全日志元数据不包含凭证。

**验证**：`go test ./cmd/server`、`go vet ./cmd/server` 和 `go test ./...` 均通过。该 P0 项已关闭。

### P1（已优化）：常规 Info 日志广泛记录用户输入、模型输出和检索内容

原检查发现的位置包括：

- `cmd/server/main.go:390-392`：暂停任务完整 `goal`；
- `internal/multiagent/coordinator.go:173`、`planner_agent.go:151,245`、`writer_agent.go:56`：完整目标；
- `internal/multiagent/researcher_agent.go:81`：完整工具 observation；
- `internal/orchestrator/eino.go:229,235`：模型 thought summary 和 final answer；
- `internal/planner/mock.go:90`：thought、计划和 final answer；
- `internal/memory/rag_search.go:43`：完整检索 query 与 endpoint。

Access log 已刻意排除 header、query string 和 body，但组件日志此前绕过了这一约束。因此“访问日志不泄露请求体”并不等于全局日志安全。

**本轮处理**：

- 在 `internal/logger` 的动态 Handler 层集中处理 `goal`、`query`、`observation`、`final_answer`、`thought`、`content`、`prompt`、URL 等字段，统一替换为 Unicode 字符数；
- 对 API Key、Authorization、DSN、password、secret、token 等凭证字段统一输出 `[REDACTED]`，同时覆盖派生 Logger 和嵌套 Group；
- Task Report 不再把 Query 拼进 message，确保其经过结构化字段过滤；
- Planner 的嵌套参数日志对 query、prompt、content、command、args、URL 等只记录字符数；
- OTel 中的任务 `goal` 和 `final_answer` 原文属性替换为 `goal_chars`、`final_answer_chars`。
- 后续加固将 endpoint、URI、body、payload、request/response、instruction、arguments、command、params 等常见正文键纳入统一长度摘要，并覆盖 Cookie、credential、private key 等凭证键；
- Task Report 的 step message 改为固定文本，step、role、action、query 全部使用结构化字段；
- 新增 AST 静态测试扫描 `cmd/` 与 `internal/` 生产代码，禁止 Logger 使用动态 message，防止未来通过 `fmt.Sprintf` 绕过字段脱敏；
- 新增内容字段和凭证字段策略矩阵测试，确保新增高风险字段仍分别执行长度摘要或 `[REDACTED]`。

**验证**：新增日志 Handler 与 Planner 参数回归测试；相关重点包测试、`go test ./...`、`go vet ./...` 均通过。该 P1 项已关闭。LLM/Langfuse 平台是否保存请求响应正文仍由其独立配置和数据治理策略决定，不属于应用普通日志字段。

### P1（已优化）：SQL 启动迁移忽略错误，可能形成部分迁移状态

**原问题**：

- `internal/store/sqlite.go:138-166` 的 ALTER、UPDATE、CREATE INDEX 基本全部使用 `_, _ = db.Exec(...)`；
- `internal/store/postgres.go:139-162` 即使支持 `IF NOT EXISTS`，仍全部忽略执行错误；
- SQLite 的 WAL 和 busy timeout 设置在 `internal/store/sqlite.go:44-45` 也忽略失败。

对“列已经存在”可以有条件忽略，但原实现也会吞掉权限不足、磁盘故障、锁冲突、SQL 方言/版本不兼容、索引冲突和数据转换失败。后续首次读写新字段时才暴露错误，定位困难，也可能让多个实例面对不同 schema。

**本轮处理**：

- SQLite 的 WAL 与 busy timeout 配置现在检查错误，初始化失败时主动关闭 DB；
- SQLite 不再通过吞掉 duplicate-column 错误实现幂等，而是通过 `PRAGMA table_info` 检查列后按需补列；
- SQLite 的建表、补列、时间回填和建索引在单一事务内执行，任何失败都会阻止启动并回滚；
- PostgreSQL 的建表、补列、数据回填和索引创建改为单一事务并逐条检查错误；
- PostgreSQL 补充旧 Schema 的 `traces.agent_role` 迁移；
- 新增 SQLite 旧 Schema 升级测试，以及用重复 Trace step 制造唯一索引失败并验证完整回滚的测试。

**验证**：Store 定向测试、`go test ./internal/store`、全项目测试和静态检查均通过。该 P1 的 silent/partial migration 风险已关闭；后续仍可增加显式 schema version 表，进一步支持跨版本迁移审计。

### P1（已优化）：ApprovalBus 未纳入主进程优雅关闭

**原问题**：`ApprovalBus` 自身在 `internal/orchestrator/approval_bus.go` 明确要求调用 `Close()`，但主程序曾使用两个 `context.Background()` 启动订阅，没有保存 cancel，也没有调用 `ApprovalBus.Close()` 或 `redis.Client.Close()`。主关闭流程只关闭 HTTP 并等待任务。

**本轮处理**：

- 新增 `approvalBusRuntime`，集中持有 Context cancel、ApprovalBus、Redis Client 和取消监听 WaitGroup；
- ApprovalBus 主订阅和远端取消订阅共享同一个可取消 Context，不再使用无法终止的 `context.Background()`；
- 主关闭顺序调整为：停止 HTTP → drain/cancel task → cancel bus context → 关闭 Pub/Sub → 等待取消监听 goroutine → 关闭 Redis Client；
- Redis Client 关闭错误会被记录，nil runtime 关闭安全；
- 新增生命周期测试，验证 Context 被取消、后台 worker 被 join、Bus 与 Client 都关闭，并覆盖 Client close error。

**验证**：ApprovalBus 与 server 定向测试、全项目测试、静态检查和相关 race 测试均通过。该 P1 项已关闭。

### P2（已处理）：`deploy/langfuse` Git 元数据不一致，影响可复现构建

Git 将该路径视为 gitlink，但仓库没有对应 `.gitmodules` 映射，`git submodule status` 直接失败。新环境 clone、CI checkout、依赖审计和部署脚本可能无法可靠还原 Langfuse 内容。

**处理结果**：提交 `df5e4a7` 已将该无 `.gitmodules` 映射的 gitlink 从仓库移除。当前 `git ls-files -s deploy/langfuse .gitmodules` 无输出，新 clone 不再尝试还原该不完整对象；Langfuse 作为外部可观测服务管理。本项关闭。

### P2（已保守正式化）：存在未接入主系统的旧 `internal/workspace` 包

`internal/workspace/sandbox.go` 与 `snapshot.go` 声明为 `package agent`，没有被其他 Go 包引用，也没有测试；其中定义了另一套 Planner/Responder/Tool/Orchestrator 抽象，与当前 `internal/orchestrator`、`internal/tools` 并行存在。

**影响**：容易让维护者误判实际沙箱实现位置，未来修改可能落到无效代码；包路径名与 package 名也增加理解成本。

**本轮处理**：

- 全仓引用检查确认该目录未被生产代码调用，也没有证据表明它是当前文件沙箱实现；
- 不在缺少产品决策时删除历史文件，保留源码以兼容潜在内部使用；
- package 名从误导性的 `agent` 统一为与目录一致的 `workspace`；
- 新增 package 文档，明确它是未接入的早期运行时原型，不具备当前 policy、审批、持久化、取消、预算或 workspace 防护，禁止新代码接入；
- 对 `Orchestrator`、`ToolRegistry` 和构造器添加 Deprecated 指引，统一引导到 `internal/orchestrator` 与 `internal/tools`；
- 新增成功执行、未知工具和 Planner/Responder 错误传播测试，并通过 race 检查。

该处理消除了“目录名看似安全沙箱”和 package 名不一致的维护误导。若后续确认无需源码兼容，可由维护者明确授权后逐文件删除；本轮未删除任何文件。

### P2（核心 builder 与运行生命周期已拆分）：`cmd/server` 入口装配过重

原入口将配置、Store/MCP/LLM 装配、HTTP 监听、信号热重载和有序关闭全部放在 `main()` 中。尤其是监听 goroutine 内调用 `log.Fatalf` 时会直接 `os.Exit`，绕过 Store、MCP、Telemetry 和 Logger 的 defer 清理，也难以在测试中验证信号行为和关闭顺序。

**本轮处理**：

- 顶层 `main()` 只负责调用返回错误的 `run()` 并设置非零退出码，所有已注册 defer 会在退出前执行；
- 启动阶段的 `log.Fatal/Fatalf` 改为带上下文的 error 返回，初始化中途失败时也能释放此前建立的资源；
- 新增独立 `runApp` 生命周期单元，将 HTTP 服务、后台任务和 ApprovalBus 抽象为最小接口；
- HTTP 监听错误不再从 goroutine 直接终止进程，而是返回主生命周期并触发清理；
- 固定并测试 `HTTP Shutdown → 后台任务 drain → ApprovalBus/Redis Close` 顺序；
- SIGHUP 只触发热重载并继续服务，SIGINT/SIGTERM 才进入关闭；多个关闭错误通过 `errors.Join` 一并返回；
- 新增正常热重载/关闭、监听失败仍清理、多个关闭错误保留三类回归测试，并通过 race 检查。
- 新增 `buildStore`，集中并测试 Memory/SQLite/PostgreSQL/Redis 的选择、默认行为和外部 DSN 必填约束；
- 新增 `buildApp`，集中装配 Gin Router、API Handler、LLM Runtime middleware、Engine 事件回调、ApprovalBus、暂停任务扫描和 HTTP Server；
- ApprovalBus DSN 选择拆为纯函数并覆盖 Redis Store 优先、独立 Bus URL 和禁用三种情况；
- 新增无真实监听的 `/ping` transport 测试，验证默认地址、路由和 Engine 回调装配；
- 新增 `mcpRuntime`，统一管理 MCP Manager 的限时关闭；必需 MCP 服务部分初始化失败时立即清理，并通过 `errors.Join` 同时保留初始化与清理错误；
- 新增 `buildEngine`，集中处理 provider/API Key 校验、Ollama planner/embedding 探测、fallback planner、审计流水线和 multi-agent coordinator 装配；
- Ollama probe 通过函数参数注入，MCP 注册器通过最小接口注入，可在不访问网络的情况下验证失败传播和资源回收；
- 新增 MCP 正常所有权、部分失败清理、nil Close，以及 Engine API Key、核心依赖、Ollama 失败和多智能体装配测试；
- `main.go` 从约 584 行降至约 254 行，网络、存储、MCP 和 Engine 构造不再散落在进程控制逻辑中。

入口的核心构造和生命周期边界已经完成拆分。后续仍可把 Logger、Telemetry、Skill Registry 与 Langfuse bootstrap 归并为更高层的 bootstrap runtime，但它们已各自具备明确失败处理，不再属于本项的主要风险。

### P2（已建立验收套件并接入 CI）：外部后端的验证深度不足

当前 Store 单元测试和接口测试较完整，但 PostgreSQL pgvector 测试带条件跳过，Redis/PostgreSQL 的真实服务集成不属于本次 `go test ./...` 的必然覆盖范围。Session 原子序号、lease、租户隔离、迁移和分布式 ApprovalBus 都依赖后端真实语义。

**本轮处理**：

- 新增显式受控的 PostgreSQL/Redis 外部集成契约测试；只有 `AI_AGENT_RUN_EXTERNAL_INTEGRATION=true` 时才会连接外部服务；
- 每次运行生成唯一 Tenant、Session、Task、Memory 和 lease ID，清理仅针对这些明确 ID，不使用 `FLUSHDB` 或共享表批量清空；
- Store 契约覆盖并发 Session 序号、跨租户 Session 拒绝、Tenant/Session Task 与 Memory 隔离、lease 抢占/释放和归档 Session 拒绝新序号；
- Redis ApprovalBus 契约使用两个独立客户端，覆盖远端审批通过、拒绝和取消信号；
- PostgreSQL 初始化路径会在测试连接时执行真实建表/迁移逻辑。
- 新增 PostgreSQL pgvector 排序契约，验证扩展启用、三维向量写入、Tenant/Session scope 和余弦距离排序；
- GitHub Actions 新增独立 `external-integration` job，使用 `pgvector/pgvector:0.8.2-pg17-bookworm` 与 `redis:7.4.2-alpine` 健康检查服务；
- CI 使用专用 `ai_agent_test` 数据库和 Redis DB 15，以 `-race -count=1` 执行 Store、pgvector 和跨客户端 ApprovalBus 契约。

运行方式：

```bash
AI_AGENT_RUN_EXTERNAL_INTEGRATION=true \
TEST_POSTGRES_DSN='postgres://...' \
TEST_REDIS_URL='redis://...' \
go test ./internal/store ./internal/orchestrator \
  -run 'TestExternalStoresSessionLeaseAndIsolation|TestApprovalBusAcrossRedisClients' \
  -count=1 -v
```

手工运行时仍应使用专用测试数据库和 Redis DB。当前本机未设置上述 DSN，因此本轮本地只验证了默认跳过行为、测试代码编译和 GitHub Actions YAML 解析；真实服务结果应以该 CI job 首次运行结果为准。后续还可增加 lease 过期、PostgreSQL 旧 Schema 升级和进程重启恢复矩阵。
