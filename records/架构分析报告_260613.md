# AI-Agent 项目架构分析报告

> 生成日期：2026/06/13
> 分析对象：`github.com/wuxujun/ai-agent`（Go 1.25）
> 代码规模：约 15.6k 行 Go 代码（不含 vendor）

---

## 1. 项目���览

这是一个用 Go 实现的 **AI Agent 执行运行时引擎**。它把"大模型规划 + 工具执行"的循环（Plan → Execute）封装成一个可通过 HTTP API 驱动的任务系统：客户端提交一个目标（Goal）和一个沙箱工作空间（Workspace），引擎在安全边界内反复"规划下一步动作 → 调用工具 → 收集证据（Evidence）→ 更新轨迹（Trace）"，直至完成目标或耗尽预算。

核心特征：

- **可插拔的编排策略**：5 种 orchestrator 模式（eino / legacy / step / adk / multiagent），运行时由配置选择。
- **可插拔的 LLM Provider**：openai-responses / openai / ollama / gemini，按 API Key 自动探测。
- **工具注册表驱动 Schema**：注册工具即自动进入 planner 的 JSON Schema 与校验逻辑，无需手改 schema。
- **完整的任务生命周期**：持久化、断点恢复、SSE 流式推送、高危动作人工审批、预算与并发控制。
- **全链路可观测性**：OpenTelemetry traces + metrics，本地 metrics collector。

## 3. 整体架构

### 3.1 分层与数据流

```
Client
  │  POST /api/tasks            (创建任务)
  │  POST /api/tasks/:id/run     (单步调试)
  │  POST /api/tasks/:id/run-all (后台跑到完成, 返回 202)
  │  GET  /api/tasks/:id/stream  (SSE 实时事件)
  ▼
┌──────────────────────────── API 层 (internal/api) ────────────────────────────┐
│ Gin 路由 / 错误中间件 / Span 中间件 / 有界 worker 池 / 任务取消 / SSE EventBus  │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                     ▼
┌────────────────── Orchestrator Engine (internal/orchestrator) ──────────────────┐
│  Engine.Next  ──按 Mode 分派──▶  eino | legacy | step | adk | multiagent         │
│  通用关注点：RAG 记忆预取 · 预算检查(step/tool/token) · 回调 · 每步持久化         │
└──────────┬───────────────────────────────────────────────┬──────────────────────┘
           ▼                                                 ▼
   ┌──── Planner (internal/planner) ────┐         ┌──── Executor (internal/executor) ────┐
   │ LLMPlanner ─ Provider 插件          │         │ 并发执行 decision.Actions             │
   │ FallbackPlanner ─ 失败降级 Mock     │         │ 工具失败=观测(非致命), 仅 ctx 取消致命 │
   │ JSON Schema 严格结构化输出          │         └──────────────────┬────────────────────┘
   └────────────────────────────────────┘                            ▼
                                              ┌──── Tools Registry (internal/tools) ────┐
                                              │ find/grep/read/write/execute/git_diff/  │
                                              │ http_fetch/web_search/use_skill         │
                                              │ middleware: 超时 + 重试 + span          │
                                              └──────────────────┬───────────────────────┘
                                                                 ▼
                                              ┌──── Policy (internal/policy) ────┐
                                              │ 工作空间防穿透 · 命令白名单 · URL 校验 │
                                              └───────────────────────────────────┘
           │
           ▼
┌──── Store (internal/store) ────┐     ┌──── Telemetry (internal/telemetry) ────┐
│ sqlite/postgres/redis/memory   │     │ OTLP traces + metrics                   │
│ SaveFullTask 原子持久化         │     └──────────────────────────────────────────┘
│ 原子状态迁移防并发竞争          │
│ QueryMemories 向量召回(RAG)     │
└─────────────────────────────────┘
```

### 3.2 任务一生（典型 run-all 流程）

1. `POST /api/tasks` → 校验工作空间 → `ExistsTask` 防覆盖 → 落库为 `created`。
2. `POST /api/tasks/:id/run-all`：
   - 先占用进程内 `activeTasks` 槽位（指针身份键，防 stale defer 误删）；
   - 再做 DB 原子状态迁移 `created/awaiting_approval → running`（防多实例竞争，冲突返回 409）；
   - 异步起 goroutine，立即返回 `202 Accepted`。
3. goroutine 内 `Engine.RunAll` 循环调用 `Engine.Next`：
   - 首步且无记忆时，预取 RAG 记忆（第三方 URL + 本地向量召回，去重后取 top 3）；
   - 按 Mode 执行一步；每步后 `SaveFullTask` 持久化并通过回调推 SSE。
4. 命中预算/最大步数/planner stop → `completed`；ctx 取消或致命错误 → `failed`。
5. 客户端通过 SSE 或轮询 `GET /api/tasks/:id` 获取权威状态。

## 4. 核心模块剖析

### 4.1 编排引擎 `internal/orchestrator`（系统主驱动）

`Engine` 是唯一的任务驱动器，`Mode` 字段在 `Engine.Next` 中选择 5 种策略之一：

| Mode | 文件 | 行为 |
| --- | --- | --- |
| `eino`（默认） | `eino.go` | 编译一次 Eino `compose.Chain` 并用 `sync.RWMutex` 双检缓存；每次 Next 跑一个 Plan→Execute 步。 |
| `legacy` | `engine.go:runLegacyNext` | 直接 Planner→Executor 调用，无 Eino 包装，便于调试主循环。 |
| `step` | `step.go` | 离散步进状态机变体。 |
| `adk` | `adk.go` | Google ADK-for-Go runner，`sync.Once` 编译一次。 |
| `multiagent` | `multiagent.go` + `internal/multiagent` | Plan→Research(×N)→Write 流水线，**一次 Next 调用完成整个任务**。 |

**与模式无关的横切关注点**集中在 `Engine.Next` / `RunAll`，对所有模式生效：
- RAG 记忆预取（仅 `StepCount==0 && len(Memories)==0` 时）；
- 三种预算闸：`StepCount >= MaxSteps`、`ToolBudget <= 0`、`TokenBudget > 0 && totalTokens >= TokenBudget`；
- 四个回调（Event/Approval/Step/Token）→ SSE；
- 每步持久化。

**高危动作审批**（`SuspendForApproval`）值得关注的设计：持久化 `awaiting_approval` 状态时使用**独立的 `context.Background()` + 10s 超时**，而非调用方 ctx——因为调用方 ctx 携带 run-all 墙钟预算与用户审批等待窗，不应中断"已挂起"状态的写入，否则重启后任务看起来像丢失了。审批本身阻塞在 `approval.go` 注册的 channel 上，由 `POST /api/tasks/:id/approve|reject` 释放。

> 新增一个模式需：加 `Mode` 常量 + `run<Mode>Next` 方法 + `Engine.Next` 的 case 分支。

### 4.2 多智能体协调器 `internal/multiagent`

`Coordinator.Run` 编排三个 Agent 角色（Planner / Researcher / Writer），并实现了两个反馈环：

1. **Plan 阶段**：`PlannerAgent` 把目标分解成 `ResearchStep` 列表。
2. **Research 阶段**：`partitionBatch` 把队首连续的只读步骤打包并发执行（`runBatchParallel`），其余串行（`runBatchSerial`）。
   - **安全要点**：`isReadOnlyAction` 以注册表 `RiskLevel()` 为权威判据——任何 `RiskLevelHigh` 工具被强制踢回串行路径，因为**只有串行路径会调用 `SuspendForApproval`**，并行路径不做审批门禁。这关闭了"高危工具被误判为只读 → 绕过审批"的漏洞。
   - 批次中任意步骤失败 → 触发**协作式 replan**（最多 3 次）。
3. **Write 阶段**：`WriterAgent` 综合全部证据产出 final answer + confidence。
   - **自适应深度扩展**：若 confidence == "low" 且仍有预算/步数，调 `Replan` 生成更多步骤再来一轮（最多 2 次）。
   - Writer 失败时标记任务 **FAILED**（而非 COMPLETED），避免把合成失败伪装成成功（这是修过的一个语义 bug）。

`tokenBudgetExhausted` 在 research 阶段与自适应深度环中都做了 token 闸，防止 plan/replan/write 迭代无限烧 token。

### 4.3 规划器 `internal/planner`

- **接口**：`Planner.PlanNext(ctx, task, onChunk) (*PlanDecision, error)`，`onChunk` 支持流式 token 回调。
- **结构化输出**：`PlanDecision` 含 `ThoughtSummary / Stop / FinalAnswer / Actions[] / TokenUsage`。
- **Provider 插件**（`provider.go`）：`LLMProvider` 接口 + `RegisterProvider`，内置 4 种：
  - `openai-responses`（默认，非流式结构化输出，走 Responses API）；
  - `openai`（Chat Completions，SSE 流式）；
  - `ollama`（本地，流式）；
  - `gemini`（`gemini_pool.go`，走 genai SDK）。
  - `runHTTPPlan` 统一 HTTP 骨架（状态码/错误体处理），各 provider 只管 schema 构造与响应解析。
- **容错**：`FallbackPlanner` 包装真实 planner，出错时降级到 `MockPlanner` 并记录 metrics（`main.go` 中接线，需保留此结构）。
- **配置解析**：`config.ResolveLLMProvider` 按存在的 API Key 自动探测（`OPENAI_API_KEY`→openai-responses；`GEMINI_API_KEY`/`GOOGLE_API_KEY`→gemini）。

### 4.4 工具注册表与"三方不变量"

这是本项目最关键的设计约束。以下四者必须**锁步一致**：

```
tools.DefaultRegistry  ──生成──▶  planner.PlannerDecisionSchema
                       ──生成──▶  planner.PlannerDecisionGenAISchema
                       ──驱动──▶  planner.ValidateDecision
```

- `PlannerDecisionSchema()`（`schema.go`）从注册表动态生成：遍历已注册工具，把 `Name()` 加入 action 枚举，把各工具 `Parameters()` 合并进参数对象。**Schema 是生成的，不可手改——要改就改工具。**
- `ValidateDecision()`（`validate.go`）同样以注册表为准：未注册的 action 直接拒绝；工具若实现可选的 `Validator` 接口，则其参数校验在规划侧即生效（通过 `unwrapValidator` 穿透 `toolMiddleware` 包装）。
- `Registry.Register` 给每个工具套上 `toolMiddleware`（超时、重试 `retryPolicyProvider`、span 属性）。`List()` 按名字排序，保证生成的 schema 与 prompt 稳定。
- 工具声明 `RiskLevel()`；任何 `RiskLevelHigh` 触发审批挂起。

**内置工具**（10 个）：`find_files`、`search_text`、`read_file`、`write_file`、`execute_code`、`git_diff`、`http_fetch`、`web_search`、`inspect`、`use_skill`。

### 4.5 执行器 `internal/executor`

`DefaultExecutor.Execute` 把 `decision.Actions` **并发执行**（每个 goroutine 写预分配 slice 的独立索引，无需额外同步）。核心约定：

- **工具失败是观测，不是任务失败**：失败被写入 `StepTrace.Error + Observation`，规划器下一轮能看到并自我纠正；
- **唯一致命条件是 ctx 取消/超时**，会向上传播让引擎停止循环（避免空转）。

### 4.6 技能系统 `internal/skills`

`skills/<name>/SKILL.md`（frontmatter + markdown）在启动时由 `skills.Registry` 加载，再通过 `use_skill` 工具暴露给规划器。**关键接线顺序**：`RegisterUseSkill` 必须在规划器首次编译 schema 之前运行（`main.go` 强制此序，否则 use_skill 不会进入三方不变量）。技能目录缺失非致命。当前内置 `code-review` 技能。

### 4.7 存储 `internal/store`

`Store` 接口，4 种实现（`store.type` 选择）：sqlite（默认，`data/agent.db`）/ postgres / redis / memory。

- `SaveFullTask` 原子持久化整个 `Task`（含 Trace / Memories / Status）。
- **并发安全**：`TryTransitionTaskStatus` 做原子状态迁移，防止两个 worker 抢同一任务（run-all 冲突 → HTTP 409）。
- `QueryMemories` 支持向量相似度召回（配合 `memory.GetEmbedding`）。
- `MemoryCandidateLimit`（默认 200）限制每次 RAG 预取时从磁盘加载的候选记忆行数，避免全表扫描——这是最近一次提交修复的"静默截断"点。

### 4.8 记忆 / RAG `internal/memory`

每个任务首步前，`Engine.Next` 从两路各取至多 5 条候选：第三方 HTTP RAG 端点（`rag.search_url`，可选）+ 本地 `Store.QueryMemories`（向量召回）。`DeduplicateMemories` 去重后裁到 3 条挂到 `task.Memories`。若 `task.Memories` 已填充则跳过这步工作。

### 4.9 安全策略 `internal/policy`

- `ValidateWorkspace`：拒绝 `.`/`/`、含 `..` 的原始路径；转绝对路径并解析所有符号链接组件；屏蔽系统敏感目录（`/etc`、`/proc`、`/sys`、`/dev`、`/root`、`/private/etc` 等）。
- 命令白名单：`rg/find/cat/python3/python/go/node/bash/sh/git`。
- URL 校验（`url_test.go` 覆盖）：用于 `http_fetch`/`web_search` 的出站 URL 允许列表。
- **约定**：任何读写路径或拉取 URL 的新工具都必须经过 policy。

### 4.10 API 层 `internal/api`

端点：创建/单步/批量运行、查询/列表（分页+状态过滤）、SSE 流、审批/拒绝、取消、metrics、config reload、ping。

并发与可靠性细节：
- **有界 worker 池**（`taskSem`，默认 10）控制并发，排队时也响应取消。
- `activeTasks` 用指针身份（`*activeRun`）作键，配合 compare-and-delete，防止 stale defer 清掉后续 run-all 重装的槽位。
- run-all **先占进程内槽位再做 DB 迁移**，冲突时无需回滚 DB。
- 后台 goroutine 用独立 `context.Background()` + 可配 `RunAllTimeoutSeconds`（默认 600s）墙钟预算，与引擎自身的 step/tool/token 预算独立。
- 优雅停机：`Shutdown` 取消所有活跃任务并等待 drain（10s 窗口）。
- 审批支持多 pending 消歧（需带 `approval_id`，否则 409 返回所有 pending ID）。

### 4.11 事件流 `internal/api/sse`

`Engine` 暴露四个回调（Event/Approval/Step/Token），`main.go` 全部接到 `api.GetBus()`，经 SSE `/api/tasks/:id/stream` 扇出。**SSE 是 best-effort**：handler 还每 15s 轮询 store 兜底，确保终态事件必达；并且 EventBus 缓存终态事件 5 分钟（最近一次提交）。需要权威状态的客户端应轮询 `GET /api/tasks/:id`。

### 4.12 可观测性 `internal/telemetry` + `internal/metrics`

`InitOTel` 导出 OTLP（traces + metrics）到 `127.0.0.1:4318`。所有引擎入口开 `engine.next*` / `engine.run_all` span，带 `agent.task.*` 属性。无 collector 时只打印 `[OTel Error]` 不影响功能（约定上不要加 `OTEL_*` 开关去静默它）。`metrics.Collector` 另维护本地指标快照（planner/executor/writer 时延、token 用量、完成/run-all 计数等），经 `GET /api/metrics` 暴露。

## 5. 关键设计模式与不变量

| 模式 / 不变量 | 体现位置 | 价值 |
| --- | --- | --- |
| 策略模式（编排模式选择器） | `Engine.Mode` + `run<Mode>Next` | 5 种编排策略可运行时切换，横切关注点不重复 |
| 插件注册表 ×3 | tools / planner provider / store | 注册即可用，开闭原则 |
| 注册表驱动的 Schema 生成 | `PlannerDecisionSchema` 从 registry 生成 | 消除"加工具要改 4 处"的漂移风险 |
| 装饰器（middleware） | `toolMiddleware`、`FallbackPlanner` | 超时/重试/降级横切，业务无感 |
| 双检锁缓存 | `einoMu` RWMutex、`adkOnce` | 编译一次、热路径无锁竞争、失败可重试 |
| 原子状态机迁移 | `TryTransitionTaskStatus` | 多 worker / 多实例并发安全 |
| 失败即观测 | executor / coordinator | 让规划器闭环自纠，仅 ctx 取消致命 |

## 6. 配置与运维

- **配置访问约定**：始终在使用点调 `config.Get()`，**绝不缓存指针**（配置可热重载）。优先用 `Resolve*` 辅助方法。
- **热重载三种途径**：SIGHUP、viper 文件 watcher（保存即生效）、`POST /api/config/reload`（返回脱敏 diff，API Key 显示为 `***`，支持密钥轮换不重启）。
- **环境变量**：前缀 `AI_AGENT_`，点转下划线（`llm.provider`→`AI_AGENT_LLM_PROVIDER`）；API Key 显式绑定到惯用名（`OPENAI_API_KEY` 等）。
- **默认值**：store=sqlite、mode=eino、max_concurrent_tasks=10、run_all_timeout=600s、llm.timeout=30s、tool.timeout=120s、memory_candidate_limit=200。

## 7. 优点评估

1. **关注点分离清晰**：编排/规划/执行/工具/策略/存储/可观测各成独立包，接口边界明确。
2. **扩展性强且防漂移**：三个注册表 + 注册表驱动 schema 生成，把"加能力"的成本降到最低，并用三方不变量 + `code-review` 技能显式守护。
3. **并发与竞争处理成熟**：指针身份槽位、原子状态迁移、独立持久化 ctx、有界 worker 池、优雅停机——多处都是对真实竞态打过补丁的痕迹。
4. **容错分层**：planner 降级、工具失败转观测、writer 失败如实标 FAILED、SSE 轮询兜底。
5. **可观测性完备**：OTel + 本地 metrics 双轨。

## 8. 潜在改进点（建议）

> 以下为基于静态阅读的观察，非确证缺陷，落地前需结合测试验证。

1. **审批状态的多实例可见性**：`SuspendForApproval` 的 approval channel 注册在进程内全局 map（`approval.go`）。多实例部署下，审批请求若被另一实例的 HTTP 接收，无法 resolve 对应 channel。若目标是水平扩展，审批通道需要外部化（如 Redis pub/sub）。
2. **并行批次的 token 预算时序**：`runBatchParallel` 一次性扣 `ToolBudget -= len(batch)`，但 token 预算闸 `tokenBudgetExhausted` 在批次开始前判断；理论上一个大并行批可在单轮内超出 token 预算。可考虑在批内做更细粒度的 token 估算。
3. **`cancelTask` 的跨实例语义**：不在本进程 `activeTasks` 中时，直接把 DB 标 `failed`——若任务正在另一实例运行，会出现状态与真实执行不一致。需要分布式取消信号。
4. **legacy 模式的静态路径函数**（`stepFindTextFiles` 等）疑似遗留代码，与 `runLegacyNext` 的 LLM 路径并存，可确认是否仍被引用，避免误导。
5. **memory 候选裁剪策略**：`MemoryCandidateLimit=200` 取"最近 200 行"再排序，对久远但高相关的记忆召回率有损；若召回质量重要，可引入近似向量索引（如 sqlite-vss / pgvector）替代全表近似。
6. **工具命令白名单较宽**：`bash`/`sh`/`go`/`node` 在白名单内，`execute_code` 的实际沙箱强度取决于工作空间隔离程度，生产环境建议进一步收紧或容器化隔离。
