## 1. OpenTelemetry Docker 配置分析

分析了 `deploy/opentelemetry/` 下的 Docker Compose、OpenTelemetry
Collector、Prometheus、Tempo、Jaeger 和 Grafana 配置，并与当前 Go 项目的遥测实现进行
了对照。

项目当前通过 OTLP/HTTP 向 `127.0.0.1:4318` 同时发送 traces 和 metrics，Collector
的 OTLP/HTTP receiver 与应用默认配置匹配。初始配置存在以下问题：

- Tempo 2.7.2 的 OTLP receiver 未显式监听容器网络接口，Collector 无法通过
  `tempo:4317` 跨容器发送 traces。
- Grafana 数据源 UID 是 `prometheus`，仪表盘引用的却是 `Prometheus`，导致面板找不
  到数据源。
- Compose 顶层 `version: "3.9"` 已废弃。
- Prometheus、Tempo、Grafana 和 Jaeger 缺少完整持久化方案。
- 宿主机端口默认绑定全部网络接口，且 Grafana 使用开发环境默认密码。
- `latest` 镜像标签、缺少 healthcheck、无 TLS/鉴权等问题使其不适合直接用于生产。
- 仪表盘只覆盖 planner/executor 等基础指标，尚未覆盖 LLM scene、token、成本、
  answer pipeline 和 multi-agent 指标。

结论：初始配置只能部分满足本地开发，不能开箱即用地提供完整 metrics 和 traces。

## 5. 数据持久化

Prometheus、Tempo、Grafana 和 Jaeger 均使用固定名称的 Docker 命名卷：

| 服务 | 命名卷 |
| --- | --- |
| Prometheus | `opentelemetry_prometheus-data` |
| Tempo | `opentelemetry_tempo-data` |
| Grafana | `opentelemetry_grafana-data` |
| Jaeger | `opentelemetry_jaeger-data` |

固定卷名不受 Compose 项目名变化影响。普通 `docker compose down` 只删除容器和网络，
不会删除这些命名卷；再次执行 `up -d` 会复用原有数据。

不得使用以下参数，除非明确要永久删除监控数据：

```text
--volumes
-v
```

讨论了命名卷与宿主机目录挂载的差异。对于当前 macOS 本地开发环境，命名卷在权限、
误修改风险和 Docker 文件系统性能方面通常更稳妥；宿主机目录挂载主要优势是文件可见、
手工备份和迁移方便，并不天然更安全。

## 6. Jaeger Badger 持久化权限修复

Jaeger 从默认内存存储改为 Badger：

```yaml
environment:
  - SPAN_STORAGE_TYPE=badger
  - BADGER_EPHEMERAL=false
  - BADGER_DIRECTORY_VALUE=/badger/data
  - BADGER_DIRECTORY_KEY=/badger/key
```

启动时出现错误：

```text
Failed to init storage factory
Error Creating Dir: "/badger/key"
mkdir /badger/key: permission denied
```

原因是 Jaeger 1.76 镜像以 UID `10001` 的非 root 用户运行，而新建命名卷根目录归
root 所有。

修复方案不是让 Jaeger 长期以 root 运行，而是增加一次性初始化服务
`jaeger-storage-init`：

- 使用 `busybox:1.37.0`。
- 以 root 创建 `/badger/data` 和 `/badger/key`。
- 将 `/badger` 及子目录所有者设置为 UID/GID `10001`。
- 初始化成功后退出。
- Jaeger 通过 `condition: service_completed_successfully` 等待初始化完成。
- Jaeger 本身继续以 `10001:10001` 运行。

`docker compose ps -a` 中 `jaeger-storage-init` 显示 `Exited (0)` 属于正常状态。

## 7. OTLP 外网访问讨论

Collector 容器内部已经监听 `0.0.0.0:4318`。如需让宿主机外部客户端连接，可以将
端口映射改为：

```yaml
ports:
  - "0.0.0.0:4318:4318"
```

外部客户端必须使用服务器实际 IP 或域名，例如：

```text
http://<server-ip>:4318
```

不能将客户端 endpoint 配置为 `0.0.0.0`。

当前 Collector 没有 TLS 和身份认证，因此不建议直接暴露到公网。推荐优先采用以下
方式：

- 绑定指定内网 IP。
- 通过 VPN、Tailscale 或 WireGuard 接入。
- 使用防火墙或云安全组限制客户端来源 IP。
- 在 Collector 前配置支持 HTTPS 和认证的反向代理。
- 只开放需要的 OTLP/HTTP 4318，不暴露 Prometheus、Grafana、Tempo 管理端口。

本次会话未将 4318 的宿主机绑定改为 `0.0.0.0`。

## 8. `teams.yaml` 与 Langfuse Prompt 启动同步分析

### 8.1 当前能力

项目已经支持运行时按以下顺序解析团队角色提示词：

```text
Langfuse prompt → teams.yaml system_prompt → 代码默认 prompt
```

相关实现：

- `internal/promptmanager/client.go`
- `internal/multiagent/teams.go`
- `internal/multiagent/prompt_binding.go`

现有 `PromptManager` 已支持：

- `GET /api/public/v2/prompts/{promptName}`。
- 按 `label` 或固定 `version` 获取。
- 默认使用 `production` label。
- 10 分钟内存缓存。
- Langfuse 获取失败时短期缓存本地 fallback。
- task 生命周期内将可移动 label 固定到实际版本。

当前缺口：

- 没有应用启动时的 Prompt 扫描和缓存预热。
- 没有调用 Langfuse `POST /api/public/v2/prompts` 创建 Prompt。
- HTTP 错误只有通用 `http status N`，无法可靠区分 404、401、429 和 5xx。
- `teams.yaml` 中多数 `prompt_name` 仍被注释。
- 仅配置 `system_prompt` 时，当前代码会直接使用本地提示词，不会访问 Langfuse。

### 8.2 推荐配置

需要为准备交给 Langfuse 管理的角色显式设置稳定名称：

```yaml
planner:
  prompt_name: "teams/software/planner"
  prompt_label: "production"
  system_prompt: |
    You are a software architect agent...
```

推荐命名规则：

```text
teams/{team-name}/{role}
```

Verifier draft 使用独立字段：

```yaml
draft_prompt_name: "teams/software-reviewed/verifier-draft"
draft_prompt_label: "production"
draft_system_prompt: |
  ...
```

### 8.3 推荐启动同步流程

```text
加载并严格校验 teams.yaml
        ↓
收集所有 prompt_name + system_prompt
        ↓
GET 指定 label/version
        ↓
200：使用远端 Prompt 并预热缓存
404：确认 Prompt 名称是否完全不存在
        ↓
POST /api/public/v2/prompts
        ↓
再次 GET，记录实际 version 并写入缓存
```

创建 text Prompt 的请求示例：

```json
{
  "type": "text",
  "name": "teams/software/planner",
  "prompt": "You are a software architect agent...",
  "labels": ["production"]
}
```

只有明确的“Prompt 完全不存在”才允许创建：

| 结果 | 建议行为 |
| --- | --- |
| `200` | 使用远端内容并预热缓存 |
| 指定 label 为 `404`，`latest` 也不存在 | 使用本地 `system_prompt` 创建 |
| 指定 label 为 `404`，但 `latest` 存在 | 标签缺失，报错，不自动覆盖 |
| 固定 version 为 `404` | 报错，不能创建指定服务端版本号 |
| `401/403` | 凭证或权限错误，禁止创建 |
| `429` | 限流，按策略重试或终止 |
| `5xx`/超时 | 服务不可用，禁止误创建 |
| 本地 Prompt 为空 | 配置错误，无法创建 |

### 8.4 推荐代码结构

建议新增：

```text
internal/promptmanager/bootstrap.go
internal/multiagent/prompt_catalog.go
```

建议接口：

```go
type Seed struct {
	Name    string
	Content string
	Label   string
	Version int
}

func (pm *PromptManager) EnsureTextPrompt(
	ctx context.Context,
	seed Seed,
) (ResolvedPrompt, bool, error)
```

Multi-agent 层负责扫描所有团队角色和 verifier draft，并检查同一 `prompt_name` 是否
对应不同本地内容。PromptManager 负责 Langfuse GET、POST、错误分类和缓存。

建议增加配置：

```yaml
langfuse:
  bootstrap_missing_prompts: false
  bootstrap_failure_policy: "fail"
  bootstrap_timeout_seconds: 15
```

启动同步应放在遥测初始化之后、HTTP 服务启动之前。

### 8.5 多实例风险

Langfuse 对同名 Prompt 再次 POST 会创建新版本。多个应用副本同时执行：

```text
GET 404 → POST
```

可能产生重复版本。

因此推荐：

- 单实例开发环境可在应用启动时创建。
- 多副本环境只允许一个 bootstrap 实例执行。
- 更稳妥的生产方案是增加独立的 `cmd/prompt-sync` 或部署前 Job。
- 普通业务实例只读取 Prompt，不拥有自动创建职责。

本次会话只完成了 Langfuse 启动同步的现状分析和设计，没有修改相关 Go 代码。

## 10. Langfuse Prompt 启动同步实施

继续完成了第 8 节设计的代码实现。

### 10.1 新增配置

`config.yaml` 和 `internal/config/config.go` 新增：

```yaml
langfuse:
  bootstrap_missing_prompts: false
  bootstrap_failure_policy: "fail"
  bootstrap_timeout_seconds: 15
```

对应环境变量：

```text
LANGFUSE_BOOTSTRAP_MISSING_PROMPTS
LANGFUSE_BOOTSTRAP_FAILURE_POLICY
LANGFUSE_BOOTSTRAP_TIMEOUT_SECONDS
```

自动创建默认关闭。开启后，`fail` 会在同步失败时阻止应用启动；`warn` 会记录警告并
继续使用本地 fallback。

### 10.2 PromptManager 创建能力

新增：

- `internal/promptmanager/bootstrap.go`
- `internal/promptmanager/bootstrap_test.go`

实现内容：

- `HTTPStatusError` 保留 Langfuse HTTP 状态码。
- `EnsureTextPrompt` 获取、确认缺失、创建和缓存 text Prompt。
- 只有请求 selector 返回 404，且 `latest` 也返回 404 时才允许创建。
- 401/403、429、5xx、超时都不会触发创建。
- 固定版本不存在时不会尝试创建指定版本。
- Prompt 已存在但缺少目标 label 时不会用本地内容覆盖。
- 创建接口使用 `POST /api/public/v2/prompts` 和 Basic Auth。
- 创建成功后立即写入现有 PromptManager TTL 缓存。
- 进程内使用互斥锁避免并发首次创建。

### 10.3 团队 Prompt 扫描

新增：

- `internal/multiagent/prompt_bootstrap.go`
- `internal/multiagent/prompt_bootstrap_test.go`

实现内容：

- `LoadTeamsConfigStrict`：启动同步时严格返回 teams.yaml 文件和解析错误。
- `TeamPromptSeeds`：按确定顺序收集所有显式 `prompt_name`。
- 支持 planner、critic、executor、verifier、researcher、writer 和 verifier draft。
- 同名 Prompt 使用不同 selector 或不同本地内容时立即报配置冲突。
- `BootstrapTeamPrompts` 顺序同步并返回 existing/created 统计。

### 10.4 启动接入
