# 统一答案审计 Pipeline 优化方案

> 版本：v2.2
>
> 日期：2026-07-17
>
> 定位：单智能体与 Multi-Agent 共用的最终实施基线

## 结论

当前生产主链路并非完全缺失 Multi-Agent 后置审计：`Engine.Next` 已在所有模式完成后统一执行 Citation、FactFreshness、NumericConsistency、Uncertainty 和 Output Guard。

真正的问题是：

- 审计逻辑仍是 `Engine` 中的私有方法顺序调用，尚未抽象成统一 Pipeline。
- `Coordinator.Run` 本身只产出 Writer 答案，直接调用会绕过后置审计。
- 审计仅在 `err == nil && StatusCompleted` 时触发，Partial、带可用答案的降级结果和 Writer 失败摘要不会审计。
- 各阶段因预算、Scene 关闭或前置条件不满足而跳过时，没有统一的“跳过原因”记录。
- Freshness 与 Numeric 可以并行，但当前串行；Uncertainty 正确地依赖二者，却没有显式依赖模型。
- 当前幂等性只检查 Trace 中是否出现过 action；答案被重写后再次执行时，可能错误复用旧审计结论。
- Multi-Agent Writer 自带的 `confidence` 和 Verifier，与最终 UncertaintyCalibrator 存在两套置信度语义。

因此建议建设统一的 `AnswerPipeline`，以“编排器产生 Draft、Pipeline 审计、发布层决定是否对外返回”为核心边界。

本方案遵循以下约束：

- 不在 `multiagent` 内复制后置审计实现，所有模式共用同一发布出口。
- Pipeline Stage 只分析不可变快照，不并发修改 `types.Task`。
- 审计与发布分离：有答案不代表可发布，执行错误也不代表可以跳过输出安全检查。
- `not_applicable` 是正常结果，不等同于 disabled、budget insufficient 或 failed。
- P0 默认采用 observe 模式，保持现有任务状态和答案行为不变。
- 配置在使用点通过 `config.Get()` 获取，不缓存热加载配置指针。

## 一、目标架构

```text
Single-Agent / Eino / ADK / Step / Multi-Agent
                       │
                       ▼
                 Answer Draft
                       │
             Unified AnswerPipeline
                       │
        ┌──────────────┴──────────────┐
        │  Citation / evidence binding │
        └──────────────┬──────────────┘
                       ▼
        Freshness ───────── Numeric Audit
                 （可并行）
                       │
                       ▼
             Uncertainty Calibration
                       │
                       ▼
                Output Safety Guard
                       │
                       ▼
          Published FinalAnswer + AuditReport
```

角色层职责应明确分开：

- Planner：只负责计划质量。
- Researcher：执行 Prompt Injection、相关性过滤、冲突与来源可信度处理。
- Writer：只生成候选答案，不把自身 `confidence` 当作最终置信度。
- AnswerPipeline：对最终候选答案做时效、数字、一致性、不确定性和输出安全审计。

不建议对每条 Researcher 输出分别运行 FactFreshnessChecker 或 UncertaintyCalibrator，否则会造成重复 Token 消耗，而且局部证据的“不确定”不等于最终答案的不确定。

## 二、Pipeline 接口设计

### 2.1 包依赖边界

新增 `internal/answerpipeline`，但审计报告等纯数据模型必须放在 `internal/types`，避免形成 `types -> answerpipeline -> types` 的 Go import cycle：

```text
internal/types
      ▲
      │
internal/answerpipeline
      ▲
      │
internal/orchestrator
```

建议新增：

- `internal/types/answer_audit.go`：`AnswerAuditReport`、`AnswerAuditStage`、`AnswerAuditFinding`。
- `internal/answerpipeline/stage.go`：Stage 和不可变输入模型。
- `internal/answerpipeline/pipeline.go`：编排、预算、状态归并和统一 Apply。
- `internal/answerpipeline/*_stage.go`：现有 Checker/Calibrator 的薄适配器。

### 2.2 Stage 接口

```go
type Eligibility string

const (
	EligibilityApplicable         Eligibility = "applicable"
	EligibilityNotApplicable      Eligibility = "not_applicable"
	EligibilityDisabled           Eligibility = "disabled"
	EligibilityBudgetInsufficient Eligibility = "budget_insufficient"
	EligibilityDependencyFailed   Eligibility = "dependency_failed"
)

type Stage interface {
	Name() string
	DependsOn() []string
	Eligible(ctx context.Context, input Input) (Eligibility, string)
	Run(ctx context.Context, input Input) Result
}

type Input struct {
	TaskID         string
	TenantID       string
	Goal           string
	DraftAnswer    string
	Evidence       []EvidenceSnapshot
	PriorFindings  []types.AnswerAuditFinding
	EvidenceDigest string
	Orchestrator   string
	ReferenceTime  time.Time
}

type Result struct {
	Stage       string
	Status      Status
	Reason      string
	Answer      string
	TokenUsage  types.TokenUsage
	Findings    []types.AnswerAuditFinding
	Fingerprint string
}

type Pipeline interface {
	Process(ctx context.Context, task *types.Task, mode string) (*types.AnswerAuditReport, error)
}
```

`Input` 不携带 `*types.Task`，从接口层阻止并行 Stage 修改共享 Task。Stage 只返回 `Result`；Trace、FinalAnswer 和 AuditReport 的更新全部由 Pipeline 按固定顺序串行完成。

`Eligible` 必须保持为纯本地、无 I/O 判断：只读取本次 `Process` 已解析好的配置、Stage 依赖结果和 Input，不得访问远程租户配置或调用 LLM。所有可能失败的 I/O 和模型预检都放入 `Run`，通过 `Result.Status/Reason` 返回。这样无需给 `Eligible` 增加独立 error 通道，也不会把真实故障误报为 `disabled`。

`Pipeline` 负责通用能力：

- 阶段排序和依赖检查。
- Scene enablement。
- Task/租户 LLM 预算检查。
- Trace、Metrics 和 OpenTelemetry 统一记录。
- 超时、取消和错误策略。
- 基于答案及证据摘要的幂等性。
- 最终答案变更的原子提交。
- 审计发现的统一枚举、长度限制和敏感信息清理。

原有 Checker/Calibrator 不需要重写，只需增加适配器：

```go
NewFreshnessStage(factfreshness.Checker)
NewNumericStage(numericconsistency.Checker)
NewUncertaintyStage(uncertainty.Calibrator)
```

Citation 和 Output Safety 也可适配为 Stage，但 P0 应先迁移现有三个答案审计模块；待行为对齐后再迁移会改写答案的 Citation/Safety，降低一次性改造风险。

## 三、推荐执行顺序

Pipeline 内部维护私有滚动状态；每个执行层开始前由当前状态生成新的不可变 Input：

```go
type pipelineState struct {
	currentAnswer string
	findings      []types.AnswerAuditFinding
	evidence      []EvidenceSnapshot
}
```

1. `citation_verify`

   先修正引用和不受支持的声明。Citation 返回新答案后，Pipeline 更新 `pipelineState.currentAnswer`，再为后续阶段生成 Input；Freshness/Numeric 不得继续使用 `Process` 开始时的旧 Draft。

2. `fact_freshness_check` 与 `numeric_consistency_check`

   两者读取同一个不可变 Draft 和 Evidence Snapshot，可以并行运行。不要让并行 Stage 直接修改 `task.Trace`，而应先返回结果，再由 Pipeline 按固定顺序 Apply，避免数据竞争。

3. `answer_uncertainty_calibrate`

   必须等待前两个阶段完成。Pipeline 把 Freshness/Numeric Findings 合并进滚动状态，再生成新的 Input 调用 Uncertainty；不能复用并行阶段启动前的旧 `PriorFindings`。

4. `safety_guard_output`

   最后执行，审查 Citation 改写及置信度限定后的完整文本。Safety 改写结果是最终 `currentAnswer`，随后才能计算 `Publishable`。

Code Review/Test Generation 建议保留为任务质量 Gate，不混入 AnswerPipeline；它们和“答案事实审计”属于不同职责。

现有 Checker 接口仍接收 `*types.Task`。适配器过渡期可从 Input 构造深拷贝的 Task Snapshot 调用 `Check/Calibrate`，但禁止把 Snapshot 或 Checker 的 Apply 结果直接写回共享 Task；Pipeline 负责将结构化 Result 统一落入真实 Task。

## 四、Multi-Agent 接入方式

将 `Coordinator.Run` 定义为“生成 Draft”，不要在 Coordinator 内复制 Freshness/Numeric/Uncertainty 实现。

建议调整语义：

```go
type DraftProducer interface {
	Produce(ctx context.Context, task *types.Task) error
}

func (e *Engine) Next(...) error {
	produceErr := e.produceDraft(ctx, task)
	// 先把 LLM budget、Writer failure 和普通执行错误归一化为最终
	// Status/FinalAnswer，不能继续依赖在 Pipeline 之后运行的 defer。
	executionErr := e.normalizeExecutionOutcome(task, produceErr)
	if shouldAudit(task) {
		report, auditErr := e.AnswerPipeline.Process(ctx, task, string(e.Mode))
		applyPipelineOutcome(task, report, auditErr)
	}
	if shouldPublish(task) {
		return executionErr
	}
	return combineExecutionAndAuditError(executionErr, task.AnswerAudit)
}
```

必须将两个判断分开：

```go
// shouldAudit：只要 FinalAnswer 可能进入 API、SSE、Memory 或日志摘要，
// 至少生成 Report，并执行适用的 Output Safety。
func shouldAudit(task *types.Task) bool

// shouldPublish：在 Pipeline 完成后，根据安全结果、执行错误和 enforcement
// 决定答案能否对外返回。
func shouldPublish(task *types.Task) bool
```

判定骨架：

```go
func shouldAudit(task *types.Task) bool {
	if task == nil || strings.TrimSpace(task.FinalAnswer) == "" {
		return false
	}
	return task.Status != types.StatusRunning &&
		task.Status != types.StatusAwaitingApproval &&
		task.Status != types.StatusPaused
}
```

`shouldPublish` 必须在 Pipeline 后执行，并至少检查 `AnswerAudit.Publishable`、Output Safety 结果和 enforcement。`StatusFailed` 但有 fallback 的任务仍应审计，是否返回文本由发布策略决定；`StatusFailed + 空答案` 不审计也不发布。

当前 `Engine.Next` 在入口直接返回 Completed/Partial/Failed，显式 re-audit 不能复用 `Next`，应提供独立方法或 API。重构时还应移除事实上恒为 false 的 `wasCompleted` 分支。

不能再用 `err == nil || StatusPartial` 作为审计条件，否则 `StatusFailed` 但带 fallback 答案的 Writer 失败路径仍会绕过输出安全检查。

当前 Multi-Agent Writer 失败会先写入 research fallback，随后 Engine 的错误 defer 再调用 `SetTaskFailed`，把它覆盖成 `Failed: <provider error>`。`normalizeExecutionOutcome` 必须统一决定最终 Status、FinalAnswer 和返回错误，只执行一次；Pipeline 审计的是归一化后的最终文本，不能审计随后还会被覆盖的中间 fallback。

具体改动：

- `Engine` 中三个独立 Checker 字段逐步替换成 `AnswerPipeline`。
- `cmd/server/main.go` 只构造一次 Pipeline，不再分别向 Engine 挂载 Checker。
- Multi-Agent Writer 继续写入 `task.FinalAnswer` 作为 Draft；Pipeline 完成后才视为 Published Answer。
- `Coordinator.Run` 若继续保持公开，应在注释和类型命名上明确它不会发布已审计答案；更稳妥的是只通过 Engine 暴露生产执行入口。
- Multi-Agent `VerifierAgent` 的 schema 改为结构化 Issue，至少支持 `unsupported_claim`、`evidence_gap`、`contradiction`，并转换为 Pipeline 的 InitialFindings。不能只把字符串 Issues 拼入 Writer EvidenceSummary，因为当前 Uncertainty evidence catalog 不读取 `write` Trace。
- Writer 的 `confidence` 改名为 `draft_confidence`，仅用于是否触发补充检索，不作为 API 最终置信度。
- Verifier 继续属于 Writer/Draft 阶段，因为它会影响 adaptive replan；其 Token/Call/Cost 继续计入生成预算。只有未来取消重规划用途时，才考虑迁入 Audit Reserve。
- 输入 Safety Guard 产生的拒答也生成 Pipeline Report，但不重复调用 Output Safety：`safety_guard_output` 记录 `passed/covered_by_input_guard`，事实类 Stage 返回 `not_applicable`。预算终止摘要和 Writer fallback 则在错误归一化后执行正常适用的 Output Safety。
- `runCodeQualityGates` 保留在 Engine，不进入 AnswerPipeline，因为它依赖 Workspace 变更而非纯答案审计。

## 五、状态与失败策略

### 5.1 Stage 状态

每个 Stage 必须产生一个明确结果：

| 状态 | 含义 | 是否满足 required stage |
|---|---|---|
| `passed` | 审计完成且未发现风险 | 是 |
| `warned` | 审计完成并发现风险 | 是 |
| `not_applicable` | 答案不包含该类声明 | 是 |
| `disabled` | Scene 或 Pipeline 配置关闭 | 由 enforcement 决定 |
| `budget_insufficient` | Token/调用/费用预算不足 | 否 |
| `dependency_failed` | 依赖 Stage 未完成 | 否 |
| `failed` | Provider、校验或内部执行失败 | 否 |

不要使用含义模糊的通用 `skipped`。Numeric 对无数字答案、Freshness 对非时效答案属于 `not_applicable`，不应导致任务降级。

### 5.2 Stage 失败策略

建议按 Stage 类型区分处理：

| Stage | 默认失败策略 | 对答案影响 |
|---|---|---|
| Citation | fail-open + warning | 保留原答案 |
| Freshness | fail-open + audit_unknown | 不直接改写答案 |
| Numeric | fail-open + audit_unknown | 不直接改写答案 |
| Uncertainty | fail-open + deterministic fallback | 必要时追加审计未完成说明 |
| Output Safety | 按现有安全策略 | 可替换或拒绝输出 |

状态范围建议扩展为：

- `Completed`：Pipeline 成功，或所有适用阶段成功。
- `Partial`：已有可用答案，但必需审计因预算、超时或 Provider 故障未完成。
- `Failed`：没有可发布答案，或严格安全策略拒绝发布。

不要因为发现 stale 或 numeric inconsistency 就直接把任务标为 Failed；默认应保留答案并附加明确限定。可通过严格模式配置决定是否转为 Partial。

### 5.3 灰度执行策略

新增三档 enforcement：

| 模式 | 行为 |
|---|---|
| `observe` | 记录 Report/Trace/Metrics，不改变现有答案和任务状态 |
| `advisory` | 可追加风险限定说明；必需 Stage 失败时转 `Partial`，不直接拒绝答案 |
| `strict` | 按 required stage 与安全策略决定 `Partial`、`Failed` 或拒绝发布 |

P0 默认 `observe`，否则“必需 Stage 失败转 Partial”会破坏零行为回归。灰度稳定后再按租户切换到 `advisory` 或 `strict`。

## 六、预算保障

目前各 Checker 单独调用 `AllowedForTask`。Writer 消耗完预算后，关键审计可能被静默跳过。

建议新增：

```yaml
answer_pipeline:
  enabled: true
  enforcement: observe
  required_stages:
    - fact_freshness_check
    - numeric_consistency_check
    - answer_uncertainty_calibrate
    - safety_guard_output
  audit_token_reserve: 4000
  stage_timeout: 20s
  parallel_audits: true
  on_required_stage_failure: partial
  stage_token_budgets:
    citation_verify: 600
    fact_freshness_check: 900
    numeric_consistency_check: 900
    answer_uncertainty_calibrate: 1000
    safety_guard_output: 600
```

执行阶段可使用的有效预算应为：

```text
effective_generation_budget =
    task.token_budget - answer_pipeline.audit_token_reserve
```

Reserve 只供 Pipeline 使用。生成阶段的所有模式必须使用 effective generation budget，不能只在任务创建时修改一个字段，否则 Eino/Legacy/ADK/Multi-Agent 的预算判断仍可能消费审计预留。

预算权威边界必须保持单一：

- Pipeline 的本地 `auditBudget` 只划分 Task TokenBudget，并为并行 Stage 分配 Token 租约。
- `llm.Runtime` 继续作为 LLM Call、实际 Cost 和租户额度的唯一 source of truth；不要在 Pipeline 内再维护一套独立累计账本。
- `AllowedForTask` 只是基于 Trace 和 `MinRemainingTokens` 的 Token 门槛，不是 Call/Cost 检查；Stage 真正调用模型时仍必须经过 Runtime 的 `ReserveTaskLLMCallForConfig` 和 `RecordTaskLLMCost`。
- 不建议直接修改 `task.TokenBudget` 扣除 Reserve，应通过 phase-aware budget context 给生成阶段暴露 effective generation budget，同时保留 Task 的原始总预算语义。

Freshness/Numeric 并行时，不能让两个 Stage 同时看到相同的全部剩余 Token。推荐在启动 goroutine 前分配独立租约：

```go
lease, ok := auditBudget.ReserveTokens(stage.Name(), configuredStageBudget)
if !ok {
	return Result{Status: StatusBudgetInsufficient, Reason: "audit budget lease denied"}
}
defer lease.Commit(actualUsage.TotalTokens)
```

`auditBudget` 使用 Mutex 保护读改写；`configuredStageBudget` 来自 `stage_token_budgets`，不依赖运行时猜测。超额或未使用部分按明确策略结算，且两个并行 Stage 的租约合计不能超过 Audit Reserve。

当前 Runtime 在调用前原子预留调用次数，但实际费用在调用完成后登记。并行调用在 Cost 接近上限时可能同时通过检查并最终超额，因此应在费用余量不足时自动退化为串行；长期可在 Runtime 增加“预估费用预留、实际费用结算”，而不是在 Pipeline 重复实现 Cost 账本。

若总预算低于 Reserve，应提前记录 `insufficient_audit_budget`。在 `observe` 模式仅记录；在 `advisory/strict` 模式按 required stage 策略处理。

优先级建议：

1. Output Safety
2. Fact Freshness
3. Numeric Consistency
4. Uncertainty
5. Citation 修复或其他增强型 Stage

该优先级用于预算退化，不表示执行顺序；执行顺序仍为 Citation → Freshness/Numeric → Uncertainty → Output Safety。

## 七、幂等性、数据模型与持久化

当前 `AlreadyChecked` 仅判断 Trace 中是否存在固定 action。建议改为审计指纹：

```text
fingerprint =
SHA256(stageVersion + finalAnswer + evidenceDigest + referenceDate)
```

其中 Freshness 必须包含审计日期，否则跨日期恢复任务时会错误复用旧结论。

`evidenceDigest` 使用审计器实际消费的、有边界 Evidence Snapshot 计算，规则必须与输入顺序无关：

```text
contentHash = SHA256(sanitizeAndBound(content))
itemKey = canonical(action, path, query, provenance) + ":" + contentHash
evidenceDigest = SHA256(join(sort(all itemKey)))
```

- 不直接 Hash 无边界的原始 RAG/Trace 内容。
- 没有显式 SourceID 时用 action/path/query/provenance 构造稳定键，不能退化为数组 index。
- 重复 itemKey 按 multiset 保留数量，避免重复证据与单条证据得到相同 Digest。
- StepCount、AgentRole、到达顺序等非证据语义字段不进入 Digest。

### 7.1 数据模型

报告类型放在 `internal/types`，不要定义在 `answerpipeline` 后再由 `types.Task` 反向引用：

```go
type AnswerAuditReport struct {
	PipelineVersion string
	DraftHash       string
	EvidenceHash    string
	StartedAt       time.Time
	CompletedAt     time.Time
	FinalConfidence string
	Enforcement     string
	Publishable     bool
	Stages          []AnswerAuditStage
}

type AnswerAuditStage struct {
	Name        string
	Status      string
	Reason      string
	Fingerprint string
	Findings    []AnswerAuditFinding
	TokenUsage  TokenUsage
	DurationMS  int64
}

type AnswerAuditFinding struct {
	Kind     string
	Detail   string
	SourceID string
}
```

Finding 的 Kind 使用受控枚举，Detail/SourceID 必须经过 `sanitize.Secrets`、长度限制和来源校验，不持久化完整答案片段。

`types.Task` 增加：

```go
AnswerAudit *AnswerAuditReport `json:"answer_audit,omitempty"`
```

`StepTrace` 继续保留简要可观测记录，完整结果进入 `AnswerAuditReport`。API 可增加可选字段 `answer_audit`，但不改变现有 `final_answer` 字段。

### 7.2 持久化改造

仅给 Task 增加字段不会自动完成持久化；SQLite/PostgreSQL 当前使用显式列保存和扫描。必须同步修改所有 Store：

- SQLite：增加 `answer_audit_json TEXT NOT NULL DEFAULT '{}'` 兼容迁移，并更新 Insert/Update/Select/Scan。
- PostgreSQL：增加 `answer_audit_json JSONB NOT NULL DEFAULT '{}'::jsonb`，并更新 Insert/Update/Select/Scan。
- Redis：继续使用 Task JSON，但需确认 Lua 更新、快照复制和旧 JSON 解码兼容。
- MemoryStore：Save/Get/List 都必须深拷贝 Report、Stages、Findings，避免调用方修改读取结果后污染 Store。
- List/Get/SaveFullTask 都必须覆盖，不能只修改单任务保存路径。

建议新增统一的 `cloneTask`/`CloneTask` 辅助函数，不要在各 Store 零散复制字段。除 AnswerAudit 外还必须覆盖当前已有的嵌套引用：

- `Task.Trace`、`StepTrace.Evidence`、`Evidence.Lines`。
- `Task.Memories`、`Memory.Embedding`。
- `Task.Unresolved`。
- `AnswerAudit.Stages`、`AnswerAuditStage.Findings`。

该辅助函数同时用于 MemoryStore 的 Save/Get/List、SQLite/PostgreSQL/Redis 的异步 Memory 索引快照，以及现有 Checker 适配器构造只读 Task Snapshot。Redis/SQL 正常读取通过 JSON/Scan 已获得独立对象，但异步 `taskSnap` 仍需完整深拷贝。

旧数据中字段为空或 `{}` 时视为“尚未审计”，不得视为解析失败。

### 7.3 幂等缓存边界

同一 fingerprint 可复用 Stage 结果；但必须满足：

- Pipeline/Stage 版本一致。
- DraftHash、EvidenceHash 一致。
- Freshness 的 reference date 一致。
- enforcement 变化不会错误复用旧的发布决策。

已完成任务不会自动再次进入 `Engine.Next`，因此跨日期 Freshness 重审还需要显式 re-audit API 或后台作业；仅把日期加入 fingerprint 并不会主动触发重审。

## 八、配置与依赖注入

`cmd/server/main.go` 只构建一次 Pipeline 和 Stage 依赖：

```go
pipeline := answerpipeline.New(
	answerpipeline.WithStages(
		answerpipeline.NewCitationStage(citationVerifier),
		answerpipeline.NewFreshnessStage(freshnessChecker),
		answerpipeline.NewNumericStage(numericChecker),
		answerpipeline.NewUncertaintyStage(uncertaintyCalibrator),
		answerpipeline.NewSafetyStage(safetyGuard),
	),
	answerpipeline.WithMetrics(mc),
	answerpipeline.WithConfigProvider(func() answerpipeline.Config {
		return answerpipeline.ConfigFrom(config.Get().AnswerPipeline)
	}),
)
eng.AnswerPipeline = pipeline
```

不得把 `config.Get()` 返回的指针或 `cfg.AnswerPipeline` 快照长期保存在 Pipeline。`Eligible`、预算分配和 enforcement 判断都应在每次 `Process` 时读取当前配置，以保持热加载语义。

新增配置时必须同步覆盖 `Config` 数据结构、Viper 默认值/环境绑定、clone、Validate 和 `diffConfigs`，确保 `/api/config/reload` 能原子切换 enforcement、Stage 预算和 required stages，并在响应 diff 中可见且不泄露敏感值。

迁移期 Engine 可保留旧 Checker 字段作为兼容入口，但必须保证同一任务只走旧链路或 Pipeline 之一，不能双重审计。建议通过构造函数集中装配，而不是依赖测试或调用者手工填充多个字段。

## 九、可观测性

统一输出以下指标：

- `answer_pipeline_runs_total{mode,status}`
- `answer_pipeline_stage_total{stage,status,reason}`
- `answer_pipeline_stage_duration_seconds{stage}`
- `answer_pipeline_stage_tokens_total{stage}`
- `answer_pipeline_stage_not_applicable_total{stage}`
- `answer_pipeline_stage_skipped_total{stage,reason}`
- `answer_pipeline_warning_total{kind}`
- `answer_pipeline_confidence_total{level,mode}`

`stage_skipped_total` 的 reason 只允许 `disabled`、`budget_insufficient`、`dependency_failed`；正常业务分布 `not_applicable` 单独统计，不能进入异常跳过告警。

每个 Pipeline Span 应包含：

- `task.id`
- `tenant.id`
- `orchestrator.mode`
- `pipeline.version`
- `stage.name`
- `stage.status`
- `answer.changed`
- `audit.fingerprint`

不要记录完整答案或证据正文，避免敏感信息进入遥测系统。

## 十、测试方案

### 单元测试

新增 `internal/answerpipeline` 测试：

- Stage 拓扑排序和依赖环检测。
- Freshness/Numeric 并行执行，Apply 顺序确定。
- Uncertainty 必须看到前两项 Finding。
- Citation 改写答案后，Freshness/Numeric 收到的是新的滚动答案快照。
- Scene disabled、not applicable、budget insufficient、dependency failed、timeout、cancel。
- Stage panic 隔离。
- fail-open、partial、strict 三种策略。
- 同一指纹不重复运行。
- 答案或证据变化后重新审计。
- Freshness 跨审计日期重新运行。
- 并行 Stage 无法修改 Task，且不会产生 Trace 数据竞争。
- 并行预算租约不会让两个 Stage 共同突破 Reserve。
- Cost 余量不足时并行组自动退化为串行。
- enforcement 热加载后下一次 Process 立即生效。
- Finding 枚举、长度、Secret 清理和非法 SourceID 校验。

- 完成答案包含 `fact_freshness_check`、`numeric_consistency_check`、`answer_uncertainty_calibrate` Trace。

- `/api/config/reload` 后，下一个 HTTP 任务立即使用新的 enforcement。

## 十一、分阶段落地

### P0a：数据模型与 Store 先行

- 在 `internal/types` 新增审计数据模型，避免 import cycle。
- 实现统一 `cloneTask`，覆盖 Trace Evidence/Lines、Memories/Embedding 和 AnswerAudit 嵌套字段。
- 先完成 SQLite/PostgreSQL/Redis/MemoryStore 的 schema、Save/Get/List、异步快照、深拷贝及旧数据迁移。
- 验证空值和 `{}` 被识别为“尚未审计”，不会导致旧任务读取失败。
- Store round-trip、旧数据兼容和别名隔离测试全部通过后，才能进入 P0b。

### P0b：统一出口 observe 上线

- 新增 `answerpipeline.Pipeline`、不可变 Input、滚动 pipelineState 和 Stage 接口。
- 先封装现有 Freshness、Numeric、Uncertainty，保持串行执行。
- 重构 Engine：`produceDraft -> normalizeExecutionOutcome -> shouldAudit -> Pipeline -> shouldPublish`，不再让 defer 在审计后覆盖状态或答案。
- Input Guard 拒答生成 Report 但复用已有安全判定，不重复调用 Output Safety。
- enforcement 默认 `observe`，保持原有答案和任务状态；`answer_audit` 是唯一允许的向后兼容新增响应字段。
- 增加 Pipeline 调用一次、Citation 滚动快照、错误归一化、Store 保存恢复和旧字段兼容测试。

### P1：补齐 Multi-Agent 语义

- 明确 Coordinator 只生成 Draft。
- 将 Writer confidence 改为内部检索信号。
- 将 Verifier schema 改为结构化 Issues，并作为 Pipeline InitialFindings；Verifier 保留在生成预算和 adaptive replan 链路。
- 增加 Multi-Agent 端到端审计测试。
- 覆盖安全拒答、Writer fallback、Partial 和预算终止答案。

### P2：预算、并发与幂等性

- 引入 phase-aware Token Reserve，Runtime 继续作为 Call/Cost/租户额度唯一权威。
- 使用并发安全的 Stage Token 租约并行 Freshness/Numeric，费用余量不足时退化串行。
- 评估 Runtime 的预估费用预留/实际费用结算，解决并行调用的 Cost 超额窗口。
- 增加答案/证据/日期指纹。
- 对跳过、失败和降级原因进行结构化记录。
- 引入 `not_applicable`、`dependency_failed`，移除模糊 `skipped`。
- 验证指纹缓存可跨进程生效，且并行预算不能超出任务或租户配额。

### P3：产品化

- 正式文档化 `answer_audit` API，并补充分页查询、管理端审计筛选和访问控制。
- 增加严格审计策略和租户级覆盖配置。
- Dashboard 展示各模式审计覆盖率、低置信度率和 Stage 失败率。
- 增加显式 re-audit API 或后台任务，支持跨日期 Freshness 重审。

最终验收标准应是：所有编排模式中，凡是可能对外发布或进入长期 Memory 的非空答案，都必须拥有一份可追溯的 Pipeline Report；任何必需 Stage 未运行，都能明确回答“为什么没运行”；并发审计不能突破任务或租户预算，Report 经所有 Store 保存和恢复后语义不变。
