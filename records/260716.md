# 2026-07-16 JIT RAG 路由与任务预算优化记录

## 背景

在任务“数学科学术顾问有哪些”的真实运行中，JIT 路由已经能够正确选择第三方 RAG，但暴露出以下问题：

1. 第一次运行时 RAG 返回空结果，任务如实停止，但 MCP `structuredContent` 尚未被解析，无法完全区分“服务端确实无结果”和“客户端遗漏结构化结果”。
2. 查询改写后能够召回文档，但执行链形成了三轮 `rag_search -> rag_fetch`，耗尽 `max_steps=6` 和 `tool_budget=6`，没有为最终答案预留机会。
3. 第 4、6 步的 `rag_fetch` 本可确定性执行，却再次调用 Gemini Planner，额外消耗约 2969 Token。
4. 相似查询通过增加空格以及“成员、老师、名单”等泛化词绕过重复查询限制。
5. 预算耗尽后的结果被标记为 `completed`，与实际“部分完成”不符。
6. 日志出现 `mode:""` 和 `primary planner succeeded`，无法准确表达默认 Eino 模式及确定性 JIT 路由来源。

## 运行日志分析结论

原执行链为：

```text
step 1: rag_search（确定性 JIT 路由）
step 2: rag_fetch（确定性 JIT 路由）
step 3: Gemini 决定执行第二次 rag_search
step 4: Gemini 决定执行第二次 rag_fetch
step 5: Gemini 决定执行第三次 rag_search
step 6: Gemini 决定执行第三次 rag_fetch
step 7: 进入预算检查，因 step_count=6、tool_budget=0 而停止
```

本次 RAG 已通过 `result.content[].text` 返回 20KB～48KB 的片段，并成功生成候选和执行 `rag_fetch`，因此最终没有答案的直接原因是检索循环和预算控制，而不是 MCP 请求失败。

Token 汇总符合 Gemini 返回的 `TotalTokenCount`。`total_tokens` 不一定严格等于 `prompt_tokens + completion_tokens`，其中可能包含模型内部推理等由 Provider 计入总量的 Token。

## 已实施优化

### 1. 外部事实查询确定性预路由

对于 JIT 模式下的外部事实查询，在调用 Provider 之前直接生成检索决策：

```text
外部事实查询且无证据 -> rag_search
rag_search 返回候选 ID -> rag_fetch
取得详情证据 -> 交由 LLM 判断回答或继续检索
```

首轮 `rag_search` 和对应的 `rag_fetch` 不消耗 Planner Token。

核心实现：

- `internal/planner/jit_policy.go`
- `internal/planner/llm.go`
- `internal/multiagent/coordinator.go`

### 2. 修复“历史证据关闭确定性 fetch”问题

旧逻辑只要任务历史中存在任意成功证据，就完全关闭确定性 JIT 路由，导致第二轮、第三轮搜索后的 fetch 重新交给 Gemini 决定。

新逻辑改为检查：

```text
最新一次 rag_search / memory_search 是否已有后续对应的 fetch/get
```

如果最新搜索尚未读取详情，则直接执行：

```text
rag_fetch / memory_get
```

因此每轮新的搜索都能自动读取候选详情，不受更早证据影响。

### 3. Planning Prompt 工具裁剪

外部事实查询的 Planning Prompt 不再暴露以下工作区工具：

```text
find_files
search_text
read_file
write_file
execute_code
```

仅保留 RAG、Memory、Web 等与外部事实检索相关的工具，降低 Planner 漂移到文件搜索或代码执行的概率。

Prompt 同时明确：

- 仅当目标明确涉及本地文件、代码库、项目或工作区时使用文件工具。
- 不得仅为解析、排序或汇总检索结果而调用 `execute_code`。
- 有证据且剩余动作容量不超过 2 时，不得启动新的检索周期，应使用现有证据回答，并在必要时声明不确定性。

核心实现：

- `internal/planner/prompt.go`
- `internal/multiagent/planner_agent.go`

### 4. 为最终答案预留执行容量

Planning Prompt 新增：

```text
remaining_action_capacity = min(max_steps - step_count, tool_budget)
```

当满足以下条件时，Orchestrator 会阻止继续扩大检索：

```text
已有支持证据
remaining_action_capacity <= 2
Planner 仍计划 rag_search 或 memory_search
```

此时优先调用 Task Finalizer，使用已有证据生成自包含答案。若到达步骤或工具预算边界时已有证据，也会再次尝试最终合成。

核心实现：

- `internal/orchestrator/eino.go`
- `internal/orchestrator/engine.go`

说明：预算边界的独立最终合成依赖 `llm.scenes.task_finalizer`。未启用该 Scene 时，主要依赖 `task_planner` 根据剩余容量规则直接停止并回答。

### 5. 限制检索轮次

默认未缓存检索调用上限从 3 次调整为 2 次：

```yaml
rag:
  jit_search_max_calls: 2
```

涉及配置：

- `config.yaml`
- `config_zh.yml`
- `internal/config/config.go`

环境变量仍可覆盖：

```text
AI_AGENT_RAG_JIT_SEARCH_MAX_CALLS
```

### 6. 相似查询去重

检索缓存增加查询归一化和相似判断：

- 忽略大小写、空格和标点。
- 移除“有哪些、有哪个人、成员、老师、名单、查询、搜索”等非核心检索词。
- 对包含关系和高相似字符 bigram 进行判定。
- RAG 与 Memory 查询保持独立，不跨检索源复用。

查询去重只针对明显的重复扩写。类似“数学科学术顾问”与“数学 学术顾问”这种可能改变召回结果的查询不会被强制合并。

核心实现：

- `internal/tools/retrieval.go`

### 7. 新增 `partial` 任务状态

新增终态：

```json
{
  "status": "partial"
}
```

适用场景：

- 步骤或工具预算耗尽且无法生成完整答案。
- Token 预算耗尽。
- LLM 调用或费用预算耗尽。

`partial` 已被 API、异步 RunAll 和 SSE 识别为终态，不再错误返回 `completed`。只有真正生成完整答案时才标记为 `completed`。

核心实现：

- `internal/types/task.go`
- `internal/orchestrator/state.go`
- `internal/api/handler.go`
- `internal/api/sse.go`

### 8. 日志语义调整

默认空 Mode 现在统一输出：

```text
mode=eino
```

Planner/Fallback 日志调整为：

```text
dispatching planning decision
attempting primary planning strategy
primary planning strategy succeeded decision_source=jit_router|llm
```

确定性路由日志：

```text
planning resolved by JIT retrieval router
action=rag_search|rag_fetch|none
rag_configured=true|false
```

预算已耗尽时不再输出误导性的 `running step step=7`，改为：

```text
checking execution limits
completed_steps=6
max_steps=6
remaining_budget=0
```

## 优化后的预期流程

对于任务“数学科学术顾问有哪些”，在首批证据不足且需要第二轮检索时，预期流程为：

```text
step 1: rag_search                         # 确定性路由，0 Planner Token
step 2: rag_fetch                          # 确定性路由，0 Planner Token
step 3: LLM 判断是否需要第二轮检索
step 4: rag_fetch                          # 最新搜索自动 fetch，0 Planner Token
step 5: LLM 基于现有证据直接回答
        或在容量保护触发时调用 Task Finalizer
```

不应再出现：

```text
第三轮未缓存 RAG 搜索
由 Gemini 决定明显必需的 rag_fetch
running step step=7
预算耗尽却返回 status=completed
mode=""
确定性路由后输出 primary planner succeeded
```

```text

```

## 12:41 检索循环第二轮修复

运行日志确认 MCP 服务端只提供 `rag_search`。本项目中的 `rag_fetch` 是内部缓存读取工具，不会调用 MCP：`rag_search` 将 MCP 返回内容保存到任务级缓存并返回候选 ID，`rag_fetch` 再按 ID 将缓存内容转换为 Evidence。

本轮按顺序完成以下修复：

1. 等价查询在执行器之前识别；命中已完成查询时不再产生新的工具步骤，而是进入最终合成。
2. `rag_fetch` 过滤已抓取 candidate ID，只处理尚未抓取的增量；所有 ID 均已抓取时禁止重复 fetch。
3. 新增独立 Retrieval State，记录查询、candidate ID、已抓取 ID、待抓取 ID、网络搜索次数和检索循环次数。Planner Prompt 使用该状态，不再依赖可能被截断的 Trace。
4. 剩余执行容量小于等于 2 且已有证据时，硬性禁止 `rag_search`、`rag_fetch`、`memory_search` 和 `memory_get`。
5. `config.yaml` 与 `config_zh.yml` 默认启用 `llm.scenes.task_finalizer`。Finalizer 不可用、失败或被 LLM 预算拒绝时，任务立即转为 `partial`，不再消耗剩余工具步骤。
6. `rag.jit_search_max_calls` 独立限制真实外部搜索；新增 `rag.jit_retrieval_max_cycles`（默认 2）限制不同检索循环。等价缓存复用不创建新循环。

修复后的预期流程：

```text
rag_search（MCP 网络请求）
→ rag_fetch（本地缓存读取，仅未抓取 ID）
→ Planner/Finalizer 合成答案
→ completed
```

如果 LLM 再次请求等价搜索，流程应变为：

```text
等价查询命中 Retrieval State
→ 不执行 rag_search
→ Finalizer 合成；失败则 partial
```

## 19:49 Finalizer 空答案与重复 Embedding 修复

日志中的主任务实际已成功：Planner 在第 4 步返回 `stop=true` 和完整答案。随后出现的
`task finalizer returned an empty final answer` 是一次不必要的二次改写失败，并非 Planner
或 RAG 失败。末尾两条完全相同的 embedding 请求，则来自终态被连续保存两次：`RunAll`
保存一次，API 异步 Handler 又无条件保存一次；两次异步 Memory 索引在第一条 Memory
写入数据库前并发启动。

本轮修复：

- Planner 已返回非空最终答案时直接完成任务，不再重复调用 `task_finalizer`。
- Finalizer 仅保留给预算边界、重复检索和检索循环上限等强制合成路径。
- Finalizer 的 `final_answer` Schema 增加 `minLength: 1`，从结构化输出阶段拒绝空答案。
- API 成功路径不再重复保存 `RunAll` 已持久化的终态；失败路径仍执行补偿保存。
- SQLite、PostgreSQL、Redis Store 增加进程内 Memory 索引门控，同一 Memory ID 并发只允许一个 embedding 任务启动。
- 门控在索引成功或失败后释放，后续保存可以重试；数据库唯一约束继续作为最终一致性保护。

修复后的正常完成路径：

```text
Planner stop + 非空 final_answer
→ 保存 completed 终态
→ 启动一次 Memory embedding/index
→ API 发布 terminal event（不再二次保存、不再二次 Finalize）
```

## 20:08 Gemini Finalizer 空字段根因修复

新日志属于强制合成路径：Planner 请求的 `rag_fetch` candidate 已全部读取，Orchestrator
正确阻止重复 fetch 并调用 `task_finalizer`。Finalizer 返回空答案的根因位于通用 Gemini
结构化传输层：调用只设置了 `response_mime_type=application/json`，但完全没有把调用方
传入的 JSON Schema 设置到 `GenerateContentConfig.ResponseSchema`。因此 Gemini 可能返回
字段名不同的合法 JSON；Go 反序列化不会报错，但 `final_answer` 保持空值。

修复内容：

- 新增通用 JSON Schema 到 `genai.Schema` 的递归转换。
- Gemini 文本与 Vision 结构化调用均设置 `ResponseSchema`。
- 保留 object、array、anyOf、properties、required、enum、长度、数量和数值边界等约束。
- Finalizer Prompt 同时明确要求非空 `final_answer`、`evidence_summary`、`confidence`，作为不支持完整 Schema 的兼容保护。
- Finalizer 失败日志从误导性的 `using planner answer` 改为 `using fallback result`。
- Finalizer 失败生成的 partial 不再错误提示增加任务预算，而是提示检查 Finalizer provider 响应并重试合成。

修复后，本次流程应为：

```text
rag_fetch candidates already fetched
→ 阻止重复工具步骤
→ task_finalizer（Gemini ResponseSchema 强制 final_answer 非空）
→ completed
```

## 14:05 rag_fetch 参数超限修复

Planner 在两轮 RAG 和一次 Web Search 后返回了 4 个历史 candidate ID：

```text
rag_fetch accepts at most 3 candidate IDs
```

该错误发生在 Planner 的 `ValidateDecision` 阶段，尚未进入 Orchestrator，因此工具层的“过滤已抓取 ID”和容量保护无法执行，最终导致任务错误地转为 `failed`。

修复内容：

- 在 `ValidateDecision` 前规范化 `rag_fetch` 和 `memory_get` 参数。
- ID 自动去重，并过滤 Retrieval State 中已经抓取的 ID。
- 待抓取 ID 自动截断至 `rag.jit_fetch_max_items`。
- 如果所有请求 ID 都已抓取，保留一个有界合法动作交给 Orchestrator 识别，并进入 Finalizer，不执行重复 fetch。
- `rag_fetch`/`memory_get` JSON Schema 增加 `minItems`、`maxItems` 和 `uniqueItems`，提前约束模型输出。
- 新增结构化日志 `normalized retrieval action parameters`，包含原始、待抓取、实际包含数量和 `all_already_fetched`。

对于本次日志中的第 6 步，修复后预期为：

```text
LLM 返回 4 个 rag_fetch ID
→ Planner 规范化为最多 3 个
→ 发现全部 already_fetched
→ ValidateDecision 通过
→ Orchestrator 禁止重复 fetch
→ task_finalizer 基于已有 RAG/Web Evidence 生成答案
```

## 13:30 等价查询误判与 Finalizer 可用性修复

日志显示第一轮检索返回的是“学术顾问岗位说明”，Planner 随后提出 `学术顾问 成员 姓名 老师 团队`，这是查找具体姓名的有效细化查询。旧等价算法删除“成员、老师、名单”等词，并使用子串包含和较低的 bigram 阈值，错误产生 `equivalent_query_already_retrieved`。

本轮调整：

- 等价查询只删除通用问法和标点，不再删除“名单、成员、老师”等检索限定词。
- 删除宽松的子串包含判断，将 bigram 相似度阈值提高到 0.85。
- `学术顾问有哪些` 与 `学术顾问 成员 姓名 老师 团队` 现在属于不同检索循环。
- `数学学术顾问有哪些?` 与 `数学 学术顾问` 仍能判定为等价查询。
- 达到 `jit_retrieval_max_cycles` 时在执行器前停止，不再产生一次注定失败的工具步骤。
- `task_finalizer: {}` 改为包含 `timeout_seconds: 30` 的非空场景，确保 Viper 将场景加载到 `LLM.Scenes`。
- Finalizer 跳过和失败日志新增明确原因：`not_initialized`、`scene_disabled`、`token_reserve`、`provider_error`。
- 修复 Finalizer Prompt：除 Trace Observation 外，现在会包含 `StepTrace.Evidence` 的 path、query 和正文。之前 Finalizer 只能看到 `fetched N items`，无法看到真正的 RAG 内容。

rag_search 学术顾问有哪些
→ rag_fetch
→ Planner 发现缺少姓名
→ rag_search 学术顾问 成员 姓名 老师 团队（允许的第二轮细化）
→ rag_fetch
→ Planner stop 或 Finalizer 使用 Evidence 正文合成答案
