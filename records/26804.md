# 2026-08-04 Langfuse 双链路接入优化记录

## 优化目标

同时接入以下两种 Langfuse 观测方式，并使 Prompt 请求、Prompt 版本与具体 LLM 调用可查询、可关联：

1. `ai-agent -> OpenTelemetry Collector -> Langfuse`：记录应用任务、Prompt 管理和 LLM 调用 span。
2. `ai-agent -> LiteLLM -> langfuse_otel -> Langfuse`：记录包含请求、回复、模型、耗时和 token usage 的 Generation。

两条链路使用同一个 Langfuse 项目。应用向 LiteLLM 请求时传递当前 OTel `trace_id` 和 `parent_observation_id`，使 LiteLLM Generation 可挂接到应用调用 span 下，而不是形成相互独立的 Trace。

## 已完成内容

### 1. OpenTelemetry Collector 转发应用 Trace

- 在 `deploy/opentelemetry/otel-collector.yaml` 增加 `otlphttp/langfuse` exporter。
- Trace 同时保留在 Jaeger、Tempo，并转发至 Langfuse；现有 metrics pipeline 不受影响。
- Langfuse endpoint 和 Basic Authorization 从环境变量注入，密钥不会写入配置文件或 span。
- Compose 和 `.env.example` 增加必需的 Langfuse OTLP 配置。

应用侧需要配置：

```dotenv
OTEL_COLLECTOR_CONFIG_PATH=/etc/otelcol/config-langfuse.yaml
LANGFUSE_OTEL_ENDPOINT=https://langfuse.example.com/api/public/otel
LANGFUSE_OTEL_AUTHORIZATION="Basic BASE64_PUBLIC_KEY_COLON_SECRET_KEY"
```

Collector 默认使用不依赖 Langfuse 环境变量的本地配置；上面的
`OTEL_COLLECTOR_CONFIG_PATH` 用于显式启用 Langfuse exporter。这样即使没有加载
`.env`，`docker compose down` 也可以正常解析和停止服务。

凭证生成示例：

```bash
printf '%s' 'pk-lf-public-key:sk-lf-secret-key' | base64
```

### 2. LiteLLM Generation 接入 Langfuse

- 在 `deploy/litellm/config.yaml` 启用 `langfuse_otel` callback，并保留已有 `smtp_email` callback。
- Compose 传入 `LANGFUSE_PUBLIC_KEY`、`LANGFUSE_SECRET_KEY`、`LANGFUSE_OTEL_HOST`。
- `LANGFUSE_OTEL_HOST` 只填写 Langfuse 基础地址，不能追加 `/api/public/otel`，该路径由 LiteLLM callback 处理。
- LiteLLM 可向 Langfuse 记录成功及失败的模型调用、输入输出、token usage、耗时和模型信息。

配置示例：

```dotenv
LANGFUSE_PUBLIC_KEY=pk-lf-replace-me
LANGFUSE_SECRET_KEY=sk-lf-replace-me
LANGFUSE_OTEL_HOST=https://langfuse.example.com
```

### 3. 应用 Trace 与 LiteLLM Generation 关联

- LiteLLM 请求体自动追加 `metadata`，仅在 provider 为 `litellm` 时生效，直接 OpenAI/Gemini 等 provider 的请求结构不变。
- 传递当前 span 的 `trace_id` 与 `parent_observation_id`。
- 传递 `task_id`、`session_id`、`tenant_id`、`user_id`、`scene`、应用版本、运行环境和 tags，便于 Langfuse 过滤检索。
- 应用 `llm.structured_call` span 增加对应的 Langfuse trace、session、user 和 metadata 属性。
- 租户 ID 仅作为观测维度记录；不会在日志或 span 中记录 API Key、JWT、Langfuse 密钥等认证凭证。

主要实现文件：

- `internal/llm/observability.go`
- `internal/llm/structured.go`
- `internal/llm/transport.go`

### 4. Prompt 请求和版本可见性

- Langfuse Prompt GET 请求新增 `langfuse.prompt.fetch` span。
- Prompt 创建请求新增 `langfuse.prompt.create` span。
- span 记录安全字段：Prompt 名称、label/version selector、HTTP method、HTTP status、耗时和结果状态。
- 不把 Prompt 正文、Authorization 或 Langfuse Secret Key 写入 span。
- Prompt 解析结果增加 `prompt_name`、`prompt_source`、`prompt_version`、`prompt_label` 等可过滤 metadata。
- multi-agent 的 planner、writer、verifier、critic 在实际 LLM 调用前携带已经解析的 Langfuse Prompt 名称和不可变版本。
- 只有 `source=langfuse` 且 `version>0` 的 Prompt 才建立版本关联；本地 fallback Prompt 不会伪装成 Langfuse Prompt 版本。
- 绑定上下文只覆盖紧随其后的 LLM 调用，避免主调用的 Prompt 信息误传给 verifier、repair 或其他后续请求。

主要实现文件：

- `internal/promptmanager/client.go`
- `internal/promptmanager/bootstrap.go`
- `internal/multiagent/teams.go`
- `internal/multiagent/planner_agent.go`
- `internal/multiagent/writer_agent.go`
- `internal/multiagent/verifier_agent.go`
- `internal/multiagent/critic_agent.go`

## Langfuse 平台预期查看结果

一次正常 multi-agent LLM 调用应满足：

1. Langfuse Trace 中能看到应用的 `llm.structured_call` span。
2. 对应 LiteLLM Generation 与该 span 使用同一个 Trace ID，并以应用 span 为 parent。
3. Generation 中可查看 LiteLLM 捕获的 request、response、model、latency 和 token usage。
4. 使用 Langfuse Prompt 时，可按 Prompt 名称和版本筛选；应用 span 中也能查看实际解析版本。
5. Prompt API 调用可看到 `langfuse.prompt.fetch`；动态初始化创建 Prompt 时可看到 `langfuse.prompt.create`。
6. 本地 fallback 时仅显示 `prompt_source=fallback`，不应生成错误的 Langfuse Prompt 版本链接。

实际的 Prompt 原生链接是否被当前固定版本的 LiteLLM `langfuse_otel` callback 识别，需要在部署环境做一次验收。即使该版本只把字段保存为 Generation metadata，Prompt 名称和版本仍可查询，不影响 Trace/Generation 关联。

## 部署与重启

先将两份示例环境文件复制为未纳入 Git 的 `.env`，填入同一个 Langfuse 项目的公钥和私钥。

重新创建 Collector：

```bash
docker compose --env-file deploy/opentelemetry/.env \
  -f deploy/opentelemetry/docker-compose.yml \
  up -d --no-deps --force-recreate otel-collector
```

重新创建 LiteLLM：

```bash
docker compose --env-file deploy/litellm/.env \
  -f deploy/litellm/compose.yaml \
  up -d --no-deps --force-recreate litellm
```

本次 callback/env 变更不要求重启 `model-bootstrap`。应用代码更新后需重新构建并重启 `ai-agent`。

## Collector 重启问题处理

部署时曾出现 `otel-collector` 持续 `Restarting (1)`。容器使用了
`/etc/otelcol/config-langfuse.yaml`，但创建时注入的
`LANGFUSE_OTEL_ENDPOINT` 和 `LANGFUSE_OTEL_AUTHORIZATION` 均为空，Collector
因此以 `exporters::otlphttp/langfuse: at least one endpoint must be specified`
退出。

确认 `.env` 已配置后，通过显式指定环境文件强制重建解决：

```bash
docker compose --env-file deploy/opentelemetry/.env \
  -f deploy/opentelemetry/docker-compose.yml \
  up -d --no-deps --force-recreate otel-collector
```

重建后状态为 `running`、`restart_count=0`，日志显示
`Everything is ready. Begin running and processing data.`。后续启动 Langfuse
配置时必须保留显式的 `--env-file`，避免使用旧容器环境或从错误目录加载 `.env`。

## 2026-08-06 多任务会话与 Session Memory

- 新增 Tenant 归属的 Session 实体，支持 `active`、`archived` 生命周期。
- `Task` 增加 `session_id`、原子分配的 `sequence_no` 和创建/更新时间。
- `Memory` 增加 `session_id`；有会话的任务只检索同 Tenant、同 Session 的 Memory，旧任务继续使用原有 Tenant 级语义。
- 新增 Session 创建、查询、更新、归档、任务列表和 Memory 列表 API。
- PostgreSQL、SQLite、Redis、内存 Store 均增加 Session 持久化；SQL 后端带幂等列迁移和检索索引。
- 最近完成的会话任务会直接成为上下文，不等待异步 Embedding 建索引，保证下一任务立即可见；数量由 `rag.session_recent_task_limit` 控制。
- 会话 Memory 使用追加式任务结果，多个并发任务不会覆盖同一个共享 JSON；并发任务序号由 Store 原子分配。
- Langfuse `session.id` 改为真实 `Task.SessionID`，`task_id` 继续作为 Trace metadata；无会话旧任务回退使用 `task_id`。
- 新增会话生命周期、租户隔离、并发序号、SQLite 持久化、Memory 隔离和 Langfuse metadata 回归测试。

### API 使用顺序

```http
POST /api/sessions
Content-Type: application/json

{"title":"EEO 课程咨询"}
```

取得响应中的 `id` 后，在同一 Tenant 的任务创建请求中传入：

```http
POST /api/tasks
Content-Type: application/json

{"session_id":"<session-id>","goal":"继续分析课程内容","workspace":"."}
```

查询接口：

- `GET /api/sessions?status=active&limit=50&offset=0`
- `GET /api/sessions/{id}`
- `PATCH /api/sessions/{id}`，可更新 `title` 或在 `active`、`archived` 间变更状态
- `POST /api/sessions/{id}/archive`
- `GET /api/sessions/{id}/tasks?status=completed&limit=50&offset=0`
- `GET /api/sessions/{id}/memories?limit=50&offset=0`
- 原有 `GET /api/tasks`、`GET /api/memories` 也支持 `session_id` 查询参数

归档后的 Session 保留历史任务和 Memory，但不允许创建新任务。没有传入
`session_id` 的旧客户端保持原行为，Memory 仍按 Tenant 范围检索。

### 配置与部署

`rag.session_recent_task_limit` 默认值为 `5`，表示每个新任务直接注入同一
Session 最近 5 个已完成任务；设为 `0` 可关闭直接历史注入。环境变量为
`AI_AGENT_RAG_SESSION_RECENT_TASK_LIMIT`。

应用启动时会为 SQLite/PostgreSQL 幂等创建 `sessions` 表，为现有 tasks、
memories 表补充 Session 字段和索引。发布新二进制后需要重启 `ai-agent`；
无需重建 LiteLLM model-bootstrap。生产数据库执行前建议常规备份。
