# qmd 混合搜索对当前 Wiki 搜索的适用性分析与优化方案

日期：2026-08-26  
参考项目：https://github.com/tobi/qmd

## 一、结论

qmd 对当前项目有明显参考价值，主要可补齐 Wiki 的语义召回、Markdown 感知分块、混合排名融合和分后端评测能力。但不建议使用 qmd 直接替换现有 Wiki BM25，也不建议第一阶段把完整 Node.js/qmd 运行时嵌入生产服务。

推荐路线是在现有 Go `DirectoryClient` 中原生实现：

```text
BM25 页面召回 + Vector Chunk 召回
                 ↓
               RRF 融合
                 ↓
             按 Wiki 页面聚合
                 ↓
       现有标题、来源和隔离规则校准
                 ↓
          Top-K 候选与有限全文读取
```

第一阶段只增加 Vector 与 RRF，LLM Reranker 和生成式查询扩展继续后置。

## 二、qmd 的检索架构

qmd 是面向 Markdown、会议记录、文档和知识库的本地搜索引擎。完整查询路径包括：

1. 原始问题同时进入 BM25 和向量检索。
2. 本地生成模型产生带类型的查询扩展：`lex`、`vec`、`hyde`。
3. `lex` 只进入 BM25，`vec` 和 `hyde` 只进入向量检索。
4. 多个有序结果通过 Reciprocal Rank Fusion（RRF）融合。
5. 默认对候选执行本地 Cross-Encoder 重排。
6. 结合原检索排名和 Reranker 分数得到最终结果。

其主要技术包括：

- SQLite FTS5 BM25。
- sqlite-vec 向量检索。
- Markdown 感知 Chunk。
- 本地 GGUF Embedding、Query Expansion 和 Reranker 模型。
- HTTP `/query`、MCP、CLI 和 Node/Bun SDK。
- BM25、Vector、Hybrid、Full 四种评测后端。
- 可解释的 FTS、Vector、RRF 和 Rerank 分数。

截至分析时，qmd 包版本为 2.8.3，要求 Node.js 22 或更高版本，主要依赖 `better-sqlite3`、`sqlite-vec` 和 `node-llama-cpp`。

## 三、当前项目已有能力

当前本地 Wiki 已具备：

- 字段化 BM25，字段权重覆盖 title、slug、heading、metadata 和 body。
- 英文、数字与 CJK 二元分词。
- 完整标题、连续短语和链接加权。
- 最小词项覆盖和无答案误召回控制。
- 导航页降权和通用 raw source 来源特异性降权。
- 确定性 slug tie-break。
- 不可变索引快照和惰性刷新。
- 固定容量 Top-K 堆。
- Graph 相关性裁剪。
- 搜索候选类别多样化和有限全文读取。
- Candidate Cache 生命周期治理。
- Explain、Benchmark 和真实 Wiki Eval。
- Tenant → Wiki Space 隔离以及完整引用审计。

当前真实 30-case Eval 的搜索、无答案、引用、Graph 和 Suggestion 门禁已通过。10,000 页宽查询 BM25 基准约为 2.43ms，因此 qmd 的 FTS5/BM25 对当前实现没有足够替换收益。

## 四、值得借鉴的能力

### 4.1 向量语义召回

当前 BM25 依赖查询与页面之间存在可匹配词项。向量召回可改善：

- 查询不包含页面标题或原文关键词。
- 同义词、缩写和自然语言改写。
- 中英文表达不同。
- 根据属性反查实体。
- 长页面中只有局部段落相关。

示例：页面写“Vanessa Ruales 负责个性化文稿批改”，用户询问“谁给学生提供一对一写作反馈”。两者词项重合有限，但语义相关。

### 4.2 RRF 排名融合

BM25 分数与向量相似度不是同一量纲，直接加权需要复杂归一化。RRF 只依赖各分支排名，适合稳定融合：

```text
score(document) = Σ weight / (rrf_k + rank)
```

建议初始 `rrf_k=60`，原始查询分支可适当加权；具体参数必须由 Wiki Eval 校准。

### 4.3 Markdown 感知分块

长页面的整页 Embedding 容易稀释局部主题。可借鉴 qmd 的边界选择思路，但应适配当前 Wiki：

- 优先按 H2/H3、段落和列表边界分块。
- 不在代码块或结构化表格中间切分。
- Chunk 保存 Space、页面 Slug、标题、页面类型和字符位置。
- 搜索后按 canonical Wiki 页面聚合，避免同一页面多个 Chunk 占满 Top-K。
- `wiki_fetch` 继续读取授权后的原始页面，而不是直接把索引内容当作最终证据。

### 4.4 分后端 Eval 和 Explain

Eval 应独立报告：

- `bm25`
- `vector`
- `hybrid`
- 后续可选 `hybrid_rerank`

Explain 应显示每个结果的 BM25 排名、Vector 排名、RRF 各分支贡献、页面聚合和现有业务倍率，便于定位召回改善或实体串线。

## 五、不建议直接引入完整 qmd 的原因

### 5.1 运行时和部署复杂度

当前生产服务为 Go。直接引入 qmd 会增加 Node.js 22、原生 SQLite 扩展、node-llama-cpp、多套 GGUF 模型、模型缓存、GPU/CPU 兼容以及 Sidecar 生命周期管理。还需解决 qmd SQLite 索引与当前 Wiki 不可变快照的双重一致性。

### 5.2 Tenant 与 Space 隔离不匹配

qmd 默认使用本机 Collection/Index；当前项目要求 Tenant 与 Wiki Space 严格绑定。如果共享 qmd 实例，还需额外保证：

- Collection 参数由服务端确定，不能由模型自由指定。
- 不同 Tenant 不共享候选、缓存、上下文或索引。
- 未知或错误参数必须 fail-closed。
- Collection 与授权 Space 一一映射。

qmd 文档说明未知 MCP 参数会被静默忽略。例如误传单数 `collection` 而不是 `collections`，查询范围可能不生效，不符合当前安全策略。

### 5.3 HTTP 接口默认不提供身份认证

qmd HTTP 服务默认绑定回环地址，并进行 Origin/Host 检查，但接口本身无认证。若以 Sidecar 或远程服务接入，仍需通过当前 API/MCP 网络策略、身份认证、Tenant 授权和私网限制，不能直接暴露。

### 5.4 查询扩展与重排存在内容漂移风险

当前 Wiki 曾出现相似课程与导师串线。生成式查询扩展可能把精确课程名扩展为宽泛主题，使其他 offering 进入候选；语义 Reranker 也可能重视主题相似而忽略实体身份差异。因此必须继续保留精确标题、Slug、实体名称、来源关联和页面类型规则。

## 六、推荐实施计划

### P0：扩充语义检索 Eval

暂不修改生产排名，先增加约 20–30 个 BM25 不占优势的用例：

- 同义词和自然语言改写。
- 中英文交叉查询。
- 不含标题词的属性问题。
- 实体属性反查。
- 长页面局部事实。
- 相似课程和相似导师负向隔离。
- 语义相关但 Wiki 无答案的查询。

建议门禁：Hybrid 的 Recall@5、Top3、MRR 相比 BM25 有可测提升，同时 No-answer false positive、近似实体串线和 P95 延迟不得明显恶化。

### P1：实现原生 Go Vector + RRF

在现有 `DirectoryClient` 中增加可回退的 `hybrid` 模式：

```text
BM25 Top-30 + Vector Chunk Top-30
              ↓
           RRF(k=60)
              ↓
         按页面取最佳 Chunk 并聚合
              ↓
  标题/来源特异性/导航页/实体隔离规则
              ↓
          Search Top-8
              ↓
          Fetch 最多 3 页
```

初始配置建议：

```yaml
wiki:
  local_search_mode: "hybrid"
  vector_candidate_limit: 30
  hybrid_rrf_k: 60
  embedding_chunk_tokens: 700
  embedding_chunk_overlap_tokens: 100
```

具体名称和默认值应在实现时结合现有配置规范确认。

必须满足：

- `bm25` 保持一键回退。
- Embedding 不可用或超时时自动降级 BM25。
- 默认仍支持完全离线运行。
- 向量索引绑定 Wiki snapshot/version 和 Embedding model fingerprint。
- 索引切换采用不可变快照，不暴露半构建状态。
- Tenant Space 不共享候选和缓存。
- 不增加 Wiki 全文读取次数与字节预算。
- Explain 不记录查询正文、页面正文或敏感路径。

### P2：评估轻量 Reranker

只有 RRF 仍存在明确排序缺口时再加入：

- 默认关闭，通过 feature flag 灰度。
- 只重排约 10–20 个候选。
- 超时、模型不可用或预算不足时保留 RRF 排名。
- 精确标题和实体候选不能被无上限降权。
- 缓存键包含模型版本、查询摘要和 Wiki snapshot。
- 单独记录延迟、命中率、排序增益与降级次数。
- 不使用生成式 Writer 充当 Reranker。

### P3：最后评估查询扩展

优先实施确定性扩展：

- Wiki aliases。
- 中英文标题映射。
- 缩写。
- Frontmatter tags。
- 已验证实体别名。

生成式扩展必须在独立 Eval 证明收益后再灰度，并限制扩展数量、类型、Token、超时和缓存；原始查询始终保留最高或加倍权重。

## 七、可选 qmd Sidecar PoC

如果需要快速验证算法而不立即实现 Go Vector，可在完全隔离的开发环境运行 qmd Sidecar，只用于离线 Eval：

1. 为测试 Wiki 建独立 Collection 和独立 SQLite Index。
2. 仅绑定 `127.0.0.1`，不对外开放。
3. 禁止使用真实多租户敏感数据。
4. 分别执行 BM25、Vector、Hybrid 和 Full Benchmark。
5. 只导出匿名化指标，不把 qmd URI 或缓存接入生产引用链。

该 PoC 仅用于验证语义检索收益，不作为生产架构承诺。

## 八、验收标准

进入生产灰度前至少满足：

- 扩充后的语义 Eval 显著优于 BM25 基线。
- 当前 30-case 指标不回退。
- 相似课程与导师隔离用例全部通过。
- 无答案误召回保持门禁内。
- Embedding 故障自动回退 BM25。
- Snapshot、模型版本和向量索引一致性测试通过。
- Tenant/Space 隔离、路径安全和候选缓存隔离测试通过。
- `go test ./...` 与相关竞态测试通过。
- 10,000 页 Benchmark 的内存、构建时间和 P95 满足预设预算。
- 真实 8088 灰度任务的 Search、Fetch、引用审计和日志闭环通过。

## 九、最终决策建议

| 方案 | 建议 |
|---|---|
| 使用 qmd 替换当前 Wiki 搜索 | 不建议 |
| 把完整 qmd 作为生产 Node Sidecar/MCP | 暂不建议 |
| 使用 qmd 做隔离的离线质量 PoC | 可选 |
| 借鉴 Markdown 感知 Chunk | 建议 |
| 在现有 Go Wiki 增加向量召回 | 建议，下一阶段重点 |
| 使用 RRF 融合 BM25 与 Vector | 强烈建议 |
| 立即引入 LLM Reranker | 暂缓 |
| 立即引入生成式查询扩展 | 暂缓 |
| 借鉴多后端 Eval 与 Explain | 强烈建议 |

下一步应先完成 P0 语义与实体隔离 Eval，再基于结果决定是否进入 P1 原生 Go `BM25 + Vector + RRF` 实现。
