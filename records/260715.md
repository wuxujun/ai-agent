# 2026-07-15 Just-in-Time Context 设计记录

## 背景

当前任务执行流程会在第一次 Planning 之前自动完成第三方 RAG、本地长期 Memory 检索、合并、去重和排序，然后将结果整体放入 Planner Prompt：

```text
第三方 RAG请求
→ Embedding请求
→ 本地Memory搜索
→ 合并、去重
→ 全量加入Prompt
→ 第一次Planning
```

这种预取模式会导致与任务无关的检索请求、首轮 Prompt 膨胀、RAG 与历史 Memory 语义混淆，以及外部内容过早进入提示词等问题。

对于当前系统，更适合采用 Just-in-Time Context：初始 Planning 只获得任务目标、工具目录和当前 Trace，由 Planner 判断是否需要检索 RAG、Memory 或其他上下文。

## 推荐架构

```text
初始 Planning
只提供：Goal + 工具说明 + 当前 Trace
          │
          ├─ rag_search
          ├─ memory_search
          ├─ rag_fetch
          ├─ memory_get
          └─ 其他业务工具
                  │
                  ▼
            返回精简候选
                  │
                  ▼
             下一轮 Planning
```

核心原则：Planner 决定是否检索、检索什么以及读取哪些结果；上下文只在需要时加入。

## 工具设计

不要让一次 `rag_search` 直接返回几十 KB 正文，应采用“搜索候选、按需读取”两阶段模式。

### RAG 搜索

```json
{
  "action": "rag_search",
  "parameters": {
    "query": "数学科学术顾问",
    "top_k": 5
  }
}
```

返回精简候选：

```json
{
  "results": [
    {
      "id": "rag-1",
      "title": "数学科学术顾问团队",
      "snippet": "包含张三、李四等顾问信息……",
      "score": 0.91,
      "source": "thinktown"
    }
  ]
}
```

Planner 确认结果相关后，再读取正文：

```json
{
  "action": "rag_fetch",
  "parameters": {
    "ids": ["rag-1"]
  }
}
```

### Memory 搜索

Memory 使用相同的渐进披露模式：

```text
memory_search → 返回ID、Goal、摘要、时间和相似度
memory_get    → 读取选中的完整历史记忆
```

RAG Evidence 和 Historical Memory 必须保持为两个独立通道，不应合并成同一种 Memory：

```text
第三方 RAG → RAG Evidence ─────┐
                               ├→ Prompt Budgeter → Planner
本地长期记忆 → Historical Memory ┘
```

## Planner 策略

- 当前事实、人物、组织、产品等信息优先调用 `rag_search`。
- 涉及历史任务、用户偏好、以前结论时调用 `memory_search`。
- 工作区代码或文件问题使用文件工具。
- 已有足够证据时不得重复检索。
- 没有证据时禁止直接生成事实答案。
- RAG 和 Memory 都不是必调工具，由任务类型决定。
- 当前 RAG Evidence 的事实优先级高于 Historical Memory。
- Historical Memory 只能作为背景，不能覆盖更新、更直接的当前证据。
- 第三方 RAG 默认只在当前任务生命周期内存在，不自动写入长期 Memory。
- 只有经过验证的最终答案和关键结论，才允许在任务完成后写入 Memory。

## 上下文预算建议

| 上下文 | 数量 | 默认预算 |
|---|---:|---:|
| 当前 RAG Evidence | 3–5条 | 6,000 bytes |
| Historical Memory | 1–2条 | 2,000 bytes |
| 合计 | — | 8,000 bytes |

处理要求：

1. RAG 和 Memory 分别解析、过滤和排序。
2. 可以跨通道去重，但必须保留原始 `source_type`、来源和可信等级。
3. 搜索阶段只返回候选摘要，详情阶段按 ID 获取内容。
4. 所有详情仍须经过单条限制和 Prompt 总预算控制。
5. 外部内容进入 Planner 前必须执行 Prompt Injection 检测。

## 优势

相比 Planning 前固定预取，JIT Context 可以避免：

- 与任务无关的 RAG 请求。
- 每个任务固定调用 Embedding。
- 首轮 Prompt 过大。
- RAG 内容挤占长期 Memory。
- 历史信息和当前证据混淆。
- 检索结果尚未被 Planner 判断就进入上下文。
- 外部不可信内容过早进入提示词。

## 代价与折中

JIT Context 通常会增加 Planning 轮次：

```text
第1轮：决定调用 rag_search
第2轮：根据搜索候选决定 rag_fetch
第3轮：根据正文生成答案
```

建议采用“混合 JIT”降低额外延迟：

- 默认不预取完整内容。
- 可通过轻量 Intent Router 判断是否大概率需要检索。
- Intent Router 只提供检索建议，不直接注入 RAG 正文。
- Planner 最终决定调用哪个检索工具。
- 搜索结果在当前任务内缓存，避免相同查询重复请求。

## 防止不检索和无限检索

- 相同工具和相同 Query 不允许重复调用。
- 每类检索工具设置独立调用次数上限。
- `rag_search` 最多返回5个候选。
- `rag_fetch` 最多读取3个结果。
- RAG 和 Memory 分别设置上下文预算。
- 如果最终答案包含外部事实但没有 Evidence，应拒绝完成并要求检索。
- 检索失败时返回明确失败原因，不能生成占位答案。
- 任务内缓存检索结果，后续通过结果 ID 引用。

## 实施顺序

1. 注册 `rag_search` 和 `memory_search` 工具。
2. 增加 `rag_fetch` 和 `memory_get` 详情工具。
3. 移除 `Engine.Next` 中 Planning 前的强制 RAG/Memory 预取。
4. 将检索结果写入 `StepTrace.Evidence`，不写入统一的 `task.Memories`。
5. 更新 Planner Prompt，明确检索、证据和来源优先级规则。
6. 增加重复查询、调用次数和独立上下文预算控制。
7. 增加“无证据不得输出事实答案”的回归测试。
8. 保留配置开关，支持旧的预取模式与 JIT 模式切换，完成灰度迁移。

## 结论

JIT Context 更适合当前系统。Planner 不应在任务开始时一次读取所有 RAG 和 Memory，而应先搜索候选，再按 ID 获取必要内容，并始终保持 RAG Evidence 与 Historical Memory 两条独立上下文通道。

## 实施状态

已按上述顺序完成第一阶段实现：

1. 已注册 `rag_search`、`memory_search`、`rag_fetch`、`memory_get`。
2. 搜索接口只返回精简候选；详情接口通过任务内候选 ID 返回 `StepTrace.Evidence`。
3. 默认 `rag.context_mode: jit`，首轮 Planning 不再强制请求第三方 RAG、Embedding 或本地 Memory；可切换为 `prefetch` 保留旧流程。
4. RAG 与 Memory 使用独立工具、独立候选类型和独立详情预算，不再写入统一的 `task.Memories`。
5. Planner Prompt 已加入检索选择、来源优先级、禁止重复检索和“无证据不得输出事实答案”规则。
6. 相同 Query 在任务内复用缓存；每类搜索默认最多执行3次未缓存请求，单次详情默认最多读取3条。
7. 当 Planner 尝试基于搜索摘要直接作答时，系统会先要求 `rag_fetch` 或 `memory_get`；检索为空时返回明确的证据不足说明，不循环检索或生成占位答案。
8. 已增加 JIT/Prefetch、候选缓存、跨 Query 隔离、调用上限、详情读取、Gemini 数组参数 schema 和无证据作答等回归测试。

相关配置：

```yaml
rag:
  context_mode: "jit"
  jit_search_max_calls: 3
  jit_fetch_max_items: 3
```
