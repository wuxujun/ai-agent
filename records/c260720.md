# Multi-Agent 双工作流可行性分析报告

**日期**：2026-07-20  
**分析对象**：`internal/multiagent` 双工作流架构  
**代码基准**：`internal/multiagent/coordinator.go` · `internal/multiagent/teams.go` · `teams.yaml`

---

## 一、两种方案架构概览

```text
方案一（Research Workflow）：
  Planner → Researcher ×N → Writer

方案二（Reviewed Workflow）：
  Planner → Critic → Executor ×N → Verifier
             ↑_____首次驳回触发 Replan_____|

第三模式（Adaptive）：
  Router —— 高风险/高复杂 ——→ 方案二
        \—— 普通查询 ————→ 方案一
```

| 维度 | 方案一：`planner_researcher_writer` | 方案二：`planner_critic_executor_verifier` |
|:---|:---|:---|
| **角色数** | 3（Planner / Researcher / Writer） | 4（Planner / Critic / Executor / Verifier） |
| **LLM 调用次数** | 2（Plan + Write） | 3～5（Plan + Critique + [Replan] + Draft + Verify） |
| **最小 Token 成本** | 低 | 较高 |
| **防错/防幻觉** | 基础（LLM 自约束） | **双重**（前置审查 + 后置证据校验） |
| **适用场景** | 信息检索、文档分析、知识梳理、报告生成 | 代码重构、系统变更、高风险脚本、强一致性校验 |
| **结果状态语义** | `completed / partial / failed` | `completed / partial / failed`（语义更精确） |

## 二、可行性分析：方案一（Research Workflow）

### ✅ 技术可行性

| 要点 | 代码实现 | 评价 |
|:---|:---|:---|
| 规划阶段 | `runPlanPhase` → `PlannerAgent.Plan` | ✅ 结构化 JSON Schema 强约束输出，避免格式错误 |
| 并行执行 | `runBatchParallel` | ✅ 只读步骤自动并行，写操作强制串行，竞态安全 |
| 失败重规划 | `Planner.Replan` | ✅ 最多 3 次 Replan，防止无限循环 |
| 自适应深化 | `draftConfidence == "low"` 触发 | ✅ 最多 2 次深化迭代，防止 Token 爆炸 |
| 政策护栏 | `policy.ValidateWorkspace` | ✅ Workspace 边界强制校验 |
| Langfuse 降级 | `resolveAgentPrompt` | ✅ Langfuse → SystemPrompt → 代码默认三层降级 |

### ⚠️ 方案一固有局限

1. **无前置计划审核**：Planner 生成的计划直接进入 Researcher 执行，依赖 LLM 自约束。
2. **Writer 自生成自汇总**：Writer 基于 Researcher 收集的证据输出最终答案，无独立校验阶段，存在幻觉风险。
3. **可选 PlanCritic**：3 角色工作流仅在 `config.LLMScenePlanCritic` 开启 + 场景复杂度达到阈值时触发 Critic，属于辅助保障，非必经节点。

### 结论：**方案一完全可行**，适合低风险、高速响应场景

## 三、可行性分析：方案二（Reviewed Workflow）

### ✅ 技术可行性

| 要点 | 代码实现 | 评价 |
|:---|:---|:---|
| 强制 Critic 前置 | `requireCriticApproval` | ✅ 不可绕过，失败直接 `StatusFailed` |
| Critic 反馈给 Replanner | Replanner Prompt 附带 Critic Evidence（最多 10 条） | ✅ 修订 P0 Bug：Planner 可见具体拒绝理由 |
| 最大 Replan 次数 | Critic 否决 → 仅 1 次 Replan → 二次否决失败 | ✅ 防死锁，任务不会无限重试 |
| Verifier 双调用 | `Finalize`：Draft 生成 + 独立 Verify | ✅ 防自生成自验证，两次 LLM 调用分离 |
| 置信度强制降级 | `supported=false` 时 `DraftConfidence` 强制 `"low"` | ✅ 确保错误答案不以高置信度输出 |
| Partial 语义精确 | `max_tool_steps_reached` / `final_answer_not_fully_supported` 等机器可读原因 | ✅ 比方案一语义更精细 |
| 工具步数与阶段分离 | `multiAgentToolStepCount` 按角色统计 | ✅ Critic/Verifier 调用不占工具执行配额 |
| 政策护栏不可绕过 | `ExecutorAgent` 与 `ResearcherAgent` 共享 `executeResearchStep` | ✅ 切换工作流不会绕过 workspace 校验和审批 |

### ⚠️ 方案二潜在风险

1. **时延与 Token 开销倍增**：正常路径 ≥ 4 次 LLM 调用，触发 Replan 可达 6～7 次，对响应时延和成本敏感场景有压力。
2. **Critic 过严导致任务失败率上升**：若 Critic Prompt 设计不当（过严），大量计划会被驳回，增加 Replan 频率，最终导致任务失败。
3. **自适应深化在 Reviewed 模式下 Replan 也须过 Critic**：深化迭代中的新计划必须再次通过 Critic 审批（`requireCriticApproval`），对计划不稳定的任务可能造成级联失败。
4. **Verifier 两次 LLM 调用的原子性**：Draft 生成成功但 Verify 失败时，仅返回错误，不做部分保存，需要调用方处理好重试逻辑。

### 结论：**方案二完全可行**，适合高风险、强一致性要求场景

## 四、两方案共享的健壮性保障

```text
任务进入
  → Workspace 边界校验（policy.ValidateWorkspace）
  → 高风险动作 → 人工审批（SuspendForApproval）
  → Token / 工具 / 步数三重预算拦截
  → JIT 检索路由（rag_search / memory_search 优先）
  → PromptInjection 检测（promptguard）
  → Evidence 相关性过滤（evidencefilter）
  → Evidence 冲突解决（evidenceconflict）
  → Source 可信度评分（sourcecredibility）
```

- **预算门限**：`task.ToolBudget`（工具次数）+ `task.TokenBudget`（Token 量）+ `task.MaxSteps`（执行步数）三重独立拦截
- **并发竞态**：`go test -race` 全部通过，`sync.WaitGroup` 保护并行批次
- **取消传播**：全链路 `ctx.Done()` 检测，超时/主动取消即时退出
- **Langfuse 降级**：Langfuse 不可用不会阻断任务，三层 fallback 保障

## 五、第三模式：Adaptive 路由（推荐生产策略）

```yaml
active_team: "software"

teams:
  software:
    workflow: "adaptive"
    routing:
      reviewed_complexities: ["high"]
      reviewed_intents: ["execute", "write", "deploy"]
      reviewed_min_plan_steps: 5
      allow_research_high_risk_tools: false
```

路由决策逻辑（`resolveWorkflow` in `internal/multiagent/teams.go`）：

| 优先级 | 条件 | 路由结果 |
|:---|:---|:---|
| 1 | 计划包含高风险工具（`RiskLevelHigh`） | → **Reviewed** |
| 2 | Task 复杂度 ∈ `reviewed_complexities` | → **Reviewed** |
| 3 | Task Intent ∈ `reviewed_intents` | → **Reviewed** |
| 4 | 计划步数 ≥ `reviewed_min_plan_steps` | → **Reviewed** |
| 5 | 其余 | → **Research** |

路由结果写入 Trace（`WorkflowRouteTraceAction`），任务恢复后不会重新路由，保证幂等性。

## 七、综合结论与建议

**两种方案均完全可行，架构完备、逻辑自洽、技术落地坚实。**

### 场景选择建议

```
📌 选择方案一（Research）：
   • 知识问答、文档检索、代码搜索、报告撰写
   • 对响应速度敏感 / Token 成本敏感
   • 任务不涉及写操作或高风险工具

📌 选择方案二（Reviewed）：
   • 代码重构、系统配置变更、脚本执行
   • 结果需强一致性校验（不接受幻觉）
   • 涉及 write_file / execute_code / 部署操作

📌 生产推荐：Adaptive 模式
   • 系统自动按风险和复杂度路由
   • 配合 reviewed_intents / reviewed_complexities 精细调优
```

### 后续优化建议

1. **Critic Prompt 优化**：补充 Few-Shot 示例，明确"应驳回"与"可放行"的边界，降低误驳率。
2. **DAG 图编排演进**：当前线性流水线可演进为基于 DAG 的图引擎，支持专家 Agent 并行调度与条件分支（如 Verifier 失败后直接跳回 Executor 补充证据）。
3. **Verifier 部分保存**：Draft 成功时临时保存候选答案，Verify 失败时返回带置信度降级的部分结果，而非纯错误。
4. **Critic 并发预审**：对于步骤数量多的计划，可并行预审各步骤合规性，减少 Critic 等待时间。
