# 2026-07-13 变更记录

## 一、功能增强

### 1. Context Compressor — Token 总量维度触发

**背景**：原有压缩触发仅依赖 Trace 条数（`context_compression_trace_threshold`），单条 Observation 非常长时（如大型代码执行结果）即使步数很少也可能导致上下文膨胀。

**变更内容**：

- `internal/config/config.go`：新增 `ContextCompressionTokenThreshold int` 字段（`mapstructure: context_compression_token_threshold`），默认 0（禁用）；同时补充配置校验（不允许负数）。
- `internal/planner/llm.go`：`PlanNext` 中在计算步数触发 (`traceLimitHit`) 之外，新增对所有新 Trace 的 `TokenUsage.TotalTokens` 累加，形成 `tokenLimitHit` 维度；两者满足其一即触发压缩，并携带 `reason: "trace_count" | "token_budget"` 区分。
- `config.yaml`：补充 `context_compression_token_threshold` 配置注释示例（默认注释掉）。

**回归测试**：`TestLLMPlannerTokenThresholdTrigger`（`internal/planner/llm_test.go`）
- 设置 Trace 阈值 999（不触发）、Token 阈值 100，构造 3 条 ×40 Token 的 Trace（总计 120）
- 断言 Compressor 被调用恰好 1 次，压缩触发 reason 为 `token_budget`

### 2. ApprovalBus — 重复/过期消息幂等告警

**背景**：Redis Pub/Sub 在消费者重连或多实例场景下可能重复投递审批消息。原代码 `ResolveApprovalByID` 返回 false 时无任何反馈，运营难以区分"正常已处理"与"消息路由异常"。

**变更内容**：

- `internal/orchestrator/approval_bus.go`：`dispatchApproval` 中当 `ApprovalID != ""` 且 `ResolveApprovalByID` 返回 false 时，增加 `busLog.Warn` 日志标注为"stale or duplicate message"，并附注不做 fallthrough 的安全原因（防止意外批准其他待审批操作）。

### 3. OTel 可观测性增强

**变更内容**：

- `internal/planner/llm.go`：
  - 压缩触发时调用 `span.AddEvent("context_compression_triggered")` 并附带 `compression.reason`、`compression.new_trace_count`、`compression.accumulated_tokens` 三个 span 属性，在 Jaeger/Grafana 中可直接筛选。
  - PlanNext 返回前追加 `llm.usage.prompt_tokens`、`llm.usage.completion_tokens`、`llm.usage.total_tokens` 到 span，无需查询 metrics 接口即可在 trace 层面看到 Token 消耗。

### 4. 配置热重载 Diff 报告增强

**背景**：在 `internal/config/config.go` 中，当配置文件或环境变量发生更改并触发热重载时，`diffConfigs` 辅助函数用于记录已更改配置项的对比信息。然而，新增的 `llm.context_compression_token_threshold` 和现有的 `embedding.model` 未在 `diffConfigs` 中进行比较，导致其在热重载时变更无法被正确输出到日志中。

**变更内容**：
- `internal/config/config.go`：在 `diffConfigs` 函数中补充对 `llm.context_compression_token_threshold` 和 `embedding.model` 字段的比对逻辑，确保这二者变更可被正确输出。
- `internal/config/config_test.go`：新增 `TestDiffConfigs_IncludesNewFields` 单元测试，专门验证 `diffConfigs` 能在热重载比较时捕获这两个字段的变化。

---

### 5. `search_text` 工具参数注入加固

**背景**：在 `internal/tools/rg.go` 中，`SearchWithRG` 函数使用 `rg` 查找指定文本。原先将 `query` 变量作为普通的位置参数附加到 `rg` 命令后，若 `query` 起始含有 `-` 字符（例如由恶意攻击者操纵），可能会被 `rg` 解析为特定的命令行参数。

**变更内容**：
- `internal/tools/rg.go`：在传递给 `rg` 的参数序列中增加 `--` 结束符，强制使之后的 `query` 参数在任何情况下都被视为模式串（pattern）而非命令行标志，有效规避参数注入漏洞。

## 四、LLM 场景与可靠性优化（追加）

### 1. LLM 场景配置继承与显式覆盖

**变更内容**：

- `internal/config/config.go`：统一场景配置解析，调用方继续使用解析后的 `ResolvedLLMConfig`。
- `fallback_scene`、`max_retries`、`min_remaining_tokens` 改为可区分“未配置”和“显式零值”的配置字段。
- 场景现在可以使用 `fallback_scene: ""` 清除网关回退场景，使用 `max_retries: 0` 禁用重试，使用 `min_remaining_tokens: 0` 清除最低 Token 限制。
- 未出现的字段继续从 `llm.gateway` 和旧版扁平 LLM 配置继承，保持现有配置兼容。
- 增加网关和场景负数策略校验，并在 `config.yaml` 中补充显式覆盖示例。
- 增加程序构造及真实 YAML 解码回归测试。

### 2. LiteLLM Readiness 与缓存并发控制

**变更内容**：

- `internal/llm/health.go`：LiteLLM 场景在默认 `gateway` 模式下先检查 `/health/liveliness`，再通过 `/v1/models` 验证当前凭证能否访问目标模型。
- `/ready` 的场景结果新增 `model`、`configured`、`gateway_reachable`、`model_available` 字段；保留原有 `provider`、`healthy` 和 `error` 字段。
- 场景结果新增 `verified` 和 `status`；状态明确区分 `ready`、`configured_unverified`、`unhealthy`。
- `/ready` 顶层新增 `llm_verified`；现在只有全部场景都通过显式 `inference` 探测时才为 true。
- OpenAI、Gemini、Ollama 等直接 Provider 不发送可能收费的生成探测；配置完整时保持 `healthy=true`，但标记为 `verified=false`、`status=configured_unverified`，不再伪报为已验证健康。
- 模型不存在、凭证无权限或网关不可达时，该场景标记为不健康，整体 `/ready` 返回 HTTP 503。
- 使用 `singleflight` 合并相同配置快照的并发探测，避免缓存失效时请求穿透。
- 健康缓存键包含 Provider、模型、Base URL 和非明文凭证指纹；模型、地址或凭证变更后不会复用旧结果。
- 不同虚拟 Key 的模型权限探测结果相互隔离，缓存和错误信息均不保存或输出明文 Key。

### 3. LLM 日志与上游错误脱敏

**变更内容**：

- `internal/planner/gemini_provider.go`：移除 Info 日志中的 System Prompt、User Prompt 和模型响应正文预览，仅保留模型、文本长度和 Token 指标。
- `internal/llm/errors.go`：统一构造 `HTTPStatusError`，不再向日志和 Trace 传播上游原始错误正文或 `message`。
- 仅保留经过长度和字符白名单限制的 `error.type`、`error.code`；非结构化正文统一显示 `response body omitted`。
- `internal/llm/transport.go` 和 `internal/planner/provider.go` 使用相同的安全错误处理逻辑。
- 增加敏感 message 丢弃、非结构化正文隐藏及安全元数据提取测试。

### 4. 重试与限流响应处理

**变更内容**：

- 支持解析 `Retry-After` 秒数及 HTTP 日期格式。
- 服务端建议等待时间最多采纳 30 秒，避免异常响应造成过长阻塞。
- 无 `Retry-After` 时使用带上限的 full jitter 指数退避，降低多实例同步重试风险。
- Structured LLM 和 Planner 的主场景、回退场景均传递实际错误到统一等待逻辑。
- 所有重试等待继续响应 Context 取消；429、408 和 5xx 状态仍按原有规则判定为可重试。
- 新增 Runtime 级跨请求熔断器，按场景、Provider、模型和端点隔离状态；默认连续 5 次可重试失败后打开，冷却 30 秒。
- 冷却结束后仅允许一个半开探测；探测成功关闭熔断器，失败则重新进入冷却。
- 新增每 Runtime 每分钟共享重试预算，默认允许 60 次额外重试；预算耗尽后快速失败，防止并发请求放大上游故障。
- Structured LLM、主 Planner 和 Planner fallback 共用 Context Runtime 的熔断状态与重试预算。
- 新增 `llm.circuit_breaker_failure_threshold`、`llm.circuit_breaker_cooldown_seconds`、`llm.retry_budget_per_minute` 配置及热重载 Diff；任一值设为 0 可禁用对应保护。

### 5. LLM Eval 命令加固

**变更内容**：

- `cmd/llm-eval` 重构为可测试的 `run` 入口，输入或参数错误不再直接 `panic`。
- 新增 `-timeout`，默认对每个用例设置 30 秒 Deadline。
- 新增 `-max-line-bytes`，默认允许最大 4 MiB JSONL 行，支持长 Prompt。
- 新增 `-format text|json`；JSON 模式输出逐用例结果及机器可读汇总。
- 支持 `expected_contains`、`expected_exact`、`expected_regex` 文本断言，并在逐用例结果中输出实际断言类型。
- 支持 `expected_json_path` + `expected_json_value` JSON 结构断言，可访问根节点、嵌套对象字段和数组索引，并按 JSON 类型和值进行语义比较。
- 新增 `-max-total-tokens` 总 Token 预算；达到上限后不再启动后续用例，单次调用导致超限时标记 `max_total_tokens_exceeded`。
- 新增输入/输出 Token 单价和 `-max-total-cost-usd` 费用预算；逐用例及汇总输出估算美元费用。
- JSONL 用例可通过 `input_cost_per_million_usd`、`output_cost_per_million_usd` 覆盖全局单价，支持不同场景模型分别计价。
- 支持 `judge_criteria` LLM-as-judge 断言，默认使用 `answer_verifier` 场景和 0.7 最低分，可覆盖 Judge 场景、阈值及独立 Token 单价。
- Judge 返回的分数、理由、Token 和估算费用进入逐用例结果及总预算。
- Judge 调用失败但返回 Token Usage 时仍按 Judge 单价计费，并可触发总费用超限，避免失败请求造成预算漏算。
- 新增 `-parallelism` 固定 Worker 池；执行可并发但结果始终按 JSONL 输入顺序输出。
- 输入改为执行前完整校验，任意行非法时不会产生部分 LLM 调用费用。
- 严格 Token 总预算与并行模式互斥，避免已在途调用突破聚合预算。
- 输入错误包含准确行号，并校验 `name`、`scene` 及三种断言字段必须且只能配置一个。
- 退出码约定：全部通过为 0，存在评测失败为 1，参数、输入或输出错误为 2。
- 增加成功、失败、超时、长输入、非法参数和 JSON 汇总测试。
- `deploy/litellm/README.md` 补充 CI 调用示例和退出码说明。

### 6. CI 检查增强

**变更内容**：

- `.github/workflows/ci.yml` 新增 `go vet ./...` 静态检查。
- Race 测试扩大到 `./cmd/llm-eval ./internal/...`，覆盖 Config、Memory、Store、API 等共享状态包。
- 硬编码密钥扫描不再排除 `*_test.go`。

- Compose 配置校验和原有单元测试步骤保持不变。

### 7. 全局状态与测试隔离

**变更内容**：

- `internal/llm/structured.go` 新增可实例化的 `llm.Runtime`，由实例独立持有 Structured Caller 和 Observer。
- Runtime 的主调用、重试、fallback 递归及 Observer 事件均保持在同一实例内；不同 Runtime 之间互不修改状态。
- 新增 `WithRuntime`、`RuntimeFromContext` 和 `ObserveContext`；包级 `CallJSON` 会优先使用 Context 中的 Runtime，缺省时才回落默认实例。
- `cmd/server` 创建带 Metrics Observer 的独立 Runtime，并通过 Gin middleware 注入请求 Context；生产启动不再调用进程级 `RegisterObserver`。
- Planner 的调用事件通过 `ObserveContext` 上报，Finalizer、Memory 和 Multi-agent 的包级调用自动使用请求 Runtime。
- Memory、SQLite、PostgreSQL 和 Redis Store 的异步记忆索引使用 `context.WithoutCancel` 保留 Runtime 等 Context 值，再单独施加 30 秒超时。
- 现有包级 `CallJSON`、`Observe` 和 `Register*` API 继续作为兼容层，避免破坏 CLI 和外部调用方。
- `RegisterStructuredCaller` 和 `RegisterObserver` 返回幂等恢复函数，并使用版本号防止旧恢复函数覆盖后续注册。
- 禁止注册 nil Structured Caller；Observer 仍允许使用 nil 显式关闭观察。
- `internal/config/config.go` 新增 `OverrideForTesting`，通过克隆配置快照执行临时覆盖，并提供幂等、带版本保护的恢复函数。
- LLM 场景 Map 及策略指针执行深拷贝，避免测试修改原始配置快照。
- LLM、Planner、Multi-agent 和 API 测试已移除对 `config.Get()` 返回对象的直接赋值。
- API 认证测试不再修改环境后调用全局 Reload，改为按测试生命周期覆盖独立配置快照。

## 五、项目重新复核：待优化项与下一步扩展

### 1. 复核结论

前序的统一场景配置、LiteLLM 接入、Fallback、重试、熔断、重试预算、Eval、健康检查和 Runtime 隔离主体已经完成。本次重新检查发现 2 个调用链覆盖缺口，以及若干生产化优化项。

### 2. 待优化项

#### P0（已完成）：后台 `run-all` 丢失统一 LLM Runtime

- `internal/api/handler.go` 的后台执行从 `context.Background()` 创建 Context，导致请求中注入的 Runtime、LLM Metrics Observer 和 Trace 上下文丢失。
- 后台执行会落到默认 Runtime，熔断和重试预算被拆成两套状态，场景指标也可能漏报。
- 已基于 `context.WithoutCancel(c.Request.Context())` 创建后台 Context，在与 HTTP 请求取消解耦的同时保留统一 LLM Runtime 和 Trace 上下文，并继续由任务级超时控制生命周期。
- 已增加回归测试，验证后台 Planner 收到同一 Runtime，且取消原 HTTP 请求不会取消已接受的异步任务。

#### P0（已完成）：Multi-agent 调用漏传可靠性配置

- `internal/multiagent/llm.go` 手工构造 `llm.Config` 时，没有传入 `CircuitBreakerFailureThreshold`、`CircuitBreakerCooldown`、`RetryBudgetPerMinute` 和 `MinRemainingTokens`。
- Planner、Writer、Verifier、Embedding 等 Multi-agent 调用因此无法完整使用熔断和重试预算。
- 已改为从 `llm.ConfigForScene(scene)` 构造核心配置，再覆盖团队级 Provider、Model、凭证、端点、超时和回退策略。
- 已增加配置捕获测试，验证熔断阈值、冷却时间、共享重试预算和最低剩余 Token 配置完整传递。

#### P1（已完成）：Readiness 分级与模型推理验证

- LiteLLM 的验证仅包括网关存活和 `/v1/models` 模型可见，随后即设置 `verified=true`；这不能验证上游凭证、配额和推理接口真正可用。
- 直连 OpenAI、Gemini、Ollama 保持 `configured_unverified`，但 `/ready` 仍可能返回 HTTP 200。
- 已增加三档探测策略：
  - `config_only`：仅检查配置，作为无调用费用的默认模式。
  - `gateway`：检查网关和模型可见性。
  - `inference`：发送最小结构化生成请求；Embedding 场景发送最小向量请求，用于严格生产 Readiness。
- 默认保持 `gateway` 兼容现有部署，但网关和模型可见仅标记为 `gateway_verified`，不再设置 `verified=true`。
- `/ready` 新增 `llm_readiness_mode`；只有 `inference` 探测成功才设置 `llm_verified=true`。
- 新增 `llm.readiness_cache_ttl_seconds` 控制探测缓存，严格探测部署可提高 TTL 以限制调用费用。

#### P1（已完成）：熔断状态按凭证版本隔离并自动清理

- `internal/llm/resilience.go` 的熔断 Key 只包含场景、Provider、模型和 Base URL。
- API Key 热更新后，新凭证可能继承旧凭证造成的熔断打开状态；长期变更模型或地址还会留下未清理的历史状态。
- 熔断 Key 已加入 SHA-256 截断凭证指纹；凭证轮换后使用独立状态，且 Key 不包含明文凭证。
- 熔断状态已增加惰性过期清理，不创建额外后台 goroutine；保留期至少 10 分钟，或为对应冷却时间的两倍，取较大值。
- 即使热重载后关闭熔断，后续调用仍会清理到期的历史状态。
- 已增加凭证轮换、明文保护、标准过期、长冷却保留期和熔断关闭后的清理测试。

#### P2（已完成）：可靠性机制专用观测指标

- 已新增 `agent.llm.circuit.opened`、`agent.llm.circuit.rejected`、`agent.llm.retry.budget_exhausted`、`agent.llm.fallback.succeeded` 和 `agent.llm.fallback.failed` OTel Counter。
- 已新增按场景、Provider、模型聚合的 Prompt、Completion、Total Token 与 `agent.llm.scene.estimated_cost_usd` 指标。
- `llm.gateway` 和具体场景支持 `input_cost_per_million_usd`、`output_cost_per_million_usd`，支持继承及显式零值覆盖；未配置单价时费用保持 0。
- `/api/metrics` 快照新增 LLM 调用、错误、Token、估算费用和五类可靠性累计值。
- 新增可选 `ContextObserver` 和 `ReliabilityObserver`，保持原 Observer 接口兼容；LLM 指标现在使用实际调用 Context 写入 OTel，可关联 Trace exemplar。
- Structured LLM 和 Planner 的熔断、预算及 Fallback 路径均已接入可靠性事件。
- 已补充 Metrics 快照、费用计算、Context 传播、熔断事件、预算事件和 Fallback 成功事件测试。

### 3.1 动态场景路由（已完成）

- `llm.scenes.<scene>.routes` 支持按规则顺序选择目标场景，首条匹配规则生效。
- 当前条件支持 `min_remaining_tokens`、`max_remaining_tokens`、`min_step_count` 和 `max_step_count`；Token 条件仅在任务设置了 `token_budget` 时参与匹配。
- 路由目标必须是已存在的场景。实际调用完整复用目标场景的 Provider、Model、Base URL、价格、重试、熔断和 Fallback 配置。
- 路由已覆盖统一结构化 Runtime、Legacy/Eino Planner、API 后台任务和 Multi-agent 工作流；Planner 构造器中显式指定的 Provider/Model 等静态覆盖不会被场景路由替换。
- 配置加载会拒绝空目标、未知目标、无条件规则、负数、无效区间和路由环；Gateway 不允许直接定义路由，避免所有场景隐式继承同一组规则。
- 当前动态路由用于生成类场景。`embedding` 的协议与能力要求不同，`adk` 的 Runner 在首次调用后固定模型，因此这两个场景会明确拒绝 `routes`，避免配置成功但运行时静默失效。
- Config 热重载响应的 `active_scenes` 会返回场景路由；OpenTelemetry 记录逻辑场景和实际场景，并在发生结构化调用路由时增加 `llm.route.selected` 事件。
- 已增加首条匹配、无 Token Budget、深拷贝、配置错误、Runtime 目标配置和独立 Planner 调用路径测试。

### 3.2 任务级 LLM 配额与成本治理（已完成）

- 新增全局默认配置 `llm.max_calls_per_task`、`llm.max_estimated_cost_usd_per_task`，均为 `0` 时不限制；支持通过环境变量和热重载调整。
- 创建任务支持 `llm_call_budget`、`llm_cost_budget_usd` 覆盖全局默认值，并返回 `llm_calls`、`llm_estimated_cost_usd` 累计用量。
- 调用次数在请求前原子预留：每个实际场景调用计一次，Fallback 计为新调用，场景内部 Retry 不重复计数；并发 Multi-agent 无法超额预留。
- 结构化 Runtime、Legacy/Eino Planner、Multi-agent、ADK 每次模型调用和远程 Embedding 均已接入调用额度。Embedding 超限时使用本地向量；启用费用预算时也固定使用本地向量，因为当前远程 Embedding 路径没有可靠 TokenUsage 可供计费。
- 费用依据实际 TokenUsage 和目标场景价格在调用后累计。单次调用可能越过美元上限，但越界后的后续调用会被拒绝；启用费用上限时，所有已配置生成场景必须设置输入或输出单价，并在每次调用前重新校验实际场景价格，防止热重载移除单价后绕过预算。
- 任务预算和累计用量已加入 SQLite/PostgreSQL 建表、增量迁移、保存、读取和列表查询，暂停恢复或跨实例接管不会重置额度。
- 额度耗尽触发 `agent.llm.task_budget.rejected` 指标，任务保留已有进度并以完成状态返回预算说明，而不是进入通用失败路径。
- Config 热重载响应返回 `llm_task_budget_defaults`；`Sample/agent-api.http` 已增加任务预算示例。
- 已增加调用/费用耗尽、Fallback 计数、并发预留、默认额度、ADK、持久化、API 校验、配置单价覆盖、指标和任务终态测试。

### 3.3 租户级身份、隔离与 UTC 日配额（已完成）

- `api.tenants.<tenant_id>` 支持独立 API Key、管理员标记、每日 LLM 调用额度和每日估算费用额度；租户身份由服务端 API Key 映射产生，不接受客户端声明的租户 Header。
- 旧 `api.api_key` 保留为 `default` 管理员 Principal，兼容已有部署和历史无租户任务；租户 Key 默认不能访问全局 Metrics 或配置热重载。
- Task 新增并持久化 `tenant_id`。所有带任务 ID 的 HTTP 接口执行归属校验，跨租户访问统一返回 404；任务列表在 Memory、SQLite、PostgreSQL 和 Redis 层按租户过滤。
- 长期 Memory 同样持久化 `tenant_id`，本地 RAG 查询在 Memory、SQLite、PostgreSQL（含 pgvector）和 Redis 层按任务租户过滤，防止跨租户历史答案进入 Planner 上下文；历史无租户 Memory 仅归入 `default` 管理域。
- 新增 `/api/usage`，租户只能查询自己的当前 UTC 日周期调用数、估算费用和配置上限，不需要访问全局 Metrics。
- Memory、SQLite、PostgreSQL、Redis 均实现原子租户账本。SQLite 使用单写连接和事务条件更新，PostgreSQL 使用事务条件更新，Redis 使用 Lua；Redis 日账本保留 35 天。
- 调用前先检查任务额度，再通过 Store 原子预留租户调用额度；Fallback 计为新调用，Retry 不重复计数。写入租户费用失败会提升为预算错误并阻止 Fallback，避免产生未登记费用。
- 日周期固定使用 UTC `[00:00, 24:00)`。调用预留会保守计入已发起但因进程中断未完成的请求，优先避免超额而不是尝试不可靠的回滚。
- Config 校验拒绝空租户 Key、重复 Key、与管理员 Key 重复及负额度；费用额度继续要求所有生成场景配置价格。
- 已增加 Principal 鉴权、管理员权限、跨租户 404、任务与 Memory/RAG 隔离、用量查询、任务归属持久化、调用/费用账本和跨任务共享日额度测试。

### 3.5 输入与输出安全检查场景（已完成）

- 新增统一场景 `safety_guard`，通过同一场景的 `input`、`output` 阶段分别检查任务目标和最终答案；可独立配置 Provider、模型、价格、动态路由、重试、熔断和 Fallback。
- 输入检查在首次执行及 RAG/Planner 之前运行。明确不允许的请求会直接完成为 Guard 返回的安全答复，不再进入工具或模型编排；检查结果通过 `safety_guard_input` 轨迹持久化，恢复和分步运行不会重复检查。
- 输出检查位于统一完成态边界，并在 `citation_verifier` 之后执行，覆盖 Legacy、Eino、Step、ADK 和 Multi-agent。Guard 可删除暴露的凭证或不必要的个人信息，也可将不安全答案替换为拒绝答复。
- 内容分类包含隐私、凭证、暴力、自伤、性内容、违法、恶意软件、仇恨和骚扰；系统提示明确允许正常编码、防御性安全、分析、摘要、教育及虚构内容，降低对合法任务的误拦截。
- 原有 Workspace、路径穿越、命令白名单、SSRF、SQL 和高风险工具审批继续作为确定性硬边界；LLM Guard 是可选内容策略层，不替代 `internal/policy` 的硬检查。
- Guard 未配置或 Token 余量不足时不调用。模型不可用、返回空结果或结构错误时采用失败开放：输入继续受确定性策略保护，输出保留原答案；失败尝试会写入轨迹，防止每个执行步骤重复消耗配额。
- 输入和输出检查均使用统一 Runtime，纳入任务及租户调用额度、成本、动态路由、Fallback 和 Metrics。启用场景后通常每个完整任务增加两次实际 LLM 调用，应同步调整调用额度。
- `config.yaml` 已增加配置示例，并补充模型契约、非法阶段、空安全文本、输入拒绝、输出净化、执行顺序、失败回退及只检查一次测试。

### 3.6 工具参数定向修复场景（已完成）

- 新增统一场景 `tool_argument_repair`。只有已注册工具自身的 `Validate` 返回参数错误时才调用；未知工具、Stop 协议错误、执行期错误、策略拒绝和审批拒绝不会触发自动修复。

- 修复输出只能替换原动作的参数，不能修改动作名、Stop 状态或最终答案。返回结果会再次经过工具 Validator，并在本地拒绝未知字段、缺失字段、路径穿越等仍然非法的参数。
- Legacy、Eino 和 Step 使用的统一 `LLMPlanner` 在原规划结果上原位修复，避免因单个空路径、URL 或参数类型问题重新执行完整规划；修复 TokenUsage 会合并到本轮 Planner 用量。

- 用户在高风险审批中修改参数时，审批结果会覆盖修复结果，防止模型修复值覆盖人工批准值；工具执行仍受 Workspace、命令、SSRF、SQL 等确定性策略约束。
- 场景调用使用统一 Runtime，继承动态路由、Fallback、重试、熔断、任务与租户额度及成本统计；未配置场景或剩余 Token 不足时保持原有 Planner 错误/回退行为。
- `config.yaml` 已增加配置示例，并补充工具 Schema、二次校验、错误类型、动作不可变、单 Agent 原位修复、Multi-agent 参数传播、默认参数及审批覆盖测试。

### 3.7 意图与质量分层路由场景（已完成）

- 新增统一场景 `intent_router`，在任务首次执行时将目标分类为 `coding`、`research`、`writing`、`data_analysis`、`automation` 或 `general`，同时给出复杂度、成本、延迟和质量四个独立层级。
- 分类位于输入 Safety Guard 之后、RAG 和 Planner 之前。当前执行轮次会立即刷新 Routing Context，因此 Query Rewriter、Reranker、Planner、Tool Argument Repair、Finalizer、Citation Verifier、输出 Safety Guard 和 Multi-agent 后续调用都可使用分类结果。
- 分类结果以 `intent_route` 轨迹持久化，意图存入 Query，复杂度、成本、延迟和质量层级存入结构化 Observation；任务恢复或跨实例接管时会从轨迹重建路由提示，无需修改 Task 表结构或执行数据库迁移。
- `llm.scenes.<scene>.routes` 新增 `intents`、`complexities`、`cost_tiers`、`latency_tiers`、`quality_tiers` 条件，并继续支持与 Token 余量、步骤数条件组合。一个规则中的不同条件执行 AND，同一列表中的值执行 OR，规则仍按声明顺序首条匹配。
- 配置校验拒绝未知分类值和重复值；路由目标、空条件、范围、循环、Embedding/ADK 限制等原有校验继续生效。路由配置和热重载响应会保留新增条件，配置快照对条件切片执行深拷贝。
- Router 只负责分类，不直接指定模型。部署方通过场景 Route 将分类映射到经济、均衡或高质量模型，继续完整继承目标场景的 Provider、价格、重试、熔断和 Fallback。
- 未配置场景、Token 余量不足、模型不可用或分类非法时保留默认场景路由；失败尝试写入轨迹且不会在每个步骤重复调用。启用后每个新任务通常增加一次 LLM 调用，应计入任务和租户额度规划。
- `config.yaml` 已增加按意图、复杂度、成本、延迟和质量层级路由的示例，并补充结构化分类、非法分类、本轮 Context 刷新、失败回退、恢复重建、首条匹配、YAML 解码、深拷贝及配置拒绝测试。

### 3.8 记忆事实冲突消解场景（已完成）

- 新增统一场景 `memory_conflict_resolver`，在 RAG 候选完成去重、重排和数量限制后、Planner 使用记忆前检查记忆之间的直接事实冲突。
- 每条记忆使用稳定的 1-based 索引，Resolver 必须为每条记忆恰好返回一次 `keep/drop` assessment。本地校验 assessment 数量、索引范围、重复索引和状态，拒绝不完整或非法输出。
- 当任务产生新的工具 Evidence 时，下一轮 Planner 前会再次比较保留记忆与当前证据。当前工具证据优先于历史记忆；没有当前证据时优先较新且支持更充分的记忆，无法确定时保留双方并要求表达不确定性。
- Multi-agent 在每轮研究结束、Writer 开始前调用同一 Resolver，确保一次 `Next` 内刚产生的研究证据也能约束 Writer 使用的历史记忆；自适应研究产生新证据后会按新版本再次复核。
- `memory_conflict_resolve` 轨迹以非空 Evidence 数量作为版本。相同证据版本不会重复调用，新增证据才触发复核；版本和结果随 Task Trace 持久化，不需要新增数据库字段或迁移。
- 只有存在至少两条记忆，或一条以上记忆且已有当前证据时才调用。未配置场景、Token 余量不足、模型失败或输出非法时保留全部现有记忆，避免可选质量步骤导致上下文丢失。
- 记忆和证据在 Prompt 中明确作为不可信数据处理，目录内容按长度及最多 20 条当前证据限制，降低 Prompt Injection 和上下文膨胀风险。
- Resolver 使用统一 Runtime，继承 Intent 动态路由、Fallback、重试、熔断、任务与租户额度、成本和 Metrics；调用 TokenUsage 写入冲突消解轨迹并参与后续 Token 路由。
- `config.yaml` 已增加场景示例，并补充记忆过滤、当前证据优先、重复索引拒绝、空证据忽略、同版本去重、新证据复核、失败开放以及 Multi-agent Writer 前执行测试。

### 3.9 图片分析场景（已完成）

- 统一 Runtime 新增可选 `VisionStructuredCaller`，图像调用继续复用动态路由、Fallback、重试、熔断、任务及租户额度、成本和 OpenTelemetry 观测；现有文本 Caller 接口保持兼容。

### 3.10 独立代码审查场景（已完成）

- 新增统一场景 `code_reviewer`，仅当任务成功执行 `write_file`、`apply_patch` 或 `execute_code`，且 Git 工作树确有变更时在完成态触发；纯读取、研究和无实际变更任务不增加 LLM 调用。
- 审查位于 Citation Verifier 之后、输出 Safety Guard 之前，覆盖 Legacy、Eino、Step、ADK 和 Multi-agent；失败时保留原答案并记录失败轨迹，成功结果不会自动修改文件。
- 变更收集同时覆盖 tracked/staged diff 和未跟踪代码文件，单次输入限制 96 KiB；无 `HEAD` 的新仓库会退化为 staged 与 working-tree diff。
- 未跟踪文件仅允许常见代码、脚本、配置和文档扩展名，跳过 `.env`、私钥和二进制资产；发送模型前确定性脱敏私钥块、Bearer Token、常见 API Key、Password、Secret 和 Token 赋值。
- 模型输出采用严格结构化 Schema，Finding 包含 `critical/high/medium/low` 严重度、已变更路径、行号、标题和说明。本地再次校验严重度、空内容和路径白名单，拒绝模型引用未变更文件。
- 发现问题时会追加 `Code review` 到最终答案，并将每条 Finding 写入 `code_review` 轨迹 Evidence；无问题时仅保留审查摘要。TokenUsage 纳入任务额度、成本和 Metrics。
- 配置示例已加入 `config.yaml`，并补充场景调用、路径约束、触发条件、重复执行保护、最终答案与 Evidence 传播、未跟踪文件过滤和凭证脱敏测试。

### 3.11 定向回归测试生成场景（已完成）

- 新增统一场景 `test_generator`，仅在任务成功执行写入类动作且 Git 确有变更时触发；它位于 `code_reviewer` 之后、输出 Safety Guard 之前，可优先覆盖审查发现的问题。
- 复用代码审查的 tracked/staged/untracked 变更收集、96 KiB 上限、文件类型白名单和凭证脱敏，变更内容及审查 Finding 均作为不可信数据处理。
- 结构化输出包含 `p0/p1/p2` 优先级、目标测试路径、框架、测试名、覆盖行为、理由和建议代码；本地拒绝路径穿越、非代码扩展名、空字段、重复建议、单段超过 4000 字符或累计超过 24000 字符的输出。
- 建议代码只追加到最终答案供人工审阅，不直接写入 workspace、不自动运行，也不绕过高风险工具审批；测试片段使用缩进代码块，避免模型内容破坏 Markdown 边界。
- 每条建议写入 `test_generate` 轨迹 Evidence，TokenUsage 纳入任务和租户额度、成本及 Metrics；没有必要补测试时允许返回空建议，调用失败时保留原答案。
- 配置示例已加入 `config.yaml`，并补充代码审查上下文传播、结构化输出、路径校验、最终答案、Evidence、TokenUsage 和重复执行保护测试。

### 3.12 终态失败诊断场景（已完成）

- 新增统一场景 `failure_diagnoser`，挂载在 `Engine.Next` 的统一错误终态处理：先完成 `failed` 状态和原始错误记录，再生成诊断，覆盖 Legacy、Eino、Step、ADK 和 Multi-agent 的真实执行失败。
- LLM/任务预算耗尽继续按已有逻辑正常完成；`context.Canceled`、Deadline 和已取消上下文不发起诊断，避免无效请求。诊断通过 `failure_diagnose` 轨迹保证同一任务只执行一次。
- 输入包含终态错误和最近 30 条执行轨迹，单条 Query、Observation、Error 分别限制长度，总 Prompt 限制 64 KiB；任务目标和轨迹均作为不可信数据处理。
- 凭证脱敏抽取为共享 `internal/sanitize`，代码审查和失败诊断统一过滤私钥、Bearer Token、OpenAI/AWS/GitHub Key 及常见 Secret、Password、Token 赋值；持久化的失败 FinalAnswer 同样先脱敏。
- 结构化结果包含根因类别、根因、失败步骤/动作、证据、1 至 8 条恢复步骤和可重试标记。本地校验类别、空内容、数量限制，并拒绝引用轨迹中不存在的失败步骤或动作。
- 成功诊断会生成可读的 `Failure diagnosis` 最终答案和 Evidence；模型不可用或输出非法时保留原失败信息。TokenUsage 纳入任务、租户额度、成本和 Metrics。
- 配置示例已加入 `config.yaml`，并补充脱敏输入、结构化契约、轨迹引用约束、失败终态集成、TokenUsage 传播及取消时不调用测试。

### 3.13 执行前计划审计场景（已完成）

- 新增统一场景 `plan_critic` 和中立计划表示，覆盖 Legacy、Eino 的 `PlanDecision`，以及 Multi-agent 初始 Plan、失败 Replan 和低置信度深度扩展 Plan；Step/ADK 没有独立的可拦截计划对象，继续依赖其确定性流程和工具策略。
- 仅对 Intent Router 标记为高复杂度、包含至少 3 个步骤或包含高风险工具的计划调用，简单只读计划不增加成本。计划指纹用于避免相同计划重复审计。
- Critic 检查完整性、顺序、依赖、安全、可行性和效率，输出 Approved、摘要以及最多 20 条 `high/medium/low` Issue；Issue 使用 1-based 步骤索引，0 表示全局问题。
- 输入中的 Goal、Summary、Description 和参数统一视为不可信数据；敏感参数按 Key 脱敏，其他字符串和嵌套值执行共享凭证脱敏及长度限制，总 Prompt 限制 64 KiB。
- 本地校验严重度、类别、步骤范围、空内容、单项长度，并拒绝“存在 High Issue 却标记 Approved”的矛盾输出。High 建议去重写入 Task Unresolved，全部 Issue 写入 `plan_critic` Evidence。
- Critic 是审计层，不自动重写、跳过或放行工具。Workspace、SSRF、命令和 SQL 策略仍为硬边界，高风险工具仍必须人工审批；最近一次 Critic 警告会加入审批 Preview，帮助用户作出决定。
- 场景失败时采用失败开放，继续执行确定性策略和审批，并用计划指纹记录失败以避免重复消耗。TokenUsage 纳入任务、租户额度、成本和 Metrics。
- 配置示例已加入 `config.yaml`，并补充高复杂度/高风险触发、脱敏、输出矛盾、指纹去重、Unresolved/Evidence、单 Agent、Multi-agent 和审批 Preview 测试。

### 3.14 外部内容提示注入检测场景（已完成）

- 新增统一场景 `prompt_injection_detector`，检测边界位于外部内容返回之后、进入下一轮 Planner 或 Multi-agent Writer 上下文之前；覆盖第三方 RAG、`web_search` 和 `http_fetch`，本地文件搜索与读取不额外调用，避免对 workspace 内代码和安全文档重复误判。
- 检测采用确定性规则加结构化 LLM 分类两层策略。明确的指令覆盖、角色操纵、凭证外泄、策略绕过和强制工具调用即使未配置 LLM 场景也会被识别；未被规则命中的外部内容在场景启用时交给模型检查隐蔽或编码指令。
- 每个外部来源使用稳定 ID，模型只能返回输入 ID，并将风险限定为 `suspicious/malicious`，类别限定为指令覆盖、角色操纵、凭证外泄、策略绕过、工具滥用或编码载荷。本地校验未知/重复 ID、风险、类别和空理由，拒绝越界输出。
- Goal 不发送给 Detector，外部正文作为不可信数据封装；来源 ID、类型、正文和判定理由执行长度限制及共享凭证脱敏，System Prompt 明确禁止服从、解码为可执行指令或复述请求的秘密。
- 命中内容不会传入下游模型：第三方 RAG 记忆直接从候选集合移除，工具和 Researcher Evidence 正文替换为统一隔离标记；URL、Path 和 Query 等来源元数据保留，便于审计和后续人工核查。
- 每次检测写入 `prompt_injection_detect` 轨迹，记录来源数、隔离数、风险类别和 TokenUsage；模型生成的原始理由不写回 Planner 可见轨迹，避免通过审计信息重新引入攻击文本。模型调用失败或输出非法时保留确定性检测结果，不影响 Workspace、SSRF、审批和其他硬策略继续执行。
- Detector 使用统一 Runtime，继承场景 Provider/Model、动态路由、Fallback、重试、熔断、任务及租户额度、成本和 Metrics；`config.yaml` 已增加独立模型配置示例。
- 已补充无场景确定性检测、结构化分类、凭证脱敏、非法来源拒绝、来源元数据保留、Legacy/Eino 工具结果、第三方 RAG 过滤及 Multi-agent Writer 前隔离测试。

### 3.15 外部证据相关性过滤场景（已完成）

- 新增统一场景 `evidence_relevance_filter`，位于 Prompt Injection Detector 之后、Planner 或 Multi-agent Writer 使用工具结果之前；仅处理 `web_search` 和 `http_fetch`，已隔离内容、失败结果和本地 workspace 证据不会进入相关性模型。
- 过滤单位为 Observation/Evidence 中的独立非空行片段，而不是整条工具结果。每个片段使用稳定 ID，模型只能返回 `keep/drop`、`high/medium/low` 相关度和理由，不能改写、摘要或生成新证据。
- 完全相同的片段先按忽略大小写和空白差异进行确定性去重；即使未配置 LLM 场景，也能移除重复片段并保留首次出现内容。
- 启用场景后按每批最多 20 个片段调用。模型必须为每个输入 ID 恰好返回一次判断；本地拒绝未知/重复 ID、缺失判断、非法相关度、Keep 与 Low 矛盾、Drop 与非 Low 矛盾，以及试图删除整批内容的结果。
- 场景失败、预算不足或结构化输出非法时采用信息保留优先策略：保留全部非重复片段，仅继续移除确定性重复项，避免可选质量步骤造成证据丢失。
- Goal、检索 Query、Path 和正文均作为不可信数据处理，执行共享凭证脱敏与长度限制；模型生成的理由不写回 Planner/Writer 可见轨迹，审计仅记录片段数量、保留/移除数量和稳定 ID。
- 过滤后的片段原样保留，不进行模型改写；当确实没有内容保留时写入固定的无相关内容标记。Legacy、Eino 和 Multi-agent Researcher 共用相同过滤契约，Step/ADK 当前没有外部网络工具入口。
- `evidence_relevance_filter` 轨迹记录 TokenUsage 并接入统一 Runtime、场景 Provider/Model、动态路由、Fallback、重试、熔断、任务及租户额度、成本和 Metrics；`config.yaml` 已增加独立场景示例。
- 已补充无场景去重、结构化选择、凭证脱敏、不完整/全删输出失败开放、片段提取与原样应用、审计理由隔离、Prompt Guard 顺序、单 Agent 和 Multi-agent Writer 前过滤测试。

### 4. 下一步可扩展的 LLM 场景

当前已覆盖 Task Planner、Finalizer、Citation Verifier、Safety Guard、Tool Argument Repair、Intent Router、Memory Conflict Resolver、Vision Analyzer、Code Reviewer、Test Generator、Failure Diagnoser、Plan Critic、Prompt Injection Detector、Evidence Relevance Filter、Context Compressor、Answer Verifier、Memory Summarizer、RAG Query Rewriter、RAG Reranker、Multi-agent Planner/Replanner/Writer、Embedding 和 ADK。建议按以下顺序继续扩展：

1. `citation_verifier`：校验最终答案是否被检索证据支持。（已完成）
2. `safety_guard`：执行输入和最终输出的安全、隐私与合规检查。（已完成）
3. `tool_argument_repair`：工具参数校验失败后定向修复，避免重新执行完整规划。（已完成）
4. `intent_router`：按任务类型、成本、延迟和质量选择模型。（已完成）
5. `memory_conflict_resolver`：处理新旧记忆之间的事实冲突。（已完成）
6. `vision_analyzer`：支持图片、截图和其他多模态任务。（已完成）
7. `code_reviewer`：对代码变更执行独立审查和风险判断。（已完成）
8. `test_generator`：根据变更和审查结果生成定向回归测试建议或测试补丁。（已完成）
9. `failure_diagnoser`：汇总失败轨迹、定位根因并给出可执行恢复建议。（已完成）
10. `plan_critic`：在高复杂度计划执行前独立检查遗漏、顺序和风险。（已完成）
11. `prompt_injection_detector`：在外部检索内容进入 Planner/Writer 上下文前识别提示注入和越权指令。（已完成）
12. `evidence_relevance_filter`：在外部工具结果进入长上下文前过滤低相关、重复和污染片段，降低上下文成本并提高证据密度。（已完成）
13. `evidence_conflict_resolver`：识别当前外部证据之间的事实冲突，为 Writer 保留双方来源并显式标注不确定性。
